# Loop 运行、文档与规则维护

本页说明本次实现的行为；总体设计与取舍继续维护在 [全流程优化方案](../docs/方案-Loop全流程优化.md)。项目业务需求、项目方案、验收标准仍由各自的权威原文负责。索引不代替它们，也不自动改写它们。

## 开发卡内核与迁移边界

当前新任务以 README「开发卡（第4步）」及工具清单「开发卡字段（第4步）」为入口。公开 `启动` 接收 version:1 开发卡：开发评审 → 可选测试 → 可选验收 → 可选提交 → 可选部署；另支持单任务 nature:评审、flow:[评审] 的只评审卡。单任务开发可不带验收，多任务必须统一验收及逐条责任归属。旧卡明确给迁移说明，旧批次引擎内部保留，不替新卡兜底。新 `bin/loop 开发 pi|claude|codex` 只有开发评审，不运行配置验收或旧 accept-cmd，没有受管新卡身份时不自动提交用户文件。新单会话测试/验收、卡上未安排的节点明确写“没验证（本次未安排）”；新卡已可选独立测试节点，只执行卡上那条命令。下文原有旧流程、验收、共用预算和工作区说明均是迁移期兼容资料，不能据此替新卡添加节点。

```text
开发卡只读校验（先于目录、分支、模型）
  → 归属登记 + 隐藏任务 worktree + 冻结开工提交
  → 既有宿主开发会话
  → 程序提交允许范围内交付（私有索引 + 原生索引锁 + CAS）
  → 共享静态评审执行器；有必修返回原会话，次数独立且恢复不清零
  → 通用节点结果落结构化账本
  → 各任务开发评审完全并行；如安排测试：跨仓库本机 FIFO → 原样命令/有限恢复 → 独立结果
      产品失败回同一任务原会话；非产品失败保留评审，通知只重跑/改卡/放弃
  → 就绪任务按实际顺序汇入批次；CAS + 意图/历史 ref + 任务检查/贡献映射
  → 全部活跃任务到齐才统一验收，和测试共用本机槽
      产品失败仅返责任任务；同轮汇齐重验不通过项和返修任务名下全部项，不追加 full
      未返修项保留原实测树/轮次/证据；非产品失败保留范围与结论，有限恢复后只停验收
  → 有提交节点时按仓库/dev 互斥，核对前置结论及实际发布树
  → 压缩发布提交，保存任务历史 ref，CAS 合入 dev，只推 origin/dev
  → 本卡明确安排部署且推送成功：项目互斥 → 实际发布版本 cmd/check → 必要且安全的本地回退/重部署
  → 结束已登记消费者，释放可证明归属且无未保存成果的任务 worktree
```

职责与依赖：`kernel.ts` / `node-ledger.ts` 只认统一候选、输入、尝试和结果，不认识 `ReviewState`；`development-node.ts`、`review-node.ts`、`test-node.ts`、`acceptance-node.ts`、`submission-node.ts` 与 `deployment-node.ts` 只依赖内核/共享执行能力，不互相引用或读取内部状态；固定执行器由 `kernel-session.ts` 装配。`static-review.ts` 共享真实评审调用、解析和有界重试；`review.ts` 是旧准备/验收/队列组合兼容层，不用于新卡节点。Pi `kernel-pi.ts` 与 `hosts/kernel-hook.ts` 共用状态与结果。`batch-integration.ts` 只组合登记贡献，不调用节点；从共同冻结基线重建替换/移出后的汇总，吸收其他任务来源会登记并剥离；同文件混合不能安全证明时停具体任务，不猜测删代码。dev 来源通过内核整合后单独登记，不由提交节点暗中纳入新树。

账本以 Git common-dir 与卡路径隔离，短锁和原子替换；多任务在同一账本 `taskRecords` 保存稳定 ID 及独立运行字段，适配器显式传任务 ID，仅用上下文投影读写，不建第二份任务账本。顶层保留批次运行/验收/发布；旧单任务原字段只读兼容，不在查询迁移。每次执行有 UUID、任务、节点、commit/tree、输入哈希、实际操作、证据及消费者释放结果。非开发节点期间文件、未跟踪项、索引或输入变化会使该次结果无效；迟到执行只留历史，不覆盖新输入。通过结论复用要求同树、同相关输入、证据存在、原执行结束并确认释放；只压缩提交不要求重评审。用户文件引用以共享解析器返回的结构化路径/内容登记，不能反解析 `--- @… ---` 或 `<file>` 展示文本；再次引用原提示词的新要求也进入版本。引用文本的确认哈希随真实用户输入冻结；读取检查输入时，用同一份文件字节计算指纹并核对确认版本。引用内容变化或旧记录缺少快照时，在开发/评审边界停止并要求原会话重新引用确认，不能只续跑就采用新版本。Markdown 总结、旧 phase 与交付索引不授予资格。

只评审路径：启动只读解析本地已有 base/head 和可选 requirement/criteria/note → 固定 commit/tree 与已确认输入版本 → 登记隐藏分离检出 → `review-node.ts` 直接共享 `static-review.ts` 调用/有界重试/解析/证据 → 同账本报告 → 释放干净目录。不经过 `runReviewRound`、准备、开发提交、返修或队列；不 fetch、不切用户分支，原用户工作区/索引不参与。只评审不要求 dev 存在。标准/说明/需求、模型或时限变化使旧报告失效，须受控改卡确认当前版本后仅重跑评审；受评 base/head 不可改，后来分支移动不换对象。五态沿用「等你决定」，明确「只评审已结束」及结果、报告、资源；不显示可合入/Loop 外已合入，普通/接受未验证合入均拒绝。旧直接评审入口保留。共享调用只有在消费者释放已确认时才做有界重试；执行器明确未启动（如 ENOENT）留真错误并提供未启动证明，已启动/释放未知立即结束为没验证、保留阻塞租约，不等待自己的 blocked 租约。租约等待和命令共用本次调用剩余时限。旧 Pi 单会话更新输入或关闭时，仍撤销旧结论并禁止旧任务继续调用宿主接口，但不会丢弃已到达的真实释放回执：只凭本次执行器明确确认的事实归还自己的租约，不因取消、空登记或所有者退出就清除未知租约。

部署配置继续只用 `.autoreview.json.deployment`，有部署卡在资源前要求提交节点及 enabled/cmd/check/timeoutMin 合法，并冻结 dev 执行目录/Git 共用目录。无部署卡绝不隐含调度。`kernel-session.ts` 将所有发布入口统一接续部署，CLI/worker/Pi/Hook 不再用 publication 早退跳过本卡安排；宿主监督器同时核对任务活动、批次活动及已安排部署是否收尾，不提前终止承载部署的最后一个任务宿主；推送失败/发布意图未确认/外部合入不自动部署、重合或重推。部署指纹独立，修改 deployment 不使未变的前置结论重跑；发布前可受控改卡确认新配置，发布后不可改卡或追加部署授权。实际执行重新检查已发布 commit/tree、目录、源码/索引、origin 和配置版本，不部署其他批次或脏内容。

`deployment-exec.ts` 抽取新旧共用的 cmd/日志/进程/资源边界；`project-execution.ts` 在 Git 共用目录登记检查读租约/部署独占租约，旧组合评审、旧验收、旧队列发布及旧部署也进入同一实际执行边界。只用短锁登记身份，等待/命令不占账本锁；部署不用全机测试槽，同仓库的子项目保守共用互斥边界。排队不伪报活动，每个命令独立 timeoutMin；停止后不再启动后续命令。cmd 非零只停部署；check 非零仅在目标仍本批、上一版明确、消费者已释放且无脏内容/挡路文件时，以登记意图 + 反向 CAS + 私有索引回退本机 dev，并用原 cmd 重部署上一版。只归一化 Git 可证明的预期方法文件转换，未授权源码/方法变更仍使本次无效。停止、超时、目标前进、未知在途动作/消费者不自动回退或重做。

发布事实/远端推送记录/部署/回退/资源分列；本地回退不等于远端回退，运行版本只列最近成功部署命令及检查证据，不冒充实时业务探针。账本保存 deploymentPlan/deploymentAttempts（发布 commit/tree、配置/输入哈希、方法清单、命令/时间/日志、失败类别、资源对象与释放、回退过程）。只有明确 `重跑 --node 部署` 才能重试已结束的失败部署，重跑意图绑定原尝试并在登记新尝试的同一短锁中核对；自动回调、合入及普通续跑不重做已有终态。重跑不重新开发/检查/提交/推送；同一成功结果只复用，回退后目标不在旧发布先拒绝，不能自动重发。未知副作用先人工核对，没有强制忽略开关；已发布停止/放弃只处理剩余活动，不能删除发布历史或擅自回滚。干净本批空间在部署收尾后释放，未知归属或未保存成果保留。

`状态/查询` 纯读取，不调用模型、不恢复旧队列。空闲会话还活着不等于节点运行；停止只撤销活动并保留成果，不是放弃。启动成功建空间但宿主失败时保留原错误、日志和 `续跑` 入口；续跑精确恢复原 ID，不新建替代会话、不重置次数。直接改卡在下个边界停止；恢复 `frozen-card.json` 中原内容后续跑。第二步已接入 `重跑 <卡> --node 测试`、`改卡 <卡> --remove-node 测试|--from 文件`、`放弃 <卡>`；完整参数见工具清单。改卡先验内容、记录来源和用户版本、新旧原文及时间，pending/prepared/applied/拒绝留史，在边界切换，只失效相关节点。移除必需测试必须真实用户决定，机器返修不得代选。机器信封核对实际收到的完整正文或可信精确文件/宿主包装与哈希，追加撤权不能被吞掉。放弃先存分支/ref/证据再核对释放，不强删脏/未知内容。

普通与用户例外合入走同一提交节点，均保留候选核对、main 保护、目标工作区保护和记账。只豁免用户明确接受的欠项；真实 interactive/rpc / 宿主用户输入或终端确认才算决定，卡/提示词/机器消息不授权。决定绑定候选、完整检查输入及用户版本，撤回/换标准/引用变化后历史决定保留但不再有效；CLI 与提交节点重复核对。旧未通过、没验证、决定原话与时间不被改成通过。目标前进产生新树时用统一 `整合` 入口引入可核对 dev 来源，再回原开发会话交付，提交节点不重评审。冻结 base/scope 不变，范围外文件仅允许已登记候选原样内容或真实 dev 合并来源，越界提交不能借整合洗白；目标有重叠未提交内容时拒绝；无交集的索引、暂存/未暂存/未跟踪原始内容前后核对保留，不 stash/reset。推送失败保留本地合入和 Git 原因，不强推、不自动重试。发布输入快照同时保存检查前与 checkout 后实际哈希，只归一化与发布树匹配的程序预期更新；正常修改已登记 guide 不应使自身推送失效，外部变更仍拒绝。

资源只按本批登记处理：原生进程组、启动时间、随机 owner、worktree 路径、任务分支、Git 共用目录同时核对。未知归属、用户暂存内容、未提交成果、本机文件变化和释放失败保留并报告；只在确认消费者结束及候选保存后移除本批 worktree。任务分支、压缩前历史、账本、失败/中断证据保留。已合入事实、远端结果和释放状态分列，Git 可证明的外部合入不补造检查通过。

验证使用受影响的 `node:test`、系统临时 Git 仓库与本地 bare origin；模型替身只证明流程。实际宿主安装/信任与真实模型、真实远端、Loop 自身新卡合入 dev 及业务验收须另留实证，不能用替身或静态评审代替。工具接入不自动更新本机插件或用户全局配置。

本机槽由 `local-node-queue.ts` 使用全用户目录串行登记，排队与实际活动分离；短锁不跨执行，不在队列锁内拿账本写锁，取执行权与改卡/停止共用同卡边界。退出与恢复均先核对已登记进程/资源再释放票据，未知消费者保留槽。测试恢复直接复用项目已登记 check/recover 配置及同一受管执行/资源能力，关闭产品写入和 repair 模型，避免准备服务内部循环另开预算。测试与评审各自次数/时限，deadline 从取槽后起算，续跑不清零。同次恢复后按最终命令退出/释放事实确定终态，先前失败留在原始 calls/日志，不覆盖最终成功。内核原生回发明确拒收或异常应答时保留未确认信封并通知，发送与读取仍分开。发布前固定节点输入及实际通过记录，合法移除 worktree 后据发布绑定和证据展示检查，不重算成失效，例外欠项不补通过。

## 执行职责与顺序

> 下列为旧内部兼容路径；本步不按旧批次开工/验收/队列启动新卡。

```text
用户确认目标、业务取舍与权限
  ↓
协调助手维护同一份任务、权威来源列表、不可改坏的行为
  ↓
Loop 准备：来源检查 + 运行条件检查
  ├─ 已有方法有效 → 执行
  ├─ 已知环境问题 → 已有恢复脚本，有限重试
  └─ 方法缺失/失效 → 限定文件范围的准备模型 → 原检查重新确认
  ↓
开发：相关定义 → 调用者/状态转换 → 根因修复 → 定向自检
  ↓
独立静态评审
  ├─ 必须修改 → 原会话返修，本轮不跑验收
  └─ 无必修 → 按批次 workflow 执行自动验收或检查完成条件
              （Loop 未运行测试）
                    ↓
             本段必需 accept-cmd（如配置）
                    ↓
             释放资源并核对候选/来源 → 本段可接力
                    ↓
全部相关段可接力 → 整批验收 → 整批完成或按归属返修
                    ↓
结果索引、原始证据和待人工事项 → 用户业务验收
```

同一 git 仓库的段串行，不同仓库按 `maxParallel`（默认 2）有限并行；准备检查可在独立项目间并行。单个候选按评审 → 验收串行，有必修先返修，避免无效的后置检查；共享端口/库未隔离时不扩大并发。扩大这部分并行需先取得资源峰值与耗时收益的实测依据。

批次固定用 `bin/loop 开工 <批次.json>` 和 `bin/loop 启动 <批次.json>`：开工先强制核对每段 workflow（默认带验收）和验收配置，缺项不建开发空间；通过后在 worktree 里建/切批次分支、复制被忽略且未跟踪的 `.autoreview.json`（已有不覆盖并说明）及 `localFiles`、按方法指纹执行非测试的项目方法自检；启动单段直接开会话，多段交给流水线。每批只写提示词和 `批次.json`，批次目录不再放门禁、棘轮或启动脚本。字段、类型、默认值、JSON 输出和会改哪些文件见 [工具清单](../工具清单.md)；本页只讲职责、调度和资源。

Pi 原生入口和流水线都会在开发前执行准备；`loop 开工` 另做一次方法自测，指纹不变时跳过。共享评审入口在昂贵检查前再次确认易失的运行条件，不运行项目测试。旧 gate 字段已停用并忽略，不校验其内容、不占预算，读到只提醒，不改项目配置；开工不再要求 gate。开发方自行做定向自检，Loop 不运行、不判定。Claude/Codex Hook 在 Stop 前执行准备，不声称能阻止宿主开始开发；需要完整开发前置准备时使用 `loop 启动` / 流水线 / Pi 入口。

```json
{
  "release": "main",
  "workspaces": { "dev分支": "../<仓库目录名>-dev分支" },
  "localFiles": ["deploy/acceptance/start.sh", "deploy/acceptance/reset-data.sh", "deploy/acceptance/release.sh", "deploy/acceptance/GUIDE.md"],
  "methods": {
    "paths": [".autoreview/methods"],
    "selfCheck": "sh .autoreview/methods/self-check.sh",
    "probe": "node -v"
  },
  "reviewTimeoutMin": 60,
  "preparation": {
    "check": "sh .autoreview/methods/prepare.sh check",
    "recover": "sh .autoreview/methods/prepare.sh recover",
    "timeoutMin": 10,
    "maxRecoveries": 1,
    "maxRepairs": 1,
    "repair": {
      "model": "按项目指定的准备模型",
      "thinking": "high",
      "paths": [".autoreview/methods/prepare.sh"]
    }
  },
  "acceptance": {
    "start": "sh deploy/acceptance/start.sh",
    "readyUrl": "http://127.0.0.1:38081/health",
    "reset": "sh deploy/acceptance/reset-data.sh",
    "cleanup": "sh deploy/acceptance/release.sh",
    "guide": "deploy/acceptance/GUIDE.md",
    "actions": "deploy/acceptance/actions",

  },
  "context": {
    "root": ".",
    "sources": [
      { "id": "rules", "path": "AGENTS.md", "role": "rules" },
      { "id": "need", "path": "需求.md", "role": "requirement" },
      { "id": "design", "path": "方案.md", "role": "design", "dependsOn": ["need"] },

```

项目固定方法写到 `.autoreview/methods/`（进仓库，只写一份），并由 `.autoreview.json` 的 `methods.paths` 指向；准备和方法自检脚本都在这里；项目测试由开发方自行定向执行，不交给 Loop，批次目录只放 `批次.json` 和结果。命令必须替换为项目已有方法，不能直接用空成功命令代替检查。

准备检查应快速确认：依赖与版本、必要文件、可写临时目录、磁盘余量与项目水位、端口、测试库及凭据入口（不打印值）、已知测试基线、日志和释放方法。通用 Loop 只提供身份、最小容量检查及调用边界，Java、数据库、MinIO 等具体规则由项目脚本负责。

`repair.paths` 是准备模型可编辑范围；没有配置就不调用修复模型。准备模型没有 bash，只能读取和编辑允许路径；AGENTS.md、CLAUDE.md、配置与业务标准不在自动修复范围。程序重跑原检查，不接受模型自报成功。环境恢复、方法修复计数在动作前持久化；自动重试与流水线返修不清零业务 `repairs`。

脚本以退出码 0 报成功；失败输出一行明确分类：

```text
AUTOREVIEW_FAILURE=product 断言失败及证据
AUTOREVIEW_FAILURE=environment 测试存储不可写
AUTOREVIEW_FAILURE=method 缺失准备脚本或检查方法失效
AUTOREVIEW_FAILURE=unknown 当前证据不能确定
```

退出码 75 声明环境，78 声明方法。共享分类器只把有错误来源的实际 ENOSPC、No space left 或存储水位故障行优先归环境，保留原错误行及冲突声明；通过的测试名、标题、引用、代码样本和 expected/actual 不作为当前故障证据。无真实存储错误时，断言失败正常进入产品返修；声明之间或声明与有效故障证据矛盾时保守记未知并列依据，模糊非零输出也不猜成产品失败。普通非零退出不会自动消耗产品返修次数。脚本对分类负责；未知原因先留证据，不能用改产品绕过失效检查。

Hook 用户输入带独立版本。短写锁只保护同步状态读改写，旧执行状态按自身变更合并，不能覆盖新标准和授权。检查阶段边界读取最新持久输入；等待期间轻量监听版本，发生变更就取消旧检查并释放资源，保留业务计数。下一次开发交付按新输入接续。标准和授权先独立落盘，再检查配置、来源和 Git；即使来源缺失、配置损坏或标记文件被删除，也不能吞掉已有会话的撤权。输入更新只有落盘成功后才通知“已记录”。

## 静态规则、动态资料与变更记录

AGENTS.md 只放长期边界和入口链接。接入用 `bin/loop 接入 <项目目录>`，只探测并确认后生成或补全 `.autoreview.json`，不创建或修改 AGENTS.md/CLAUDE.md，也不读取、写入或检查项目的 `.autoreview/CONVENTIONS.md`；已有旧副本原样保留，由用户另行决定。验收与提示词写法只在 Loop 仓库的 `README-验收标准.md` 维护，开发约定运行时注入，起草会话按需指路；Loop 升级后的下次运行自动使用当前规则，无须同步项目副本。需求与方案各保留一份当前权威原文；进度和证据写运行记录，不回灌到常驻规则。

会话完成（含部分验证）时，程序往本机共用的 `~/.pi-autoreview/交付记录.md` 追加一段（项目、任务、结果、总结路径和欠项），只追加不覆盖，历史段落原样保留；总结开头写明该路径。用户直接看 Loop 总结，不要求协调方更新原单；新段落只为人工和部分验证欠项保留勾选，不能把未验写成通过。写入失败只提示，不暂停 Loop。只有 `bin/loop 开发 claude` / `bin/loop 开发 codex` 启动的会话才是自动评审开发会话；直接打开的会话不记录需求或基线，不评审、不暂停、不发通知，也不写状态和总结。SessionStart 不读取交付总表、不注入结果整理提醒；生产 Loop 仍在工具动作后按需指路。

```text
启动 / 用户任务 / 候选检查 / 任务结束 / 定时补漏
  ↓
限定来源范围，读取实际内容并计算 SHA-256
  ├─ 内容与来源声明都没变 → 不写新版本，不调用模型
  └─ 有变化 → 增/改/删记录 + 来源声明变化 + 受影响依赖
                  ↓
          内容按哈希保留，更新只读索引和候选定义位置
                  ↓
          活动任务输入仍冻结，不能静默替换需求或授权
```

索引默认在 `~/.pi-autoreview/projects/<项目根哈希>/`，包含 `snapshot.json`、`context.md`、`changes.jsonl`、`contents/<SHA>` 和 `deliveries/`。记录包含来源、版本、路径、前后哈希和依赖影响；角色/路径/依赖声明改变也产生记录。代码定位是候选定义与行号，不声称具备完整调用图；开发与评审应据此定向读取调用者及测试。

Pi 的 `/review-inputs` 查看当前索引和变化记录；来源内容变化由 Loop 自动换用新版本继续，`/review-inputs accept` 只作确认，不再是继续运行的必经步骤。标准与权限只通过真实用户入口改变：Pi 使用展开前 input 事件的 interactive/rpc 来源，扩展消息不能更新它们；用户文件可以提供标准，文件内容不能代替亲手授权。当前标准与授权版本会进入静态评审输入。识别需求、标准或授权变化时撤销完成状态、总结和段 done，即使源码未变也要重新检查；来源文件内容变化不撤销，只在总结补记变化的文件和发现时间。机器返修同样撤销旧段资格，未接收返修的旧 done 不能用于 --from 验收。登记路径（文件或目录本身）缺失或来源配置被移除时先暂停，那是配置错误，不按旧来源发布当前版本完成；目录型来源里个别文件增删按资料变化处理。

每次取得新的完成资格生成 `readyEpoch`，与会话、候选和输入绑定；同一资格恢复重发保留原值。流水线在启动下游、启动整批验收、验收期间及最终发布前核对全部段的资格与收件箱。任何段撤销资格或换了资格，当前整批验收结果立即失效并执行资源释放，不能继续宣布完成。整批验收证据目录保存 `upstream.json` 说明本轮实际依赖的资格；旧版缺少资格身份的 done 必须重新检查。段巡检遇到登记路径缺失或配置移除时撤销旧资格；内容变化自动换用新版本并记入总结。消费者在接力边界直接核对实际来源，即使段会话已退出或未启用巡检，也不能用缺失来源的旧 done 完成。验收期间每 30 秒补查来源，阶段边界立即复查；250 毫秒状态轮询不重扫全部内容。

`node project-context.ts <项目目录>` 做一次刷新；加 `--watch` 每隔配置秒数补漏（最少 30 秒），Pi 会话内也支持 `intervalSec`。没有创建系统定时任务或修改全局配置。只同步索引，不自动提炼/改写业务事实；经验先记录问题、证据、适用条件与失效来源，由项目维护者判断是否进入当前基线。历史事实失效不等于可删除历史证据。

源码相同不意味着环境相同：缓存的是内容副本和定位，验收结论不跨候选盲用。定时读取有 I/O 成本，来源范围上限 2000 个文件、单文件 1 MiB、总计 16 MiB；应登记必要目录，不扫描整个磁盘。

## 验收复用与资源释放

复用项目维护的 `acceptance.actions` 和 `guide`，每轮复制脚本到 `actions/`，动作通过 `./ev` 留本次证据。每条完成后可用 `./result A1 结果.json` 保存 verdict 和 fields；程序仍核对 evidence 中的摘录。中断后已提交条目可查，漏项不会补成通过。检查点按调用 ID 分目录，过期调用不能覆盖当前结果；更正时新检查点覆盖历史缓存，同次报告与检查点的明确矛盾必须重验，不能作为部分验证放行。

同一次报告更正不重复 reset；强模型从头重验时归档旧代次并清空当前证据和检查点。新候选/新轮次使用新目录，不复制旧证据冒充当前实测。同版标准返修后只重验未通过项，暂时沿用的通过结论须标明原实测轮次和材料；完成前再完整验收全部条目，回退注明「之前通过，这次失败」。新标准、授权或验收配置变化后重新完整验收；整批验收同样处理。定向与最终完整验收共用本轮预算，完整验收未完成或自动条目尚未全部通过均不得接力；自动未验证项暂停，保留原始判定及原因，不能转成人工放行。只有人工及用户不授权的条目仍按既有处理单列；Loop 未运行测试，评审规则不变。这里只保证已提交检查点的保留，不保证模型尚未提交的推理可以恢复。

- 准备、验收命令、自动验收都有 UUID 身份与临时目录。脚本取得 `AUTOREVIEW_RUN_ID`、`AUTOREVIEW_TEMP_DIR`、`AUTOREVIEW_EVIDENCE_DIR`、`TMPDIR`；准备/验收脚本另有 `AUTOREVIEW_RUN_DIR` 证据目录。
- 默认在资源盘可用量不足 256 MiB 时拒绝启动昂贵检查；项目可用 `AUTOREVIEW_MIN_FREE_MIB` 调整，并在准备脚本检查实际数据库/构建盘的更高水位。准备恢复本身仍可启动，避免容量不足时连释放动作也被挡住。
- 长进程登记组号、启动时间与唯一标记；不能证明归属或回收失败就保留登记，下次补漏，不能假称已释放。端口占用者没有本轮标记时不杀。
- `acceptance.cleanup` 在收尾执行，释放项目拥有的测试库、容器、账号租约等；必须幂等，只处理本轮 ID。复用 `resetTimeoutSec` 的时间上限，独立写 `cleanup.log`，失败阻止接力。Pi 关闭/重载、Hook 与流水线的可捕获退出信号都走独立收尾执行器，等待有界释放；cleanup-task.json 保存运行身份、方法入口、状态与日志，失败可按身份补偿。不要清理真实账号/生产数据。
- `AUTOREVIEW_TEMP_DIR` 是明确可释放的缓存目录；`TMPDIR` 与 `AUTOREVIEW_EVIDENCE_DIR` 指向独立保留目录，避免旧脚本使用系统临时目录保存的报告被误删。成功、失败、中断先保留证据路径；孤儿回收先核对已登记消费者已结束。项目应逐步将可丢弃缓存改写到 AUTOREVIEW_TEMP_DIR。
- 开发会话完成（含部分验证，且必需验收已结束）时，按登记瘦身该会话全部轮次的验收目录、资源缓存与 `resources/evidence/<id>`；暂停和进行中不动。保留结果、输入、证据、检查点、日志、png/jpg 和 ≤256 KiB 的小文件（脚本/文本，以及保守保留的未知小二进制）；删除其余大文件、`node_modules`（含小文件）和清空的目录。保留目录的后代继承保护，`node_modules` 除外。会话材料 `.materials.json`、验收目录 `.loop-run.json` 与资源登记相互核对；历史轮次须与会话引用、实际 result.json 对应。材料登记仅作归属索引，历史清理始终另查当前原生 Hook/Pi 会话状态；登记或总结与原生状态不一致、原生状态无法核对时保留，逐项删除前持续检测原生状态文件是否变化。归属不明、符号链接、硬链接、特殊文件和消费者释放未确认的材料保留并列出；真实 `node_modules` 目录内的链接仅删除链接本身，不跟随或改动目标。不碰源码、用户目录或共享缓存。
- 历史存量先执行 `bin/loop 清理` 查看路径和预计空间，确认后才用 `bin/loop 清理 --apply`。默认/`--dry-run` 全程只读，不写任何状态或总结；`--json` 提供结构化路径、空间及未知归属清单，完整用法见 [工具清单](../工具清单.md)「loop 清理」。自动瘦身在总结写一行文件数、空间和保留类别；删除失败仅提示，不改变会话完成状态。
- 总结、日志、检查点及失败证据保留。源码、用户工作目录、共享依赖缓存不自动删除。SIGKILL 无法当场执行 finally，登记用于下次恢复补漏；外部数据库等资源必须由项目幂等脚本在 prepare/recover 中补偿。
- 流水线开发窗口在等待整合返修期间属于活动任务，不当作孤儿清理；报告中保留其运行入口。后台启动的日志描述符在父进程及时关闭。

## Ponytail 与 Skill

单会话开发可使用 `bin/loop 开发 claude ...` 或 `bin/loop 开发 codex ...`，完整参数见 README「Claude Code / Codex 用法」。入口设置 `AUTOREVIEW_DEV_ROOT=<启动时找到的 .autoreview.json 所在目录>`，Hook 只认这个变量；项目根在启动时固定，不随会话中途 `cd` 改变。直接打开的宿主会话不注入开发约定、不评审或暂停、不写状态与总结，SessionStart 也不读取总表或注入提醒。变量指向的目录不存在或没有 `.autoreview.json` 时按「项目配置不可用」处理，提示里写出变量值。入口复用已安装的本机插件，核对 Hook 指向当前 Loop，并保留宿主自动审批模式；不改全局配置、不代为信任 Hook。Ponytail 在这些宿主里沿用宿主已有技能/插件配置，启动器不替它们安装或声称已加载。多段流水线和后置验收命令仍使用下面的 Pi 入口。

使用 Ponytail 自带的 `pi-extension/index.js`，显式加载；不导入 Codex 插件容器，不复制整个规则进 AGENTS.md。流水线的 `pi.ponytail` 为 `{ "extension": "固定版本路径/pi-extension/index.js", "mode": "full" }`；单段可用 `ponytail: false` 关闭。准备脚本修复可设 `preparation.repair.ponytail` 为原生扩展路径，模式 full。

开发会话用 `bin/loop 启动` 或 `bin/loop 开发 pi` 启动（用法见 README「Pi 单会话开发（bin/loop 开发）」和 `工具清单.md`），它固定加载权限扩展、`autoreview.ts` 和 Ponytail（`PONYTAIL_DEFAULT_MODE=full`），缺任何一项就报错退出；不要手抄启动命令。Pi 开发会话启动后还会按实际注册的命令检查 `/ponytail`；没有注册时终端提醒一次，并在完成总结开头写「未加载 Ponytail（开发角色要求加载）」，只提醒，不暂停、不改变完成或验收结果。Ponytail 路径变了用环境变量 `PONYTAIL_EXTENSION` 指定。实际路径由接入时核对；不要把 Codex 可清理的缓存路径当永久依赖。项目部署应固定来源/版本，升级后验证注入与报告格式。默认仅开发和准备修复角色加载；正确性评审、验收不受“少做”指令替代。

Ponytail 已加载不等于成本已下降。应对照完整交付时间、返修、重复读取、模型用量和残留资源；没有真实对照样本时不宣称节省百分比。本批不创建新 Skill，归档与固定结果优先复用程序输出和模板。

## 内部实现：兼容入口

`bin/loop 开发` 分别调用 `bin/pi-dev`（Pi）和 `bin/loop-dev`（Claude/Codex）；多段启动由 `pipeline.ts` 执行，接入由 `setup-acceptance.ts` 执行。原脚本均保留直接调用兼容，但用户与项目统一使用 `bin/loop <动作>`。所有路径共用项目配置读取与预算校验，开工、启动和 dry-run 在开会话前检查预算；显式参数优先于支持的环境覆盖、文件和默认值。

## 迁移与检查

**新卡迁移**：不自动转换用户卡或改项目规则。新建 `version:1` 开发卡，将旧 stages 的任务提示词和 scope 明确填写到 tasks，将旧 workflow/steps 换成 flow；本步支持并行开发评审、可选测试/统一验收/提交，目标 dev，不填旧 workspaces 字段。多任务必需验收，标准用 acceptance 路径并逐条标责任任务；第 4 步已接入提交后的显式部署，以及单任务已有提交只评审。旧路径删除仍待第 5 步清单确认。测试命令写入任务 test，不搬成隐含检查。不要把旧全量测试、accept-cmd 或 gate 搬成隐含前置节点。原需求、标准、授权、历史批次文档保留，接入项目的实际迁移须另获授权。

以下编号是旧内部路径维护说明，不扩大新卡能力：

1. 同一候选顺序为静态评审 → 自动验收；批次 workflow 默认 with-acceptance，不带验收须明确写 without-acceptance，缺 gate 不拒绝或暂停。开工、每段及合入队列都不运行项目测试，也不复用旧测试；总结、通知、交付记录、队列状态和查询的测试项写「Loop 未运行测试」。候选身份、合入与推送边界不变。验收预算必须小于 reviewTimeoutMin，不再加上门禁时长。完成总结以逐条证据的交付报告开头，单段通知及交付记录给报告路径，缺失评审/验收结论写「没有记录」。
2. accept-cmd 默认 required；评审与验收资格绑定候选、标准、授权和检查开始时实际使用的配置（来源内容变化不使结果失效）；上级配置在检查中变化也会使结果失效，用户输入变化后 /accept 不能沿用旧资格；仅需要参考报告的老项目显式设 advisory。恢复会话重新校验完成依据；旧状态缺少依据或 advisory 改为 required 时暂停，保留计数。整批验收只配置到流水线的 `acceptance`，不能让每段等待整批完成。
