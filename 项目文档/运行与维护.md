# Loop 运行、文档与规则维护

本页说明本次实现的行为；总体设计与取舍继续维护在 [全流程优化方案](../docs/方案-Loop全流程优化.md)。项目业务需求、项目方案、验收标准仍由各自的权威原文负责。索引不代替它们，也不自动改写它们。

## 执行职责与顺序

```text
用户确认目标、业务取舍与权限
  ↓
协调助手维护同一份任务、权威来源列表、不可改坏的行为
  ↓
Loop 准备：来源检查 + 运行条件检查
  ├─ 已有方法有效 → 执行
  ├─ 已知环境问题 → 已有恢复脚本，有限重试
  └─ 方法缺失/失效 → 限定文件范围的准备模型 → 原检查重新确认
  ↓
开发：相关定义 → 调用者/状态转换 → 根因修复 → 定向自检
  ↓
程序门禁：单测/类型/构建等项目确定性命令
  ├─ 产品失败 → 原会话返修
  └─ 环境/方法/未知 → 有界恢复或暂停，保留业务计数
  ↓
独立静态评审
  ├─ 必须修改 → 原会话返修
  └─ 无必修 → 自动验收（配置了 acceptance 才执行）
                    ↓
             本段必需 accept-cmd（如配置）
                    ↓
             释放资源并核对候选/来源 → 本段可接力
                    ↓
全部相关段可接力 → 整合 E2E → 整批完成或按归属返修
                    ↓
结果索引、原始证据和待人工事项 → 用户业务验收
```

同一 git 仓库的段串行，不同仓库按 `maxParallel`（默认 2）有限并行；准备检查可在独立项目间并行。单个候选的门禁和评审仍串行，避免门禁快速失败时浪费模型调用，也避免共享端口/库尚未隔离时扩大并发。扩大这部分并行需先取得资源峰值与耗时收益的实测依据。

Pi 原生入口在用户任务开始前执行准备；流水线在启动段之前执行准备，共享评审入口在昂贵检查前再次确认。这里复查的是易失的运行条件，不重复全量测试。Claude/Codex Hook 在 Stop 前执行准备，不声称能阻止宿主开始开发；需要完整开发前置准备时使用流水线/Pi 入口。

## 项目配置示例

下面展示字段组合，命令必须替换为项目已有方法，不能直接用空成功命令代替检查：

```json
{
  "reviewTimeoutMin": 60,
  "preparation": {
    "check": "sh deploy/acceptance/prepare.sh check",
    "recover": "sh deploy/acceptance/prepare.sh recover",
    "timeoutMin": 10,
    "maxRecoveries": 1,
    "maxRepairs": 1,
    "repair": {
      "model": "按项目指定的准备模型",
      "thinking": "high",
      "paths": ["deploy/acceptance/prepare.sh"]
    }
  },
  "gate": { "cmd": "sh deploy/check.sh", "timeoutMin": 10 },
  "acceptance": {
    "start": "sh deploy/acceptance/start.sh",
    "readyUrl": "http://127.0.0.1:38081/health",
    "reset": "sh deploy/acceptance/reset-data.sh",
    "cleanup": "sh deploy/acceptance/release.sh",
    "guide": "deploy/acceptance/GUIDE.md",
    "actions": "deploy/acceptance/actions",
    "timeoutMin": 20
  },
  "context": {
    "root": ".",
    "sources": [
      { "id": "rules", "path": "AGENTS.md", "role": "rules" },
      { "id": "need", "path": "需求.md", "role": "requirement" },
      { "id": "design", "path": "方案.md", "role": "design", "dependsOn": ["need"] },
      { "id": "methods", "path": "deploy/acceptance", "role": "guide", "dependsOn": ["design"] },
      { "id": "code", "path": "src", "role": "code" }
    ],
    "maxChars": 12000,
    "intervalSec": 60
  }
}
```

准备检查应快速确认：依赖与版本、必要文件、可写临时目录、磁盘余量与项目水位、端口、测试库及凭据入口（不打印值）、已知测试基线、日志和释放方法。通用 Loop 只提供身份、最小容量检查及调用边界，Java、数据库、MinIO 等具体规则由项目脚本负责。

`repair.paths` 是准备模型可编辑范围；没有配置就不调用修复模型。准备模型没有 bash，只能读取和编辑允许路径；AGENTS.md、CLAUDE.md、配置与业务标准不在自动修复范围。程序重跑原检查，不接受模型自报成功。环境恢复、方法修复计数在动作前持久化；自动重试与流水线返修不清零业务 `repairs`。

脚本以退出码 0 报成功；失败输出一行明确分类：

```text
AUTOREVIEW_FAILURE=product 断言失败及证据
AUTOREVIEW_FAILURE=environment 测试存储不可写
AUTOREVIEW_FAILURE=method 缺失准备脚本或检查方法失效
AUTOREVIEW_FAILURE=unknown 当前证据不能确定
```

退出码 75 归环境，78 归方法；ENOSPC、No space left 和已识别的存储水位错误优先归环境。普通非零退出不会自动消耗产品返修次数。脚本对分类负责；未知原因先留证据，不能用改产品绕过失效检查。

Hook 用户输入带独立版本。短写锁只保护同步状态读改写，旧执行状态按自身变更合并，不能覆盖新标准和授权。检查阶段边界读取最新持久输入；等待期间轻量监听版本，发生变更就取消旧检查并释放资源，保留业务计数。下一次开发交付按新输入接续。标准和授权先独立落盘，再检查配置、来源和 Git；即使来源缺失、配置损坏或标记文件被删除，也不能吞掉已有会话的撤权。输入更新只有落盘成功后才通知“已记录”。

## 静态规则、动态资料与变更记录

AGENTS.md 只放长期边界和入口链接。`.autoreview/CONVENTIONS.md` 放接入写法，`setup-acceptance.ts` 只更新该文件和配置；一次性迁移后不再自动写 AGENTS.md/CLAUDE.md。需求与方案各保留一份当前权威原文；进度和证据写运行记录，不回灌到常驻规则。

会话完成（含部分验证）时，程序往本机共用的 `~/.pi-autoreview/交付记录.md` 追加一段（项目、任务、结果、总结路径、待回写和欠项），只追加不覆盖；总结开头写明该路径。只有 `bin/loop-dev` 启动的 Claude/Codex 会话才是自动评审开发会话；直接打开的会话不记录需求或基线，不评审、不暂停、不发通知，也不写状态和总结。SessionStart 的待回写提醒是唯一例外：本项目有未勾「已回写原单」的段时，开发会话和直接打开的会话都注入一句（直接打开的会话不带开发约定），项目仍按当前目录判断；Pi 开发会话不注入。读取失败、格式异常或写入失败都只提示，不暂停 Loop。回写原单的规则随【块 1】下发，协调方 AI 按「收尾回写」更新原单并在总表里勾选；程序不自动改原单、不自动归档。

```text
启动 / 用户任务 / 候选检查 / 任务结束 / 定时补漏
  ↓
限定来源范围，读取实际内容并计算 SHA-256
  ├─ 内容与来源声明都没变 → 不写新版本，不调用模型
  └─ 有变化 → 增/改/删记录 + 来源声明变化 + 受影响依赖
                  ↓
          内容按哈希保留，更新只读索引和候选定义位置
                  ↓
          活动任务输入仍冻结，不能静默替换需求或授权
```

索引默认在 `~/.pi-autoreview/projects/<项目根哈希>/`，包含 `snapshot.json`、`context.md`、`changes.jsonl`、`contents/<SHA>` 和 `deliveries/`。记录包含来源、版本、路径、前后哈希和依赖影响；角色/路径/依赖声明改变也产生记录。代码定位是候选定义与行号，不声称具备完整调用图；开发与评审应据此定向读取调用者及测试。

Pi 的 `/review-inputs` 查看当前索引和变化记录；来源内容变化由 Loop 自动换用新版本继续，`/review-inputs accept` 只作确认，不再是继续运行的必经步骤。标准与权限只通过真实用户入口改变：Pi 使用展开前 input 事件的 interactive/rpc 来源，扩展消息不能更新它们；用户文件可以提供标准，文件内容不能代替亲手授权。当前标准与授权版本会进入静态评审输入。识别需求、标准或授权变化时撤销完成状态、总结和段 done，即使源码未变也要重新检查；来源文件内容变化不撤销，只在总结补记变化的文件和发现时间。机器返修同样撤销旧段资格，未接收返修的旧 done 不能用于 --from e2e。登记路径（文件或目录本身）缺失或来源配置被移除时先暂停，那是配置错误，不按旧来源发布当前版本完成；目录型来源里个别文件增删按资料变化处理。

每次取得新的完成资格生成 `readyEpoch`，与会话、候选和输入绑定；同一资格恢复重发保留原值。流水线在启动下游、启动整合验收、验收期间及最终发布前核对全部段的资格与收件箱。任何段撤销资格或换了资格，当前整合结果立即失效并执行资源释放，不能继续宣布完成。整合证据目录保存 `upstream.json` 说明本轮实际依赖的资格；旧版缺少资格身份的 done 必须重新检查。段巡检遇到登记路径缺失或配置移除时撤销旧资格；内容变化自动换用新版本并记入总结。消费者在接力边界直接核对实际来源，即使段会话已退出或未启用巡检，也不能用缺失来源的旧 done 完成。验收期间每 30 秒补查来源，阶段边界立即复查；250 毫秒状态轮询不重扫全部内容。

`node project-context.ts <项目目录>` 做一次刷新；加 `--watch` 每隔配置秒数补漏（最少 30 秒），Pi 会话内也支持 `intervalSec`。没有创建系统定时任务或修改全局配置。只同步索引，不自动提炼/改写业务事实；经验先记录问题、证据、适用条件与失效来源，由项目维护者判断是否进入当前基线。历史事实失效不等于可删除历史证据。

源码相同不意味着环境相同：缓存的是内容副本和定位，完整门禁/验收结论不跨候选盲用。定时读取有 I/O 成本，来源范围上限 2000 个文件、单文件 1 MiB、总计 16 MiB；应登记必要目录，不扫描整个磁盘。

## E2E 复用与资源释放

复用项目维护的 `acceptance.actions` 和 `guide`，每轮复制脚本到 `actions/`，动作通过 `./ev` 留本次证据。每条完成后可用 `./result A1 结果.json` 保存 verdict 和 fields；程序仍核对 evidence 中的摘录。中断后已提交条目可查，漏项不会补成通过。检查点按调用 ID 分目录，过期调用不能覆盖当前结果；更正时新检查点覆盖历史缓存，同次报告与检查点的明确矛盾必须重验，不能作为部分验证放行。

同一次报告更正不重复 reset；强模型从头重验时归档旧代次并清空当前证据和检查点。新候选/新轮次使用新目录，禁止把旧成功迁移到新环境。这里只保证已提交检查点的保留，不保证模型尚未提交的推理可以恢复。

- 门禁、准备、验收命令、自动验收都有 UUID 身份与临时目录。脚本取得 `AUTOREVIEW_RUN_ID`、`AUTOREVIEW_TEMP_DIR`、`AUTOREVIEW_EVIDENCE_DIR`、`TMPDIR`；准备/验收脚本另有 `AUTOREVIEW_RUN_DIR` 证据目录。
- 默认在资源盘可用量不足 256 MiB 时拒绝启动昂贵检查；项目可用 `AUTOREVIEW_MIN_FREE_MIB` 调整，并在准备脚本检查实际数据库/构建盘的更高水位。准备恢复本身仍可启动，避免容量不足时连释放动作也被挡住。
- 长进程登记组号、启动时间与唯一标记；不能证明归属或回收失败就保留登记，下次补漏，不能假称已释放。端口占用者没有本轮标记时不杀。
- `acceptance.cleanup` 在收尾执行，释放项目拥有的测试库、容器、账号租约等；必须幂等，只处理本轮 ID。复用 `resetTimeoutSec` 的时间上限，独立写 `cleanup.log`，失败阻止接力。Pi 关闭/重载、Hook 与流水线的可捕获退出信号都走独立收尾执行器，等待有界释放；cleanup-task.json 保存运行身份、方法入口、状态与日志，失败可按身份补偿。不要清理真实账号/生产数据。
- `AUTOREVIEW_TEMP_DIR` 是明确可释放的缓存目录；`TMPDIR` 与 `AUTOREVIEW_EVIDENCE_DIR` 指向独立保留目录，避免旧脚本使用系统临时目录保存的报告被误删。成功、失败、中断都保留证据路径；孤儿回收先核对已登记消费者已结束。代价是旧脚本未区分的临时数据也会保留，项目应逐步将可丢弃缓存改写到 AUTOREVIEW_TEMP_DIR；保留材料按项目策略清理，不猜文件类型后删除。
- 总结、日志、检查点及失败证据保留。源码、用户工作目录、共享依赖缓存不自动删除。SIGKILL 无法当场执行 finally，登记用于下次恢复补漏；外部数据库等资源必须由项目幂等脚本在 prepare/recover 中补偿。
- 流水线开发窗口在等待整合返修期间属于活动任务，不当作孤儿清理；报告中保留其运行入口。后台启动的日志描述符在父进程及时关闭。

## Ponytail 与 Skill

单会话开发可使用 `bash bin/loop-dev claude ...` 或 `bash bin/loop-dev codex ...`，完整参数见 README「Claude Code / Codex 用法」。入口设置 `AUTOREVIEW_DEV_ROOT=<启动时找到的 .autoreview.json 所在目录>`，Hook 只认这个变量；项目根在启动时固定，不随会话中途 `cd` 改变。直接打开的宿主会话不注入开发约定、不评审或暂停、不写状态与总结，只在 SessionStart 保留交付总表待回写提醒。变量指向的目录不存在或没有 `.autoreview.json` 时按「项目配置不可用」处理，提示里写出变量值。入口复用已安装的本机插件，核对 Hook 指向当前 Loop，并保留宿主自动审批模式；不改全局配置、不代为信任 Hook。Ponytail 在这些宿主里沿用宿主已有技能/插件配置，启动器不替它们安装或声称已加载。多段流水线和后置验收命令仍使用下面的 Pi 入口。

使用 Ponytail 自带的 `pi-extension/index.js`，显式加载；不导入 Codex 插件容器，不复制整个规则进 AGENTS.md。流水线的 `pi.ponytail` 为 `{ "extension": "固定版本路径/pi-extension/index.js", "mode": "full" }`；单段可用 `ponytail: false` 关闭。准备脚本修复可设 `preparation.repair.ponytail` 为原生扩展路径，模式 full。

开发会话用 `bin/pi-dev` 启动（用法见 README「启动」），它固定加载权限扩展、`autoreview.ts` 和 Ponytail（`PONYTAIL_DEFAULT_MODE=full`），缺任何一项就报错退出；不要手抄启动命令。Pi 开发会话启动后还会按实际注册的命令检查 `/ponytail`；没有注册时终端提醒一次，并在完成总结开头写「未加载 Ponytail（开发角色要求加载）」，只提醒，不暂停、不改变完成或验收结果。Ponytail 路径变了用环境变量 `PONYTAIL_EXTENSION` 指定。实际路径由接入时核对；不要把 Codex 可清理的缓存路径当永久依赖。项目部署应固定来源/版本，升级后验证注入与报告格式。默认仅开发和准备修复角色加载；正确性评审、验收不受“少做”指令替代。

Ponytail 已加载不等于成本已下降。应对照完整交付时间、返修、重复读取、模型用量和残留资源；没有真实对照样本时不宣称节省百分比。本批不创建新 Skill，归档与固定结果优先复用程序输出和模板。

## 迁移与检查

1. 同一候选默认顺序改为门禁 → 静态评审 → 自动验收，更新旧脚本中“必须先验收再评审”的判断。
2. accept-cmd 默认 required；评审与验收资格绑定候选、标准、授权和检查开始时实际使用的配置（来源内容变化不使结果失效）；上级配置在检查中变化也会使结果失效，用户输入变化后 /accept 不能沿用旧资格；仅需要参考报告的老项目显式设 advisory。恢复会话重新校验完成依据；旧状态缺少依据或 advisory 改为 required 时暂停，保留计数。整合 E2E 只配置到流水线，不能让每段等待整批完成。
3. 配置来源索引与准备脚本，已有未纳入来源的文件不会自动成为权威依据。接入工具不更改业务标准或全局工具配置。
4. 稳定规则一次性引用可变手册；后续接入、索引刷新和归档都不修改稳定规则。

本仓库单测：`PATH="/Users/Admin/.hermes/node/bin:$PATH" node --test test/*.test.ts`。扩展加载：`pi --offline --no-extensions -e ./autoreview.ts --help`。开发本仓库的真实 E2E 由 `--autoreview-accept-cmd "node test/e2e.mjs" --autoreview-accept-mode required` 在评审后自动执行，报告位于系统临时目录 `autoreview-e2e-*/report.md`。

A8 的顺序断言变为“已先做一次静态评审”；A9 改为“首次重置、同次更正不重复重置”；A10 验证“真实评审后真实验收”。成果正确性、证据、归责、返修和端口释放检查继续保留。技术验证不等于用户项目的业务验收。
