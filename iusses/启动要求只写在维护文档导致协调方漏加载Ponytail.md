# 启动要求只写在维护文档，协调方照 README 模板启动时漏加载 Ponytail

状态：待处理，排第 3 批（顺序：1 运行不停 → 2 交付总表 → 3 本单）。用户 2026-10-19 要求提单。本单只登记问题和处理方向；第 1、3 层（启动脚本、文档）用户已同意由协调方实施，第 2 层（程序检测）交 pi 开发。

## 问题与影响

【建议】`项目文档/运行与维护.md` 要求开发角色加载 Ponytail（`-e …/ponytail/pi-extension/index.js`，`PONYTAIL_DEFAULT_MODE=full`），但 Loop 的 `README.md`「启动」一节给出的启动模板里没有这一项。协调方照 README 模板写启动命令，漏掉了 Ponytail；漏掉之后，程序和总结都没有任何提示。

本例：2026-10-19 「运行不停」「交付总表」两批 Loop 自身开发，开发方都在没有 Ponytail 的情况下启动。用户事后问起才发现。

严重程度：影响开发效率（多读、多做），不影响评审、验收的正确性。第 1 批已完成并通过，结论不受影响。不列为【必须修改】。

更普遍的问题是：**写了要求，但执行不彻底**。协调方必须照做的启动要求分散在多份文档里，靠人工抄写长命令；文档之间不一致时，就按其中一份执行，漏掉的部分没有任何检测。

| 位置 | 内容 |

| `项目文档/运行与维护.md:141-147` | 开发和准备修复角色加载 Ponytail，并给出直接启动写法 |

因果链：

```
要求只写在维护文档 → README 启动模板缺这一项 → 协调方照模板手抄命令
→ 漏加载 → 程序不检测、总结不提示 → 用户事后才发现
```

## 处理方向（三层）

1. **唯一启动入口**（协调方实施）：新增 `bin/pi-dev` 脚本，把固定部分写死：`--offline`、`--no-*`、权限扩展、Loop 扩展、Ponytail（含 `PONYTAIL_DEFAULT_MODE=full`）、默认工具；只留模型、思考档、工作目录、提示词、验收命令等参数。README 和接入项目的启动说明改为调用它。
2. **程序检测，只提醒不拦截**（交 pi 开发）：Loop 开发会话启动时检查是否加载了 Ponytail；没有加载，就在总结开头写「未加载 Ponytail（开发角色要求加载）」，并在终端提示。不暂停、不拒绝启动。
3. **文档只留一处**（协调方实施）：`README.md` 启动一节只写「用 `bin/pi-dev`」，具体规则引用 `运行与维护.md`，不再另抄一份命令。

推广原则：协调方必须照做的要求，优先放进唯一入口；放不进的，由程序检测并写进总结；文档只作说明。

## 拟验收条件
