# 07 架构与扩展

## 1. 最小业务骨架

```text
冻结规则/输入 → 开发 → 交付协议校验 → 冻结候选
                              ↓
                   程序门禁 → 独立评审 → 全部有效通过？
                                             ├ 是：达标交结果
                                             └ 否：有业务返修预算？
                                                    ├ 是：新开发会话
                                                    └ 否：未达标交结果
故障、越界、失去执行者 → 推不动交结果
```

DAG 在单元外看依赖，不在单元内部加入经理/观察员。线程只负责并发编排；成员与门禁始终是独立受管子进程。

## 2. 模块职责

| 模块 | 作用 |
|---|---|
| loop.py / cli.py | 命令入口、环境检查、创建运行、查询与导出 |
| rules.py | 严格规则规范化、DAG、边界冲突、Markdown 视图 |
| common.py | 严格 JSON、原子写、POSIX 锁、快照/指纹、路径与环境处理 |
| storage.py | 权威清单、计数、封存记录、结果视图、通知 |
| protocol.py | 成员 JSON schema、交付验证、门禁覆盖语义结论 |
| adapters.py | Pi/Codex/自定义命令，新会话提示及上下文 |
| engine.py | 单元循环、候选冻结、独立门禁、DAG组合与停止 |
| runner.py | 每命令 guardian、输出采集、时限、父进程丢失与进程组清理 |
| supervisor.py | worker 监督、孤儿恢复、信号处理 |
| audit.py | 存档完整性核对、只向新目录导出 |

## 3. 数据布局

```text
ROOT/runs/RUN/
├── rules.json / rules.md          权威规则快照和自动阅读版
├── response.schema.json          完整交付协议
├── manifest.json                 唯一权威状态与结果
├── events.jsonl                  程序事件
├── supervisor.lock / owner.lock  单一拥有者锁，锁文件不随意删除
├── controller.log                控制进程原始日志
├── units/UNIT/
│   ├── input.json                当前单元组合输入身份
│   ├── candidate-001.json         当前/历史候选清单、差异
│   ├── attempts/ATTEMPT/
│   │   ├── context.json           本次有效上下文
│   │   ├── response.template.json 本次生成骨架，默认全 UNKNOWN
│   │   ├── response.json          成员交付
│   │   ├── accepted.json          程序核对后包上身份的交接
│   │   └── job/                   命令、stdin、日志、进程身份、回执
│   ├── gates/r001-G1/             本次候选的程序测试证据
│   └── result.json                单元结果阅读视图
└── result.md / result.json / report.html / notification.json

ROOT/snapshots/RUN/                源快照、单元输入、格式修复冻结种子
ROOT/checkouts/RUN/UNIT/            可执行但不自动回写原项目的副本
ROOT/artifacts/RUN/UNIT/round-NNN/  历史和当前候选代码
```

工作区保存规则、交接和记录；产品代码分别放 checkouts 和 artifacts，符合原稿“产品文件不混入交接文档”的区分。完整拷贝而非 worktree 使无 Git 项目也能用，代价是磁盘和复制开销。

## 4. 状态与事务

运行：CREATED → RUNNING → TERMINAL。单元：PENDING → RUNNING → TERMINAL；phase 进一步显示 preparing/developing/testing/reviewing/finalizing 等细节。终态结果与状态在一次 manifest 原子替换中一起提交，不存在“状态成功但本次结果未写入”的正常窗口。

写法：同目录临时文件、fsync、os.replace，再尽力 fsync 父目录。进程异常退出后可以用已提交记录恢复；这不是抵御磁盘硬件丢失的复制数据库。

关键交接文件设只读并记 SHA-256。成员不能通过少填标准、重复 ID、旧 attempt_id、旧候选哈希或范围外建议绕过检查。评审意见里的新标准不计入本轮门槛。

## 5. 上下文不是整段历史回灌

每次成员新会话收到：适用单元规则、实际标准内容、任务 notes、输入/候选身份、工作副本、必要反馈、当前门禁证据、历史索引、协议与模板。开发方不需要拿到评审启动命令。旧日志不全部塞入提示；需要时按索引读局部。

状态/事件的持续写入由程序完成，不每轮额外调用模型维护记忆。上下文超限会明确停止，而不是把关键规则裁掉。当前一次反馈可能较大，没有智能摘要服务；保持小型、可独立验收任务。

## 6. 扩展顺序

适配新工具优先写外部 command wrapper，不先改核心状态机。修改规则字段需同步 normalize、阅读版、上下文、测试与手册，不能只加一个被程序忽略的键。

增加外部副作用前需要确定：授权边界、幂等键、远端操作可查询状态、取消/补偿和断网后的未知处理。当前版禁止生产/不可逆操作，不提供这些协议。

增加并行能力前先验证单元正确、无共享隐式写入、合并规则与集成门禁。资源字符串只在本次 DAG 内互斥，不能当分布式锁。

修改后运行 selftest。运行期间引擎会核对自身代码，因此不能一边修改源码、一边用同一份引擎跑任务。测试中的协议桩和故障注入不是独立模型评审，也不是生产完成证明。
