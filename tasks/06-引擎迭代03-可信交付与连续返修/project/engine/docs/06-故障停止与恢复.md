# 06 故障、停止与恢复

## 1. 三层程序，不增加模型角色

```text
监督程序 supervisor
  └─ 调度 worker：状态、DAG、业务循环
       └─ 每次命令一个 guardian：时限、输出、取消、父进程存活
            └─ 成员或测试进程组
```

guardian 监控自己与调度者的父子关系、取消文件、时限与输出，不分析语义。成员主进程正常退出后，同组遗留子进程也会被清理。终止采用有限 TERM 宽限后 KILL。程序只杀能确认归属的受管进程，不按模糊名称批量杀你的其他程序。

不能覆盖的情况：成员另开 session/setsid 脱离进程组、远端作业、机器停电、磁盘不可写、同账号恶意破坏全部程序。不要在成员适配器里开启这些模式。

## 2. 主动停止

```bash
python3 loop.py stop RUN_ID --root /absolute/path/to/loop-runs
```

命令只写停止请求；监督/调度/guardian 收到后取消本次受管工作、写结果，再通知。命令返回 0 不表示已经完成收尾，随后用 status 读取状态。它不会询问模型，也不是修改验收标准。

已经终态的运行不改变。如果没有持锁调度进程，stop 不会自己启动恢复程序，此时使用 recover。

## 3. 调度 worker 意外消失

supervisor 还活着时，检测到 worker 退出后，确认并取消受管工作，给未终态单元补 BLOCKED 结果。已提交终态单元保留。没有完整 receipt 的副作用写为未知，不能假装执行成功。

若故障发生在输入/规则读取阶段，只要权威清单仍可读取、存储可写，也会按创建时保存的标准 ID 填 UNKNOWN，而不是丢掉标准表。

## 4. 两个控制进程都没了，或电脑重启

本版不安装系统服务，不在开机时自动拉起；本地后台 start 只是脱离终端，不能跨断电继续。机器和存储恢复后：

```bash
python3 loop.py status RUN_ID --root /absolute/path/to/loop-runs
python3 loop.py recover RUN_ID --root /absolute/path/to/loop-runs
```

recover 遇到仍存活的监督锁会拒绝接管；不能双调度。孤儿运行会被收尾为推不动，保留已知候选与记录。对已经终态的运行只重建阅读视图，不更改原 manifest。

这是一种“可恢复后补齐结果”的保证，不是声称断电当场能写报告。manifest 或存储已经丢失时无法还原不存在的证据。

## 5. 恢复执行用 retry，新运行不覆盖旧结果

```bash
python3 loop.py retry RUN_ID --root /absolute/path/to/loop-runs
# 或
python3 loop.py retry RUN_ID --root /absolute/path/to/loop-runs --background
```

必须上一运行已经终态，且可复用记录通过完整性检查。规则损坏时不 retry；先在循环之外修复正本，用新的 run/start。

单单元：复用合法输入与已落盘候选代码作为新起点，重新开发、门禁、评审。不是从半句模型回答继续，不重用旧 PASS。候选之外的临时改动不自动带入。

多单元：本版保守地从旧原始输入快照重新跑静态 DAG，不选择性复用各单元旧评审结果。需要改任务结构、上限或权限，编辑新的规则并新 run。

retry 每次重新建立本次预算，是用户主动的新运行，不在无人值守循环里无限递归 retry。

## 6. 常见定位

| 结果/现象 | 看哪里 | 处理方向 |
|---|---|---|
| 成员退出 0 却没交付 | attempts/*/job/stdout.log、protocol-error.txt | wrapper 必须输出/保存符合协议的 JSON |
| launch_error 或 unknown option | stderr.log、receipt.json | 程序缺失、版本参数不兼容或 PATH 不对 |
| nonzero_exit 反复发生 | stderr 与 infra_retries | 登录/凭据、供应商错误、CLI 初始化问题；先本机确认 |
| 门禁 UNKNOWN | gates/*/evidence.json、receipt.json | 环境、超时、启动失败，不是业务通过 |
| 测试 FAIL，模型写 PASS | 最终标准行 review_status 与 status | 硬门禁优先，返修业务代码 |
| 上下文太大 | 结果 reason | 缩小规则/反馈/任务；不静默截掉标准 |
| 超时但日志持续刷新 | stage_timeout_seconds | 输出不延长阶段期限；合理调整下一次规则 |
| 只读评审/格式修复修改代码 | result reason、代码差异 | 检查角色工具、提示与 wrapper，不放宽评审冻结 |
| 规则/门禁日志指纹变化 | audit、controller-error.txt | 查清来源，拒绝沿用旧通过；不要手改清单 |
| 没弹桌面通知 | notification.json | 无图形会话或通知命令不可用；结果仍有效 |
| status 表示未检测持锁进程 | supervisor/owner 锁和日志 | 确认停止后 recover，不直接删锁文件 |

## 7. 通知与预算的边界

macOS 尝试 osascript，Linux 尝试 notify-send；无桌面/权限会失败并保存说明。没有手机推送。可用 `LOOP_NO_NOTIFY=1` 禁用。通知不参与通过判断。

总运行/单元时限和成员阶段期限分别控制；单次静默门禁只受 gate.timeout_seconds 与总时限控制。没有额外付费“最后总结模型”，收尾由程序完成。

不要同时修改运行中的引擎。自身 Python 源文件指纹变化会触发完整性故障；升级版本应先停下旧任务，保留旧包与数据。
