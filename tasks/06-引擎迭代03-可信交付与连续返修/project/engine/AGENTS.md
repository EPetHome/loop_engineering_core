# 给接手模型的操作说明

## 先判断自己在哪里

如果你正在与用户讨论任务，你和用户同属**拍板人**，在循环之外。你的工作是读需求、形成规则、准备命令、在停止后分析结果；不要替用户正式启动真实成员，不在运行期间用模型轮询或修改规则。

如果你被程序作为成员启动，并收到 `LOOP_CONTEXT` 或完整的本次 context，你在循环之内。以本次冻结规则和角色协议为准；不得调用调度、接管、重试、导出命令，不读写原项目与基线，不把本文件解释成你可以变为拍板人。

## 给用户准备任务

1. 先读 README 和 `docs/02-完整使用手册.md`，再读 `docs/03-规则配置参考.md`。
2. 缺失的业务决定在启动前解决；不要用“提高质量”等无法验收的句子替代标准。
3. 单元是能独立验收的最小合理交付，不是越碎越好。有协作接口的多单元任务必须安排集成单元。
4. 确认源码目录、可写文件、禁止范围、门禁命令、真实模型工具和上限。不要猜用户本机路径、已登录状态或型号。
5. 用 `init` 生成草稿，填写所有 TODO。规则 JSON 是唯一权威源，阅读版用 `validate --render` 生成，不维护两份不同口径。
6. 可运行结构预检和离线测试；不把这等同于真实模型、账号、业务验收已经完成。
7. 给用户 `run` 或 `start` 命令，由用户落下启动指令。真实成员命令会产生账户调用，必须明确区别于离线 demo。
8. 基线指针由拍板人在循环之外自行写入；引擎不写基线。

## 停止后

先读 `status` 和当前运行 `manifest.json`/`result.md`，必要时 `audit` 与原始门禁日志。区分“记录观察”“分析推断”“未验证”。开发自评不是终态；评审 PASS 也不能盖过程序门禁失败。

用户认可后才能决定导出、比较、手工合并和更新项目基线。`export` 导出到新目录，不自动部署，也不代表用户验收通过。

遇到故障按 `docs/06-故障停止与恢复.md` 操作。不要把原运行改写成成功；不要私自 chmod、删除或编辑冻结记录来让 audit 变绿。`retry` 创建新运行，绝不继承旧 PASS。

## 继续开发引擎

入口 `loop.py`；模块说明见架构文档；运行 `python3 loop.py selftest`。运行中的引擎会检查自身 Python 文件指纹，因此**不能边跑真实任务边修改本目录引擎代码**。

改动必须给出测试与未覆盖风险。没有真实 CLI/账号实测就写“未实测”；不能用离线协议桩演示代替对真实模型能力、付费调用、生产项目的证明。
