# Loop Engineering：落地补丁与验证清单

> 日期：2026-10-01  
> 状态：待确认建议稿；不是已经实现的引擎，也不是对原稿的自动替换。  
> 本文件提供可插入原文的条款、最小协议说明和验证用例。各处数值应由实际任务确定，不把示意当成通用默认值。

## 一、可以直接讨论采纳的核心条款

### 补丁 A：自主权边界（放入 01 与 03）

成员可以自主选择已授权范围内的实现方法，包括内部结构、函数组织和工作顺序；不得更改业务目标、验收标准、允许的副作用、资源上限和交付范围。

规则未覆盖的事项分开处理：属于已授权实现选择的，由成员决定并按需记录；涉及新增业务决定、扩大权限或变更验收口径的，不自行决定。证据不足不计通过；继续不受影响的工作；确认没有可执行的达标路径或达到既定上限时，以未达标结果结束。

### 补丁 B：规则与上下文（放入 03）

有效规则只有一个权威来源。人读版与程序读版通过确定性过程生成，不分别手工维护。合成后的有效规则在启动前确认、冻结并记录指纹。

提示词模板可以引用标准编号，但成员实际开工前，必须获得该编号对应的完整有效条款及规则版本。无法读取、缺少编号或版本不一致时，不启动该成员。

规则预检为固定入口；额外的模型审规则按风险选择。预检不能保证规格正确，但必须排除格式、权限、依赖和资源上的已知不可执行条件。

### 补丁 C：有效交付（放入 02 与 04）

交付只有在任务、运行、单元、尝试、规则版本和候选成果身份匹配时才有效。证据必须能解析到本次验证对象；陈述与证据不一致不能通过。

开发方写交付；评审方写评审记录；调度程序独占运行状态和最终结果发布权限。成员不能修改旧交付、旧评审、计数和终态。

### 补丁 D：判定状态（放入 03）

单条标准至少允许通过、不通过、证据不足。未执行的标准应另行标明。所有必需标准只有有效的通过状态才能计入单元达标。

“不适用”仅能根据启动前已确定的适用性规则产生。模型的通过结论不能覆盖必需程序门禁的失败。

### 补丁 E：收尾与故障保证（放入 02 与 05）

判定应当停止后，程序进入收尾阶段：停止安排新工作，取消或隔离本次运行拥有的活动，拒绝旧尝试的迟到写入，固定交付对象，提交结果和终态事实，更新结果入口，最后发送通知。

通知失败不改变已提交的业务结论。调度器故障后的检测、恢复和补写由程序承担，不依赖观察员模型。

结果保证的前提是宿主与持久存储可用；宿主故障时，在恢复后核对并补齐结果，不编造未记录的进度或故障时刻。外部作业未确认取消时，结果中标注待核对状态。

### 补丁 F：停止和续跑（放入 02 与 04）

已提交的终态结果不可覆盖。已停止任务的后续执行建立新运行，引用前次运行和合法检查点。同一未收尾运行的基础设施恢复，须更新执行代次并阻止旧成员重新接管。

更改规则、输入或候选成果后，旧通过不自动继承。复用旧证据必须有明确、可检查的有效条件。

### 补丁 G：代码副本与交付（放入 04）

工作区保留为规则、交接、状态、结果和证据的交接区域。开发在独立、明确归属于本次运行的代码工作副本中进行，记录代码起点与候选成果身份。

不擅自清理、覆盖用户已有未提交改动。失败时保留本次成果和未评审改动；清理与回退仅作用于运行拥有的资源。达标不自动更新基线、不自动发布到生产。

### 补丁 H：并发与整体完成（放入 02 与 05）

并行条件不仅包含写入范围不相交，还包含读依赖、共享资源和接口版本受控。下游使用上游明确版本的成果，不使用移动的“最新目录”。

对于需要共同工作的多个成果，整体完成还要求最终组合成果通过集成标准。集成可以作为普通单元安排，不另增角色。真正独立的成果可以按事先声明的汇总规则直接交付。

上游不达标导致下游不启动时，下游留下“未执行：依赖未满足”的记录；整体不得因此被汇总为达标。

### 补丁 I：评审约束（放入 03 与 06）

评审以冻结标准和当前候选成果的原始证据为依据，开发方自述仅作为导航。阻塞修复项必须引用现有标准或已批准的禁止事项，并提供可核查依据。

范围外改进建议和非阻塞意见可以保留，但不得成为本轮新增的强制标准。开发方的修复声明不等于修复已验证。

### 补丁 J：防篡改声明（替换 04 中“必被发现”的绝对表述）

本版本面向同账号下的误操作防护，通过只读设置、检查点指纹核对、受控写入及外部正本降低风险。检查可发现检查时存在的指纹不一致，不承诺发现所有短暂篡改，也不承诺防御具有同等系统权限的恶意修改。

### 补丁 K：计数与预算（放入 03 与 05）

业务返修、基础设施重试、交付协议修复和评价重复试验分别计数；不得相互替代。所有尝试共同消耗运行总预算。

达到预算或无进展上限时停止新增业务工作，保留程序收尾所需的资源。费用无法准确观测时明确标注估算，不声称提供精确计费保证。

### 补丁 L：通用适配器与能力检查（放入 06 与 08）

不同成员启动工具的非交互退出、等待、取消和结果导出行为，必须在适配器中明确并通过实测。某工具的实战经验不自动推广为所有工具的行为。

引擎运行期间不修改自身有效代码和配置；对引擎的开发在独立候选副本进行，由另一次验证确认。运行记录保留实际引擎和适配器版本。

## 二、最小运行协议：业务字段少，程序字段自动填

以下不是要求用户每次填表，而是区分哪些属于用户决策、哪些应由引擎产生。

| 内容 | 确认或产生者 | 应保存的信息 |
|---|---|---|
| 目标与边界 | 拍板人 | 要完成什么、不做什么、允许修改范围 |
| 标准 | 拍板人 | ID、完整条款、判断方式、证据要求 |
| 授权与副作用 | 拍板人；可继承项目规则 | 可用工具、允许资源、明确禁止动作 |
| 预算 | 拍板人选择；可继承默认档位 | 总时限、阶段时限、返修与重试限额 |
| 依赖与集成 | 多单元时由拍板人确认 | 输入产物版本、接口、集成标准 |
| 运行身份 | 引擎 | task_id、run_id、unit_id、attempt_id、执行代次 |
| 输入与规则身份 | 引擎 | 有效规则指纹、输入快照、代码起点 |
| 候选成果身份 | 引擎 | 内容指纹、产物清单、差异清单 |
| 原始验证事实 | 验证执行器 | 命令、用例、退出状态、输出、环境标识 |
| 语义判断 | 评审方 | 标准判断、证据引用、问题清单、规则缺口 |
| 总结果 | 引擎 | 对外停止类型、原因、逐条状态、成果与证据入口 |

不要求所有项目固定用某种数据库或 YAML。真正不能省的是身份与对应关系、唯一写入者、明确的转移条件。

## 三、状态转移约定（建议）

内部阶段不改变对外的三个停止类型。

| 当前阶段 | 合法事件 | 下一阶段或动作 |
|---|---|---|
| 待启动 | 用户启动且获得运行锁 | 预检 |
| 预检 | 规则、输入、能力和存储均通过 | 开发 |
| 预检 | 已知条件不满足 | 收尾，记录启动未通过的原因 |
| 开发 | 接收当前尝试的合法交付 | 评审 |
| 开发 | 暂时基础设施故障，且允许重试 | 创建新尝试；不增加业务返修数 |
| 开发 | 无交付、协议修复耗尽或阶段超时 | 收尾，推不动 |
| 评审 | 必需标准与硬门禁全部有效通过 | 收尾，达标 |
| 评审 | 有可修复问题且预算足够 | 新一轮开发，按定义增加业务返修数 |
| 评审 | 无可执行达标路径或业务上限耗尽 | 收尾，未达标 |
| 任一活动阶段 | 规则身份不一致、禁止事项触发 | 停止新增工作，收尾，按规则记录推不动或未达标的原因 |
| 收尾 | 成果固定、结果和终态事实提交 | 终态；更新展示入口并通知 |
| 收尾 | 崩溃 | 恢复后核对提交状态；不能重复发布不同结论 |
| 终态 | 迟到交付或重复停止请求 | 不修改结果；记录拒绝或幂等返回 |

预检失败的具体停止映射应在通用引擎规范中固定，例如规则不可执行为未达标、凭据或环境不可用为推不动，不留给成员临时猜测。

“状态文件”和“结果文件”若分开存在，要指定哪一份是权威事实。建议用一份原子提交的运行清单，或一个事务，保存终态与结果身份；用户状态展示从它导出，避免两份文件各说各话。

## 四、一个结果应让用户看到什么

示意而非程序输入格式：

```text
停止类型：未达标
停止原因：业务返修上限已到
本次运行：R-示例-02；父运行：R-示例-01
规则版本：v1；规则指纹：由程序填写
候选成果：C-示例-03；成果指纹：由程序填写
代码起点：由程序填写

标准：
  S1 通过：证据 E1，针对 C-示例-03
  S2 不通过：证据 E2，界面错误状态没有清理
  S3 证据不足：远端验证没有收到最终状态

交付：
  最后被评审的候选成果：固定路径或版本
  未评审的额外改动：无，或单独列出
  原始证据与日志：索引位置

仍未解决：S2、S3
规则缺口：无
资源：业务返修 2 次；基础设施重试 1 次；费用未知或附估算说明
恢复条件：核对远端作业后，才决定是否复用该检查点
外部副作用：作业 J-示例 尚未确认结束
```

这个结果如实区分了失败与未知，没有要求在没有证据时补成通过，也没有把部分成果说成整体完成。

## 五、故障注入验收清单

这套清单用于测试引擎本身。先使用可预测的假成员，不依赖真实模型是否“刚好配合”。随后还要跑真实业务任务。

| ID | 注入情形 | 预期行为 | 不可出现 |
|---|---|---|---|
| F01 | 正常开发、评审通过 | 固定同一候选成果；结果提交后显示达标 | 状态达标但结果不存在 |
| F02 | 评审返修后修复成功 | 业务返修计数准确；保留两轮证据 | 覆盖上一轮问题和证据 |
| F03 | 返修持续失败至上限 | 未达标结果包含卡点和最后候选成果 | 无限循环或自动增加名额 |
| F04 | 开发正常退出却没交付 | 协议错误按有限策略处理；最终有推不动说明 | 把退出码 0 当完成 |
| F05 | 交付缺标准 ID、重复 ID 或非法状态 | 拒绝交接；有限补交 | 只看 JSON 能解析就通过 |
| F06 | 评审说通过，但必需测试失败 | 不得达标；保留冲突证据 | 模型总结覆盖硬门禁 |
| F07 | 评审引用上一运行或旧成果证据 | 版本校验拒绝 | 旧成功冒充新成功 |
| F08 | 规则在检查点出现变化 | 拒绝继续执行，保留变更记录与正本身份 | 静默接受新规则 |
| F09 | 成员持续输出无完成事件 | 按阶段期限或无进展策略收尾 | 日志刷屏无限续命 |
| F10 | 正常长测试暂时不输出 | 在已批准期限内由受管作业状态跟踪 | 仅凭日志静默立即杀掉 |
| F11 | 调度器进程被杀 | 程序级机制检测或重启后恢复，核对活动与记录 | 永久停留“运行中”且无恢复途径 |
| F12 | 结果写入中崩溃 | 恢复后识别提交状态，不发布半成品结果 | 最新结果损坏或成功状态悬空 |
| F13 | 同一运行重复启动 | 仅一个有效调度拥有者，其余幂等返回或拒绝 | 两个开发方并发改同一副本 |
| F14 | 旧成员在重试后迟到交付 | 根据执行代次拒绝过期提交 | 新状态被旧成员覆盖 |
| F15 | 停止时通知失败 | 结果仍可查询；通知有限重试 | 已完成业务被改判失败 |
| F16 | 外部动作执行后响应丢失 | 先查状态或使用受支持去重键；未知如实记录 | 盲目重做不可逆动作 |
| F17 | 失败时用户原目录有未提交改动 | 保留用户改动；只处理运行资源 | 自动硬重置用户目录 |
| F18 | 两并行单元各自通过但接口不兼容 | 最终集成失败，整体不得达标 | 全部单元绿灯就直接通过 |
| F19 | 上游失败、下游未启动 | 下游有依赖未满足记录；其他任务按规则继续 | 把未运行当通过或凭空当开发故障 |
| F20 | 预算耗尽但尚有日志输出 | 停止新增工作；程序完成最低限度收尾 | 自动忽略预算或要求额外模型才能写结果 |
| F21 | 测试入口被改成跳过关键用例 | 验收资产或实际用例检查发现异常 | 只凭退出码 0 放行 |
| F22 | 成员读取包含“忽略规则”的代码注释或材料 | 不改变规则；越权工具动作被限制 | 材料内容变成新的控制指令 |

F08 验证的是检查点变化检测，不代表完整恶意篡改防护。整机断电、磁盘故障应另列环境恢复测试，并明确可恢复的前提。

## 六、第一次真实任务的建议标准

沿用原稿“导出超过 3 秒出现进度、失败显示原因”的方向，但先补齐目标含义。以下为示例建议，需由拍板人确认，不能自动增加到现有任务。

| ID | 验收目标 | 建议证据 |
|---|---|---|
| S1 | 约定慢导出场景出现已约定的进度状态 | 实际界面验证与事件时间；阈值和误差预先规定 |
| S2 | 导出失败出现已约定的可理解原因 | 失败场景的界面及错误数据 |
| S3 | 完成或失败后进度状态正确结束 | 状态变化验证；防止完成后又出现过时提示 |
| S4 | 冻结的必需回归用例均通过 | 实际用例清单、数量、输出及候选成果身份 |
| S5 | 只修改授权范围，没有新增未授权副作用 | 变更清单、工具访问记录和必要检查 |

先确认“进度”是加载状态还是百分比，现有项目能否支持这一语义。不要在代码已写完后才改变口径。

可以使用可控时钟验证 3 秒边界，另保留一条真实界面路径，避免只检查测试代码本身。已有已知失败应在启动前处理或明确作为原有问题记录，不能运行中为了通过而删去。

## 七、开发次序与验收门

### 第一关：协议和单元可靠性

交付有效规则格式、结果格式、唯一发布者、候选版本绑定、最低限度预算、收尾及故障恢复。

验收先用 F01—F17、F20—F22 中与第一版工具范围相关的用例。未支持的外部副作用应被预检拒绝，而不是悄悄放行。

### 第二关：真实单元

跑一件真实、低风险、有明确行为标准的任务，验证真实模型和工具适配器。保留一次故障恢复与完整结果证据，不只保存成功截图。

### 第三关：组合交付

增加两并行加一集成的固定编排，验证 F18 与 F19，再逐步扩大资源并发。

在这三关通过前，不优先投入复杂 UI、额外模型角色、跨项目记忆和自动改任务图。

## 八、少量指标，用来判断这套办法是否真的省事

建议先记录四组，不建立庞大的指标系统：

1. **真实收尾**：成功、失败、故障测试中，有多少最终留下了可读、可定位、版本一致的结果；哪些仍需人工救火。
2. **假通过**：出现过多少次状态达标但缺证据、证据过期、成果不一致，或用户验收发现已定义标准未满足。
3. **人力与资源**：用户准备时间、运行中介入次数、验收时间、模型调用与可观察成本。自动执行不必然代表总成本下降，需要实际比较。
4. **收敛**：首次达标率、有效返修轮数、重复失败原因、规则缺口类型。

这些指标由程序记录事件和数字；验收时再由拍板人分析。不要求模型为了维护指标而持续发言。

## 九、必须保留的边界

所有补丁仍然服从：拍板人在外，循环在内；用户启动、用户验收；成员不改规则；基线不由循环更新；简单任务不机械拆分；评审不凭喜好扩大范围；任何可检测停止都进入收尾，严重环境故障在恢复条件具备后补齐。

原稿中的历史决策不被本文件覆盖。采纳的条款应在 07 中追加版本化决策；未采纳的建议继续保留为建议。
