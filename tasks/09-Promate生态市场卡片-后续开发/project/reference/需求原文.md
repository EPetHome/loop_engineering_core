**目标**：通过 Promate 总插件带身份分发、静默升级并留痕。  
**什么叫做完**：点卡片装好，更新完成后告知；保留一键安装。

# Promate 生态市场与专家团发布需求

记录日期：2026-09-30。状态：需求和方案方向经四轮讨论及复核确认，新需求尚未实施。0.2.14 的两项 P2 已在 0.2.15 修复；用户于 2026-09-30 确认真实 WorkBuddy 升级和 401 配置链接验收正常，前置事项已完成。用户 2026-09-30 决定先完成《MCP 工具补齐需求》，之后再做第九节实测、分批开发；本次授权仅为更新需求文档，不构成实测或开发授权。

## 一、要解决的问题

Promate 的 MCP 插件已经落地，用户希望以它作为统一入口，带出平台自己的技能和后续的生态资源。成员不应为每个资源重复查找文件、配置身份或粘贴安装提示词。

产品智能体专家团现在靠微信发安装包，再由使用者执行“一键提示词安装”，每次迭代都要重新分发、重新指导。期望改成：发布者把新版上传 Promate 发布，成员在 WorkBuddy 里点一下就装好，之后自动跟着升级；原来的一键安装能力保留。

两个需求共用一套发布和分发机制，但分别交付、分别验收，不能用完成一个代替全部完成。

## 二、整体做法

已登录的 Promate 总插件负责“带身份同步”：它用本机 Key 向平台拿当前成员可获取的资源清单，写进本机的一个目录型市场（暂名“Promate 生态市场”），WorkBuddy 原生的“＋”从这个本机市场安装。公开的 promate 市场仍只有总插件一个，保留网页接入入口；总插件自身升级所需的地址和加载适配见第五节。

市场里的每个条目都是一张“卡片”：一个只有名称、简介和版本的空壳插件，不带代码，也不带业务内容。点“＋”表示“我要这个”。总插件在下一次同步触发时（本轮回答结束、新对话开始或用户说“同步一下”）发现卡片已装上，就带身份到平台拉取本体并安装：技能装进 WorkBuddy 的技能目录，保持原名；专家团拉取整包后运行 install.py。卡片被卸掉或停用后，下一次同步按资源归属记录清理对应本体，不按同名目录猜测归属。总插件统一协调同步、留痕和结果回报；技能复用总插件现有的安装能力，专家团复用包内的 install.py，不需要另写插件代码。

```text
Promate 平台
  发布、审核、正式版本、摘要（已有）
  目录接口：按成员返回卡片、版本、摘要、下次检查间隔（新增，挂在 MCP 服务下）
        │  带 Key
        ▼
Promate 总插件（已登录）
  同步：写本机“Promate 生态市场”里的卡片 ──► 成员点“＋”
  发现卡片已装 ──► 带身份拉取本体、校验
        ├─ 技能 ──► ~/.workbuddy/skills/<原名>
        └─ 专家团 ──► install.py（免问答）
                      技能、运行时、钩子、my-experts 专家登记
  结果写回平台留痕；轮末告知已完成且未告知的更新，晚完成的留到下一次
原一键提示词 ──► 让总插件拉包，走同一个 install.py
```

这样做的原因是本机核对发现：WorkBuddy 原生“＋”的下载不带任何身份，专家中心也只认 experts 和 my-experts 两个市场，见第八节。鉴权因此放在“总插件向平台拉取”这一步，而不是点“＋”那一刻。

## 三、需求一：平台自建技能进市场

范围是 Promate 平台自己上传、审核、发布的技能，不包括只有外部链接的技能索引，也不把外部工具转成插件。

平台继续作为技能内容和正式版本的管理入口。技能审核上架后，下一次同步时卡片出现在本机市场；成员点“＋”后，总插件从平台拉取正式版本的完整内容（SKILL.md、脚本、模板和引用资源），装进技能目录；新版本审核通过后按第五节静默升级；待审版本不替换正式版本；下架后卡片不再出现，已装本体的处理见第十二节待定事项。

每个技能对应一张卡片，身份稳定，升级不产生同名副本。先用一个真实技能走通从平台发布到新对话实际使用的全过程，再覆盖平台约定的全部可分发技能。更新失败不能把可用的旧版破坏成半成品。

技能同样只处理资源归属记录里的目录。技能目录里已有同名、但不在归属记录里的技能（成员自建或其他来源）时，不覆盖、不删除，本次不安装，并在告知里说明冲突，由成员改名或移走后再同步。

技能装进技能目录，而不是整个打进插件，原因有两个：一是保持技能原名，二是每次获取都经过平台，谁装了哪一版平台都有记录。静默升级的下载同样计入获取次数，渠道记为 MCP，日志里区分首次安装和自动升级；技能卡片上的“N 人获取”按人去重，不受升级影响。

旧的 /cx 安装方式（promate-skill-installer）已废弃，不做接管。

## 四、需求二：产品智能体专家团发布和升级

基线：用户指定桌面交付目录下的 2.1.5。交付目录是 `/Users/Admin/Desktop/产品智能体交付资料/version/v2.1.5/`，完整安装包是 `产品智能体_安装包_v2.1.5.zip`，对应源目录是 `产品智能体/`。不得以本机零散的已安装文件代替这份基线；实施时要核对源目录与发布 ZIP 一致。

必须保留的完整能力：整包包含一名主理人和六名成员的专家定义和头像、29 个技能、运行时、6 个钩子和统计机制。市场化后要整包可用：能从专家中心进入专家团，加载其依赖的技能和运行时，按既有方式调度成员，不能只装专家定义而漏掉其他部分。

做法：

1. 发布者把整包上传 Promate。平台新增“套件”类型，复用技能页的上传、审核、上下架和版本。套件只允许管理员指定的发布者上传，审核时须能看到安装脚本和钩子相对上一正式版的改动，原因见第六节。
2. 成员在本机市场看到一张“产品智能体专家团”卡片，点“＋”。
3. 总插件带身份拉取整包、校验，运行 install.py，并显式指定 WorkBuddy 宿主。复用已有的 `--name`、`--department`、`--person-id` 参数，由平台返回的成员身份带入，不再让本人在对话里填写；补齐身份字段传递与校验，不另写一套免问答安装器。
4. install.py 照旧负责技能、运行时、钩子和 my-experts 专家登记，并刷新 WorkBuddy 注册表。
5. 平台发布新版后按第五节静默升级，始终是同一张卡片，不为每个版本新建卡片。

已通过旧提示词装过 2.1.5 的机器，仍由同一个 install.py 升级，不另做用户操作的“接管”入口。现有安装器按目录名和内容差异替换文件，尚不能证明同名目录归本产品所有；实施时要补资源归属记录，并核对旧版安装记录与文件后纳入管理，无法确认归属的目录不覆盖、不删除。钩子继续按标记先删后加，升级结果须保证技能、钩子和专家不重复。

原一键提示词保留为兼容入口，但改为让总插件拉包并调用同一个 install.py，同样经过身份校验和留痕。常规分发改由平台完成，不再靠微信发 ZIP。

升级只处理本产品自己的资源，保留用户配置、身份绑定、安装实例、历史记录、任务产物和其他插件设置；失败时保留可用的旧版。现有安装器已有备份和异常回滚，但技能、运行时、配置及专家目录分步更新，强制终止时不能依靠异常回滚；后台升级前须补齐中断后的恢复规则，见第五节。升级策略还要包括清理旧运行时目录，本机已积累 2.0.2 到 2.1.5 共 13 个；只有确认不再被进行中的会话或恢复流程使用时才能清理。

安装结果要分别说明哪些已落盘、专家是否已登记、注册表是否已刷新；如仍需重启，要明确提示，不能提前说“已可用”。

身份衔接：Promate 成员模型已有部门字段，当前身份响应尚未返回部门，需补齐到插件的传递。2.1.5 安装器要求姓名为 2–5 个汉字且姓在包内姓氏列表中、部门非空、工号以 CX 开头；实施前核对平台资料是否兼容，以及平台工号是否就是该 CX 工号。缺失或不兼容时明确指出字段问题，不伪造默认值、不覆盖已有身份绑定；由管理员在平台成员管理中改正资料后，成员说“同步一下”重试。

包内的共享飞书凭据 connection.dat 共 30 份（运行时 1 份，29 个技能各 1 份），首期保留（整包只能带身份下载，已经比微信发包收紧），二期去掉，见第六节。

## 五、同步与升级

触发：三路共用一个“同步一次”入口：新对话开始、每轮回答结束（Stop）、用户在对话里说“同步一下”（MCP 新增一个同步工具）。同步工作由独立后台进程执行；钩子拉起进程、处理已有的完成通知后即返回，不等待下载或安装，不挡用户正常使用。两次同步之间的最小间隔由平台在目录接口里下发，改平台配置就能调整，不用重新发插件；用户主动说“同步一下”时不受最小间隔限制，仍遵守同一时间只跑一个同步。

不做定时同步。WorkBuddy 自带的市场自动更新默认 24 小时一次、需要开启，而且不会运行我们的代码。每轮回答结束都会触发 Stop，再加上间隔控制，成员在用 WorkBuddy 时自然会定期检查；成员不用时也没必要同步。打开 WorkBuddy 本身不会运行插件代码，最早的时机是第一个对话。

幂等：同步必须能任意重复、并发触发，而结果一致。

- 同一时间只跑一个同步：加锁，锁失效要能自动回收（吸取 0.2.14 恢复锁残留那项 P2 的教训）。
- 本机的版本和摘要已与平台一致时跳过重复安装；未完成的恢复、结果回报和告知仍须处理。
- 先下载到暂存区并校验，再按可恢复的步骤切换。技能、运行时、配置和专家登记涉及多个位置，不能把单次目录替换当成整包原子切换；记录资源归属、切换进度及恢复依据。中途断网或进程被杀后，下次同步先恢复一致状态，再继续或回退，不让半成品被当作可用新版。
- 钩子按标记替换，不重复写入。
- 本体下载和安装结果回报均带稳定请求号，同一次操作的重试复用原号，平台据此去重；每次同步尝试照样记日志。现有技能服务支持获取计次去重，但 MCP 下载客户端尚未传入 requestId，本次需补齐，不能只给结果回报加请求号。

写权限：后台同步进程以成员本人身份运行，必须能写技能目录、运行时目录、my-experts、本机生态市场目录和用户级 settings.json，否则做不到静默安装和升级。成员点“＋”即表示同意安装并跟随升级。写入范围只限资源归属记录里的位置，以及 settings.json 中带本产品标记的钩子条目，其他内容不动。不关闭、不绕过宿主的沙箱和安全保护；如果实测发现宿主拦截后台写入或要求审批，改为在对话里由成员确认后安装，这属于体验调整，先交用户决定。

本机改动：卡片是唯一开关，本机状态向卡片看齐。卡片还在、本体却被删除或修改时，下一次同步恢复为平台正式版；恢复前把本机内容备份，并在告知里说明一次备份位置，同时提示“不需要请卸载卡片，想自己改请另存为新名字”。另存为新名字的技能不在归属记录里，同步不管。卡片卸载或停用都按关掉处理，按归属记录清理本体；和升级一样，卸载时保留用户配置、身份绑定、历史记录和任务产物。这样本机版本和平台记录始终对得上。

静默升级：技能、专家团和总插件默认都静默升级，平台发版时可以勾“需要用户确认”，留给有破坏性的大改。目标是后台下载、校验后自动切换，进行中的对话继续用旧版，下一个新对话用新版。当前技能及脚本仍在原目录覆盖，仅将运行时按版本保存不能保证旧对话仍用旧版；实施前须验证会话实际读取路径及版本隔离能力，再确定切换方式。若宿主无法保证隔离，应提出等待相关会话结束等调整，由用户确认，不能直接承诺立即切换且互不影响。旧版只在确认不再被会话或恢复流程使用后清理，不能仅因又同步了一次就删除。

静默升级是必要的：不静默的话，成员大多不会去点更新，版本会越来越分散；2.1.5 这类版本和统计字段强绑定，版本对不齐，统计就会出错。

结尾告知：每轮结束时报告截至当时已完成、尚未告知的更新；本轮触发但在结尾之后才完成的，留到下一次可展示时告知，不等待下载阻塞回答，也不提前报成功。内容包括资源、原版本、新版本和实际生效条件，例如在已确认新对话可用时报告“后台已更新：竞品分析 1.2→1.3；产品智能体专家团 2.1.5→2.1.6（新对话生效）”。同一次更新只告知一次。Stop 触发不等于输出一定对用户可见，展示方式须经第九节实测确定；只落盘、待刷新或待重启时须如实说明状态。

少重启：目标是只有首次安装总插件时重启一次，之后技能和专家团的安装、升级都做到新对话生效、不重启。能否做到取决于第九节的实测。

总插件自身升级：公开市场的地址里带版本摘要，每升一版地址就变，所以现在只能从网页重新接入。固定地址或由插件调用先导只是获取新版的候选做法，还须验证宿主是否重新读取插件清单、新会话是否实际启动新版 MCP 代理。文件已更新、钩子显示新版都不能证明代理已换版；地址、加载及是否需要重启一并实测后确定。

## 六、权限、留痕与防绕过

访问边界：仅限 Promate 登录成员，首期不分级，有效登录成员都能看到、都能获取，和现在网页上的技能规则一致。WorkBuddy 这边的身份就是总插件里配置的成员 Key，不靠自填姓名或工号认定身份。

分级授权的引子：每个资源加一个“可见范围”字段，默认“全体登录成员”，判权逻辑集中在一处。以后需要按角色、部门、项目或个人限制时，只改配置、补界面，不改同步和安装。

心跳：插件查版本和同步合并成一个带 Key 的请求，同时作为心跳，上报成员、安装实例号、插件版本、各卡片和本体的版本、系统和 WorkBuddy 版本，不上报对话或文件内容。还没配 Key 的新机器保留现在不带 Key 的版本查询。心跳遇到 401 只记录，不弹配置链接；现有的 401 规则不变，只有成员实际用到工具时，才在对话里给链接。WorkBuddy 下载公开市场包仍是匿名的（宿主下载不带身份），公开包里只有总插件，没有业务内容。

留痕：所有经 MCP 进入平台的操作都要留痕。现有 MCP 工具调用已记录成员、工具、结果和错误码（按设计不记参数原文），技能服务已支持按请求号去重的获取计次，但 MCP 下载链路尚未传入该请求号。新增同步、本体下载和安装结果回报都写进同一套操作日志，并补齐请求号传递与重试去重。插件请求带插件版本号和安装实例号，用于定位机器和版本；这些客户端自报字段不作为身份或用户确认的证明。

防绕过：首期承诺是阻止 Key 从外部直调业务接口，统一经 MCP 鉴权和留痕。网关规则分三档：带 Key 的请求只放行 MCP 服务的明确路由；匿名请求只放行 `/api/skills/plugins/` 下的公开插件地址（版本查询、公开市场包、先导接入和先导脚本）；其余业务接口只认网页登录。不能仅按 `/api/mcp` 路径前缀放行，因为该前缀下还存在转到认证服务的 Key 管理接口。MCP 服务调用后面的服务走内部直连，不经网关，不受影响；前提是业务服务端口不对外开放，只开网关。插件新增的同步、心跳、回报和二期统计接口均挂在 MCP 服务下。上线前改掉 confirm.mjs 用 Key 直调 `/api/requirements/{id}` 取需求标题的做法，改经 MCP（已并入 MCP 工具补齐需求）；插件内目前只有这一处 Key 直调（version.mjs、guard.mjs 用的是匿名地址），上线前再复查一次。

确认边界：上述网关规则不保证写操作经过本机确认。持有 Key 的调用者仍可直接向 MCP 发起工具调用，绕过 WorkBuddy 的确认钩子；现有服务端未校验该次本机确认。首期保留正常插件流程中的写操作确认，不宣称确认不可绕过；若要求这一保证，需另做服务端确认机制，不计入本次首期范围。

签名：平台用私钥给发布清单签名，插件内置公钥验签，证明下载的内容确实是平台发布的、中途没被改过；再按清单里的 SHA-256 核对每个文件。私钥只在服务器上。前提是公开市场和平台地址走 HTTPS：公钥随总插件经匿名公开市场下发，总插件本身不在签名保护之内；更换公钥随总插件自身升级进行。本机不放用来防绕过的密钥：成员电脑上插件能读到的东西，同一个用户（包括他让 agent 执行的命令）也都能读到，放在客户端挡不住本人。

发布权限：套件会在成员电脑上后台执行安装脚本、修改钩子，签名只能证明内容是平台发布的，不能证明内容安全，所以把关放在发布和审核两道。套件只允许管理员指定的发布者上传，审核时须查看安装脚本和钩子相对上一正式版的改动，由审核人决定是否勾“需要用户确认”。每次发版 install.py 里的版本号都会变，因此不能以“脚本有改动”为由一律要求确认。

能力边界：已经装到本机的纯文本技能，无法保证不被复制或改写，也无法远程收回。下架或撤权后的本地可用及清理规则见第十二节；本方案没有推送或常驻同步，不能承诺离线机器立即清理。真正需要撤权即失效的能力，由服务端检查执行。

凭据回收（二期）：专家团插件版本会调整回传方式，统计改为以成员身份回传到平台，数据存在平台；以后有其他需要时，再由平台写入飞书，飞书凭据只放在平台配置里。包内 30 份 connection.dat 去掉，安装器对它的校验一并调整。这样统计也进入平台留痕。

## 八、已核实的事实

以下是 2026-09-30 对本机 WorkBuddy 5.6.2 和当前代码的静态核对，不是运行验收结论；后续适配要以实施时的实际版本重新核对。

1. WorkBuddy 专家中心只认 experts（官方）和 my-experts（自定义）两个市场，放在其他市场里的专家包不会被识别为专家（app.asar 中的 isExpertMarketplace、resolveLocalExpertPluginDir）。
2. WorkBuddy 下载市场和插件包时不带任何身份，直接请求地址（CLI 中的 fetchJson、downloadFile）。
3. WorkBuddy 支持本机目录型市场，experts 和 my-experts 本身就是这种类型（`~/.workbuddy/plugins/known_marketplaces.json`）。
4. WorkBuddy 自带的市场自动更新默认 24 小时一次，可以按市场开关；promate 市场当前是关着的。
5. 公开 promate 市场只有一个插件，先导安装时校验 `plugins.length === 1`；按本方案公开市场保持单插件，这项校验不用改。
6. 平台已有：技能审核、正式版和待审版分离、每个版本的 SHA-256、带身份的下载接口、MCP get_skill、MCP 调用日志，以及技能服务按请求号去重的获取计次；当前 MCP 下载客户端未传入 requestId，不能据此认定该链路重试已去重。平台没有：按成员或分级的可见规则、给同步用的目录接口、套件类型。
7. MCP 服务把成员 Key 原样转给后面的业务接口，当前代码允许带 Key 直调这些业务接口；服务端权限检查仍在，但不经过 MCP 调用日志或本机写操作确认。confirm.mjs 有一处这样的直调。平台服务之间已有内部密钥（X-Promate-Internal-Token），MCP 服务调用后面的服务走内部直连。另一路径是持 Key 直接调用 MCP：它会经过 MCP 权限和日志处理，但服务端同样不校验本机确认。网关收紧业务接口不能消除后一路径。
8. 2.1.5 的 install.py 把 29 个技能按原名装进 `~/.workbuddy/skills`，运行时按版本放在 `product-agent-runtime/<版本>`，钩子按标记合并进用户级 settings.json，专家装进 my-experts，并调用 WorkBuddy 命令刷新注册表；专家包规范禁止携带 hooks 和 commands 目录。安装器已有姓名、部门、工号参数，旧提示词负责向用户收集；Promate 成员模型已有部门，当前身份响应未返回部门。安装器按名称替换目录，有备份和异常回滚，但没有完整的资源归属校验及强制中断恢复机制，也没有为技能脚本提供会话版本隔离。共享飞书凭据 connection.dat 在运行时和 29 个技能里各有一份，共 30 份，安装器要求每个技能都带。安装器需要 Python 3.9 以上，钩子命令里写的是安装时所用解释器的绝对路径；原一键提示词靠 AI 找本机实际可用的解释器，并注明 Windows 的命令钩子还需要 Git Bash。每次正式安装都会把姓名、部门、工号登记进飞书人员表并回传，只有加 `--test` 才与正式统计分开。
9. 关于 2.1.5 是否必须重启：使用说明要求装完重启，但没写原因；安装报告记录刷新注册表的命令挂起了 9 分钟，建议靠重启解决；一键安装提示词却写着“重启不能代替刷新注册表”，材料之间互相矛盾。报告中挂起的那次，没有按安装器要求在干净环境（env -i）中执行，而安装器注释说明带着 WorkBuddy 会话的环境变量执行就会卡住。WorkBuddy 代码按 plugin.json 的修改时间决定是否重新读取自定义专家。结论：没有可靠依据证明必须重启，需要实测。
10. WorkBuddy 自带技能云同步：app.asar 中有 skill-cloud-sync 的上传、下载、删除和合并逻辑，本机 `~/.workbuddy/skill-cloud-sync` 已有迁移记录。它是否自动运行、是否会处理我们装进 `~/.workbuddy/skills` 的技能，尚未核实。如果会，可能把平台技能带到其他设备（绕过平台下载和留痕）、在卸载后又合并回来，或与静默升级互相覆盖。

## 九、实施前要实测的事项

0.2.15 前置验收已由用户确认正常。获实测授权后，由实现者准备隔离账号、资源、宿主环境及恢复依据，先核对实施时的宿主版本，再验证以下事项；结果用于确定做法，不把实测任务扩大为整批开发。实测中的安装一律带测试标记（2.1.5 为 `--test`），测试资源发布在独立环境，或用“可见范围”限定到测试账号，不进正式统计，也不让其他成员同步到。

1. 在干净环境中执行注册表刷新命令，看是否仍会挂起；刷新后新开对话，看专家中心是否显示新版。这决定专家团能否免重启。
2. 总插件能否自己登记本机目录市场并刷新；只含 plugin.json 的空壳卡片，能否在其中点“＋”装上、卸掉；卡片被停用时同步能否识别。
3. 钩子拉起的后台进程，在钩子返回后能否继续跑完；它写技能目录、my-experts 和用户级 settings.json 时，是否被宿主拦截或要求审批；Stop 的结果能否实际展示给用户。分别覆盖轮末前已完成、轮末后才完成的更新，确认不提前报成功、后续可告知且不重复。
4. 新装的技能和钩子是否在新对话中生效。
5. 总插件能否自己升级：除了地址和文件更新，还须核对宿主清单刷新、新会话实际加载的 MCP 代理版本及重启要求，不能用钩子版本代替。
6. 平台侧：实测拿 Key 直调业务接口及直接调用 MCP 的两条路径；盘点直调点、网关路由和既有权限，明确留痕与本机确认各自的边界。
7. 升级前保持一个使用旧版资源的会话，升级后在该会话再次调用技能脚本，同时新开会话使用新版；核对技能、运行时和钩子的实际版本，以及旧版何时可安全清理。
8. 后台安装用哪个 Python：成员电脑上不一定有 python3，要确定总插件怎样找到 3.9 以上的解释器（WorkBuddy 自带的 `~/.workbuddy/binaries/python` 可作候选），以及解释器变化后钩子怎样保持可用。
9. Windows：总插件本身的安装和钩子（命令钩子依赖 Git Bash）、后台进程、Python、路径和文件占用，按以上各项在 Windows 上各测一遍，结果用于决定首期是否包含 Windows。
10. WorkBuddy 技能云同步是否自动运行，会不会上传、恢复或覆盖我们装进技能目录的技能。

本轮实测做到能明确说明卡片安装、后台同步、提示展示和版本生效分别是否可行，并写明不支持或仍未知的部分，即完成。Stop 事件存在不能代替用户可见提示的验证；实测若要求调整既定体验，先提出具体调整供用户决定。

## 十、验收方式

以下是新需求后续实施的验收清单，尚未执行；0.2.15 的既有插件验收不代替本清单。开发者负责准备隔离账号和资源、安装环境和恢复依据；用户验收实际业务和体验。验收中的安装同样带测试标记，测试资源不对其他成员可见。技术检查通过不代替真实宿主的加载和使用验收。

| 编号 | 操作与条件 | 预期结果 |
| --- | --- | --- |
| S1 | 在平台发布一个真实自建技能，成员触发同步 | 本机市场出现对应卡片，名称、简介和正式版本正确，无需手工改市场文件 |
| S2 | 点该卡片“＋”并使用技能 | 本体经平台拉取，装进技能目录并保持原名；新对话实际加载并完成约定的示例任务；平台有该成员的获取记录 |
| S3 | 提交新版本，分别处于待审和审核通过 | 待审不替换正式版；通过后按第五节静默升级，完成后在可展示时告知，新对话用新版，不产生重复安装；这次升级下载计入获取次数并标为自动升级 |
| S4 | 卸载技能卡片后触发同步 | 按资源归属记录清理本体，其他技能及无法确认归属的同名资源不被误删 |
| S5 | 技能目录里已有同名、但不归平台的技能时，点该卡片“＋” | 不覆盖、不删除原有技能，本次不安装，告知冲突 |
| E1 | 干净环境装好总插件后，点专家团卡片“＋”；另覆盖身份字段缺失或不兼容 | 平台身份通过已有参数传入；有效资料无需问答即可完成安装，专家、技能、运行时和钩子就绪；身份异常明确报错，不伪造字段或覆盖旧绑定；核对专家中心实际可用及重启要求 |
| E2 | 在已手动安装 2.1.5 的机器上发布后续版本 | 静默升级，版本与实际加载一致，技能、钩子和专家不重复生效 |
| E3 | 按原一键提示词安装或升级 | 结果与卡片方式一致，同样经过身份校验和留痕 |
| E4 | 从专家团入口执行约定的业务样例 | 主理人调度成员、技能引用和统计正常，保留真实结果和未验证项 |
| P1 | 未配 Key、Key 失效、成员停用时触发同步和下载 | 平台拒绝，直接请求文件地址也绕不过去；心跳遇到 401 只记录，不弹链接 |
| P2 | 拿 Key 直接调业务接口、Key 管理接口；经 MCP 正常调用；另核对绕过本机钩子直接调用 MCP 的路径 | 前两类直调被拒绝；经 MCP 按权限处理并留痕；如实记录本机确认可被直接 MCP 调用绕过，不将此项通过表述为确认不可绕过 |
| P3 | 非指定发布者上传套件；审核套件新版本 | 上传被拒绝；审核时能看到安装脚本和钩子相对上一正式版的改动 |
| I1 | 篡改下载包、发布清单或签名后安装 | 验签或摘要不通过，拒绝安装并说明原因，旧版保持可用 |
| U1 | 三路同时触发、连续触发；下载和多位置切换过程中分别断网或杀进程后重跑，另重试下载与结果回报 | 先恢复一致状态，再继续或回退；不重复安装，不把半成品当成功；同一操作重试复用请求号，获取计数不虚高且回报不丢失 |
| U2 | 升级前后对比用户配置、任务产物、使用记录和其他插件；保留旧会话，升级后再次调用技能脚本，并新开会话调用 | 只处理已确认归属的资源；旧会话仍使用匹配的旧版，新会话使用新版；旧资源在会话和恢复流程均不再使用前不被清理。若实测后另获批准调整切换时机，先同步本条预期 |
| U3 | 本轮结束前及结束后分别完成更新，再触发后续轮次 | 只报告已完成的更新，晚完成的在下一次可展示时告知；每次更新只告知一次，提示与实际生效状态一致 |
| U4 | 发布总插件新版并走自身升级流程 | 分别核对下载版本、钩子版本与新会话实际 MCP 代理版本；明确刷新或重启要求，不以文件更新代替已生效 |
| U5 | 卡片仍在时手动删除或修改本体后触发同步；另停用卡片后触发同步 | 删改的本体恢复为平台正式版，恢复前已备份并告知一次；停用按卸载处理，保留用户配置、历史记录和任务产物 |
| L1 | 在平台查同步、下载、安装回报和 MCP 调用记录 | 能查到成员、时间、资源、版本和安装实例号 |
| M1 | 连续发布同一资源的两个版本，再下架 | 静默升级和结尾告知符合既定规则；下架后的处理按第十二节拍板后的规则验收 |

每项验收分别记录平台发布版本、本机本体版本、实际加载版本、操作系统、操作结果和必要的日志。首期如包含 Windows，S2、E1、U1、U2 在 Windows 上各做一遍。需要重启或仍有未验证的运行行为时，必须明确标注。鉴权和完整性相关的验收必须包含拒绝场景。

- 下架或撤权后，已装本体是否继续可用、成功同步获知状态后是否清理，以及 Key 失效或离线时怎样处理；不承诺未同步机器立即清理。
- 勾了“需要用户确认”的升级，在对话里怎么确认。
- 平台独立技能和专家团内的技能重名时怎么办。倾向于：专家团内的技能归套件，平台不再单独分发同名技能。
- 首期是否包含 Windows，以及 WorkBuddy 最低版本，按第九节实测结果定；不能把本机 macOS 5.6.2 的静态结论推广为所有客户端都支持。
- 旧会话与新版资源的隔离方式、切换时机及旧版安全清理依据，以第九节实测结果确定。
- 总插件自身静默升级的地址、宿主刷新及 MCP 代理加载方案，不能只确定下载地址。

## 十三、已放弃的做法

- 把专家团当普通插件放进 promate 市场，点“＋”直接整套装好：专家中心不识别，“＋”也做不到完整安装和鉴权。
- 把技能整个打进插件：调用名可能被加上插件前缀，而且安装在本机完成，平台看不到。
- 另做用户操作的接管入口：/cx 旧方式已废弃；专家团仍用同一个 install.py，但需补旧版资源归属核对及中断恢复。
- 定时同步：原因见第五节。
- 首期按成员分级可见：改为只留引子，以后再启用。
- 在成员电脑上放密钥（例如 RSA 私钥）来防止绕过 MCP：挡不住本人，锁改放在服务端。
