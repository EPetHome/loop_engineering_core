# 02 完整使用手册

## 1. 工作分界不变

循环之外：用户与陪用户讨论的模型明确目标、边界、标准、模型工具、资源上限；用户启动；停止后共同验收，再决定是否更新项目基线。

循环之内：程序启动开发成员、收取交付、自行跑必需门禁、启动独立评审、接受返修清单、计数、调度依赖、停止并保存结果。没有等待中途拍板的状态，也没有观察员模型。

“自主”指在已授权目标和边界内选择实现方式，不指修改标准、访问任意外部资源或替用户验收。

## 2. 建立任务规则

在引擎根目录执行，源码路径改为你的真实项目：

```bash
python3 loop.py init --source /absolute/path/to/your-project --out task.json
```

这只生成带 TODO 的草稿，不执行成员。和用户一起填写 `title`、`goal`、可修改路径、受保护文件、标准、门禁，以及时限与成员工具。模板里的模型未写死，不表示当前本地默认就是你想要的配置。

用 `notes` 放已确认的通用业务约束；这些内容会进入每次成员调用（包括显式业务续接）。可程序判断的要求仍应写为明确字段或门禁，不能仅依赖 notes。代码/文档原始材料放在纳入快照的源项目里，规则里指明路径。这个版本不另行同步外部知识库。

标准不要只有“测试通过”：还要说清用户可见行为与允许副作用。程序只能判断你提供的测试退出码，不能自动知道测试是否遗漏业务。

## 3. 预检与人工确认

```bash
python3 loop.py validate task.json --render task.readable.md
python3 loop.py doctor --plan task.json --check-tools
```

阅读版从 JSON 生成，不能单独修改成另一份口径。输出文件已存在时命令拒绝覆盖；确认无需保留后由你删除旧阅读版或换新文件名。

`validate` 检查结构、上限、编号、依赖图、并行边界等，不运行门禁，不调用模型，也不证明目标无矛盾。

`doctor` 检查 Python/POSIX、源码目录和成员程序是否存在，可选运行 CLI `--version`。不验证账号、模型是否存在、额度是否足够，不自动下载工具。

正式首次使用前，按成员接入文档完成小型真实试跑。必须确认 gate 命令在干净代码副本中能执行，测试文件数量和测试发现范围正确。

## 4. 启动一次

前台模式适合首次观察：

```bash
python3 loop.py run task.json --root /absolute/path/to/loop-runs
```

正式需要关闭终端时使用本地后台模式：

```bash
python3 loop.py start task.json --root /absolute/path/to/loop-runs
```

两者都使用程序监督，不消耗额外观察员模型调用。`start` 返回表示监督进程已启动，不表示业务达标。它不安装开机自启服务，也不能让电脑断电后继续运行。

数据根目录不能放在 `source` 内部，以免工作副本递归进入源快照。引擎可在各项目之外复用；不同任务共享同一个根目录时运行编号自动去重。并发开启多个相同任务会创建多个独立运行，不是幂等去重；每个具体运行只有一个有效调度者。资源锁只约束同一运行中的单元，不跨独立运行或外部进程预留资源。

启动后不要改原规则、运行副本、引擎代码或冻结成果。修改原项目不会回流到已生成的快照，但创建快照期间源文件变化会被拒绝；不要在那个阶段同时改源码。

默认 developer_session=fresh。仅需要同单元开发业务返修复用时，在启动前显式审批 reuse_repairs 及交付内本地 Pi command/stdout 接法；不在运行中改策略。macOS 实际旧路径保护必须可用，评审/格式修复和失败重试不续接。完整接法、会话映射/实际工具 cwd、失败原因及用户真实对照见 [15](15-开发会话复用.md)。真实收益尚未验证。

## 5. 进度和终点

```bash
python3 loop.py status --root /absolute/path/to/loop-runs --all
python3 loop.py result 运行编号 --root /absolute/path/to/loop-runs
```

状态命令读取本地记录，不调用模型。状态包含阶段、轮数、成员进程调用数、最后输出时间、最后有效交接/门禁步骤时间；“有日志”不意味着有业务进展。组合 Pi JSONL 接法新增成员 last_event_at、最后有事件依据的 waiting/responding/tools 阶段与按 toolCallId 的工具状态；缺事件显示 unknown。member_observations / member_usage 保留含失败调用的活动及分维用量，null 为未知，coverage 小计不替代总量。端到端时间和成员/简报 guardian 时间分开，实际 HTTP/费用未知；详见 [14 活动与简报边界](14-活动用量与简报边界.md)。`status --json` 还可查看单元的 issue_history；普通文本不展开历史。每次成员 context 的 comparison 直接索引本运行本单元的冻结旧正文、上轮候选、完整差异与已接受评审原报告，双方都收到问题历史，不需要从当前代码复原旧正文。比较与显式关项约定见 [13 版本比较与问题历史](13-版本比较与问题历史.md)。

| 停止类型 | 本版意义 |
|---|---|
| 达标 PASSED | 当前候选所有标准有效通过，必需门禁通过；总体达标还要求 finalization=PASS（冻结记录、输入、当前候选及原项目收尾核对完成） |
| 未达标 NOT_MET | 已有有效业务失败、证据不足到返修上限、规则缺口无路可走，或总资源上限到达 |
| 推不动 BLOCKED | 工具、协议、环境、阶段超时、规则或代码越界等阻断执行 |
| 未执行 NOT_RUN | 该单元从未启动，例如依赖失败；这是编排记录，不是第四种执行终点 |

总结果仅在所有单元都有结果记录后发布。单元结果和总收尾是两层结论：`result.finalization.status` 为 PASS / FAIL / UNKNOWN，绑定本次规则、输入及各单元当前候选，随总状态在同一权威清单中原子提交。总收尾异常或无法确认完成时，总体为 BLOCKED，已提交单元结论不变；只有总收尾 PASS 后才按单元停止类型汇总（全部 PASSED 为达标，任一 BLOCKED 为推不动，其余为未达标）。未执行原因逐项保留。空 `source_drift=[]` 不等于核对已完成。

## 6. 验收和合并

先确认读的是本次运行，而不是旧文件。查看总收尾 `finalization`，运行 `audit`，再看具体标准、证据、规则缺口和未解决问题。需要时读 stdout/stderr 原始记录，而不是相信摘要。正式导出还要求所选单元 PASSED、完整性通过且总收尾有效绑定为 PASS；旧运行缺少 finalization 只表示核对未知，不自动补认成功，候选仍保留。详细语义见 [05 结果验收与导出](05-结果验收与导出.md)。

导出到新目录后由用户自行比较和合并。引擎从不自动覆盖原项目、不创建提交、不推送仓库、不更新基线。源码起点是输入快照，基线仍然是你的长期状态文档，两个概念不混用。

## 7. 改规则与再跑

规则只能在上一运行停止后由拍板人修改。改了标准、范围、工具、测试或预算时，把修改记到你的任务决策记录，使用更新后的 JSON 再 `run/start`，新运行获得新指纹。

`retry` 用于同一旧规则下的新尝试，不是编辑旧结果。单单元可将上次合法候选作为代码起点重新开发/测试/评审；多单元保守地从原输入重跑 DAG。旧通过不继承，详见故障文档。
