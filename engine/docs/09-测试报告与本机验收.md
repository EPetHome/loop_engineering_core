# 09 测试报告与本机验收

版本：0.1.0。构建日期：2026-10-01。

## 1. 实测结论

**84 个不同的自动化测试，在 root 和普通用户 uid=1000 两种环境下各完整执行一次，全部通过。** 不是“168 种不同场景”：两轮覆盖的是同一套 84 项测试。耗时分别为 157.997 秒、159.422 秒，只是本次构建记录，不是你本机的运行耗时承诺。

环境为 Linux、Python 3.13.5。所有成员都使用本地可预测协议桩，没有付费模型调用。文件修改、测试子进程、超时、进程被杀、进程组清理、原子写失败、依赖编排和导出都是实际执行或明确注入的程序级测试，不是口头模拟。

证据：`verification/unittest-root.log`、`verification/unittest-standard-user.log`、`verification/summary.json`。日志包含全部测试名称，核心引擎文件指纹保存在 summary 中。

另将程序压缩后解压到包含中文和空格的目录，用普通用户验证：环境检查、单单元演示、两并行加集成、后台启动、状态/结果读取、完整性审计、导出后四个真实 Python 测试、已有导出目录拒绝覆盖、原始示例不变。均已核对通过。安装验证见 `verification/installation-check.json`。

安装测试的首次组合驱动超过工具单次 45 秒调用限制，在后台运行已启动后被中止，**没有把那次驱动记为成功退出**；随后独立复验脚本逐项读取已保存的三次终态并重新执行审计、导出测试及原文件比较，确认通过。后台任务有自己的监督进程，这个限制不等于任务本身失败。

## 5. 你本机的验收顺序

先运行 doctor 和离线 demo，确认结果与指纹；随后 demo --dag，确认三单元及组合代码；再用 export 到全新目录，检查原项目没有变化。

然后在本机确认真实工具的版本、登录和可用模型。由用户启动 examples/real_pi_codex.json，验证真实成员能交付、门禁正常、评审独立；阅读完整结果后再给自己的真实项目写规则。模型调用失败先查工具/凭据和日志，不放宽标准。

有条件时可在一个低风险测试任务中主动 stop 验证本机进程清理；不要对未知进程使用广泛 kill 命令。宿主机睡眠、终端关闭和通知行为应按你实际操作系统补一次验证。

复跑随包测试：

```bash
python3 loop.py selftest
```

运行期间不要修改引擎文件，程序会将其当作完整性异常。离线测试无模型费用，但需要创建临时文件和真实子进程。
