# 05 结果验收与导出

## 1. 哪一份是事实记录

每次运行 `runs/<run_id>/manifest.json` 同时保存状态与结果，采用同文件原子替换；程序不会先公布“已完成”再尝试写结果。`result.md`、`result.json`、`report.html` 与各单元 result.json 都是从它生成的视图，可重建。

终态清单不被 retry/recover 覆盖。通知另存 notification.json，通知失败不修改业务结论。事件日志 events.jsonl 用于定位过程，权威状态以 manifest 为准；不能只看最后一句 stdout。

组合入口另存 delivery-overview.json / 交付结果.md，分列引擎成员预算计数与额外简报进程的次数、耗时、可用用量，绝不为简报统计改原 manifest 终态。成员活动、用量是有覆盖范围的观察，不是标准 PASS 的证据替代；null 保持未知，小计不可冒充总量，真实 HTTP/费用/重复理解成本未计量。简报提示区分真实参与、新接法未实测和人工未验收；静态提示不保证模型摘要语义正确。文件、计时与链接约定见 [14](14-活动用量与简报边界.md)。

## 2. 绑定关系

```text
运行ID + 规则指纹 + 输入快照
                 ↓
单元 / 轮次 / 尝试ID → 候选树指纹
                         ↓
             同一候选上的门禁与评审
                         ↓
                标准逐条最终结论
```

每次开发产出被冻结为单独目录。评审必须报告当前 attempt_id 和 candidate_hash。code: 文件证据记录实际哈希；gate: 证据指向程序保存的当前执行记录。代码、规则、交接、门禁日志在关键交接点核对，末尾再核对。

开发方自评仅为线索；评审方 PASS 若对应必需门禁 FAIL，最终仍然 FAIL，并保存 review_status 方便解释。UNKNOWN 不转换为 PASS。不接受“旧版本跑过，所以新版本也算过”。

总收尾另存于同一权威清单的 `result.finalization`，与成员交付及显式问题解决记录分开：

| 字段 | 含义 |
|---|---|
| status | PASS：冻结证据、输入快照、全部当前候选及原项目核对均完成且无异常；FAIL：发现完整性异常、原项目变化或扫描失败；UNKNOWN：未执行或无法确认完成 |
| rule_hash / input_hash | 本次规则指纹与运行输入快照指纹；未取得输入时 input_hash 为 null，不能 PASS |
| candidate_hashes | 单元 ID 到该单元结果中当前候选的 hash；包括未达标但已形成的候选，无候选的单元不列 |
| checks | integrity 与 source 两项核对的 PASS / FAIL / UNKNOWN，用于解释报告，不以空差异数组代替核对状态 |

`state=TERMINAL`、总停止类型和 finalization 在一次 manifest 原子替换中提交。总收尾 FAIL / UNKNOWN 都使总体 BLOCKED；各单元已经提交的结果、标准和候选不被回改。finalization=PASS 也不代表各单元业务通过或人工验收完成。

## 3. 先看什么

```bash
python3 loop.py status RUN_ID --root /absolute/path/to/loop-runs
python3 loop.py result RUN_ID --root /absolute/path/to/loop-runs
python3 loop.py audit RUN_ID --root /absolute/path/to/loop-runs
```

RUN_ID 换为真实编号。查看顺序：总停止类型、单元停止类型、候选版本、标准行、原始证据、规则缺口、调用与返修计数。达标只表示本轮规则满足，human_acceptance 始终为 NOT_PERFORMED；产品是否值得接受由用户决定。

若最后一轮只写了代码尚未完成评审，结果会区分当前候选和上一次已评审候选，不沿用旧通过。尚未形成正式候选的成员临时改动仍可在 checkouts 中查看，但不会被宣布为已验证交付。

正常收尾时，引擎按启动时同样的纳入范围、排除规则和快照上限重新扫描本次输入来源，与启动时的输入快照清单比较（retry 的输入来源是所复用的输入快照目录）。`manifest.json` 的 `result.source_drift` 与 `result.json` 的 `source_drift` 是有差异的相对路径数组，包含内容变化、新增、删除，以及清单记录的目录和可执行位变化；排除的文件不算差异。没有差异时为 `[]`，不改变原有总停止类型。

`source_drift` 非空时，总停止类型改为 `BLOCKED`（推不动），命令退出码为 3，`result.md` 列出路径；各单元自己的结论和证据不被改写。先人工核对这些路径、确认变化来源并处理原项目，再决定是否重跑或接受候选；不要仅凭单元达标就合并。引擎不自动还原原项目，不更新基线。

重新扫描失败时，以 `finalization.status=FAIL`、总体 `BLOCKED` 收尾并照常生成结果；`source_drift_error`、总摘要和 `result.md` 会写明原因，此时 `source_drift=[]` 不代表原项目没有变化。纳入范围的目录无法枚举（例如权限不足）也按扫描失败处理，不会把不完整清单当作无差异或文件删除。冻结证据、输入快照或任何当前候选核对失败，同样总收尾 FAIL，保留完整性原因和已提交单元成果。

由故障恢复补写总结果时不做这次核对：即使所有单元已 PASSED、原项目差异已算出但尚未随总结果提交，仍记录 `finalization.status=UNKNOWN`、总体 `BLOCKED`，不重跑成员，不猜测核对完成。结果 Markdown / HTML 明示失败或未知，空数组不作为无异常证明。已终态运行只重建视图，不扫描或改写权威记录；旧终态缺少 finalization 时，报告写明“核对未知”，原有停止字段保持原样。

### 怎么看门禁重跑记录

单元的 `stats.gate_reruns` 是历轮累计的门禁重跑次数，首次执行不算重跑，为 0 也会列出。`result.md` 的“门禁重跑记录”按轮次和门禁展示每次执行的状态、退出码与失败原因：

- 最终 PASS 但不是首次通过，会醒目标注 **“重跑后通过（不是一次通过）”**，失败那次仍列在表中。
- 同一单元同一轮里同因两次（可以来自不同门禁）会写明 **“同一原因出现两次，停止重跑”**；最终 FAIL，不继续消耗剩余额度。
- 返修前的重跑记录也按旧轮次保留；旧候选的通过不代表当前候选通过。

查看原始记录：`units/<单元>/gates/r<三位轮次>-<门禁ID>/evidence.json` 每轮每个门禁只有一份，`attempts` 数组按执行顺序提供每次的 `attempt`、`status`、`exit_code`、`reason`、`stdout`、`stderr`。失败原因来自 stdout 的最后一条 `LOOP_FAIL_REASON=` 标记；没有有效内容记为 `unspecified`，通过或 UNKNOWN 那次 reason 为 null。`reruns` 是该门禁本轮的重跑次数，`passed_after_rerun` 标识重跑后才通过，`repeated_reason` 记录触发停止的重复原因（未触发为 null）。原有顶层 status、receipt、argv、stdout、stderr 均对应最后一次执行。

每次日志路径不同；第 1 次仍在 `job/`，后续在 `attempt-002/job/` 等目录，失败日志不会被最后一次覆盖。当前候选的结果证据索引中 `gate:` 条目也带 `attempts`；单元结果 `history` 的每轮 `gates` 保留那轮完整记录，评审上下文的 `gate_evidence` 能看到当前轮每次执行。核对最终状态时也要查看失败与重复原因，不能把最后一条 PASS 误读成一次通过。四条护栏和字段限制见 [03 规则配置参考](03-规则配置参考.md)。

### 怎么看历史问题与显式解决

单元 `issue_history` 同时保留历史 issues / rule_gaps 的稳定 ID、首个来源、历次原始提出、当前 OPEN / RESOLVED / UNKNOWN 状态，以及追加的处理依据。`result.md` / `report.html` 把历史提出、当前状态、处理记录分开，不删改原始提出；`result.rule_gaps` 只列当前未解决缺口，全部历史缺口另列 `historical_rule_gaps`。未再提及或某标准 PASS 不会自动关项；达标可能仍有未显式解决的历史记录，它们不是新增完成标准。

仅评审能提交可选 `issue_resolutions`，必须引用本次已知 ID 和当前候选有效证据。有效 resolution 绑定本轮 candidate_hash、轮次、尝试及原评审报告；相关门禁 FAIL / UNKNOWN、缺失或旧绑定时声明不生效，保留拒绝原因。新交付后旧解决只作历史，即使候选内容相同，新业务轮仍须显式复核。详细字段、只读旧正文授权与兼容约定见 [13](13-版本比较与问题历史.md)。

## 4. audit 的含义

核对冻结规则、交接、门禁日志、运行与单元输入快照、当前/历史候选和代码证据指纹、问题原始来源及显式解决证据（包括仅解决时引用的取证文件），以及已记录的 finalization 与当前规则、输入、候选的绑定，拒绝 PASS 或 RESOLVED 与已知异常矛盾的记录。`integrity_ok=true` 意味着本程序完整性检查范围内未发现变化，不等于总收尾 PASS；旧记录缺少 finalization 可以完整性正常，但核对完成仍未知。audit 不重新扫描原项目或改变旧记录，不证明测试充分、模型语义判断无误、文件从未被短暂改动，或同账号攻击者没有连清单一起改写。

运行期间发生修改并非一定能即时发现，而是在下一交接/最终检查或显式 audit 时被发现。不要编辑 frozen 文件后又让程序沿用旧通过。

## 5. 导出

```bash
python3 loop.py export RUN_ID --root /absolute/path/to/loop-runs --to /absolute/path/to/new-output
```

正式导出要求：运行已终态、所选单元 PASSED、audit 完整性成功，以及总收尾 finalization 为 PASS 且绑定匹配本次规则、输入及所有当前候选。原项目异常、核对未知、绑定不匹配或完整性失败均拒绝，并说明所选候选的保留位置；拒绝不会改旧记录或删除候选。旧运行缺少 finalization 不自动视为收尾完成，核对未知时也不能正式导出。目标目录必须不存在，程序不接受覆盖，防止误写已有工程。多独立成果需显式 `--unit 单元ID`；集成模式默认导出最后集成单元的组合代码。

总结果仅因其它独立单元业务 NOT_MET，而总收尾 PASS、没有全局异常时，已通过的独立单元仍可用 `--unit` 显式导出，但不表示整体产品完成。不能因某单元绿色就忽略原项目、任一当前候选或冻结证据的全局异常。

导出是**整个纳入范围的候选树**，不是 Git patch，不包含 .git、排除的秘密/依赖和运行日志。代码元数据 candidate-NNN.json 包含 changed_paths，供手工比较。由用户决定后续合并、测试、提交、发布和基线更新。

## 6. 搬迁与分享

运行记录使用绝对路径以避免多项目歧义。不要随意搬动仍在运行或准备 retry/audit 的数据根目录；本版不提供运行存档路径重映射。如果仅要交付代码，用 export；要分享证据时连同对应运行、快照和候选另存，并告知路径可能指向原机器。

stdout/stderr 为原始日志，不保证自动去除秘密。分享前检查。包中 verification 的日志是构建期离线测试记录，不是你本机运行结果入口。

本次总收尾、版本比较和问题历史改动只用本地离线协议桩和故障注入验证。真实 Pi/Codex CLI、账号与模型可用性、质量以及会话复用的节省收益均未验证，离线通过不等于真实模型收益或业务验收通过。
