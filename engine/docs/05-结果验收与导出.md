# 05 结果验收与导出

## 1. 哪一份是事实记录

每次运行 `runs/<run_id>/manifest.json` 同时保存状态与结果，采用同文件原子替换；程序不会先公布“已完成”再尝试写结果。`result.md`、`result.json`、`report.html` 与各单元 result.json 都是从它生成的视图，可重建。

终态清单不被 retry/recover 覆盖。通知另存 notification.json，通知失败不修改业务结论。事件日志 events.jsonl 用于定位过程，权威状态以 manifest 为准；不能只看最后一句 stdout。

## 2. 绑定关系

```text
运行ID + 规则指纹 + 输入快照
                 ↓
单元 / 轮次 / 尝试ID → 候选树指纹
                         ↓
             同一候选上的门禁与评审
                         ↓
                标准逐条最终结论
```

每次开发产出被冻结为单独目录。评审必须报告当前 attempt_id 和 candidate_hash。code: 文件证据记录实际哈希；gate: 证据指向程序保存的当前执行记录。代码、规则、交接、门禁日志在关键交接点核对，末尾再核对。

开发方自评仅为线索；评审方 PASS 若对应必需门禁 FAIL，最终仍然 FAIL，并保存 review_status 方便解释。UNKNOWN 不转换为 PASS。不接受“旧版本跑过，所以新版本也算过”。

## 3. 先看什么

```bash
python3 loop.py status RUN_ID --root /absolute/path/to/loop-runs
python3 loop.py result RUN_ID --root /absolute/path/to/loop-runs
python3 loop.py audit RUN_ID --root /absolute/path/to/loop-runs
```

RUN_ID 换为真实编号。查看顺序：总停止类型、单元停止类型、候选版本、标准行、原始证据、规则缺口、调用与返修计数。达标只表示本轮规则满足，human_acceptance 始终为 NOT_PERFORMED；产品是否值得接受由用户决定。

若最后一轮只写了代码尚未完成评审，结果会区分当前候选和上一次已评审候选，不沿用旧通过。尚未形成正式候选的成员临时改动仍可在 checkouts 中查看，但不会被宣布为已验证交付。

正常收尾时，引擎按启动时同样的纳入范围、排除规则和快照上限重新扫描本次输入来源，与启动时的输入快照清单比较（retry 的输入来源是所复用的输入快照目录）。`manifest.json` 的 `result.source_drift` 与 `result.json` 的 `source_drift` 是有差异的相对路径数组，包含内容变化、新增、删除，以及清单记录的目录和可执行位变化；排除的文件不算差异。没有差异时为 `[]`，不改变原有总停止类型。

`source_drift` 非空时，总停止类型改为 `BLOCKED`（推不动），命令退出码为 3，`result.md` 列出路径；各单元自己的结论和证据不被改写。先人工核对这些路径、确认变化来源并处理原项目，再决定是否重跑或接受候选；不要仅凭单元达标就合并。引擎不自动还原原项目，不更新基线。

重新扫描失败时，同样以 `BLOCKED` 收尾并照常生成结果；`source_drift_error`、总摘要和 `result.md` 会写明原因，此时 `source_drift=[]` 不代表原项目没有变化。纳入范围的目录无法枚举（例如权限不足）也按扫描失败处理，不会把不完整清单当作无差异或文件删除。由故障恢复补写结果时不做这次核对，空数组也不代表完成了扫描；已终态结果重建视图不会重新扫描或改写结论。

## 4. audit 的含义

核对冻结规则、交接、门禁日志、输入快照、候选和代码证据指纹。`integrity_ok=true` 意味着本程序检查范围内未发现变化；不证明测试充分、模型语义判断无误、文件从未被短暂改动，或同账号攻击者没有连清单一起改写。

运行期间发生修改并非一定能即时发现，而是在下一交接/最终检查或显式 audit 时被发现。不要编辑 frozen 文件后又让程序沿用旧通过。

## 5. 导出

```bash
python3 loop.py export RUN_ID --root /absolute/path/to/loop-runs --to /absolute/path/to/new-output
```

只有所选单元达标且完整性检查成功才能正式导出。目标目录必须不存在，程序不接受覆盖，防止误写已有工程。多独立成果需显式 `--unit 单元ID`；集成模式默认导出最后集成单元的组合代码。

多个单元并非全都通过时，已通过的独立单元可显式导出，但不表示整体产品完成。任何总体完整性异常要先分析，不要只挑绿色一行。

导出是**整个纳入范围的候选树**，不是 Git patch，不包含 .git、排除的秘密/依赖和运行日志。代码元数据 candidate-NNN.json 包含 changed_paths，供手工比较。由用户决定后续合并、测试、提交、发布和基线更新。

## 6. 搬迁与分享

运行记录使用绝对路径以避免多项目歧义。不要随意搬动仍在运行或准备 retry/audit 的数据根目录；本版不提供运行存档路径重映射。如果仅要交付代码，用 export；要分享证据时连同对应运行、快照和候选另存，并告知路径可能指向原机器。

stdout/stderr 为原始日志，不保证自动去除秘密。分享前检查。包中 verification 的日志是构建期离线测试记录，不是你本机运行结果入口。
