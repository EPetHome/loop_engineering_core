# 13 版本比较与问题历史（0.3.0 / u7）

本单元把已有的快照、候选、已接受报告及证据交接给双方成员，不增加问题平台或新的业务标准。默认仍是新会话；真实 Pi/Codex CLI、账号、模型质量及会话复用的时间/费用节省均未验证。离线报告桩不等于真实收益或用户验收。

## 1. 每次 context 的 comparison

| 字段 | 含义 |
|---|---|
| unit_input={path,hash} | 本运行本单元组合后的只读冻结输入；各轮保持不变，hash 与 unit_input_hash 相同 |
| current={path,hash} | 本次代码副本的起点，hash 与 context.input_hash 相同；开发是当前开发起点，评审是当前冻结候选 |
| previous_candidate | 上一业务轮完整候选对象（path、hash、metadata_path、round、input_hash）；首轮为 null，不把格式/基础设施重试当成上一业务轮 |
| changed_from_input | current 相对 unit_input 的全部变化路径，排序；包括新增、删除、文件内容、目录和可执行位变化 |
| changed_from_previous | current 相对上一业务轮候选的全部变化路径；首轮为 [] |
| previous_review | 上一业务轮已接受评审的**原始报告**，不是被门禁覆盖后的 evaluated 行；没有时为 null，双方都收到 |
| diff_index={path,sha256,bytes} | 本次尝试目录下只读、封存的 comparison.diff；完整文本 diff 和文件/目录元数据，不回灌整个正文进提示 |

开发的 current/diff 指向开始工作时的树，不声称预知之后的修改。格式修复使用新的尝试副本及其冻结起点，但 previous_candidate / previous_review 仍指向上一业务轮。第一轮即使使用 retry 的代码种子，也没有本运行上一业务轮，previous 为 null。

提示明确允许成员只读 comparison 索引中的**本运行本单元**冻结旧正文和差异；不得扩大到原项目、其它单元或其它运行，也不得改旧交接。完整旧正文直接存在 unit_input / previous_candidate 中，不需要从当前文件复原历史。比如保留文档的 0.2.0 / 0.1.0 原条款，第一轮便可直接比较冻结正文，不用因缺正文再安排一轮复原。

comparison.diff 按比较对象和变化路径列出元数据与 UTF-8 unified diff，保留没有末尾换行的标记。非 UTF-8 / 二进制不伪装成文本：提供内容指纹，并通过索引树读取全部原始字节。没有剪掉正文或变化路径；diff 文件不属于成员 stdout/stderr，不按 max_log_bytes 裁剪。源码树仍受 max_source_files / max_source_bytes 限制。提示超过 max_context_bytes 时，在启动成员前 BLOCKED，不静默删规则、报告、问题历史或差异索引；存储或生成差异失败同样不冒充完整交接。

## 2. issue_history 是来源记录加当前状态

context.issue_history 与单元 result.issue_history 都包含历史 issues / rule_gaps。程序为每个提出项分配稳定 ID：同一运行、单元、种类、描述、相关标准相同则合并为同一 ID；来源轮次、角色不参与 ID，不同标准或种类不会混成一项。

每项保存：

- `id`、`kind`（issue / rule_gap）、`description`、`criterion_ids`、首个 `suggested_fix`。issue 绑定冻结标准；内层 rule_gaps 是字符串数组，没有标准映射，criterion_ids=[]。
- `source={round,role,attempt_id,candidate_hash,report_path}`：首个已接受提出的来源，不删改。`occurrences` 追加历次原始提出及来源，包括后来不同的建议；原始报告继续只读封存。
- `status`：OPEN（已提出，未有效解决）、RESOLVED（评审显式解决且当前候选证据有效）、UNKNOWN（新候选尚未复核或关联门禁未知）。`state_note`、`state_candidate_hash`、`state_round` 解释当前投影，不改写来源事实。
- `resolution_attempts`：追加历次评审显式处理声明、原 note/evidence、候选与轮次绑定、证据索引、门禁核对、applied 和原因。
- `resolution`：最后一次有效解决记录，含 candidate_hash；旧解决记录仍保留作历史，不代表新候选已解决。

新开发的起点仍是上轮候选，历史状态会标明原处理轮次。新交付接受后，旧 RESOLVED 对新候选/业务轮投影为 UNKNOWN，即使内容 hash 相同也要求本轮重新显式复核。再次明确提出同一项则为 OPEN。未再次提及、仅标准 PASS、开发自评、旧候选 PASS 都不会自动关项。

已接受的问题历史及时写入原有权威清单；候选、门禁及原始轮次报告也保留。恢复可保留这些记录，但不据此补认业务通过或总收尾完成。retry 创建新运行，不把其它运行的问题/通过偷偷灌入当前单元。

## 3. 可选的内层 issue_resolutions

旧响应不含此字段仍合法；模板仍可不填写。需要显式解决时，**仅评审**增加：

```json
{
  "issue_resolutions": [
    {"id": "从本次 issue_history 复制的程序 ID", "note": "核对当前候选的处理依据", "evidence": ["code:invites.py"]}
  ]
}
```

这是完整响应的可选附加字段，不是独立响应，也不改变驱动本次开发的外层协议。允许的证据沿用当前角色协议：code: 当前普通文件、gate: 当前引擎门禁；仅 reviewer_exec=true 的评审还可引用 scratch: 本次取证文件。仅用于解决的 scratch 引用也封存并记录文件指纹。

- 未知或重复 ID、开发非空关项声明、空 note/evidence、越界引用、旧响应候选 hash 或旧 gate 候选 hash，按交付协议错误处理，沿用角色的 max_protocol_retries。
- 合法声明仍须核对 issue 对应标准的所有关联门禁；rule_gap 无标准映射时保守核对本单元所有必需门禁，此外核对声明所引用的门禁。FAIL、UNKNOWN、缺失或旧候选绑定均不能有效关项。
- 当前文件证据合法但关联门禁 FAIL 时，声明被保留、applied=false、状态 OPEN；关联门禁未知为 UNKNOWN。门禁 UNKNOWN 的正常执行会在新评审前停止，不能沿用以前的解决。程序不能替代评审判断证据的业务充分性。
- 有效处理记录绑定本轮 candidate_hash、round、attempt_id 和已接受原报告；code / scratch 证据保存 path、sha256、candidate_hash，gate 证据保存当前候选执行记录。

## 4. 看结果和 CLI

单元 `result.rule_gaps` 只列当前 OPEN / UNKNOWN 的缺口；`historical_rule_gaps` 列全部历史缺口；issue_history 和 history 中的原报告不会删除已经解决的缺口。Markdown / HTML 分别展示历史提出、当前状态、处理依据及是否生效。全部标准/门禁通过与“历史问题明确解决”不是同一事实：可以达标但仍有未显式关项的历史记录；程序不把这些记录变为新的完成标准。

- `status --json` 的 `units.<ID>.issue_history` 是已接受交接的状态投影；终态的 `units.<ID>.result.issue_history` 是单元结果。普通 status 文本仍主要显示阶段、轮次、计数及总收尾，不展开整段历史。
- `result` / `result.md` / `report.html` 展示完整问题历史；各单元 result.json 由 manifest 重建，不能编辑视图来改变结论。
- `audit` 增加核对单元冻结输入、历史候选、问题原始来源和显式解决证据（包括非 PASSED 单元）。旧终态没有这些字段时只读兼容，不补造历史、补认解决或重写旧记录。
- `export` 和停止退出码的 u6-finalization 约定不变。没有新增关项/编辑历史的 CLI 命令，也不调用额外模型。

本次离线反例覆盖上轮差异、直接读取文档旧正文、原评审与门禁覆盖的区分、超预算完整索引、稳定来源、开发越权/未知 ID/旧证据、关联门禁失败与未知、仅解决引用的取证封存、候选变化以及故障恢复。真实 CLI、账号、质量、节省收益和人工业务验收未进行；0.3.0 集成单元已统一版本与 SHA256SUMS；显式开发业务续接不改变本页的候选/证据/关项规则，默认 fresh，接法见 [15](15-开发会话复用.md)。
