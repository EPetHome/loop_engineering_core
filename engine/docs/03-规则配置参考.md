# 03 规则配置参考 · schema_version=1

JSON 为唯一权威源。未知字段、重复键、非有限数字、TODO 占位符和无效路径会拒绝启动。JSON 不支持注释。最小可运行规则见 `examples/demo.json`；真实适配器见 `examples/real_pi_codex.json`；多单元规则见 `examples/dag.json`。

## 1. 顶层

| 字段 | 必填 | 作用 |
|---|---|---|
| schema_version | 是 | 固定整数 1 |
| task_id | 是 | 字母数字开头，字母/数字/点/下划线/短横线，不超过 64 字符 |
| title | 是 | 人读名称，可中文 |
| source | 是 | 源码/产物输入目录，相对路径以规则文件所在目录为基准 |
| agents | 是 | 成员配置字典 |
| units | 是 | 至少一个单元 |
| limits | 否 | 程序资源上限 |
| notes | 否 | 已确认补充说明，默认空；随每次成员上下文注入 |
| exclude_paths | 否 | 额外排除的相对文件或目录；加在内置排除上，不能取消内置排除 |
| completion | 单元多于一个时是 | `{"mode":"independent"}` 或 `{"mode":"integration","unit":"集成单元ID"}` |

规则本身、完整自然语言标准、单位角色配置会冻结；成员只看到适用单元的规则，不拿到另一方启动命令。

## 2. 全局上限

以下为**默认值**，示例和真实模板可显式覆盖。所有字段均为正整数，`true` 不接受为整数。

| limits 字段 | 默认 | 准确含义 |
|---|---:|---|
| max_parallel | 2 | 同一运行同时执行的单元数，上限 16 |
| max_wall_seconds | 7200 | 自运行创建开始的总墙钟秒数；监督层另有用于清理的有限宽限 |
| max_member_invocations | 24 | 成员进程启动预算；包括开发、评审、基础设施与格式重试，不等于 API 请求数 |
| max_source_bytes | 104857600 | 每个纳入范围的代码树累计文件字节上限（100 MiB），不是全部磁盘配额 |
| max_source_files | 20000 | 每次代码树扫描的文件与目录项数量上限 |
| max_log_bytes | 8388608 | 每个受管成员/门禁进程 stdout+stderr 总上限（8 MiB）；也是每次评审取证目录普通文件的累计字节上限 |
| max_context_bytes | 262144 | 单次传给成员的提示和上下文 UTF-8 字节上限，超出即停、不静默截断 |
| max_response_bytes | 1048576 | 成员交付 JSON 读取上限（1 MiB），不是操作系统文件大小配额 |

没有 `max_cost`、`max_tokens`：本版拿不到所有 CLI 的可靠计费数据，不接受伪精确金额字段。时限和启动次数只能限制部分资源消耗，无法保证精确金额上限。

## 3. 成员 agents

```json
{
  "dev": {"kind":"pi", "identity":"project-developer", "inherit_env":[]},
  "review": {"kind":"codex", "identity":"independent-reviewer", "inherit_env":[]}
}
```

`identity` 是本次配置的角色身份，不是供应商认证身份。一个单元的开发与评审必须引用不同 agent ID，并有不同 identity；程序保证开发/评审分开启动，默认新会话；显式本地 Pi 业务返修复用只留在同开发身份，评审与格式修复始终新会话，不能证明配置中的两个模型真的不同或没有共同盲区。

`model` 为可选字符串；Pi 可设 `provider`；Codex provider 由本地配置决定。缺省使用本地 CLI 默认，不代表引擎验证过默认型号。正式任务建议明确模型和版本约定。

`inherit_env` 只允许填写需要继承的环境变量**名称**，不放密钥值。基础环境会保留 PATH、HOME、语言和常用代理变量等。成员本身可以使用本地账户文件；这不是凭据隔离沙箱。`extra_args` 用于已审查的少量参数，安全、会话、目录、工具、输出覆盖参数受到限制；复杂接入改用显式 command，详见接入文档。

### 本机 Pi 组合配置

在本机组合项目中，用下面的对象替换规则模板的 `agents` 字段即可，不必从历史任务中拼接。其余目标、单元、标准、门禁和预算仍按本次任务填写；这不是可直接执行的完整任务。开发 Sol / max、评审 Astra / xhigh 沿用既有项目配置，未在此重新验证远程模型权限或额度。

```json
{
  "dev": {
    "kind": "command", "identity": "sol-developer", "output": "stdout", "inherit_env": [],
    "argv": ["{python}", "{engine}/../adapters/pi_member.py",
             "--model", "openai-codex/gpt-6.1-sol", "--thinking", "max",
             "--tools", "read,bash,edit,write,grep,find,ls"]
  },
  "review": {
    "kind": "command", "identity": "astra-reviewer", "output": "stdout", "inherit_env": [],
    "argv": ["{python}", "{engine}/../adapters/pi_member.py",
             "--model", "openai-codex/gpt-6-astra", "--thinking", "xhigh",
             "--tools", "read,grep,find,ls"]
  }
}
```

`{engine}` 是正在调度的引擎目录；完整项目必须同时有 `engine/` 和 `adapters/`。适配器保留显式权限扩展、项目规则加载及既有本机 Pi/Node 路径；不关闭权限保护。工具按任务需要在已授权范围内选择，上面是本地代码开发和静态评审配置，不是所有任务的固定白名单。默认 `developer_session="fresh"`、`reviewer_exec=false`、`idle_output_seconds=0`；显式开启取证或复用时才查相应字段/接法，不能只改开关就假定权限或保护已经可用。

## 4. 单元 units

必填：`id`、`goal`、`writable_paths`、`criteria`、`gates`、`developer`、`reviewer`。

| 可选字段 | 默认 | 含义 |
|---|---|---|
| depends_on | [] | 等这些单元达标才启动 |
| protected_paths | [] | 即使其他可写范围覆盖它，也不能改 |
| read_paths | [] | 声明跨单元读依赖，用于提前拒绝并行读写冲突；不是 OS 读权限白名单 |
| resources | [] | 同名资源在本次运行内部互斥；不自动分配端口/账号 |
| kind | work | `work` 或 `integration` |
| reviewer_exec | false | 只接受布尔值 `true` / `false`；为 true 时给评审方开放只读命令取证及独立可写取证目录，不给开发方开放 |
| developer_session | fresh | 只接受字符串 `fresh` / `reuse_repairs`；后者仅同 run/unit/developer 的连续业务返修、交付内本地 Pi command/stdout 支持，其他接法明确拒绝；macOS 实际旧路径保护不可用时拒绝启动 |
| max_repairs | 2 | 首轮之后最多增加几轮业务返修，即最多 3 轮开发+评审 |
| max_infra_retries | 1 | 此单元累计基础设施失败重试额度，不是每个阶段都重新获得额度 |
| max_protocol_retries | 1 | 同一单元内开发方、评审方各自累计的 JSON 交付格式修复额度；互不占用，与业务返修分开 |
| max_seconds | 3600 | 单元启动后的总时限，不能超过整次运行剩余时限 |
| stage_timeout_seconds | 900 | 单次成员执行硬时限；再多输出也不延长 |
| idle_output_seconds | 0 | 成员 stdout/stderr 连续无输出阈值，0 关闭；不作用于门禁进程 |

前三个次数是非负整数。时间字段允许有限数值；max_seconds 和 stage_timeout_seconds 最小 0.1，idle_output_seconds 最小 0。真实 CLI 可能静默较久，默认不启用“无输出即停”，以阶段硬时限兜底；它与原稿“没动静”的粗判不同，避免把合法长测试误杀。

任一角色耗尽自己的格式修复额度后，再出现交付格式错误仍停为 BLOCKED。额度为 0 时不进行格式修复。单元 `stats.protocol_retries` 保留为整数，统计双方格式修复的总次数；`stats.protocol_retries_by_role` 分别记录开发方和评审方次数，即使均为 0 也包含 `{"developer": 0, "reviewer": 0}`。这些计数在同一单元的业务返修轮次之间累计，不重置。

### 显式开发业务返修会话

`developer_session` 默认 fresh；省略字段保持原新会话行为，不允许 continue/latest。reuse_repairs 的归属/配置摘要、精确路径、并发锁、Pi 实际工具 cwd 重绑、旧路径 OS 拒写与失败 fresh 原因见 [15](15-开发会话复用.md)。每轮独立代码/候选/attempt，旧回执与旧 PASS 不继承，评审/格式修复始终新会话；本次不证明真实会话节省收益。

### 评审方只读命令取证

单元设置 `"reviewer_exec": true` 后，评审方每次启动都得到候选副本之外的可写取证目录；上下文 `scratch_path` 和环境变量 `LOOP_SCRATCH` 指向它。脚本和命令输出只能写在那里，候选副本仍只读，改动照旧以 BLOCKED 停止。开发方以及未开启开关的评审方，`scratch_path` 为 null，环境不提供 `LOOP_SCRATCH`。

只有开启开关的评审方可在 `evidence` 中引用 `scratch:<相对路径>`。引用必须指向取证目录内已存在的普通文件；绝对路径、越界路径及任一层符号链接都拒收。开发方引用、未开启开关时引用或目录中普通文件总大小超过 `limits.max_log_bytes` 都算交付格式错误，使用该角色的格式修复额度；未引用文件也计入大小，不应用源码缓存排除规则。

格式修复重启时，将上次取证目录内容复制到本次目录，候选仍冻结。被接受的交付所引用文件设为只读，并记录 path、sha256、候选指纹到证据索引及完整性清单；事后修改会使 `audit` 退出 5。未引用文件保留原处，不删除也不封存。工具差异及 Codex 的只读沙箱限制见 [04 成员工具接入](04-成员工具接入.md)；此处的「只读」约定不是系统沙箱，见 [10 安全边界](10-安全边界与已知限制.md)。

### 路径规则

`src/a.py` 是一个精确文件，`src/` 是目录前缀。不要写 `/src`、`../x`、`src/**`、反斜杠或 shell 通配符。空 writable_paths 可用于纯评审/集成验证单元，不代表任意可写。

程序逐次比较纳入快照的相对文件、目录、内容和可执行位。修改范围外文件或目录会阻断通过。目录可写时，其下新增文件也在范围内；受保护路径优先。

默认排除 `.git/`、`.venv/`、`venv/`、`node_modules/`、`.env`、`.env.local`、`.DS_Store`。扫描还会忽略各层 `__pycache__`、`.pyc/.pyo`、`.git`、`node_modules`、`.venv` 与 `.env`/`.env.*`（`.env.example/.env.sample` 除外）。这不是所有秘密格式的识别器，证书、token.json、自定义密钥名须你额外排除。被忽略的缓存/依赖不纳入候选、指纹或导出。

包括在快照中的符号链接、特殊文件不支持；出现则拒绝。源项目不要求 Git，可以包含未提交文件；引擎不复制 Git 历史。

## 5. 标准与门禁

```json
{
  "criteria": [
    {"id":"S1","text":"待接受且已过期邀请允许重发，其他状态拒绝。","gate_ids":["G1"]},
    {"id":"S2","text":"错误文案符合已确认产品口径。","gate_ids":[]}
  ],
  "gates": [
    {"id":"G1","argv":["{python}","-m","unittest","discover","-s","tests","-v"],
     "timeout_seconds":60,"output_paths":[]}
  ]
}
```

每个门禁都必须关联至少一条标准；每个列出的门禁都必需通过。语义标准允许 gate_ids=[]。门禁**总在当前候选的新副本里由程序启动**，不相信开发方自述测试已跑。

单次执行退出 0 表示 PASS，非 0 表示 FAIL；无法启动、超时、输出超限等表示 UNKNOWN。最终状态取最后一次执行：重跑后退出 0 算门禁 PASS；UNKNOWN 不重跑，照旧以 BLOCKED 停止。一个测试命令可能“发现 0 个测试且退出 0”，因此应自行写可信测试入口验证用例数，不能只凭退出码保证测试完整性。冻结 tests/ 或明确维护策略，禁止通过删除原测试放宽标准。

### 门禁限次重跑与四条护栏

门禁可选字段 `max_reruns` 默认 `0`，只接受 **0 到 5 的整数**，表示首次执行之外最多重跑几次（最多总共 6 次执行）。布尔值、小数（包括 `1.0`）、字符串、负数和大于 5 的值在规则检查时拒绝。例如在门禁对象中加入 `"max_reruns": 1`，允许首次非 0 退出后再执行一次。

1. **限次重跑**：仅进程非 0 退出的 FAIL 且尚有额度时重跑；每次在同一冻结候选的新代码副本与独立 HOME 中执行。UNKNOWN 不使用这份额度，不作为业务失败重跑；全局和单元时限、输出上限与源码完整性护栏仍适用。
2. **失败保留**：重跑不会覆盖失败日志或将失败那次改成 PASS。每个门禁每轮一份 `units/<单元>/gates/r<三位轮次>-<门禁ID>/evidence.json`；原有字段（包括 status、argv、receipt、stdout、stderr）表示最后一次执行。新增 `attempts` 列出每次的 `attempt`（从 1 开始）、`status`、`exit_code`、`reason`、`stdout`、`stderr`；通过或 UNKNOWN 的 reason 为 null。另有 `reruns`、`passed_after_rerun` 和 `repeated_reason`（未重复时为 null）。各次日志单独保存并核对指纹，失败会写进 result.md。
3. **同因两次不再重跑**：同一单元同一轮里，某次失败原因与之前任何一次失败原因相同（包括其他门禁、后来已重跑通过的门禁），当前门禁立即停止重跑，最终 FAIL，并在 `repeated_reason` 写明原因；有剩余额度也不用，必须走业务返修。没有给出原因的失败同样参与比较。
4. **候选一改全部重来**：业务返修产生新候选后，所有门禁从第 1 次重新执行；上一轮的通过与失败原因均不沿用。旧轮 evidence.json 和日志原样保留，结果历史也保留逐轮门禁记录。`stats.gate_reruns` 按单元累计实际重跑次数，跨轮累计，为 0 也有此字段，不占用成员格式或基础设施重试额度。

失败原因约定：非 0 退出时，从**标准输出**取最后一行以 `LOOP_FAIL_REASON=` 开头的行（前缀须在行首），使用等号后的内容；去掉首尾空白后最多保留 200 个字符。没有这样的行，或最后一条内容为空，都记为 `unspecified`；不取 stderr，也不使用通过或 UNKNOWN 那次输出的标记。例如测试可以输出 `LOOP_FAIL_REASON=json-invalid`。原因是逐轮去重的标识，宜使用稳定、可区分的文字。

不写 `max_reruns` 不会重跑；首次执行的代码目录 `gate-r<三位轮次>-<门禁ID>` 和 `gates/r<三位轮次>-<门禁ID>/job/{stdout,stderr}.log` 保持不变。重跑代码副本放在同一单元 checkout 下独立的 `gate-reruns/r<三位轮次>-<门禁ID>/attempt-<三位执行次数>/` 层级，不与任何合法门禁 ID 的首次执行目录混用（例如 `G1` 与 `G1-a002` 可以共存）。重跑的日志位于同一门禁记录目录下的 `attempt-<三位执行次数>/job/`，不会覆盖第 1 次。

`output_paths` 只允许门禁创建的新临时路径，例如 `tmp-test-output/`。不能与候选中的已有路径重合；不能用它允许测试进程修改源码或原测试。扫描中忽略的缓存目录不会成为交付内容。

门禁继承最小基础环境，HOME 指向单独目录，不继承成员显式授权的 API 密钥。每次副本不包含 node_modules/venv，开发成员临时安装的依赖也不自动带到门禁。真实工程需要你预先准备可信、可重复的测试命令与依赖环境；引擎不会擅自安装项目依赖。

argv 是参数数组，不是 shell 字符串；`&&`、重定向不会自动执行。需要 shell 时由用户明确写 `['bash','-lc','...']`，并自行审查副作用。成员 argv 支持 `{python}`、`{engine}`、`{code}`、`{workspace}`、`{context}`、`{response}`、`{schema}`、`{role}`、`{unit}`。门禁只替换 `{python}`、`{engine}`、`{code}`、`{workspace}`、`{unit}`。

## 6. 编排与集成

准备规则的 LLM 要主动判断成果依赖、文件读写冲突和共享资源：独立工作可并行，有成果依赖写入 `depends_on`，紧密耦合的工作可合并为一个单元。用单元的 `writable_paths` / `read_paths` 声明边界、`resources` 声明共享资源，用 `limits.max_parallel` 限制并发；只需简短说明安排，不另做演练。资源互斥只防止同时运行，不确定先后，也不传递成果；需要上游结果时仍必须声明依赖，不能用资源锁或并发数 1 替代。

并行可写范围不能相交，也不能覆盖对方声明的冻结/读范围。程序检查的是已声明依赖；未声明的共享数据库等不会自动识别。共享资源同名会串行执行，但彼此真正独立的副本仍不共享未交付改动。

上游达标后，下游从原始输入快照叠加祖先已达标候选的确定差异。保守逐文件合并发生冲突时停止，不让模型暗中改合并规则。

需要共同工作的产品：completion.mode=integration，指定 kind=integration 的最终单元，而且它必须传递依赖所有其他单元。互不组合的独立文档才可用 independent。程序不会替你添加集成用例。
