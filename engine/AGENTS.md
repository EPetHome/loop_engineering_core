# 给接手模型的操作说明

## 先判断自己在哪里

如果你正在与用户讨论任务，你和用户同属**拍板人**，在循环之外。你的工作是读需求、形成规则、准备命令、在停止后分析结果；不要替用户正式启动真实成员，不在运行期间用模型轮询或修改规则。

如果你被程序作为成员启动，并收到 `LOOP_CONTEXT` 或完整的本次 context，你在循环之内。以本次冻结规则和角色协议为准；不得调用调度、接管、重试、导出命令，不读写原项目与基线，不把本文件解释成你可以变为拍板人。

## 给用户准备任务

1. 先读 README 和 `docs/02-完整使用手册.md`，再读 `docs/03-规则配置参考.md`。
2. 日常顺序：目标/授权范围/完成标准与预算 → 复用合适的已有规则、模型工具配置和测试入口 → 必要检查 → 唯一启动命令。关键业务歧义在启动前解决；已授权的常规实现选择由执行者决定，不逐项等待确认。
3. 单元是能独立验收的合理工作单元，不是越碎越好；小任务可只有一个。有协作接口的多单元任务必须安排集成单元。
4. 确认本任务源码、可写/禁止范围、门禁、已确认模型工具和上限，不猜路径、登录状态或型号。新门禁优先复用原测试；有疑点时确认命令、发现范围和失败原因，不要求先做出完整成功解。
5. 优先复用合适的规则；需要新建时用 `init` 生成草稿，填写 TODO。规则 JSON 是唯一权威源，阅读版用 `validate --render` 生成。成员提示由引擎依据本次 context 生成，不重复手写角色启动协议。
6. `validate` 检查结构、依赖和已声明边界，不运行门禁/模型；`doctor` 检查本机 Python/POSIX、源码/成员程序存在性及可选 CLI 版本。它们不证明凭据、远程模型/额度、业务可行性或所有运行冲突。相关运行要看全部记录，修改引擎前还须核对实际进程/路径，不只看 latest。
7. 常规启动不先实现临时成功解，不以假成员完整演练、全引擎回归或真实模型试调用为条件。完整引擎回归和适配器演练用于安装、升级、相关接口或安全边界变化后的针对性验证；高风险/可行性验证限定具体疑点。给用户唯一命令，由用户启动；组合项目日常用根目录 `python3 run_loop.py PLAN --root DATA_DIR`，默认只生成程序汇总且不扫描全部日志判断长度，仅显式追加 `--brief` 才在完整终态且未取消时生成一次 AI 简报（短日志也生成，失败保留原结果，退出码不变）。独立引擎的 `run/start` 入口仍保留；真实成员调用和另行授权的简报须区别于离线 demo。
8. 基线指针由拍板人在循环之外自行写入；引擎不写基线。

## 停止后

先读 `status` 和当前运行 `manifest.json`/`result.md`，必要时 `audit` 与原始门禁日志。区分“记录观察”“分析推断”“未验证”。开发自评不是终态；评审 PASS 也不能盖过程序门禁失败。

用户认可后才能决定导出、比较、手工合并和更新项目基线。`export` 导出到新目录，不自动部署，也不代表用户验收通过。

遇到故障按 `docs/06-故障停止与恢复.md` 操作。不要把原运行改写成成功；不要私自 chmod、删除或编辑冻结记录来让 audit 变绿。`retry` 创建新运行，绝不继承旧 PASS。

## 继续开发引擎

入口 `loop.py`；模块说明见架构文档；运行 `python3 loop.py selftest`。运行中的引擎会检查自身 Python 文件指纹，因此**不能边跑真实任务边修改本目录引擎代码**。

改动必须给出测试与未覆盖风险。没有真实 CLI/账号实测就写“未实测”；不能用离线协议桩演示代替对真实模型能力、付费调用、生产项目的证明。
