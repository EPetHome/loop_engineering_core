# 05 全过程与可观测

## 1. 从讨论到验收的完整过程

```text
① 讨论        拍板人：头脑风暴，把需求说清
      │
      ▼
② 方案        拍板人：拆成单元；定哪些并行、哪些串行
      │
      ▼
③ 规则        拍板人：每个单元写规则；多单元再写任务安排；启动前查一遍
      │
      ▼
④ 准备        陪用户讨论的模型：写提示词、备好启动指令、在基线留指针
      │
      ▼
⑤ 启动        用户：在控制台输入启动指令，只输一次
      │
══════╪══════════════ 以下在循环之内，拍板人不参与 ══════════════
      ▼
⑥ 运行        编排程序按安排启动单元；每个单元里开发 ⇄ 评审
      │
      ▼
⑦ 停止        每个单元停止即交结果；全部停下后出总结果；通知用户
      │
══════╪══════════════ 以上在循环之内 ══════════════════════════
      ▼
⑧ 验收        拍板人：打开会话，读结果，分析，决定认不认
      │
      ▼
⑨ 更新基线    拍板人：把认可的结果写进项目基线；没达标的改规则后回到 ③
```

| 阶段 | 谁 | 产出 |
|---|---|---|
| ① 讨论 | 用户和模型 | 说清楚的需求 |
| ② 方案 | 用户和模型 | 单元清单和先后关系 |
| ③ 规则 | 用户和模型 | 每个单元的规则；任务安排 |
| ④ 准备 | 模型起草，用户过目 | 提示词文件；启动指令（给在对话里，不写进文件）；基线里的指针 |
| ⑤ 启动 | 用户 | — |
| ⑥ 运行 | 循环 | 工作区里的交付、评审、状态、日志 |
| ⑦ 停止 | 循环 | 每个单元的结果；总结果 |
| ⑧ 验收 | 用户和模型 | 认可或不认可；下一步 |
| ⑨ 更新基线 | 用户和模型 | 基线 |

## 2. 运行期间：拍板人不在

用户明确说过：不希望陪他讨论的模型守着运行，因为耗费 token。所以：

- 模型不轮询、不守望、不被后台事件唤醒。
- 用户可以去做别的事。
- 循环自己留痕、自己通知。

## 3. 可观测：怎么看到进度和结果

全部由程序完成，不需要模型。

| 想知道 | 怎么看 | 花 token 吗 |
|---|---|---|
| 现在跑到哪了 | 一条状态命令，每个单元输出一行：阶段、第几次、已跑多久、最近动静 | 不花 |
| 停了没有 | 停止时桌面弹通知：哪个单元、停止类型、一句话结论 | 不花 |
| 结果是什么 | 工作区里固定位置的结果文件 | 不花 |
| 接下来怎么办 | 打开会话，和模型一起读结果、分析 | 只在这时花 |

调度程序要保证的三件事：

1. **状态随时可查。** 状态文件持续更新，包含最近一次动静的时间。
2. **停止即通知。** 三种停止都通知。
3. **没动静也算停。** 超过规则里设定的时间没有任何动静，按「推不动」处理并通知。

## 4. 为什么不要观察员（Sidecar）

讨论过要不要加一个便宜模型做的观察员，专门盯着循环、把结果讲成人话。结论：**先不做。**

| 观察的两件事 | 谁能做 |
|---|---|
| 发现停了、卡住了、规则被改了 | 调度程序，不需要模型 |
| 把结果讲成人话 | 评审方按规定的结果格式写；或者拍板人开会话时由模型来读 |

加观察员的代价：多一份提示词要维护，多一个会出错的环节（实战里出现过便宜模型把原因说反的情况）。

什么时候再考虑：用户想完全不开会话、自己直接读结果，而评审方写出来的东西读着费劲。

## 5. 并发和串行

用户的要求：有些任务要并发执行，可能复杂到部分并发、部分串行。

循环本身不用改。并发和串行是单元之上的一层：给每个单元加一个启动条件，即「等哪几个单元达标后才能启动」。编排程序按这张安排自动启动，用户仍然只启动一次。

要并发，必须守住三条：

| 约束 | 为什么 |
|---|---|
| 并行的单元，各自能改的文件不能有交集 | 否则互相覆盖。有交集的只能串行 |
| 一个单元冻结的东西，不能落在另一个并行单元的可改范围里 | 否则对方一改，这边的结果全部作废 |
| 共用的东西要分开 | 运行编号、端口、目录这类。实战里的运行编号是「取现有最大号加一」，两个单元同时跑就会撞号 |

某个单元没达标时：依赖它的单元不启动；不相干的照常跑；总结果里写明哪些没跑、为什么。

不适合并发的别硬拆：两个任务要改同一批文件，或者一个的标准依赖另一个的结论，就该串行，或者合成一个单元。

## 6. 验收时看什么

| 看 | 说明 |
|---|---|
| 总表 | 每个单元的停止类型 |
| 每个单元的结果 | 标准逐条的结论和证据位置 |
| 规则缺口栏 | 成员记下的「规则没说清」的地方。这是下次改规则的输入 |
| 证据 | 结果只是结论；拿不准时回到工作区看原始记录 |

验收之后的三种走向：

| 情况 | 做什么 |
|---|---|
| 认可 | 更新基线 |
| 未达标，规则没问题 | 分析卡点；决定是加次数重启、拆小单元，还是换做法 |
| 未达标，规则有缺口 | 改规则（版本加一），重新启动 |
