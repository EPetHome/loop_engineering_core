# Loop Engineering v1：架构审查与补充建议

> 日期：2026-10-01  
> 性质：对本次上传的九份文档的审查；以下补充均为建议，尚不构成用户已确认的决策。  
> 范围：文档与协议设计审查，不是代码审计。没有取得或运行 Promax 的调度脚本，不能据此宣称已有程序已经实现了这些能力。  
> 原稿不作修改。沿用原稿中的“拍板人、单元、规则、工作区、达标／未达标／推不动、基线”等术语。

## 一、总体判断

这套设计值得继续落地，不需要推倒重来。它已经明确了四个重要关系：讨论与执行分开；开发与评审分开；循环达标与用户验收分开；单元闭环与多单元编排分开。

现在最需要补的，不是更多角色、更多阶段或更长提示词，而是**运行契约**：状态如何变更、证据对应哪个成果、哪些动作得到授权、出故障如何收尾、重启如何避免重复执行、各单元的成果如何组成同一份可验收交付。

原稿 README 将状态写成“设计已定，引擎尚未实现”；08 又明确规则和结果的程序格式、调度器故障处理等尚未确定。因此更准确的状态是：**愿景与核心原则已确认；运行协议待补齐；通用引擎未实现。** 这不是否定原有决策，而是避免实现者把尚未确定的接口当成已经确定。

建议将愿景解释为：

> 拍板人在启动前确认目标、边界、验收和授权；循环在冻结的约束及资源上限内，自主选择实现方法，开发、验证、评审，并在正常运行或故障恢复条件具备时，留下可追溯的结果。是否认可及更新基线，仍由拍板人在循环之外决定。

这里的“全自动”是**受约束的自动执行**，不是保证所有任务都能成功，也不是保证永远不遇到未知情况。原稿已经允许未达标和推不动，这是正确的。

### 最重要的三个缺口

1. 目前有“每条标准的结论和证据位置”，但缺少“结论究竟属于哪个不可变的候选成果”。
2. 目前有“成员交不出时调度程序代写”，但调度程序本身死亡、结果写一半、停止后旧进程继续写等情况还没有闭合。
3. 目前有“所有单元达标就是整体完成”，但没有要求证明组合后的同一个成果也达标。

以上判断是基于原稿结构提出的风险分析，不是对未提供的代码作出缺陷认定。

## 二、应当保持、不应被补充工作破坏的部分

**保持循环内外分离。** 不增加需要拍板人中途回答的正常流程。紧急取消权可以保留，但不应让中途拍板成为系统才能运行的依赖。

**保持开发与评审分离。** 不必为了独立性继续堆叠经理、观察员、仲裁员等模型。优先让现有评审得到正确对象、原始证据和清晰判断权限。

**保持三个对外终点。** 达标、未达标、推不动已经足够表达用户关心的结果。程序内部需要更细的运行状态，但不必把内部状态全部变成用户的新术语。

**保持基线在循环之外。** 原稿把基线定义为项目长期状态文档，本报告不擅自把它改称 Git 主分支。下文另行引入“代码起点”和“候选成果”，解决产品文件的隔离问题。

**保持简单任务也能简单使用。** 必要的运行字段大部分应该由程序生成，通用约束应该继承，而不是让用户为每个小问题重新填写大量表格。

## 三、规则要冻结，但实现决策不能全部冻结

### 3.1 “不能改标准”不等于“不能作判断”

原稿要求成员不改规则、缺口从严处理。需要补充区分四类事情：

| 类别 | 示例 | 建议权限 |
|---|---|---|
| 已确认的业务与验收约束 | 哪些用户有权限、失败后是否自动重试、怎样算完成 | 成员不能更改 |
| 明确禁止的动作 | 写正式基线、删除用户数据、访问生产环境 | 不执行；记录需要的能力或边界 |
| 已授权的实现选择 | 函数拆分、内部数据结构、允许目录内的代码组织 | 成员自主决定 |
| 尚未授权且影响结果的未知事项 | 是否可以改接口、换测试集、扩大范围 | 不自行决定；记录缺口，处理不受影响的部分 |

否则，变量名、函数位置都可以被解释成“规则没说清”，自动化就会变成过度保守的停滞。

建议条款：

> 成员可以在已授权的范围内自主选择实现方式，但不得改变业务目标、验收口径、允许的副作用、资源上限和正式交付范围。

### 3.2 “最严理解”应改成能执行的处理原则

相互冲突的要求未必存在唯一的“更严”：例如“保留全部日志”与“不保存敏感信息”，不能只靠一句“按最严处理”解决。

建议用明确顺序替代笼统口号：先服从已经声明的禁止事项；不擅自扩大权限；证据不足不记通过；记录受影响的标准和不同解释；继续已确认不受影响的工作。已确认没有可执行的达标路径，或达到事先设定的无进展上限时，按未达标结束，不必把剩余预算耗尽。

当两种解释都不违反约束、且已被授权属于实现选择时，成员可以选一种并记录理由。这样的记录不等于改规则。

### 3.3 启动预检不是可选业务阶段

02 把“启动前查一遍规则”放在可选做法，03 与 06 又要求启动前检查。这需要统一。

建议把最低限度预检作为引擎的固定入口：格式合法、标准编号唯一、每条有判断方式、必需输入存在、上限明确、工具与权限可用、输出存储可写、并行依赖不存在环。如果检查不通过，不进入开发，保存启动失败的说明。

复杂任务的额外模型审规则仍可选。预检不是保证规则正确，只是阻止已知无法执行的规则进入运行。

## 四、规则只能有一个权威来源；模型必须看到实际内容

### 4.1 人读一份、程序读一份，不能手工维护两个真相

原稿同时要求“标准唯一出处”和“人读、程序读各一份”。这两者可以兼容，但必须规定生成方向。

建议选择一种：

- 结构化规则作为权威来源，其中保留完整自然语言标准，程序生成 Markdown 阅读版。
- 带结构化元数据的 Markdown 作为权威来源，程序确定性地提取可执行配置。

不建议让另一个模型在运行期间把 Markdown 临时翻译为 JSON 再执行，因为翻译结果可能改变计数、边界或验收语义。

通用规则、项目约束和任务规则可以在启动前合成，但合成后的有效规则必须冻结、留版本、列出来源；项目和任务不能暗中放宽已经锁定的底线。

### 4.2 只引用编号，不能代替提供规则

“提示词只引用 S1—S3”有利于避免重复维护，却不能保证新会话知道 S1 的内容。

建议：提示词模板引用编号；运行时由程序从唯一权威来源解析实际条款，将本角色所需内容注入上下文，并带规则版本与指纹。引用不存在、读取失败或版本不一致，就不启动该成员。

**不重复维护，不等于不向模型展示。** 这一点也适用于上下文压缩：压缩后仍须保留当前目标、禁止事项、有效标准、候选版本和未解决问题，而不只是保留历史对话的摘要。

### 4.3 程序校验要检查语义上的完整性

结构格式校验可以用 JSON Schema 等现有工具实现；JSON Schema 官方文档明确区分字段的定义与必填要求，也能限制额外字段。[外部依据 E1]

但格式合法还不等于交接有效。引擎还应核对：标准 ID 的集合相等且不重复、状态值合法、证据引用能够解析、当前成果身份一致、结论与硬检查结果不矛盾。不是看到一段合法 JSON 就算交付。

## 五、“达标”必须绑定一份具体成果

### 5.1 当前缺少的不是报告，而是报告与实物的绑定

考虑一个假设：开发交付版本 A，评审通过；开发方遗留的后台进程随后把文件改成版本 B；用户打开“最新结果”，看到的仍是 A 的通过结论，但拿到的代码已经是 B。

原稿的“有结论、有路径”不足以排除这个情况。

建议每次有效交付和评审至少关联：

| 身份或证据 | 作用 |
|---|---|
| 任务、运行、单元、尝试编号 | 防止把其他执行的结果拿来交接 |
| 有效规则指纹 | 说明按哪一版约束判断 |
| 输入快照与代码起点 | 说明从什么状态出发 |
| 候选成果指纹 | 说明检查的是哪份代码或文档 |
| 验证环境、配置与测试集标识 | 防止不同环境和标准下的证据混用 |
| 原始证据引用 | 回到实际运行输出、文件、界面或数据状态 |

这些通常应由程序自动采集，不需要用户手填。小任务可以很轻量，不必一次建设复杂的数据平台。

### 5.2 单条结果不能只有“过／不过”

建议至少保留 PASS、FAIL、UNKNOWN；确实尚未执行的标准可用 NOT_RUN。

FAIL 表示已有证据证明不满足；UNKNOWN 表示证据不够；NOT_RUN 表示没执行。这三者都不能计为必需标准通过，但它们的后续修复方向不同。环境没启动，不能随意等同于产品逻辑错误。

不适用只能依据启动前规定的适用性条件产生，不能由成员为了凑齐通过而自行宣布。

### 5.3 最终通过应是合取，不是听取一句总结

建议把达标定义为：必需标准逐条有效通过；必需硬门禁全部通过；评审对象与候选成果一致；输入和规则版本匹配；没有未处理的边界违规；结果能够持久保存。

确定性硬检查失败，模型的“总体通过”不能覆盖它。评审判断中的 UNKNOWN 也不能被程序自动转换为 PASS。

### 5.4 评审方写判断，调度程序发布结果

04 目前写“结果由调度程序和评审方写”，最终文件可能存在两个写入者。

建议明确：开发方写交付；评审方写评审记录；调度程序是最终结果、运行状态和最新结果指针的唯一发布者。状态展示是已持久化事实的投影，不允许成员直接修改计数或宣告终态。

### 5.5 防止通过改检查来通过检查

规则冻结不代表测试、测试入口、评分脚本和运行配置也冻结。若成员能删测试、改期望值、跳过场景，再拿退出码 0 交付，规则文件完全没变也可能制造假通过。

建议区分受保护的验收资产与开发自测资产。成员可以按授权增加测试；不能未经允许删减必需用例、修改权威判断器或更换测试集。记录实际执行的用例清单和数量，不能只记录命令成功退出。

## 六、停止必须有收尾协议，而不只是一个分支

### 6.1 维持三个对外结果，增加内部阶段

建议内部状态至少区分：待启动、预检、开发、评审、收尾、终态。自测和交接可以继续作为开发或评审阶段中的子步骤，不必增加新的业务角色。

收尾的意义在于：已经决定停，不代表结果已经安全发布。

建议顺序：

```text
判定需要停止
  → 不再安排新工作
  → 取消或隔离本次运行拥有的活动，拒绝过期写入
  → 固定待交付成果及证据
  → 由程序提交结果及终态事实
  → 更新最新结果入口
  → 发送通知
```

结果与终态可以放在同一份原子提交的清单中，或用事务性存储；状态页从该事实生成。不能先显示“达标”，再慢慢写报告。

通知失败不应撤销已经完成的业务结果，而应单独记录、有限重试。

### 6.2 不能把“有输出”等同于“有进展”

原稿使用“最近一次动静”判断卡住。建议拆成三个观测值：进程或受管作业仍存活；最近输出时间；最近一个可验证步骤完成的时间。

不断打印“正在处理”并不证明任务前进。反过来，一个正常运行但暂时不输出的测试，也不应该仅因日志静默就被杀掉。

程序不需要判断深层语义。它可以观察测试命令完成、合法交付被接收、评审产生了有效结论、受管作业返回结果等事件。无法可靠观测进展的阶段，用已经批准的阶段期限作为兜底。

Temporal 官方资料把执行超时、整体重试时间和心跳机制分开处理，可以作为设计参照，不意味着必须采用该框架。[外部依据 E2]

### 6.3 调度器死亡需要程序级兜底

原稿 08 已经指出这一点，但尚未确定处理方式。要承诺无人值守，至少要有一种经过测试的程序级恢复机制：系统进程管理器重启调度器、独立的轻量看门程序，或重启后自动扫描未收尾运行。

这不是 Sidecar 模型，不消耗模型 token，也不让拍板人中途值守。它的职责仅是检测、恢复状态与补写结果。

应诚实限定保证范围：整台机器断电、磁盘无法写入或持久记录损坏时，本机程序不能保证当场写出最终报告。可承诺的是在宿主与存储恢复且记录可用后，识别遗留运行并进行核对与收尾；不能把不知道的故障时刻或未记录进度补写成事实。

### 6.4 停止本地进程不一定停止外部任务

对于远端模型请求、测试服务或其他外部作业，应记录作业 ID，按适配器能力取消或查询。取消未得到确认时，结果中必须保留“外部状态待核对”，不能宣称副作用或计费已经停止。

第一版建议限定在本地测试环境和可管理的工具范围内，不要把不可逆生产动作纳入默认授权。

## 七、续跑要先定义身份和检查点

原稿同时写“停止都是终点”和“修好后从断点续跑”，两者需要一条明确接口。

建议区分：任务是长期目标；运行是某一版规则和输入下的一次执行；尝试是其中一个成员的一次启动。

终态结果不可覆盖。已经停止后重新启动，生成新运行，引用父运行与合法检查点。同一尚未收尾运行的基础设施恢复，可以保留运行编号，但必须产生新的尝试或执行代次，防止旧成员回来继续交付。

规则、输入、判断器或候选成果改变时，旧通过不能默认继承。复用证据必须有明确的有效性条件；第一版宁愿少复用，也不要误用旧证据。

### 重试不等于返修

| 类型 | 例子 | 建议计数 |
|---|---|---|
| 业务返修 | 评审返修后进入新一次开发 | 单独的返修计数 |
| 基础设施重试 | 网络暂时失败，重试同一次调用 | 基础设施计数 |
| 协议修复 | 交付缺字段，补交合法结构 | 协议修复计数 |
| 评价重复试验 | 相同候选成果再跑一次场景 | 试验计数 |

这些可以有不同上限，但全部计入运行总时间和资源预算。只靠把失败归为“不算返修”，不能绕过总预算。

恢复点应落在已提交的成果、证据或完成步骤上，而不是“聊天似乎进行到了这里”。对于创建、发送、写入等带副作用的动作，超时后先确认结果；没有去重键、可查询状态或安全回滚能力，不要盲目重做。

Temporal 官方说明：活动已完成但没有成功报告时，可能被再次执行，因此有副作用的操作需要考虑幂等与重复调用。这里借用这个故障模型，不要求安装 Temporal。[外部依据 E3]

## 八、不改基线，还不足以保护项目代码

原稿将工作区定义为交接文档的地方，并说明产品文件不在工作区内。需要另外回答：循环到底在用户当前目录改代码，还是在独立候选副本里改？

建议保留原有“工作区”术语，并增加“代码工作副本”：

```text
项目长期基线文档：循环外；仅拍板人更新
代码起点：本次运行认可的初始版本或显式快照
单元工作区：规则、交接、状态、结果、证据
代码工作副本：该单元允许修改的候选代码
最终候选成果：与评审证据绑定，等待拍板人验收
```

开始前应处理用户尚未提交的改动：明确纳入快照或拒绝以不确定状态启动，而不是自动清理。失败时保留本次工作副本、最后有效候选成果与未评审改动；不要用仓库级硬重置去“恢复干净”。

Git worktree 是可选实现：官方文档支持在同一仓库下建立多个工作树、分别检出分支。但它们仍共享部分仓库信息，不能把 worktree 说成权限沙箱。[外部依据 E4]

所谓“验收后更新基线”仍沿用原稿。代码是否合并或发布、由谁执行，是需要在循环之外另外明确的交付动作，不应该被“已达标”暗中触发。

## 九、多单元需要成果合同与最终集成验证

### 9.1 文件写范围不相交，不等于没有依赖

假设 A 只改前端、B 只改后端，文件完全不同。但 A 发送字段 `inviteCode`，B 接受字段 `token`，各自用模拟接口测试都可能通过，组合后却不可用。

原稿的并发条件应补成：写入不冲突；需要读取的输入不被别人改变；共享数据库、端口、缓存与测试账号受控；上下游接口版本一致。

第一版不必自动分析整个仓库的读写依赖。由拍板人在任务安排里声明关键依赖，依赖不足的单元宁可串行。

### 9.2 串行也可能使先前结果失效

A 先通过，B 随后改变 A 依赖的共享接口，A 之前的证据可能不再适用于最终组合。因此问题不只是并发调度，还包括证据的版本有效性。

### 9.3 下游要消费上游具体成果，而不是“通过”标签

每条依赖应指出：上游候选成果 ID、产物位置、接口或数据约定、有效验证条件。下游读取不可变产物，不读取一个会不断移动的“最新目录”。

### 9.4 整体完成必须落到同一组合成果

建议对于需要共同运行的软件交付，预先安排最终集成单元：

```text
A：前端开发与评审 ─┐
                   ├→ C：组合候选成果、端到端验证、独立评审 → 总结果
B：后端开发与评审 ─┘
```

C 仍然使用原来的单元骨架，不增加新角色。

只有彼此真正独立、无需组合验证的交付，才可以直接汇总各单元结果。原稿“所有单元达标就是整体完成”应加上这个适用条件。

上游未达标导致下游未启动时，下游应有“未执行：依赖未满足”的调度记录，而不是凭空制造一个开发故障。它不是第四种执行终点，但总结果必须明确体现整体没有完成。

## 十、独立评审与验收标准还要补两道约束

### 10.1 不同成员不保证没有共同盲区

07 已记录：开发方与评审方都围绕同一份有缺口的规格和离线用例工作，较晚才发现真实问题。因此不能把“换一个评审模型”当成完整的独立性保证。

建议开发自述只作为导航。评审先按冻结规则检查实际候选成果和原始证据，再参考自述。需要验证真实运行的任务，应尽早执行一条代表性的真实路径，不要把所有真实反馈推迟到最后。

必需门禁之外，评审可以指出规格缺口和范围外建议，但不能把自己的偏好变成本轮新标准。阻塞修复项必须引用已有标准或已批准的禁止事项，并给出可核对证据。

Anthropic 的评估资料区分了实际环境中的结果与代理的自述，也指出模型评分需要与人工判断校准，并允许证据不足时返回 Unknown。[外部依据 E5]

### 10.2 原稿的导出进度示例还没有完整覆盖目标

03 的示意目标是“超过 3 秒显示进度；失败时显示原因”，但列出的标准主要是原有测试通过、新测试存在、改动范围合法。它还可以被补成直接验证行为的标准，而不只是验证做了测试。

例如：在约定的慢导出场景中，实际界面按要求出现进度状态；失败后出现指定可理解的原因；完成或失败后进度状态不残留；既有回归用例仍通过；修改范围没有扩大。

“进度”是等待提示还是百分比、3 秒边界和允许误差、失败原因的展示口径，都应在启动前定清。此处是对示意的补充，不是断言原稿已经承诺了这些新增要求。

### 10.3 修复记录应稳定，不要每轮换一套问题名称

建议阻塞问题带稳定 ID、关联标准、首次发现证据、当前候选版本、修复声明、复查结论。开发方说修好是“已声明修复”，评审验证后才是“已验证修复”。

后续改动使旧证据失效，应重开相应问题或重新验证。无关的风格建议不阻塞本轮达标。

## 十一、累计达标不能变成可靠性证明

原稿将“累计达标加护栏”列为按任务选择的办法，07 还明确了当时 Promax 的冻结代码与重跑规则。这里不否定那个已确认口径，而是限制它的解释范围。

“每个场景至少成功过一次”证明的是曾经具备该能力；“重复运行时大多数都成功”关心的是稳定性。这两件事不等价。

例如某场景失败九次、第十次成功，不能只留下那一次成功就宣称稳定。所有尝试和失败原因必须保留，试验上限和统计口径启动前冻结，不能跑完后挑口径。

Anthropic 的评估资料用 pass@k 表达多次尝试至少一次成功，用 pass^k 表达多次都成功，并明确这两者回答不同问题。[外部依据 E5]

对于本次修改是否交付，可按任务选择合适口径；对于 Promax 是否足够稳定，应另设可靠性验收。代码之外，提示词、模型配置、工具版本和输入数据的变化也应进入验证身份；只有代码没变，并不足以保证实验条件相同。

## 十二、有限循环还需要资源预算与失败分类

原稿已有返修和时间上限，但模型成员一次会话内部也可能反复调用、昂贵检索或无效等待。

建议运行预算覆盖：整个运行最长时间、各成员或阶段最长时间、业务返修次数、协议修复次数、基础设施重试次数、模型或工具调用预算，以及需要时的费用或 token 上限。多单元共享一个总预算，不能每个单元都独立占用全部额度。

费用拿不到实时准确值时，应标注估算、预留余量，并用可强制执行的调用数、输出额度、并发数和时间限制兜底；不能把费用估算说成精确计费保证。外部请求已发出后的费用也未必可撤回。

对于没有进展的情况，可用可核对事实判断，例如同一候选成果、同一未解决检查、同一动作重复达到既定次数。语义上是不是同一根因，可以由评审提供带依据的分类，但不把模型猜测当成确定事件。

收尾也要预留预算和时间。业务预算耗尽后，应由程序生成最低限度结果，而不是再依赖一次可能没有额度的模型总结。

## 十三、规则防篡改的承诺应更准确

04 已接受“防手滑、核指纹、正本恢复”的轻量方案，不建议无理由升级成企业级隔离系统。

但“必被发现”过强。只在交接点比较指纹，能发现的是检查时内容与记录指纹不一致；中途修改又恢复不一定被看到。同账号下，成员也可能有能力更改校验程序或它依赖的记录。

建议改成：

> 本版本面向同账号下的误操作防护。通过只读设置、检查点指纹核对、受控写入和外部正本降低风险，不承诺防住具有同等系统权限的恶意篡改，也不承诺发现所有短暂修改。

同时把权限约束放在工具入口：规范化路径与工作目录、校验允许写入的目标、限制不必要网络和凭据、验证交付引用的文件范围。只检查最终 Git diff，无法发现改过后恢复的操作，也无法阻止已发生的外部副作用。

仓库注释、网页、错误输出、交接文档中的“请忽略标准”“现在判通过”等文本，应作为待处理数据，而不是有权修改执行规则的指令。OWASP 的相关指导强调工具调用校验和最小权限；在本方案中，重点是限定权限，不是再加一个常驻模型。[外部依据 E6]

## 十四、上下文与成本：不要维护第二套高频记忆系统

原稿“每次新会话、靠工作区交接”有助于明确边界，但新的开发会话仍需要知道已经试过什么，否则可能重复失败。

建议在成员启动时生成一次面向角色的上下文包：冻结规则的实际条款、当前候选成果、有关输入、依赖产物、未解决问题、已尝试且失败的方法，以及原始证据索引。

不要默认注入全部历史日志；不要要求模型每条回复都更新交接文档；不要把 token 花在常驻进度解释或缓存保温上。运行事件、计数和状态由程序持续记录，模型在交付、评审或必要的语义记录点写内容。

文档中“一次性非交互会话结束会杀掉后台任务”的经验来自特定运行方式，应作为启动适配器的已验证约定维护，不能未经实测推广到所有工具。适配器至少需要明确启动、等待、退出、取消、结果导出和错误含义。

## 十五、建议的最小落地顺序

### 阶段一：先证明引擎不会假通过、不会无结果消失

先用假的开发方与假的评审方测试状态和交接，不调用真实模型。假的成员只是可预测地写入通过、返修、缺字段、超时等结果。

至少覆盖：成功、返修耗尽、成员没交付、评审和证据矛盾、版本不匹配、规则被改、持续输出但无有效步骤、调度器被杀、收尾中断、重复启动、通知失败、旧进程迟到交付。

这一步验证的是控制逻辑，不是用玩具业务替代真实业务验收。

### 阶段二：一个真实、低风险、可独立验收的小任务

使用真实代码、真实测试路径、独立工作副本及实际模型。验证正常交付，也有意验证一次可恢复故障。让用户只启动一次，之后读到可用结果。

一个单元应是“能够独立形成验证结果的最小合理交付”，不是机械地越小越好。拆分带来的交接、重复上下文和集成成本也需要考虑。

### 阶段三：两个并行单元加一个最终集成单元

先固定依赖和接口，再运行。除了全部通过，也验证一个上游失败后，下游不启动、其他无关任务按规则继续、总结果正确汇总的情况。

### 暂不增加

暂不建设观察员模型、复杂控制台、自动生成并随时修改任务图、跨项目自动记忆库、大规模模型投票、无限重试、自动缓存保温或运行中自我修改引擎。

通用底座负责身份、权限、状态、交接、证据、上限和收尾；业务差异留在任务规则和验证方式里。这是小骨架可复用的前提。

## 十七、最后的判断

你的方向不是缺一个更聪明的“经理 Agent”，而是缺一些让成员的工作能被可靠接收、判定、保存和恢复的协议。

更合适的下一步不是让模型立即按照现有九份文档自由发挥、写完整引擎，而是先把**规则身份、成果身份、判定身份和运行身份对齐**，补齐收尾与恢复，再用一个真实小任务验证。

最重要的目标可以压缩为一句话：

> 无论成功还是失败，循环都能在已声明的运行条件下，把对的证据对应到对的成果，按对的标准结束，并把尚未解决的事情如实交给拍板人。
