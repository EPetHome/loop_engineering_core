# 项目模板：接入 loop 的项目长什么样

本目录是一个「接入 loop 的项目」的样板，开发 loop 时用来对照上下游：代码放在哪、开发分支在哪、文档放在哪、规则怎么写、每批的材料放在哪、loop 从哪一步接手、做完交给谁。

样板取自 Promate（`/Users/Admin/Desktop/Promate`），它是 loop 的第一个真实使用方，2026-10-12 核对。

- `项目根/` 下按真实项目的位置摆好了每类文件的骨架，`<尖括号>` 里是要替换的内容。
- 每个骨架文件开头有一段「模板说明」：这个文件做什么、谁写谁读、Promate 里对应哪个文件。
- 会变的写法规则（提示词怎么写、验收标准怎么写、`.autoreview.json` 有哪些字段）不在这里重复，只指向 [README-验收标准.md](../README-验收标准.md) 和 [README.md](../README.md)。

```

└── 项目根/                             一个接入 loop 的项目（本身不是 git 仓库）
    ├── AGENTS.md                      协调方规则（只放稳定内容）
    ├── CLAUDE.md                      只有一行 @AGENTS.md
    ├── docs/
    │   ├── baseline/                  基线四页：项目现在在哪
    │   │   ├── 当前基线与入口.md
    │   │   ├── 主线图.md
    │   │   ├── 当前能力.md
    │   │   └── 尚未完成与后续顺序.md
    │   ├── requirements/              需求书；做完的移进 xxx/
    │   │   └── 需求-示例.md
    │   ├── prompt/                    方案、提示词、启动说明；执行完的移进 xx/
    │   │   ├── 方案-示例.md
    │   │   ├── 提示词-示例.md
    │   │   └── 启动说明.md

    │       └── 示例批次-20261012/

~/.pi-autoreview/git-baselines/<分支>.git    外部基线（开工点）
```

## 和 Promate 对照

| 模板 | 作用 | Promate 实际位置 |

| `AGENTS.md`、`CLAUDE.md` | 协调方规则 | 同名 |
| `docs/baseline/` | 基线四页 | `重新出发/00-基线/`（07、06、02、03） |
| `docs/requirements/` | 需求书 | `新需求/<线>/`，做完的在 `新需求/xxx/` |
| `docs/prompt/` | 方案、提示词、启动说明 | `coding/prompt/`（启动说明叫 `pi启动方式.md`），执行完的在 `coding/prompt/xx/` |
| `docs/batches/<批次>/` | 批次目录 | `coding/docs/<批次>-<日期>/` |
| `线上/` | 线上代码 | `Promate产品中台/`（后端）和 `promate-frontend/`（前端），各有团队 .git |
| `dev分支/` | 开发分支 | `dev分支/`（根目录对应后端，`promate-frontend/` 对应前端）；用户授权并行时还有 `dev分支2/` |
| 模板没放 | 产品依据、问题清单 | `文档/`、`iusses/` |

## 谁在干活

- 用户：拍板，做业务验收。唯一亲手做的操作是在终端执行启动脚本，不打开文件夹，也不跑别的命令。
- 协调方：Claude Code，工作目录在项目根。负责写需求、方案、提示词；准备开发分支、批次目录和验收环境；Pi 跑完后核对结果；合入线上；维护基线，归档。本机的 Claude Code 装了 loop 插件。
- 开发方：Pi，工作目录在开发分支，加载权限扩展和 `autoreview.ts`。权限扩展的全局配置开了 yoloMode，所以边界只靠提示词约束。
- 评审方、验收方：由 loop 启动，评审方只读。

## 一批从需求到上线

```
① 头脑风暴（用户和协调方在聊天里）
② 需求书 docs/requirements/          用户在聊天里拍板，当轮写回需求书
③ 方案 docs/prompt/方案-*.md          要点先聊，拍板后才写
④ 提示词 docs/prompt/提示词-*.md       四节；验收标准先给用户看
⑤ 开工准备（协调方，目前全手工）
   把线上同步到 dev分支 → 在外部基线提交「开工基线」
   → 写批次工具、启动脚本、.autoreview.json、验收环境 → 外部基线再单独提交一笔
⑥ 用户在终端执行 bash <批次>-启动Pi.sh
─────────────────── loop 管的部分 ───────────────────
⑦ Pi 开发 → 门禁 →（自动验收）→ 评审 → 返修（最多 4 次）→ 完成 / 暂停
   产出：~/.pi-autoreview/<分支>/<会话>.md；Pi 另外写 docs/batches/<批次>/结果.md
──────────────────────────────────────────────────────
⑧ 协调方核对：读 loop 总结、结果.md 和原始日志
⑨ 合入线上 = 上线：三方对比（开工基线 / 线上现在 / dev分支 改后），只搬本批改的文件
   避开分支专属文件；数据库先备份；插件还要更新发布清单
⑩ 用户业务验收（[人工] 条目和 loop 判「需人工」的条目在这一步验）→ 在基线「待你核销」里核销
⑪ 归档：提示词标题下写「✅ 已执行」，移进 xx/；主线图留一行
```

loop 现在只接触四样东西：提示词（作为第一条消息 @ 进来，loop 从里面取验收标准）、`dev分支/.autoreview.json`、外部基线（通过 GIT_DIR）、`~/.pi-autoreview/`。前面的 ①–⑤ 和后面的 ⑧–⑪，loop 都看不到。

## 规则分四层

原则：稳定的规则写进常驻文件，会变的只写一个指向。常驻文件每次都会加载，一改就让缓存失效。

1. 用户全局 `~/.claude/CLAUDE.md`：管输出格式。规定「出 pi 提示词」前，先读 loop 的两份 README 和项目的启动说明。
2. 项目 `AGENTS.md`：分工、流程、分支与合入、评审边界、上线与数据保护、沟通方式。
3. 外部文档：写法规则看 loop 的 README；项目自己的选择（模型、工具组合、同步命令）看 `docs/prompt/启动说明.md`。Promate 故意没有把【块 1】贴进 AGENTS.md，而是让协调方每次去读 loop 的 README。
4. 提示词：每批一份。loop 会自动往 Pi 的系统提示里追加开发约定。

## 缺口：现在靠人手补、希望 loop 能感知

1. **Pi 读到的是协调方的规则。** Pi 在 dev分支 启动，会往上层目录找到项目根的 AGENTS.md，整份放进自己的系统提示（Promate 10-12 P0 会话 jsonl 第 7 行，已核实）。模板的 AGENTS.md 先在开头加了一句「开发方以提示词为准」作为临时做法。开发方规则放在哪，等 loop 定。
2. **门禁脚本本身出错，loop 当成开发方的错打回。** 门禁脚本是协调方写的，开发方不能改。Promate P0 批第 1 轮门禁退出码为 1，Pi 记录的原因是脚本尾行在 Bash 3.2 下被 `set -u` 判错（未复核）。建议开工时先在开工基线上空跑一次门禁，并且让 loop 能区分「被测代码失败」和「门禁工具出错」。
3. **工作目录不是 git 仓库。** dev分支 故意不建 .git，靠启动脚本设 GIT_DIR。这带来两个问题：流水线的开跑前检查要求「有提交的 git 仓库」，没法直接用；Claude Code 插件的 Hook 拿不到这两个变量，协调方的 shell 一停在 dev分支，Hook 就对协调会话跑评审、取证失败，弹「暂停（自动评审内部错误）」。希望 `.autoreview.json` 能写外部基线的位置，或者 Hook 能分清开发会话和协调会话。
4. **开工准备全靠手工。** 同步线上（排除清单是安全边界）、建外部基线、提交开工点、单独提交验收环境、写启动脚本，每批都手工做。希望有标准的「开分支 / 开工」动作，至少检查两件事：分支专属文件没被线上覆盖；开工基线和线上一致。
5. **合入在 loop 之外。** loop 完成后，协调方要做三方对比、只搬本批文件、避开分支专属文件、备份数据库。loop 总结里有改动文件列表，但没有机器可读的结束状态（状态、改动文件、需人工条目、未解决的必修）。
6. **结果分在两处。** loop 总结在 `~/.pi-autoreview/`，`结果.md` 在批次目录，loop 不知道 `结果.md` 的存在。可以让批次目录成为 loop 认识的概念，或者在配置里指定结果文件的路径。
7. **中途停下被当成完成。** Pi 用 bg_run 等后台任务或断网停在半路时，没写交付标记但工作区有改动，loop 就开始评审，可能判「完成」，之后只评增量（Promate 10-09 出现过两次）。
8. **会话被关后不好恢复。** 要用户带 `--session <id>` 重新启动，id 得去会话目录里查。希望 loop 暂停时直接给出完整的恢复命令。
9. **并行分支共享环境。** 第二个分支复制了同一套 `deploy/acceptance/`，端口和测试库都会撞；后端的 target 目录、运行中的服务也只有一套。单个会话目前不做端口冲突检查。
10. **提示该给谁看。** loop 的暂停提示常写「把【块 N】复制到…」「在项目目录执行…」，而用户只做决策、不跑命令，这些实际都由协调方去做。希望提示分成「要用户做的决定」和「要协调方做的操作」。
11. **需人工条目的去向。** loop 列出的需人工条目，现在由协调方手工抄进基线的「待你核销」。有了第 5 条说的结构化结束状态，这一步就能自动。

## Promate 和模板不一致的地方（Promate 那边要改）

- Promate 的 `deploy/acceptance/GUIDE*.md` 还写着让验收方自己运行 reset-data.sh 重做。loop 现在的规则是数据由程序重置，验收方不许自己清。模板的 GUIDE.md 已经按 loop 的规则写。
- Promate 没有固定做「开工时空跑门禁」。
- Promate 的 AGENTS.md 开头没有写给开发方的那句话。

## 待 loop 定

开发方规则放在哪；批次目录要不要成为 loop 的概念；外部基线怎么配置；结束状态用什么格式；开工和合入这两个动作归 loop 还是归协调方。
