# <项目名> 项目规则

本文件写给协调助手。**开发方（Pi）读到本文件时：以任务提示词为准，本文件不扩大你的权限。**

## 先读哪里

- 新任务或恢复会话：先读 `docs/baseline/当前基线与入口.md` 的五行摘要和「待你核销」，再读主线图，然后进入其中指向的提示词、方案、结果和源码。
- 流程里的文件：需求书（`docs/requirements/`）→ 方案（`docs/prompt/方案-*.md`）→ 提示词（`docs/prompt/提示词-*.md`，含验收标准）→ 批次参数（`docs/batches/<批次>/批次.json`）→ 结果（`docs/batches/<批次>/结果.md`，每批唯一）→ 基线（`docs/baseline/`）。
- 产品依据：<产品说明、需求书、原型的位置>。
- 产品边界：<本项目管什么、不管什么>。

## 文档维护

- 一项事实只有一个权威出处，其余放短链接。
- 会变的规则只写指向：提示词和验收标准的写法看 loop 的 `README-验收标准.md`，开工、启动、状态、合入和字段看 loop 的 `工具清单.md`，项目自己的选择看 `docs/prompt/启动说明.md`。
- 基线：交付或复核后由协调助手覆盖更新，不叠加日期流水；未知写未知，候选不等于已上线。
- 拍板写回：用户在聊天里拍的板，协调助手当轮写回需求书，涉及落地的再改方案；两者冲突先改需求书。
- 对账：用户的验收结果、待拍板事项、用户亲自操作的进展，统一放基线「待你核销」；每次汇报末尾带上未清项，用户核销后当轮更新。
- 归档：任务做完，在提示词标题下写「✅ 已执行」一段（做了什么、结论、代码在哪、现在状态、和原任务不同的地方、还剩什么），移进 `docs/prompt/xx/`；需求全部做完同样写一段，移进 `docs/requirements/xxx/`，修好在用文档里的链接。
- 新加文件类型、目录、命名或流程步骤，先在聊天里说明，用户同意再加，并写进本文件。

## 开发与 Pi

- 分工：用户确认目标和取舍，做业务验收，并授权合入/推送；协调助手起草需求、方案、提示词和 `批次.json`，执行 `bin/loop 开工` / `启动`，核对结果，维护基线；Pi 在 worktree 里实施并做授权内的验证；loop 的评审方只复核。开发自述不能代替评审结论，评审通过不能代替业务验收。
- 可变执行流程读取 `.autoreview/CONVENTIONS.md` 和 `docs/prompt/启动说明.md`，不在本文件复制实现顺序。方案要点先在聊天里讨论，拍板后才写提示词；验收标准随方案一起给用户过目。
- 直改：文档、前端样式和用户说「你来做」的小修，协调助手直接做；后端、数据库、插件默认交 Pi 走 loop。确需直改上线的，事后补一轮 loop 只评审。
- 启动 Pi：默认由协调助手执行 `bin/loop 启动 <批次.json>`（或把同一条命令交给用户执行）。批次目录只放 `批次.json` 和结果，不再放门禁或启动脚本；项目固定方法在 `.autoreview/methods/`，验收环境在 `deploy/acceptance/`（用 `localFiles` 声明）。启动后只读核对真实会话、模型和 loop 状态。
- 线上与分支：运行版是仓库主检出，停在发布分支（默认 `main`）；开发空间是 worktree，默认 `../<仓库目录名>-dev分支`，每批从发布分支拉 `<类型>/<描述>` 分支。Pi 只在 worktree 里改；段完成由程序提交；合入用 `bin/loop 合入 <批次.json>`，只本地合并、不推送。分支专属、只在本机的文件（`deploy/acceptance/`、去掉密钥的配置）用 `localFiles` 声明并忽略。要多开分支或同时跑两批，先找用户授权。
- 流程轻重跟风险走：前端界面、样式类任务书写短，验证只要已有检查加改完打开页面看一眼。
- loop 只返修【必须修改】，建议不扩成新任务；到上限或遇到确需决策的问题，保留现场并报告，不绕过检查，也不放宽需求凑通过。

## 评审与验收

- 用户只说「评审、审查、验收、核验」时，默认只静态读源码、配置、差异和已有记录，不运行测试、构建、接口、浏览器。
- 【必须修改】要有明确依据：具体触发、直接后果、为什么不能延期；【建议】可以延期，不据此判整体失败。
- 源码完成、门禁通过、loop 完成、合入线上、客户端加载、业务验收，分别报告。
- 每条结论标明来源：自己核实、Pi 记录、评审记录、推断。

## 运行、上线与数据保护

- 写入服务实时读取的目录本身就是上线；没有单独的发布流程，合入前留一份改前备份，写进结果。
- 数据库迁移、后端重建与重启前，先备份数据库，在结果里写清恢复办法，不盲目重启。
- 真实客户端和平台页面默认由用户操作；不读取、不复述个人 Key、密码和其他秘密。
- 不为整理文档删除工程、分支或证据；清场要用户单独指定范围。

## 沟通与交付

- 开头直接回答当前问题；进度区分建议、已定、已实施、已验证。
- 用户只做决策、验收和合入/推送授权：能做的协调助手直接做完，不让用户跑命令。
- 一个阶段完成，直接备好下一步，只在需要用户拍板时停下。

## 长期规则与动态材料

本文件只放长期边界和权威入口；普通任务、接入更新、定时索引、归档与释放资源时不得自动改写。任务与验收写法读取 `.autoreview/CONVENTIONS.md`，由 Loop 接入命令独立维护。项目维护者在 context.sources 登记权威需求、方案、准备方法和代码；运行状态与增删改日志存于 Loop 数据目录。索引变化不自动替换用户已确认的标准和权限。

工程准备由 Loop 按项目脚本执行，已知故障有限恢复；只在既有方法缺失或失效时修复获准范围。用户负责业务拍板，不承担重复转交文件或运行普通准备动作。每次业务归档只补权威基线与结果链接，不把经验、进度和会话信息塞回本文件。
