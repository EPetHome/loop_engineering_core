## 1. 要解决的问题

| # | 问题 | 本方案 |
|---|---|---|
| ① | 合入后更新缺陷单，Loop 因来源变化停下 | 「运行不停」第 1 条已解决，本方案不再处理 |
| ② | 搞不清哪些做完了、哪些还欠：部分验证、人工项、未验项散在各批结果里 | 程序维护一份交付总表 |
| ③ | 做完后要用户开口才有人去更新原单 | 规则随 Loop 接入约定下发，加上程序提醒；对所有使用 Loop 的 AI 生效，不依赖某个 AI 的私人配置 |

原则：**记录交给程序，判断和改原单交给协调方 AI，验收交给用户。所有新增行为只提醒、不拦截，任何情况都不让 Loop 停下。**

## 2. 整体流程

```
会话完成
  │
  ├─ 程序：往交付总表追加一段（含还欠什么），总结开头写明总表路径
  │
  ▼
协调方 AI（Claude、Codex 或其他）开会话
  │
  ├─ 程序（Hook SessionStart）：本项目有未回写的段 → 注入一句提醒和总表路径
  ├─ 规则（.autoreview/CONVENTIONS.md「收尾回写」）：读总结 → 更新原单 → 勾「已回写原单」
  │
  ▼
用户说「A4 验过了」→ 协调方 AI 勾掉 A4，原单同步
```

## 3. 设计

### 3.1 交付总表

**位置**：`~/.pi-autoreview/交付记录.md`，本机所有项目共用一份。放在项目外，不进 Git、不是来源，修改它不会触发评审或暂停。

**何时写**：会话进入完成状态时追加一段，部分验证也算完成。暂停不写：暂停时总结已经告诉用户怎么继续。

**格式**（每段一次写入，只追加不覆盖）：

```markdown
## 2026-10-19 03:12 · /Users/Admin/Desktop/Promate/dev分支 · 会话 01a15257…
- 任务：03三项必修（取自提示词第一个标题，没有标题时取需求前 40 字）
- 结果：完成（部分验证）；评审 3 次，返修 2 次
- 总结：/Users/Admin/.pi-autoreview/dev分支/01a15257….md
- [ ] 已回写原单
- [ ] A4 部分验证：<一句原因>
- [ ] A10 人工
```

- 还欠的条目来自与总结「需要你做的事」、验收结果相同的结构化数据，不从展示文字里推断。没有欠项时只写「- [ ] 已回写原单」。
- 同一会话再次完成（返修后重新评审）时追加新的一段；判断是否提醒时，只看同一会话的最后一段。
- 项目路径记 Git 顶层目录，没有 Git 时记当前目录。

**写入入口**：Pi（`autoreview.ts` 中现有的 `recordOutcome` 调用处）、Claude Code / Codex Hook（`hosts/hook.ts` 中现有的 `recordProjectOutcome` 调用处）。流水线各段本身就是 Pi 会话，不另写。不要求配置 `context`。

**失败处理**：写入失败只提示用户，不暂停、不影响完成状态。

### 3.2 总结里的提示

会话完成时，总结开头写一行：「已登记到交付总表：<路径>；待回写原单」。

### 3.3 会话开始时的提醒

- Claude Code / Codex 的 Hook 在 SessionStart 读取交付总表：本项目（同一 Git 顶层目录）各会话的最后一段里，只要有「- [ ] 已回写原单」，就在注入内容末尾追加一句：「交付总表里本项目有 N 段待回写原单：<路径>。按 .autoreview/CONVENTIONS.md「收尾回写」处理。」
- 没有待回写时什么都不注入。同一会话只注入一次。
- SessionStart 只有 10 秒时限：读取失败或超时就跳过提醒，不报错、不拦截。
- Pi 开发会话不注入：Pi 里跑的是开发方，核销不是它的事。

### 3.4 收尾回写规则（随【块 1】下发）

`README-验收标准.md`【块 1】升到新版本，新增一节「收尾回写」，接入命令（`setup-acceptance.ts`）按现有方式整段替换。要点：

- 读完 Loop 总结或看到提醒后，更新对应原单（缺陷单、需求单）的状态：已合入、部分验证、待人工、未验，逐条写，不得把未验写成通过。
- 原单更新完，在交付总表里勾「已回写原单」；没有原单时写「无原单」再勾。
- 条目的勾只在用户明确说「验过了」，或之后 Loop 运行验证通过时才打。不得代替用户勾人工项。
- 不改动验收标准和授权。

## 4. 不做

- 不在项目内建台账，不做程序自动写回原单、自动归档。
- 不做自动接入、受管启动入口、历史对账、多会话并发核销、中断恢复。
- 不新增命令和配置项；不因总表或提醒的任何问题暂停。
- 不修改 `test/e2e.mjs` 的场景和断言；不修改接入项目（是否在 Promate 等项目上重跑接入命令，由用户另行决定）。

## 5. 验收标准

```
A1. 操作：Pi 会话完成，其中一条验收部分验证、一条人工
    预期：交付总表多一段，含项目、任务、结果、总结路径、「- [ ] 已回写原单」和这两条欠项；总结开头写明总表路径
A2. 操作：Claude Code / Codex Hook 会话完成
    预期：与 A1 相同格式写入总表
A3. 操作：使交付总表不可写后完成一个会话
    预期：只提示写入失败，会话照常完成，不暂停
A4. 操作：本项目总表里有一段未勾「已回写原单」时，在该项目开一个 Hook 会话；再在另一个没有待回写段的项目开会话
    预期：前者注入一句带数量和路径的提醒，后者不注入任何提醒
A5. 操作：同一会话返修后再次完成，旧段未勾、新段已勾
    预期：不再提醒这个会话
A6. 操作：在两个会话中同时完成并写总表
    预期：两段都完整，互不覆盖、不交错
A7. 操作：对已接入旧版【块 1】的项目执行接入命令
    预期：识别新版本，整段替换为含「收尾回写」的新【块 1】，标记外的内容不变
```

## 6. 验证方式

- 开发方：受影响模块的定向单元测试（`test/hook.test.ts`、`test/autoreview.test.ts`、`test/onboarding.test.ts` 或接入测试），每条验收标准至少一个正例和一个反例。
- Loop：门禁跑 `node --test test/*.test.ts`；Astra xhigh 静态评审；评审后执行 `node test/e2e.mjs`，场景和断言不变。
- 结果写入 `docs/batches/交付总表/结果.md`。
