# Loop 全流程优化方案

日期：2026-10-17（America/New_York）

状态：实施版本。程序、项目文档、规则入口及模板已在 update/prepare-dev-check-e2e 分支迭代；验证与限制见本文第 16 节。未修改接入项目、全局插件配置或系统定时任务。

本次调整：明确自动恢复保留业务返修计数；按范围区分评审通过、本段可接力与整批完成；将第一批内部顺序调整为先理顺现有执行链、再接准备、随后接定位与行为优化。整体范围不变，不增加平行方案。

## 1. 直接结论与目标

Skill 不是本次优化的必需依赖。必须做的是分开管理稳定约束、业务要求、执行方法、固定格式和动态事实。不能把所有流程都放进 AGENTS.md，也不必把每个重复动作都包装成 Skill。

推荐分工：

- **AGENTS.md：稳定约束与稳定入口，默认只读。** 不写运行状态、批次进度、端口、模型版本、变更日志或每次复盘。
- **项目文档：需求、设计决定、当前能力、操作说明与历史依据。** 每种事实只有一个权威出处。
- **脚本与模板：确定性操作和固定输出。** 文件整理、字段校验、资源释放不依赖模型记住步骤。
- **Skill：按需加载、确实需要模型判断的可复用方法。** 第一批不新建 Skill；优先复用现有能力，缺口经重复任务证明后再提炼。
- **Loop：准备、调度、判定、恢复、记录和资源管理。** 已授权的普通工程问题由执行方处理，减少用户充当人工转接员。

优化范围覆盖“上游文档与规则 → 工程准备 → 开发评审 → E2E → 实际交付 → 资源释放 → 事实与经验更新”，不局限于自动返修循环。

目标是减少流程故障造成的用户介入、无效返修、重复输入与重复执行，同时减少交付后的主流程缺陷。不能单独用通过率、代码行数或自动调用次数判断收益。

## 2. 依据、现状与边界

分析阶段已读取近 7 天历史记录、相关源码、项目模板、用户提供的工程实践材料及本机 Ponytail/Pi 源码。当时只作静态分析；这不代表后续开发阶段未执行验证。

历史统计口径：2026-10-11 至 2026-10-17，50 个至少保存一轮结果的 Pi 项目会话，共 137 轮，11 个首轮通过。轮次记录累计约 23.2 小时，其中门禁约 10.3 小时、自动验收约 7.7 小时。统计按会话，不是去重后的业务任务；耗时含并行累计，不等于用户等待或操作时长，也不包含全部开发自跑检查及未落盘的中断工作。它用于定位改进方向，不作为承诺节省比例的依据。

已观察到的具体问题包括：环境故障占用业务返修次数；完整门禁规定性重复执行；验收耗时较长却没有形成可接收报告；同类状态逻辑分轮局部修补；准备与维护责任依赖主会话协调。

现有基础应保留：Git 快照和指纹、独立评审、同会话返修、流水线、验收证据工具、进程登记与中断处理。项目模板已经提出“AGENTS.md 只放稳定内容”，可直接沿用其分工。

补充评审依据：Pro 声明使用 10 月 12 日远端源码快照，分析时另对照本地源码（含当时已有未提交修改）。门禁重复要求、暂停后的用户接管清零计数、评审完成先于 accept-cmd 结束发布段完成等机制仍可从源码确认；具体项目是否因此提前接力，不能仅由通用代码推定，需考虑其额外包装逻辑。分析阶段未运行复现，不把当时的设计约束写成已验证的运行效果。

方案本身不扩大操作权限。用户随后已授权本仓库代码、项目文档和规则层实施、控制台运行 Loop，以及提交并推送指定分支；实际验证使用隔离示例。接入项目、历史资料、全局工具和真实业务数据不在此次修改范围。其他历史 `docs/` 与用户 `temp/` 保留。

## 3. 职责与总体流程

| 责任方 | 主要职责 |
| --- | --- |
| 用户与主会话 | 确认目标、业务规则、设计取舍、不能改坏的行为及权限边界；真正的业务歧义仍在这里解决 |
| Loop | 组织准备、提供一致输入、安排依赖和资源、执行检查、分类失败、恢复、形成记录并释放受管资源 |
| 按需调用的准备模型 | 在首次接入或已有做法失效时分析项目、补齐准备方法；不通过放宽标准让任务通过 |
| 开发与评审模型 | 共享当前事实和原始证据，分别负责实现与独立判断；不把开发自评当作评审结论 |
| 项目脚本 | 承载构建、检查、隔离环境、数据重置、证据采集和释放等具体实现 |

门禁与静态评审并行是可选优化，必须基于同一固定候选且输出不互相干扰；未满足条件时保持顺序。E2E 在开发和静态评审完成后进行。准备时确定每项必需验收的负责入口；本段没有负责的验收时不额外执行一遍，整批整合验收也不与段内验收重复。单段任务按同一规则简化执行。

成功、失败、暂停、取消均进入各自的资源释放路径，不只在最终成功时清理。本段接力前满足该段的资源交接条件；最后一段后再完成整批所需的释放或约定保留。已约定可后置的人工确认项继续单列，不临时增加新的接力阻断条件。

## 4. AGENTS.md 保持静态

### 4.1 固定职责

AGENTS.md 只保留长期有效的工作边界：权威资料入口、授权原则、改动与数据保护、评审分级、事实和推断的区别、如何找到适用流程。

动态内容移交其原本应在的位置：

| 内容 | 放置位置 |
| --- | --- |
| 当前功能、待办、部署或候选版本 | 项目当前基线与能力说明 |
| 每批目标、范围、验收要求 | 需求、方案及本批执行任务 |
| 启动参数、模型选择、端口、资源配置 | 项目执行配置与操作说明 |
| 模板字段和具体操作步骤 | 模板、流程说明或适用 Skill |
| 变更、失败、验收和释放记录 | 本批结果及 Loop 运行记录 |
| 原始事故、旧方案与历史结论 | 既有历史资料位置 |

### 4.2 更新控制

- 日常任务、定时维护、哈希失效处理、归档和插件接入默认不改 AGENTS.md。
- 只有用户明确要求改变长期协作规则时，才形成单独的规则变更；首次整理为稳定入口也属于明确的迁移工作，本次已随用户的规则层实施授权完成。
- 规则文件可以参与只读哈希核对。发现意外变化时定位差异与来源，不自动接受为新授权，也不自动覆盖恢复。
- 任务开始记录适用规则版本，任务中不静默更换；新的明确用户指令仍按权限与指令优先级处理。
- 稳定入口指向流程索引或已有说明，不在 AGENTS.md 中列出不断变化的全部 Skill、模板、参数和状态。
- 自动维护文件不得通过间接引用扩大权限或降低任务完成标准。流程说明的实质变化必须留记录并检查与稳定规则的兼容性。

原 `setup-acceptance.ts`、`onboarding.ts` 和手册向 AGENTS.md 追加验收写法块的路径，已改为维护 `.autoreview/CONVENTIONS.md`；接入模板、提示文案和对应检查已同步。稳定规则只引用入口，普通接入不重写 AGENTS.md。

## 5. Skill、脚本与模板怎么选

### 5.1 判定

反复使用不是必须创建 Skill 的充分理由。先判断工作是否需要模型持续作判断：

| 工作 | 首选载体 | Skill 是否必要 |
| --- | --- | --- |
| 文件归档、命名、更新索引、校验路径 | 确定性脚本及项目配置 | 不必要；权限、保留规则和幂等处理由程序落实 |
| 固定格式的检查或结果记录 | 数据结构、模板与程序渲染 | 不必要；缺字段明确报缺，不由模型编造内容 |
| 把零散材料整理为有判断的方案或交接 | 模板加模型工作流程 | 跨任务稳定重复且确有判断成本时，可用 Skill |
| 筛选可复用经验、处理文档事实冲突 | 现有文档治理能力，必要时按需加载 | 可选；优先复用已有能力，不另建同义 Skill |
| 资源释放、定时巡检、哈希和变更检测 | Loop 与项目脚本 | 不依赖 Skill；退出和崩溃时不能等待模型记起规则 |
| 开发中的复用、最小实现、避免过度设计 | Ponytail 原生 Pi 扩展 | 本方案建议接入，不能代替正确性检查 |

**第一批新建 Skill 数量为零。** 在已有脚本、模板或能力仍无法可靠承载，且同类模型判断流程已证明具有复用价值时，再提炼 Skill。新增时写清触发条件、输入、输出、边界和现有资源引用，不复制项目事实和运行状态。

### 5.2 固定格式生成

检查结果、退出码、来源版本、证据路径和资源状态由程序写入记录；模板负责显示；模型只补业务解释、原因判断及未决问题。程序校验必填字段、引用和允许状态，不能只凭模型写出“通过”判定成功。

简单格式可以用现有 Markdown 模板，不必为每种文档发明 schema。需供程序读取和作决策的结果，才使用结构化字段。

### 5.3 归档流程

```text
任务形成可靠结果
      ↓
核对交付状态、未验证项和证据完整性
      ↓
更新本批唯一结果及受影响的当前说明
      ↓
判断是否有值得复用的经验
      ├─ 没有：保留本批记录，不写长期规则
      └─ 有：更新已有主题，保留来源与适用边界
      ↓
按已有项目约定归档任务材料、维护引用
      ↓
释放符合条件的受管临时资源
```

归档不等于删除。已有历史资料、失败现场、含唯一修改的工作副本和用户材料，均按原授权与保留规则处理。对同一任务重复归档，应识别已完成部分，不能再次移动、重复追加或覆盖不同内容。

## 6. 上游文档与变更传播

保留每类内容的唯一权威出处：需求回答“要什么”，方案回答“怎么做及取舍”，源码回答“实现了什么”，运行证据回答“实际验证了什么”。执行提示词引用这些来源，只补本批执行信息，不重新定义业务规则。

```text
需求条款 → 设计决定 → 执行任务 → 相关实现 → 验收证据 → 当前能力说明
    ▲                      │                          │
    └── 新歧义或不可满足约束 ┘                          │
                           实际结果与经验更新 ←────────┘
```

上游变更要查任务、实现与检查是否同步；实现和证据带来新事实时，回查受影响的设计和说明。机器可直接维护有来源的技术事实；业务决定、验收标准和长期规则的变化不能由代码差异代替用户确认。

## 7. 哈希、变更记录与定时补漏

事件触发为主：任务启动、候选固定、检查完成、任务结束。定时检查补漏，第一版可在 Loop 运行期间低频执行；退出后的遗漏在下次启动补查，确有离线长期维护需求时再设计系统定时任务。本轮不创建计划任务。

检测对象限于登记的相关源码、规则、文档、准备脚本和配置。覆盖必要的未提交和未跟踪文件；排除无关依赖、构建缓存和运行日志。修改时间只能辅助筛选，关键判断使用内容哈希。执行候选身份与内容复用身份分开，不能仅因路径或提交名相同就复用。

```text
事件触发／定时补漏
        ↓
比较登记来源的内容版本
        ├─ 没变化 → 不调用模型、不重写事实、不重复建索引
        └─ 有变化
              ↓
       生成简短变更记录
              ↓
       找到受影响的事实、定位、准备及检查结果
              ↓
       标记失效或待核对 → 增量分析与更新
              ↓
       发布新版本；运行中任务保留其冻结依据
```

变更记录由程序产生基本信息，模型只补必要解释：变更对象、前后可回看的版本、来源、事实变化、受影响内容、处理状态及阅读入口。详细 diff、日志和证据不在记录里复制多份。仅有哈希不足以回看旧内容，必须引用可保留的源版本或必要快照。

稳定节点合并同批编辑，避免每次保存都生成记录。源文件删除时，从当前导航移除或标失效，历史证据不随之删除。发生来源冲突或并发编辑时保留冲突，不覆盖他人正在修改的内容。

**源码与文档没变，不代表环境和资源没变。** 资源巡检始终独立执行，不受内容哈希是否变化控制。

## 8. 准备、快速定位与内容复用

准备分项目级、任务级和运行级：项目启动/检查/重置/释放做法按依赖复用；本次修改范围和检查对应按任务形成；磁盘、端口、存储可写性及活动任务冲突在使用前重新确认。

准备检查证明执行条件与验证方法可用，不要求尚未开发的功能提前通过。已授权的路径、命令接入和准备脚本问题交准备维护方处理；不能让开发方通过修改产品绕过检查。

准备按以下三种情况执行：

| 情况 | 处理方式 |
| --- | --- |
| 已有准备方法有效 | 调用项目脚本，核对本次运行条件后继续；不重复调用模型研究项目 |
| 运行环境出现已知问题 | 在已有授权和有限预算内执行已有恢复方法，保留证据；无法解决时报告明确阻塞 |
| 方法缺失或已经失效 | 才调用准备模型分析并补齐项目脚本或配置，记录依据和适用条件，供后续复用 |

Loop 承接准备的组织责任，项目保有自己的启动、初始化、检查和释放知识。第一版沿用既有配置与脚本，不以建设完整插件框架为准备接管的前提。运行条件不足本身不等于准备方法失效；方法错误也不能靠反复重试环境掩盖。

为开发与评审提供精简代码定位信息：模块职责和入口、与本任务有关的调用及状态路径、本轮差异、关联调用方、已有检查入口、失败证据和未决问题。程序给出可定位事实，模型解释任务关系；未确认的动态调用明确标记。

第一版复用项目说明、Git 差异、rg 和已有语言工具，不先引入全仓向量库或大型知识图谱。地图用于找路，不限制评审继续查相关源码。

同一内容版本保存一份；同一会话只补变化与缺失片段。大日志给相关摘录和原文位置。新会话仍需获得必要内容，不能只给缓存编号。跨角色共享事实和证据，不能要求评审接受开发自评或根因假说。

## 9. 开发、门禁、评审与返修

开发先理解真实调用链，复用现有实现；复杂状态、权限、恢复或迁移问题先明确关键行为和相邻路径。返修目标写清“被破坏的要求 → 触发条件 → 实际后果 → 关联入口 → 修复后如何判断”。

门禁位于开发定向自测之后、E2E 之前。根据项目要求执行必要编译、类型、静态检查、回归、范围保护及交付物一致性检查。开发方做定向自测，完整门禁由程序负责，取消固定要求开发方与 Loop 各完整跑一次。

现有门禁已经会把超时、命令无法执行等情况判为暂停，不能概括为所有环境故障都算产品失败。本次补齐的是普通非零退出中有明确证据的环境和检查方法故障分流，保留现有有效分类。

| 结果原因 | 处理 | 是否消耗业务返修次数 |
| --- | --- | --- |
| 明确产品缺陷或必要回归失败 | 原开发会话修复，核对根因与影响 | 是 |
| 明确环境故障 | 恢复环境，保留产品候选与已有记录 | 否 |
| 门禁、准备或验收脚本错误 | 相应维护方修正方法，再执行受影响检查 | 否 |
| 原因不明 | 先收集最小证据并分类，不盲目改产品 | 不先记为产品错误；诊断另有有限预算 |

环境失败不能仅凭模型自述改判，须有明确错误或受管检查证据。诊断、环境重试和业务返修都应有限，不能通过分开计数变成无限循环。接入初期不承诺能识别所有非零退出原因。

自动恢复必须有独立于“用户接管”的程序路径：

- 环境恢复、准备维护和程序续跑保留已使用的业务返修次数、原候选及历史记录，不得复用当前用户接管时清零 `state.repairs` 的路径。
- 环境、诊断和检查方法重试使用各自有限预算，并记录原因；重开执行进程或恢复会话不能规避原任务预算。
- 用户接管和新任务的计数处理保留其已定义语义，并记录触发依据；机器消息不能冒充用户接管或新增授权。
- 保留检查记录不等于沿用全部通过结论。恢复后按候选、命令、标准、环境和数据的实际变化判断有效性，只重做必要检查。
- 候选或必需证据已经变化时，如实记录失效；不能为了继续恢复而伪称仍是原候选。

例如，业务返修已经使用 2 次，期间两次环境恢复成功后仍应记为 2 次；环境恢复消耗自己的预算，不额外扣减或补发业务返修机会。这是新增自动恢复的实施约束，不声称当前已经存在自动无限重试。

评审保留【必须修改】与【建议】区别。只有明确业务后果的严重问题阻断；普通复杂度、命名与更好写法可延期。沿用现有必修位置与依据、旧必修复查、新改动范围和接受合理异议的规则，不另建一整套评审制度。独立评审默认只做静态分析，运行验证遵循当次任务授权，不能通过 Ponytail 或其他 Skill 扩大权限。

## 10. E2E 后置、动作复用与中断恢复

### 10.1 验收负责入口与完成信号

开发和静态评审完成后再对候选进行 E2E。准备时明确每项必需验收属于本段还是整批，以及由项目级 acceptance、流水线整合 E2E 或 accept-cmd 中的哪个入口负责。同一项必需验收只设一个负责入口，避免重复执行；附加诊断命令与必需业务验收分开记录。

| 状态含义 | 发出条件 | 不能据此声称 |
| --- | --- | --- |
| 评审通过 | 当前候选的静态评审无未解决必修；门禁另有实际结果 | 本段必需验收、实际交付或整批已经完成 |
| 本段可接力 | 本段门禁和评审通过，本段负责的必需验收已通过，本段约定的候选与资源交接条件满足 | 只能在所有段之后执行的整批整合 E2E 已通过 |
| 整批完成 | 各相关段可接力，整批必需自动验收通过，本批约定的交付、文档与资源处理条件满足 | 计划明确留待人工确认的业务事项也已通过 |

这三项是程序行为的区分，不要求立即增加复杂状态框架。现有状态、总结、通知、退出交接与流水线接收方必须使用一致含义。

具体约束：

- 如果 accept-cmd 承担本段必需验收，必须等待它对当前候选取得通过结果，才允许本段接力；失败、超时、中断、无法执行或缺少必需证据都不能发出可接力完成。
- 如果验收属于整批整合入口，各段先完成自己负责的工作并允许接力，等相关段齐备后再做整合 E2E。不能要求各段等待整合 E2E，同时又让整合 E2E 等各段，形成互相等待。
- 是否要求开发进程退出由具体接力约定决定。需要保留原会话接收 E2E 返修时可以保留，不能统一要求退出；仍在执行的必需验收则必须等到取得结果，不能混作有意保留的开发会话。
- 已约定可后置的 `[人工]`、不授权条目等继续按既有规则单列；不得把必需自动验收的失败或无法验证临时改成可后置项。允许部分验证接力时必须有已确认的依据和明确缺口。
- 旧配置迁移时说明验收命令是附加用途还是必需验收，不静默改变其完成含义，也不把一次进程正常结束等同于验收通过。

旧通用 Pi 扩展先报告段 `done` 再执行 accept-cmd，通用流水线可以据此继续。本次默认 required 模式在必需验收通过前不再发布 done，具体资格失效与恢复规则见运行文档。Promate 的串行包装另有等待进程退出和核对交接记录的处理，不能仅凭通用代码断言该项目已经发生提前接力；分析阶段没有运行验证。

### 10.2 动作复用与恢复

确定性程序回归交门禁；E2E 负责跨组件业务链和用户可见行为。保留现有验收标准，优化执行，不通过删场景提高通过率。本仓库 E2E 场景口径由用户决定，调整必须另列具体条目与理由。

优先固化高频公共动作，如登录、角色上下文、隔离数据、上传和异步等待。每轮使用当前候选真实执行，页面行为不能全部用 API 成功替代。一个浏览器可按角色建立隔离上下文；修改共享状态的场景使用独立数据，登录和停用等场景不能错误复用身份状态。

逐项保存结论、证据引用和依赖。超时保留可核对结果，但不能从证据文件存在推断通过。候选、方法、环境或数据改变后判断哪些结果失效；数据已重置的动作链须重做；写入是否完成不明时先查询状态，不能盲目重放。

复用执行方法先于跨轮复用通过结论。最终候选仍完成必要整链检查；部分验证明确列出子场景缺口，不把复合标准中一部分通过扩大为整项完成。

## 11. 并行边界

优先并行独立读取、配置核对、代码定位和验收路径分析。开发可与不依赖新实现、且不修改开发文件的基础环境准备并行。

固定候选的门禁与静态评审可并行，前提是资源充足、产物隔离、评审不修改代码；两边结束后合并反馈，不在另一边仍运行时修改候选。门禁高概率早失败时可先门禁，避免无效评审。

E2E 只有在账号、数据、路径和资源不互相干扰时并行。真实业务链的创建、提交、批准、恢复保留依赖顺序。不同仓库不代表不争用磁盘；同盘重任务须考虑资源峰值。

不预先增加大量 Agent。按实际独立工作调度，收益不足或冲突增多时恢复顺序执行。

## 12. 资源释放与异常补偿

资源管理由程序负责，不能依赖 Skill 或模型记住收尾。创建时登记任务归属、资源身份、用途、释放方式与保留条件；确认使用者结束后处理。复用现有进程登记基础，项目资源由项目脚本提供具体释放操作。

```text
声明、登记资源 → 创建使用 → 成功／失败／暂停／取消
                                  ↓
                        保存必要证据与恢复信息
                                  ↓
                        关闭本任务进程及服务
                                  ↓
                        清理允许释放的临时资源
                                  ↓
                        核对实际释放结果
                           ├─ 成功：更新记录
                           └─ 失败：保留待处理记录和影响

崩溃／强杀 → 下次启动或周期巡检 → 确认拥有者与活动状态
                                  ↓
                    归属和释放条件明确才补偿回收
```

| 资源 | 处理原则 |
| --- | --- |
| 模型子进程、测试进程、浏览器 | 阶段结束关闭；核对任务身份和进程启动信息，避免 PID 复用误杀 |
| 隔离服务、容器、端口 | 最后一个有效使用者结束后释放，不能仅凭端口和启动时间认定归属 |
| 临时副本、构建产物 | 必要证据保存后按策略清理；有唯一修改或保留用途时不能删除 |
| 隔离数据库、存储卷 | 与容器分别登记；停止容器不代表释放卷，不对未知归属的数据做删除 |
| 共享依赖缓存 | 有容量、保留和使用中保护，不每轮清空，也不无限累积 |
| 报告、日志、截图、失败现场 | 遵循项目保留规则；当前约定保留的 E2E 报告和失败现场仍保留 |

暂停默认保留候选、证据与恢复信息，释放昂贵计算资源；交付约定要求保留体验入口时照约定执行。清理失败不能丢弃登记。资源残留影响隔离或容量时阻止下一项重任务；无关尾项单独报告，不篡改已取得的业务检查结果。

低余量时停止启动新重任务，优先保留最小状态；证据写入失败要标记录不完整，不能伪报完成。定时巡检只检查受管范围，不全盘清理。首次实施不自动清除历史材料。

## 13. Ponytail 接入与成本边界

本机 Ponytail 4.13.0 已带 `pi-extension/index.js`，支持 Pi 的结构化系统提示区及模式恢复；当前 Loop 关闭扩展自动发现，须按角色显式加载。复用原生扩展，固定来源和版本，避免长期依赖 Codex 的可变缓存路径。

开发、返修和准备脚本编写建议采用 full。需求和设计保留必要说明，不因简化偏好省略明确要求。独立评审继续覆盖正确性与安全；`ponytail-review` 只审过度设计，不能替代完整评审。E2E 不能因成本偏好缩减标准。

不在 AGENTS.md 复制整份 Ponytail 规则。由角色启动配置与运行记录说明扩展版本、实际加载和生效模式。用户显式切换模式时按其要求处理，不能把安装成功等同于本次实际启用。

分析阶段只核对了静态接口；开发阶段已用本机原生扩展检查 full 注入、其他段保留及 off 移除，实际模型成本收益仍未验证。本机 Pi 安装目录与包内版本标记不一致，实施时重新确认真实入口和加载结果，不将本次路径或版本写成长期常量。

成本按三方面治理：文档与定位减少重复理解，Loop 减少重复执行与环境返修，Ponytail 减少不必要实现。插件规则自身也占上下文，不承诺固定节省比例。

## 14. 实施顺序与完成条件

### 第一批：先减少错误打回和人工协调

整体范围保留，内部按下面三个交付点推进，仍使用这一份方案。上游文档职责、稳定规则入口、AGENTS.md 默认只读和既有保留边界从第一步生效，不因调整顺序移出范围。一次性规则迁移按明确授权处理，不先建设完整知识治理系统。

1. **先理顺现有执行链。** 取消开发方与 Loop 规定性完整门禁双跑；落实失败去向、有限预算及自动恢复保留业务计数；明确必需验收负责入口，将 E2E 后置，并接清评审通过、本段可接力、整批完成的信号；该执行链使用的资源必须有释放或约定保留结果。
2. **再让 Loop 承接准备。** 按第 8 节三种情况复用方法、处理已知环境问题或调用准备模型。沿用项目配置和脚本，形成一致执行输入、来源版本和简短变更记录，普通工程处理不再依赖用户转交。
3. **随后接定位与行为优化。** 提供共用代码定位和增量输入，按角色接入 Ponytail 原生 Pi 扩展；分别核对实际生效及收益，避免同时改变过多因素后无法判断效果。

先用一个已授权的实际批次贯穿首个交付点，观察错误返修、重复检查、接力与资源收尾，再继续完成第一批其余能力。真实业务批次运行仍以当次授权为前提；本次工程回归和隔离示例验证见第 16 节。交付点是同批内部顺序，不另建三套平行方案，也不以第一点完成代替整批交付。

### 第二批：提高复用与稳定性

1. 根据来源版本增量更新事实、任务定位和准备成果。
2. 模板渲染固定记录，固化高频 E2E 步骤，增加逐项结果和恢复。
3. 满足依赖与资源条件后扩大并行。
4. 根据实测取舍流程；仅在现有方法确实不足时新增 Skill。

两批均覆盖已确认的整体范围，不把完成某个局部等同于整批交付。优先更新本方案和现有权威材料，不堆叠平行任务书。

以下为实施验收要求，实际范围与仍需项目侧接入的部分见第 16 节：

- AGENTS.md 在普通任务、定时事实更新、归档和资源释放中保持不变；规则的明确变更单独可追溯。
- 无内容变化不调用模型维护事实；有变化能定位相关内容，且不静默改变运行中任务标准。
- 环境故障不消耗业务返修次数；检查方法错误不要求产品绕过检查。
- 自动恢复前后业务已用次数保持不变；环境、诊断和方法修复的预算有限，机器续跑不冒充用户接管。
- 同一候选不再被规定性要求开发方与 Loop 各跑一次完整门禁。
- 准备已有方法有效时直接调用；已知环境问题先用已有恢复方法；只有方法缺失或失效时才调用准备模型。
- 开发、评审和 E2E 能引用同一需求、方案与候选；缺口如实保留。
- 本段必需验收未通过时，下游不能因评审已通过而接力；没有段内验收责任时也不重复执行整批验收。
- 整合 E2E 能在各相关段可接力后启动，不与段完成条件互相等待；其未通过时不发布整批完成。
- 已确认可后置的人工项继续单列，不扩大为新的接力阻断要求，也不冒充业务验收通过。
- 停止、中断和恢复后能说明受管资源哪些释放、哪些保留、哪些失败；不影响非本任务资源。
- E2E 中断不等于全部成果丢失，也不因保留旧证据而把新候选误判通过。
- Ponytail 实际加载可确认，既有必要检查与报告格式完整保留。
- 固定格式缺字段时明确报告缺口；归档可重复执行且不复制多套当前事实。

开发阶段按授权复用定向测试及项目必需检查，覆盖失败分类、自动恢复不清业务计数、必需验收失败或中断不能提前接力、整合验收无循环等待、版本失效、资源误归属、中断恢复和格式缺字段等必要反例。纯评审仍遵守只读静态边界；真实模型、外部平台、启停与清理按当次授权。技术检查不能代替业务验收。

效果比较优先看：流程故障引起的用户介入、交付后主流程缺陷、可用交付总时间、资源峰值与残留；辅助看重复内容输入、工具调用、模型用量及 E2E 准备耗时。区分并行累计耗时与墙钟时间，不用“通过率上升”单独证明成功。
