# Loop 运行不停：三处减停修复方案

日期：2026-10-19（America/New_York）

分支：`fix/running-not_stop`

状态：方案稿，待用户确认后出 pi 提示词。本文件不授权提交或推送。

## 1. 目标

Loop 停得太多，用起来像不可用。本批只做一件事：**去掉三个不该停的地方**。不加新功能、新命令、新配置项。

2026-10-18 当天停了 9 次，没有一次是「评审发现真问题、返修收不住」。本批针对其中 Loop 自己造成的部分：

| # | 改什么 | 现在 | 改完 | 对应 10-18 暂停 |
|---|---|---|---|---|
| 1 | 资料变了不再停 | 需求、规则、说明等来源文件一变，就撤销完成资格、暂停等用户 accept | 照常跑，在总结里记一笔「开发期间哪些来源变过」 | 约 3 次，另加 10-19 五系列那次 |
| 2 | 开发方质疑验收方法时不停 | 只要写「A2：异议」就暂停，不管质疑的是标准还是方法；同一条旧异议还会反复触发 | 只有质疑标准本身才停；质疑方法的照常验收；处理过的异议不再触发 | 约 1 次 |
| 3 | 清理资源时不误判 | 同一会话的进程登记不分属于哪次运行，别的运行还有进程就判「释放未确认」 | 只看属于本次运行的进程 | 约 1 次 |

其余约 4 次是协调方准备漏项，不靠本批解决。

## 3. 设计

### 3.1 资料变了不再停

**原则**：来源文件只是给开发方和评审方看的资料，不再是「冻结的任务依据」。资料变了，Loop 换用新版本继续跑，并在总结里写明，由用户看总结时判断。

**行为要求**：

- 来源内容变化（任何 role）时，不暂停、不撤销完成资格、不让进行中的评审、门禁或验收结果作废、不要求 `/review-inputs accept`。
- Loop 把记录的来源版本更新为当前版本，下一次给开发方和评审方的来源索引用新版本（现在每轮已经重新生成，保持即可）。
- 总结里增加一节「开发期间来源变化」：列出变化的文件和发现时间；拿不到文件列表时写「来源有变化（第 N 版）」。只有发生过变化才出现这一节。
- 已完成的会话之后来源变化：保持完成，只在总结里补记，不自动重新评审。
- 来源文件**缺失**（登记了但读不到）照旧暂停：这是配置错误，不是资料更新。
- `/review-inputs` 保留，作为查看命令；`accept` 仍可用，但不再是继续运行的必经步骤。

**涉及位置**（以 `2a1749b` 为准，开发方以实际代码为准，不得遗漏入口）：

| 文件 | 位置 | 现在的行为 |
|---|---|---|
| `autoreview.ts` | `before_agent_start` 中「上游来源已变化」 | 暂停并中止开发方 |
| `autoreview.ts` | 来源巡检定时器 → `invalidateSources` | 完成或评审中时撤销资格并暂停 |
| `autoreview.ts` | `completionProblem` 中 `sourceInputsProblem`；`acceptanceInputs` 含来源指纹 | 来源变化使完成或验收结果失效 |
| `autoreview.ts` | `/review-inputs`（不带 accept）在完成态 | 撤销资格并暂停 |
| `autoreview.ts` | 会话恢复时 `completionProblem` | 「恢复完成依据失效」暂停 |
| `review.ts` | 评审前来源检查（约 519—525 行） | 返回暂停 |
| `hosts/hook.ts` | Claude Code / Codex 入口的来源接收（约 601—604 行） | 只在 accept 时接收新版本 |
| `pipeline.ts` | 段状态核对中 `sourceInputsProblem`（约 357 行） | 把该段判为失效 |

Pi、Hook、流水线三个入口行为一致。

### 3.2 开发方质疑验收方法时不停

沿用 2026-10-18 用户已确认的稳定批 4.1、4.2 写法。

开发方对验收条目的回应分两种：

| 写法 | 含义 | Loop 行为 |
|---|---|---|
| `A2：异议：理由` | 认为标准本身不对，要改预期、范围或授权 | 照旧暂停，等用户决定 |
| `G2：方法存疑：理由` | 认可标准，质疑验收方法、环境或失败归因 | 不暂停，照常验收；理由随该条交给验收方，并写进总结 |

- `方法存疑` 的条目照常判定，不因开发方一句话就算通过。失败时按现有失败归因（`product / environment / method / unknown`）处理，不新增归因规则。
- **处理过的异议不再触发**：现在每次验收都读开发方最后一条回复（`lastAssistantText`），用户回应后再 `/review` 会因为同一段旧回复再停一次。改为：只有 Loop 还没处理过的开发方回复里的异议才触发暂停；已处理的记入会话状态。
- 开发方系统提示里的约定（`acceptance-core.ts` 第 18、662 行附近）补上 `方法存疑` 的写法和适用场景；`README.md`、`README-验收标准.md` 对应说明同步。

落点：`findObjections` 分两组返回；`runAcceptanceStage` 只对标准异议暂停。

### 3.3 清理资源时不误判

沿用稳定批 4.6。

- `ProcEntry` 增加可选的 `runId`；登记被测系统进程时记下它属于哪次运行（资源编号）。
- `releaseRunResource` 判断「还有没有消费者」时，只看 `runId` 等于本资源编号的登记。
- 没有 `runId` 的旧登记按身份不明处理，继续保护，不释放。
- 不清空会话登记，不终止其他运行的进程。

## 4. 不做

- 交付核销（重跑批）不合入；稳定批其余各项（4.3—4.5、4.7—4.9）、项目方法复用都不做。
- 不新增命令、配置项、模块、状态机。
- 不修改 `test/e2e.mjs` 的场景和断言。开发方认为必须修改时，写【需要你决定】并停下。
- 不修改接入项目（Promate 等）、全局配置和全局安装。
- 不清零、不重置业务返修次数。

## 5. 验收标准

```
A1. 操作：开发进行中修改一份 requirement 来源文件，再修改一份 guide 来源文件
    预期：不暂停，开发方继续；下一轮评审拿到新版本来源；总结「开发期间来源变化」一节列出这两个文件
A2. 操作：会话已完成后修改来源文件；再执行 /review-inputs（不带 accept）
    预期：保持完成，不撤销完成资格、不暂停；总结补记变化文件
A3. 操作：必需验收进行中或刚通过时修改来源文件
    预期：验收结果不因来源变化作废，会话照常完成
A4. 操作：删除一份已登记的来源文件
    预期：照旧暂停，原因写明缺失的来源
A5. 操作：分别经 Hook 入口和流水线入口，在开发中途修改来源文件
    预期：与 Pi 入口一致，不暂停、不判段失效，变化写进总结
A6. 操作：开发方写「G2：方法存疑：理由」，随后 G2 验收失败
    预期：不暂停，照常验收；G2 按现有失败归因记录，不记为通过；理由出现在总结里
A7. 操作：开发方写「A2：异议：理由」；用户回复让它按原标准继续，开发方未再提异议，之后执行 /review
    预期：第一次暂停等用户决定；之后不因同一段旧回复再次暂停
A8. 操作：同一会话里前一次运行的被测系统进程仍在登记中，释放后一次运行的资源
    预期：后一次资源正常释放；前一次的登记保留不动；没有 runId 的旧登记继续保护
```

每条至少一个正例和一个反例（例如 A1 的反例：来源未变时总结不出现变化一节）。
