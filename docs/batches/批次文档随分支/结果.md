分支：`fix/batch-docs-follow-branch`。开发模型 `opencode-go/deepseek-v4.1-flash` / `max`；独立评审 `openai-codex/gpt-6-astra` / `xhigh`。按要求未跑 e2e，未推送、未自动合入，开发方未提交。

结果：95 项通过，0 项失败。完整 Node 测试由 Loop 门禁执行。测试里的仓库、worktree、`methods.json` 都建在系统临时目录并由 `test/loop.test.ts` 的 `after` 清理。

## 实现摘要

- `loop 开工` 只要求运行版停在发布分支；与本批无关的未提交改动保留，并列为「未提交，不在本批分支上」。
- 本批文档按批次目录、各段 `prompt`、`e2e.criteria` 收集；只取仓库内、相对发布分支 HEAD 未跟踪或有修改的文件，搬进顶层 `branch`（没写时第一段）对应的开发空间，由程序提交 `<类型>: 批次文档`，然后恢复项目根。
- 开工输出的 `启动`、`状态`、`合入` 都使用开发空间里的批次文件路径；项目根原路径在批次文件仍在发布分支上时照常可用。
- `loop 合入` 先算批次分支相对发布分支的改动、加上批次工作区里即将自动提交的改动，再和项目根未提交文件求交集；有交集不合并。无关的已跟踪改动（含暂存、部分暂存）用临时 stash 保存，合入后用 `--index` 恢复；未跟踪文件不碰，只清理能证明属于本次的 stash。
- 合入冲突时用 `git reset --keep` 退回到本次开始前的 HEAD，保留无关改动；不强制重置。运行版已有 `MERGE_HEAD` 时先停下，不中止用户原有的合并。

## A1–A10

### A1 批次文档随批次分支提交，无关改动保留

实现：运行版只核对分支；`workingChanges` 用 `git status --porcelain -z --untracked-files=all` 列出已跟踪修改和未跟踪文件。批次文件在仓库根或项目根时，只把批次文件本身和引用的 `prompt` / `e2e.criteria` 当本批文档，不把同目录无关文件误算进来。开发空间切到批次分支后复制、提交，提交成功后删除未跟踪的项目根文档，已跟踪的用 `HEAD` 还原。

证据：`test/loop.test.ts` 的「A1 开工只要求运行版停在发布分支；批次文档随批次分支提交，无关改动保留」通过。断言了批次分支上的 `feat: 批次文档` 提交、正文批次名、提交只含两份文档、项目根文档已移走、无关 `README.md` 修改和未跟踪 `notes.txt` 保留，`uncommitted` 只列无关文件。

未验证：没有在真实接入项目里跑一批完整开发；本项用临时 git 仓库覆盖。

### A2 发布分支上已跟踪的提示词被改过

实现：批次文档对比项目根工作区和 HEAD，已跟踪但被修改的提示词进入搬运集合；提交成功后用 `git checkout HEAD -- <路径>` 恢复项目根。批次文件里仓库内的绝对 `prompt` 路径会改写到开发空间；批次文件本身没改但引用需要改写时，也把它加入本次搬运并提交，保证开发空间里的批次文件直接指向新内容。

证据：`test/loop.test.ts` 的「A2 发布分支上已跟踪的提示词在项目根改过，也搬进批次分支并恢复」通过。批次文件用绝对提示词路径，提示词在项目根改过；断言批次文件因绝对路径改写也进入「批次文档」提交、批次分支里是新内容、项目根恢复成发布分支内容，并用开发空间里的批次文件启动时提示词指向开发空间的新文件；再用 `parsePlan` 按流水线入口解析开发空间批次文件，提示词也指向新内容。

未验证：没有覆盖项目根里提示词被删除的情况；删除的文件不搬运、也不恢复，按“只搬未跟踪或有修改的文件”处理。

### A3 `--dry-run` 列出搬运和恢复文件

实现：dry-run 只计算 `batchDocs.files` / `batchDocs.restore` 和 `uncommitted`，不建 worktree、不切分支、不复制、不提交、不恢复。

证据：`test/loop.test.ts` 的「A3 开工 --dry-run 列出要搬的批次文档和要恢复的项目根文件，不改任何东西」通过。断言文档和恢复列表、无关未提交文件、worktree/分支/HEAD 未变、项目根文件仍在。

未验证：无。

### A4 越界检查不把批次文档算作开发方改动

实现：批次文档提交发生在方法自测和启动之前。流水线启动段时 `snapshotRef(stage.cwd)` 取的是包含该提交的 HEAD，作为 `AUTOREVIEW_BASE_REV`；单段会话启动时 `autoreview.ts` 也在会话开始时以当时 HEAD 为 baseline。越界检查从该依据起算，因此批次文档提交不在开发方改动里。

证据：A1/A2 测试断言「批次文档」提交就是开发空间 HEAD；`scope.ts` 的 `changedSince` 从传入依据起对比，现有 `test/loop.test.ts` 的启动与串行测试通过。A1 测试还确认开发者未改动时没有额外提交。

未验证：没有在真实评审流程里触发一次越界检查并观察打回结果；本项依据提交顺序和现有 baseline 机制的静态链路。

### A5 用开发空间批次文件执行启动、状态、合入

实现：`batchDocsPlan` 计算开发空间里的批次文件路径，开工输出 `startCommand`、`statusCommand`、`mergeCommand` 都用它。引用重定位收进 `batch-refs.ts`，在搬运批次文件时完成：仓库内绝对路径改到开发空间，仓库内相对路径保持原样，原来指向仓库外的相对路径改写成原绝对目标；需要改写时批次文件本身也进入提交。`cmdStart` / `cmdStatus` / `cmdMerge` 和 `pipeline.ts` 都直接读改写后的文件，不再按 worktree 位置猜来源；直接在开发空间创建的原生批次不改。`repoOf` 从链接 worktree 回到主 worktree，命令从开发空间目录执行也能找到项目根。

证据：`test/loop.test.ts` 的「A5 开工输出用开发空间里的批次文件路径，loop 启动能取到提示词并经过 bin/pi-dev」通过。批次文件、提示词、验收标准都在临时仓库里未跟踪，提示词和验收标准用绝对路径；断言开发空间批次 JSON 的绝对路径已改写，启动、状态、合入三条命令都指向开发空间批次文件，`loop 启动 --dry-run` 经过 `bin/pi-dev` 并取到开发空间提示词；从项目根和开发空间目录执行都能启动 dry-run。另有「多段流水线使用开发空间批次文件，仓库外相对引用保持原目标」通过：自定义 worktree、两段批次、仓库内绝对提示词和仓库外相对提示词；断言复制后的批次 JSON 和 `parsePlan` 都取到正确目标。还有「原生开发空间批次保留相对引用解析，不按 worktree 来源重定位」通过：直接在开发空间创建的批次引用 `../prompt.md` 和 `../criteria.md`，`parsePlan` 仍按批次所在目录解析。

未验证：没有启动真实 Pi 会话；只验证到 `bin/pi-dev --dry-run` 的实际命令，以及流水线共用的 `parsePlan` 解析。

### A6 运行版不在发布分支时不开工

实现：`checkRuntime` 先核对当前分支等于 `release`，不等就直接抛错，早于任何 worktree、分支或文档操作。

证据：`test/loop.test.ts` 的「A6 运行版不在发布分支时不开工，项目根、分支和 worktree 都不变」通过。断言非 0、错误带当前分支、当前分支和 HEAD 未变、没有建 worktree、没有建批次分支。

未验证：无。

### A7 合入时保留无关未提交改动

实现：合入前仅要求运行版停在发布分支；先算批次分支改动，和项目根未提交文件求交集，无交集才继续。已跟踪改动（含暂存、部分暂存）保存成 stash commit 并钉在本命令自己的 `refs/loop/merge-stash/*` 私有引用上，合入后 `git stash apply --index` 恢复并删除该引用；未跟踪文件原样留在工作区，暂存内容不进入合并提交。全程不读写共享的 `refs/stash`。清理前先检查未跟踪文件是否挡在 HEAD 要写回的路径上；有阻挡就停下，不覆盖未跟踪内容。扫描未跟踪文件本身失败时也停下，不把空白或部分输出当成完整清单。

证据：`test/loop.test.ts` 的「A7 合入没有冲突时本地合并、不推送；远端没变」通过。项目根同时有未暂存 `README.md`、部分暂存 `prompt.md`（索引里是旧一版、工作区是新一版）和未跟踪 `未提交.txt`；断言合入成功后三者内容/索引状态保留，合并提交不含 `prompt.md`，批次工作区的未提交改动先提交，远端未变，用户原有的 stash 仍在栈顶，本次私有引用已清理。另有「合入期间 stash 栈变化时只保留本次记录，不按位置删别人的 stash」「保存 stash 时其他 worktree 同时新增 stash，也不认错或删除」「清理 stash 前发现未跟踪文件挡住 HEAD 路径时，不覆盖它」「未跟踪文件扫描失败时不合入，项目根和索引不变」通过。阻挡测试构造 HEAD 跟踪 `dir/a.txt`、项目根暂存删除它并在 `dir` 位置放未跟踪普通文件，断言停止合入、未跟踪内容和暂存删除都保留、没有创建私有引用。扫描失败测试用假 git 分别返回非 0 的空输出和部分输出，断言命令非 0、错误说明扫描失败、HEAD、暂存内容和工作区状态都不变、没有私有引用和合并。

未验证：没有在真实项目里用大量二进制或子模块改动做合入；本项用普通文本文件覆盖。

### A8 未提交文件和批次分支改动重叠时合并前停下

实现：用 `git diff --name-only --no-renames release...branch` 算各批次分支相对发布分支的改动，再加上批次工作区里 `commitAll` 即将提交的改动，和项目根未提交路径求交集；有交集在提交批次工作区、stash 和合并之前抛错。

证据：`test/loop.test.ts` 的「未提交文件和批次分支改动重叠：合入前停下，发布分支和项目根都不动」通过；「批次工作区未提交改动和项目根重叠时，合入前停下且不自动提交」通过。后者项目根和批次工作区都改 `README.md`，断言发布分支 HEAD、批次分支 HEAD、两边内容和批次工作区未提交状态都没变。

未验证：没有覆盖文件/目录路径前缀碰撞（例如批次分支新增 `docs` 文件、项目根未跟踪 `docs/x`）；当前交集按同一路径判断。

### A9 第二个分支冲突时两个合并都退回

实现：冲突时先收集冲突文件，`git merge --abort`；若本次命令已经产生前序合并提交，用 `git reset --keep` 退回本次开始前的 HEAD，再恢复临时 stash。重置失败时停下，报告当前提交、stash 和项目根状态，不做强制重置。

证据：`test/loop.test.ts` 的「第二个分支冲突：两个合并都退回，无关的已跟踪和未跟踪改动保留」通过。第一个分支合并成功后第二个冲突；断言 HEAD 回到合入前、没有留下第一个 `feat: 一` 合并提交、部分暂存的 `prompt.md` 内容和索引都保留、未跟踪 `保留.txt` 保留、错误列出 `README.md`。

未验证：没有制造 `git reset --keep` 本身失败的场景；失败分支只做静态检查和错误数据保留，未用测试触发。

### A10 工具清单一致性

实现：`工具清单.md` 的「loop 开工」写明运行版不再要求干净、本批文档会搬进批次分支、开发空间不能放在运行版目录里（被忽略也不行）、开发空间必须干净（未跟踪也算）；「loop 合入」写明交集检查、已有合并状态、临时 stash 恢复和保留改动的回退。对应 JSON 字段同步更新。

证据：`node --test test/tool-manifest.test.ts` 通过（工具清单覆盖所有入口、子命令和字段一致、helper 读取方式负向检查）。`test/template.test.ts` 也通过。

未验证：无。

## 未验证与已知边界

- 未跑 e2e；未启动真实 Pi 开发会话；未在真实接入项目上跑完整批次。
- 未覆盖 `git reset --keep` 或 `git stash apply --index` 自身失败的现场；代码会停下并报告 HEAD、stash 和项目根状态，不强制重置。
- 批次文档直接放在仓库根或项目根时只搬批次文件和引用文件，不搬同目录无关文件；这是为了避免把无关改动误当批次文档。批次目录在子目录时收集目录内全部文件。
- 合入交集按同一路径判断，未覆盖文件/目录前缀碰撞；这种情况仍可能由 Git 在合并时拒绝，命令会回退并报告冲突。
- 未制造真实的 8 MiB 输出超限；用假 git 的非 0 空/部分输出覆盖失败路径，代码按退出状态处理，超时和超限同样返回非 0。
- 项目根原有未完成合并时只识别 `MERGE_HEAD`；rebase / cherry-pick 中断不在本批范围。
