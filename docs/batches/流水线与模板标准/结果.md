# 流水线与模板标准 · 结果

## 第 1 段：开工工具、worktree、方法指纹、统一启动

### 实现范围

- 新增 `bin/loop`（实现 `loop.ts`）和 `loop 开工 / 启动 / 状态 / 合入`，每个子命令支持 `--dry-run`、`--json`，开工额外支持 `--recheck`。
- 新增 `workspace.ts`：本地提交、分支校验、worktree 枚举；新增 `methods.ts`：方法指纹、`methods.json`、基线空跑缓存、候选门禁树哈希记录。
- `config.ts` 解析 `.autoreview.json` 的 `release`、`workspaces`、`localFiles`、`methods`；`project-context.ts` 导出项目数据目录和项目根哈希，供 `methods.json` 复用。
- `pipeline.ts` 写 `prompt` 的段统一生成 `bin/pi-dev` 启动命令；解析段级 `workspace` / `branch`；段完成后、启动下一步前由程序提交；新增 `--project-root` 和 `--default-workspace`，让 `loop 启动` 与 `loop 开工` 使用同一套工作区解析。流水线在启动会话前核对实际分支。
- `bin/pi-dev` 新增 `--ponytail <路径>`、`--ponytail-mode <档>`、`--no-ponytail`；权限扩展路径可用 `PERMISSION_EXTENSION` 覆盖（测试用），`PI_DEV_DRY_RUN=1` 等价于 `--dry-run`。
- `review.ts` 在候选门禁通过时把该候选的树哈希写进 `methods.json`（最近 50 个），供开工判断基线是否已有通过记录。`git.ts` 增加有效内容指纹（树内容 + 未跟踪文件覆盖），`autoreview.ts` 的完成依据核对用它兼容自动提交。
- `README.md` 补 `bin/loop` 最小用法、`pi-dev` 的 Ponytail 选项和流水线启动入口说明。
- 新增 `test/loop.test.ts`；更新 `test/pipeline.test.ts` 的两处启动命令断言（由旧的内联 pi 命令改为 `bin/pi-dev`）；`test/review.test.ts` 夹具把项目数据目录指向临时目录，避免测试写真实 `~/.pi-autoreview/`。

### A1 开工建 worktree、启动经过 `bin/pi-dev`

- 实现：`loop 开工` 检查运行版干净且停在 `release`（默认 `main`）；默认开发空间为 `../<仓库目录名>-dev分支`，也按 `.autoreview.json` 的 `workspaces` 解析；不存在则 `git worktree add`，存在则切/建批次分支。切换前先查目标分支的树，发现目标已跟踪声明的本机路径、其子路径或其父路径（含父路径被普通文件/符号链接替换）就拒绝，避免 checkout 覆盖被忽略的本地文件；切换/新建后在目标工作区核对这些路径确实被忽略且未被跟踪。自动提交统一在仓库根执行 add/reset/commit，子目录段也使用仓库根路径基准，并在提交前核对暂存列表里没有本机文件。`loop 启动 --dry-run` 让单段计划执行 `bin/pi-dev --dry-run`，输出里能看到权限扩展、`autoreview.ts`、Ponytail 和 `PONYTAIL_DEFAULT_MODE=full`，不需要 `GIT_DIR`。
- 证据：`test/loop.test.ts` A1 通过；断言了 worktree 路径、`feat/测试` 分支、`localFiles` 复制、`startCommand` 经过 `bin/pi-dev`、三条扩展加载和没有 `GIT_DIR`。另有「目标分支缺少忽略规则时拒绝复制本机文件」「切换分支前发现目标已跟踪本机文件就拒绝，原文件保留」「切换分支前检查父路径被文件或符号链接替换，拒绝并保留本机文件」「自动提交不会纳入声明的本机文件（从仓库子目录调用）」四个用例通过。
- 未验证：没有启动真实 pi 会话；测试用假 `PI_BIN`、权限扩展和 Ponytail 文件，只验证了启动命令生成和存在性检查。

### A2 指纹未变跳过方法自测

- 实现：指纹由 loop 的 `git describe --always --dirty`、`methods.paths` 下全部文件哈希、`.autoreview.json` 的 `methods` / `gate` 配置、可选 `methods.probe` 输出组成。记录写到 `~/.pi-autoreview/projects/<项目根哈希>/methods.json`；相同且没有 `--recheck` 时输出「指纹未变，跳过方法自测」，不执行 `selfCheck`，也不跑基线空跑门禁，不更新记录。
- 证据：`test/loop.test.ts` A2 通过；第二次开工后 `selfCheck` 和基线门禁的日志行数都不变。
- 未验证：没有用真实项目的长门禁测时间收益；只验证了跳过行为。

### A3 方法变化重跑自测、`--recheck`

- 实现：指纹不同或 `--recheck` 时列出变化组成部分（loop 版本、方法文件新增/内容/缺失/删除、方法配置、`methods.probe`），执行一次 `methods.selfCheck` 和基线空跑门禁，全部通过后才写记录。基线门禁按树哈希缓存；`--recheck` 会强制重跑基线门禁，便于环境变化但指纹未变时使用。
- 证据：`test/loop.test.ts` A3 通过；修改 worktree 里的方法文件并提交后，输出包含 `methods/check.sh（内容）`，`selfCheck` 和门禁各增加一次；随后 `--recheck` 再执行一次 `selfCheck` 和门禁。
- 未验证：没有测试 `methods.probe` 输出变化的真实外部命令；测试里只用了 `true`。

### A4 运行版或开发空间不干净时停下

- 实现：开工前先检查运行版分支和工作区，再检查每个已登记 worktree 的工作区；任一有未提交改动或运行版不在发布分支，命令非 0 退出，报告原因和文件，不 stash、不 reset、不丢改动。显式写 `cwd` 且指向本仓库已登记 worktree 的段同样进入脏检查和分支核对；全部段都用 `cwd` 时方法自测也会执行。`localFiles` 未被 git 忽略也直接失败。
- 证据：`test/loop.test.ts` A4 通过；运行版新增文件后开工失败并保留文件；worktree 修改 `README.md` 后开工失败，`git status` 仍显示该文件。「显式 cwd 的本仓库 worktree 同样做脏检查和方法自测」用例通过：脏时不跑自测、清干净后自测执行一次。
- 未验证：没有覆盖 worktree 已存在但不是本仓库 worktree 的场景（代码里会拒绝并提示，未单独测试）。

### A5 串行两段同 worktree 自动提交、资格保留

- 实现：流水线在每批段都取得 `done` 后、启动下一步前，对声明了 `branch` 的段执行 `git add -A` 和提交；说明为 `<类型>: <描述>`，正文为 `批次：<批次名>`、`段：<段名>`。提交不触碰状态文件，`readyEpoch` 和 `sourceInputs` 保持原值。真实会话恢复时 `completionProblem()` 原来会比较候选指纹（含 HEAD、树、未跟踪文件）；现在增加有效内容核对：用 `--full-tree` 取完整候选，未跟踪文件按快照时冻结的模式和仓库根相对路径覆盖，未跟踪文件转成已跟踪、程序提交改变 HEAD 都不会撤销资格；目录外候选改动、内容或文件模式真实变化仍会失效。
- 证据：`test/loop.test.ts` A5 通过；同一 worktree 两段完成后 `main..HEAD` 有 2 个提交，正文分别含批次名和甲/乙；甲的 `status.json` 仍是 `done` 且有 `readyEpoch`。`test/autoreview.test.ts` 新增「程序自动提交后恢复完成状态不被撤销；真实内容变化仍撤销」用例通过：已跟踪改动和未跟踪新文件一起被程序提交后，真实扩展恢复仍为 `done`；直接改候选内容则恢复为 `paused`。另有「子目录会话提交后资格保持，目录外候选改动仍撤销资格」和「自动提交后发现可执行模式变化仍撤销资格」通过；`test/git.test.ts` 的有效内容指纹用例覆盖完整树、子目录未跟踪路径和冻结模式。
- 未验证：没有在真实流水线窗口里恢复一个真实 pi 会话；扩展状态用测试夹具模拟，恢复路径调用的是真实 `autoreview.ts`。

### A6 并行两段各自 worktree 和分支

- 实现：计划解析支持顶层 `branch` 和段级 `branch` / `workspace` / `cwd`；流水线按工作区 `repoKey` 排开同仓库段，不同 worktree 可并行；每段完成后在自己的分支提交。
- 证据：`test/loop.test.ts` A6 通过；两个 worktree 分别在 `feat/甲`、`feat/乙`，各自有一个符合条件的提交，两个假段的启动时间差小于 2 秒。「启动前发现工作区分支和批次不一致就停下」用例也通过。
- 未验证：没有制造同一分支被两个 worktree 同时检出的真实冲突；开工预检会检查并拒绝。

### A7 `loop 合入` 无冲突合并、有冲突恢复

- 实现：运行版必须干净且停在 `release`；先提交批次分支 worktree 里未提交的改动，再逐个 `git merge --no-ff`。冲突时收集 `git diff --diff-filter=U` 的文件、`git merge --abort`，如果本次已经产生前序合并提交则 `git reset --hard` 回合并前 HEAD。成功和 dry-run 都不执行 push。
- 证据：`test/loop.test.ts` A7 两个子测试通过；无冲突时先提交了批次分支上的未提交文件，发布分支出现 merge 提交且本地 bare 远端的 `main` 未变化；有冲突时返回 `conflicts: ["README.md"]`，HEAD 和 `git status` 都恢复到合并前。
- 未验证：没有对真实远端仓库执行；只验证了本地 bare 远端引用未变化。多分支批次中途冲突时恢复所有已产生的合并结果，未单独覆盖。

### A8 写 `prompt` 的段统一经过 `bin/pi-dev`

- 实现：删除 `pipeline.ts` 里内联拼接 pi 参数的命令生成，`piCommand()` 现在生成 `bin/pi-dev --cwd … --model … --thinking … --tools … --name … [--ponytail … | --no-ponytail] <prompt> [-- 追加参数]`。`ponytail: false` 转成 `--no-ponytail`；段级模型、思考档位、工具、参数照常覆盖。Ponytail 未加载时的提醒仍由 `autoreview.ts` 按实际注册命令发出，本段没有改动那段逻辑。
- 证据：`test/loop.test.ts` A8 通过；`ponytail: false` 的启动命令经过 `bin/pi-dev` 且带 `--no-ponytail`，直接执行 `pi-dev --no-ponytail --dry-run` 的输出不含 Ponytail 扩展和 `PONYTAIL_DEFAULT_MODE`；段级模型覆盖出现在命令里。`test/pipeline.test.ts` 的 P11 和 Ponytail 用例已按新入口更新并通过；`test/autoreview.test.ts` 的「未加载 Ponytail」提醒用例原样通过。
- 未验证：没有用真实 Ponytail 扩展启动开发会话；只验证了命令和 dry-run 输出。

### A9 `--json` 与 `--dry-run`

- 实现：四个子命令都支持 `--json`，标准输出只有一个 JSON 对象，失败时带 `ok: false`、`error`，冲突还带 `conflicts`；`--dry-run` 只做检查和打印，不建 worktree、不切分支、不写 `methods.json`、不提交、不合并。
- 证据：`test/loop.test.ts` A9 通过；开工 dry-run 后没有 worktree、分支和方法记录；实际开工后再做启动/状态/合入 dry-run，HEAD 和方法目录 mtime 未变；运行版弄脏后开工 `--json` 输出可解析的失败对象。另有单段状态用例：单段启动传入现有 `AUTOREVIEW_PIPELINE_DIR` 和段名，写完状态后 `loop 状态` 能读到阶段、轮次、暂停原因和总结路径。
- 未验证：没有用真实 `prompt` 段跑 `loop 启动 --json` 的端到端会话（A5/A6 用假 `start` 实际跑过多段流水线并经过 `--json` 包装；单段状态用假 `start` 写状态文件）。

### 已知实现细节

- `methods.json` 复用 `project-context.ts` 现有的项目根哈希（项目根 `realpath` 的 SHA-256 前 16 位）。因此每个 worktree 按自己的项目根各有一份记录；同一运行版和它的 worktree 之间不共享这份记录。
- 基线空跑缓存只用于开工时判断「这个树之前门禁通过」，不会让任何新候选跳过门禁。
- `loop 合入` 的冲突恢复会使用 `git reset --hard` 回到本次命令开始前的 HEAD；只在该命令已经产生合并提交且随后冲突时执行，前提是运行版在开始前干净。
- 自动提交排除 `localFiles` 是兜底，不代替开工时对目标分支忽略规则的核对；目标分支缺少规则时开工直接拒绝，不自动修改忽略配置。

## 第 2 段：项目方法分层、越界检查、权限检查

### 实现范围

- 新增 `method-env.ts`：统一生成本段交给项目方法的 `AUTOREVIEW_BASE_REV`、`AUTOREVIEW_BATCH_FILE`、`AUTOREVIEW_STAGE`；没有批次文件时不设置批次变量。
- `pipeline.ts` 的 `Plan` 记录批次文件绝对路径，段的启动脚本把 `AUTOREVIEW_BATCH_FILE`、`AUTOREVIEW_STAGE` 交给 `bin/pi-dev` 会话；流水线的准备检查、联调准备、整合验收也带上同一套方法环境变量。`loop` 的单段启动同样带批次文件和段名。
- 新增 `scope.ts`：解析批次段 `scope.allow` / `scope.deny`，按项目根相对路径前缀匹配；`deny` 优先。`review.ts` 在门禁之前用开工依据（`state.baseline`）对比改动文件与未跟踪文件，越界时走现有门禁返修路径。
- 新增 `permission-check.ts`，由 `bin/pi-dev` 在真正启动前调用。检查用实际 Pi 权限扩展模拟 edit、write、bash 三个工具调用；不执行工具、不调用模型、不改用户配置。检查结果按第 1 段的方法指纹记在 `methods.json` 的独立字段里，指纹不变时跳过。
- `preparation.ts`、`acceptance.ts`、`review.ts`、`autoreview.ts` 的命令执行支持显式环境变量；自动验收的被测系统启动、重置、释放、验收命令都拿到同一套变量。
- `README.md` 补 `scope`、三个环境变量和启动入口权限检查的最小说明；未改项目模板和工具清单（留给第 3 段）。

### A1 单段和流水线都拿到三个环境变量

- 实现：`loop 启动` 单段把 `AUTOREVIEW_BATCH_FILE`、`AUTOREVIEW_STAGE` 放进会话环境；多段由 `stageScript` 把批次文件绝对路径和段名导出后再启动 `bin/pi-dev`。门禁执行时由 `methodEnv` 用 `state.baseline` 生成 `AUTOREVIEW_BASE_REV`，覆盖启动环境中可能存在的旧值。
- 证据：`test/review.test.ts` 新增「项目方法三个环境变量：准备检查和门禁都拿到本段开工依据、批次文件和段名」通过；预置了错误的 `AUTOREVIEW_BASE_REV=stale-value`，准备检查和门禁两行都得到真实的开工依据、批次绝对路径和段名。`test/pipeline.test.ts` 新增「批次文件与 scope」通过，断言 `plan.file` 是绝对路径且 `stageScript` 带 `AUTOREVIEW_BATCH_FILE`。
- 未验证：没有用真实 Pi 会话在单段和两段流水线里各交付一次；流水线部分只验证了启动脚本生成和单段门禁执行路径。

### A2 准备、自动验收启动/重置和验收命令拿到同一套变量

- 实现：`runPreparation` 的检查、恢复、方法修复命令都接收 `deps.env`；`runAcceptanceStage` 的被测系统启动、重置、资源释放、验收方命令共用 `deps.env`；Pi 扩展的独立验收命令（`--autoreview-accept-cmd`）也带同样的变量。流水线准备和整合验收分别用当时的开工 HEAD 作为 `AUTOREVIEW_BASE_REV`。
- 证据：`test/acceptance.test.ts` 新增「项目方法三个环境变量：启动、重置、验收命令都拿到同一份」通过，三处都读到 `base-rev|/tmp/批次.json|甲`。`test/review.test.ts` 的准备检查与门禁用例通过，两处拿到同一份变量。
- 未验证：没有在真实自动验收环境里用项目方法读取这三个变量完成一次业务验收；流水线整合验收只覆盖单段计划的段名，多段计划没有发明一个整合段名。

### A3 allow 外的文件越界打回

- 实现：`parsePlan` 校验并保存段级 `scope`；`review.ts` 的 `scopeStep` 在门禁前对比检查起点以来的受跟踪改动和未跟踪文件。未跟踪文件按开工快照的哈希和模式判断：只有确实没变的才豁免，内容/模式变化、删除或转为受跟踪都进入检查。把不在 `allow` 里的文件按 `GateRecord` 失败处理：不执行门禁、不评审，走 `buildGateRepairMessage`，`state.repairs += 1`、`awaitingRepair = true`，不新增暂停点。
- 证据：`test/review.test.ts` 新增「A3/A4 越界检查」通过；`scope.allow: ["src/"]` 时修改 `src/a.ts` 并新建 `docs-x.md`，门禁调用 0 次，返修消息含 `docs-x.md`，返修次数为 1，状态仍是 `idle`。
- 未验证：没有在真实 Pi 会话里观察返修消息进入原会话；没有覆盖“先提交再越界”的改动，当前检查对已提交和未提交改动都按 `git diff <baseline>` 统计。

### A4 deny 命中打回；没写 scope 不检查

- 实现：`scope.deny` 优先于 `allow`；段没写 `scope` 时 `scopeStep` 直接返回，不调用越界检查，门禁和后续流程保持原顺序。
- 证据：同一测试里 `scope.deny: ["src/secret/"]` 修改 `src/secret/k.ts` 被打回且门禁未执行；没写 `scope` 时门禁执行 1 次并正常完成。
- 未验证：没有覆盖嵌套 deny 与 allow 同时命中时的真实业务场景；只验证了 deny 优先的基本路径。

### A5 启动入口权限检查按方法指纹跳过

- 实现：`bin/pi-dev` 在非 `--dry-run` 启动前调用 `permission-check.ts`。检查优先加载实际 Pi 权限扩展并模拟 bash/edit/write；加载器不可用时退化为读取全局与项目权限配置的保守判断。失败时不写记录、直接退出并说明原因；通过后把当前方法指纹写进 `methods.json` 的 `permissionFingerprint`，下次指纹相同就跳过。检查使用临时 agent 目录，不改用户配置。

### 方案与实现的差异/补充

- `loop 开工` 的方法自测失败以抛错形式返回（非 0、错误文本带输出尾部），不是 `--json` 里单独的方法失败对象；工具清单按实际行为写。
- `localFiles` 指向目录时，如果目标 worktree 里该目录还不存在，`git check-ignore` 对带尾斜杠的目录规则可能判定失败；模板改用具体文件路径（`deploy/acceptance/start.sh` 等），避免把「忽略规则已提交」误报成「没有忽略」。这不是本段改代码，记录给迁移时参考。
- 直接执行 `pipeline.ts` 且不传 `--default-workspace` 时，段的默认目录仍是计划文件目录；`loop 启动` 会传 `--default-workspace dev分支`。工具清单分别写明两个默认值。
- `e2e.acceptance` 复用 `parseAcceptanceConfig`，字段表用交叉引用而不是重复 20 多行；一致性测试把 `e2e.acceptance` 作为批次字段，`acceptance.*` 作为 `.autoreview.json` 字段覆盖。
- 项目模板的 `localFiles` 用具体文件而不是目录，原因见上；方案只写「列出只在本机存在、不进仓库的文件」，没有规定目录写法。
