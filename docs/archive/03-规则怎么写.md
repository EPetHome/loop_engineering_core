# 03 规则怎么写

规则是循环唯一的方向盘。启动之后拍板人不再介入，所以规则写成什么样，循环就跑成什么样。

用户的要求：

> 这里要求我们尽可能地提供一份明确的规则，包括目标、边界、验收标准、什么时候算停、什么叫完成之类的，这些都得想清楚。全部要落到规范上。

## 1. 规则要写清的内容

每个单元一份，缺一项不启动。

| 项 | 回答什么问题 | 写不清会怎样 |
|---|---|---|
| 目标 | 这个单元要做成什么 | 成员各自理解，做偏 |
| 边界 | 能改哪些文件、不能碰什么、明确不做什么 | 顺手改了不该改的，或和别的单元撞车 |
| 完成标准 | 做完的样子，逐条能检查，每条带编号 | 没法判过没过 |
| 怎么验收 | 每一条谁来判、看什么证据、怎样算过 | 评审方和开发方对「过」的理解不一样 |
| 什么时候停 | 达标就停；来回几次、最长多久也要停；多久没动静算卡住 | 一直转，或卡死没人知道 |
| 停下交什么 | 结果的固定格式 | 停了却拿不到能读的结果 |
| 没说清的怎么办 | 默认：从严处理、记进结果、继续做其余的 | 成员自己定，或停下等人 |
| 工作区里谁能写哪 | 见 [04](04-工作区与防篡改.md) | 互相改文件 |

多个单元时，再加一份：

| 项 | 回答什么问题 |
|---|---|
| 任务安排 | 有哪些单元；谁和谁并行；谁等谁达标后才启动 |
| 共用资源怎么分 | 运行编号、端口、目录等，每个单元用哪一段 |

## 2. 「完成」要分层写

实战里的教训：把几层完成混成一句话，是标准自己打架的根源。

| 层 | 含义 | 谁判 |
|---|---|---|
| 单条标准 | 这一条满足了 | 程序，或评审方 |
| 单元达标 | 这个单元的每一条都满足 | 评审方给结论，调度程序核对 |
| 整体完成 | 所有单元都达标 | 编排程序汇总 |
| 验收通过 | 结果被认可，写进基线 | 拍板人。循环不管这一层 |

还要写明哪些情况**不算**完成。实战里出现过的：

- 进程正常退出，不等于做对了。
- 开发方自己说过了，不等于过了。
- 换了一批更容易的用例通过，不等于原标准通过。

## 3. 标准以什么形式呈现，成员才会遵守

三种形式，可靠程度不同。凡是「必须遵守」的，尽量从文字搬到程序和表格里。

| 形式 | 可靠程度 | 用在哪 |
|---|---|---|
| 程序门禁：不达标，程序就不放行 | 最可靠 | 能用程序判断的：文件是否存在、数量、格式、指纹是否一致、次数是否超限 |
| 逐条填的表：每条标准一行，必须填通过或不通过，并写证据位置 | 较可靠 | 需要人判断的：内容对不对、行为合不合规 |
| 文字规则：一句话 | 最不可靠 | 实在搬不动的。要短，要写原因 |

实战证据：

- 程序拒绝的，没有一个成员绕得过去；被拒后成员都老实停下、如实交代。
- 评审方和开发方都按验收表逐格填了。
- 文字写了「说明不超过 8 行」，成员照样写 9 行；写了「逐份写明次数」，照样漏。

每条标准都要问一句：**它被违反了，谁能发现？** 答不上来，这条标准等于没有。

## 4. 让标准「时刻」起作用的五条

成员开工时读一遍是不够的，一个会话可能有几十轮，早就读远了。

```text
标准（唯一出处，带编号）
   │
   ├─▶ 开发方的提示词：只引用编号，不另写一遍
   ├─▶ 开发方的交付：按编号逐条自评，缺一行算没交
   ├─▶ 评审方的结论：按同一批编号逐条独立判
   ├─▶ 调度程序：核对每个编号都有结论，才认这次交接
   └─▶ 循环停止时的结果：就是这张逐条填好的表
```

| # | 做法 | 为什么 |
|---|---|---|
| 1 | 标准只有一个出处，别处只引用编号 | 同一条标准在三个地方各写一遍，写得不一样，标准就自己打架了 |
| 2 | 每个成员只看到自己该看的 | 把只给调度方用的命令发给了开发方，开发方就会拿来用 |
| 3 | 程序拒绝时，报错里写清下一步该怎么做 | 报错说清楚了，成员每次都照做 |
| 4 | 和工具自带提示冲突的地方要点名否定 | 工具自己会建议另一种做法，不点名，成员就听工具的 |
| 5 | 标准人读一份、程序读一份 | 程序那份用来自动核对「每条都有结论」 |

## 5. 启动前查一遍规则

这一步用来替代「中途拍板」。查什么：

| 查 | 例子 |
|---|---|
| 有没有自相矛盾 | 一处允许「没做完也可以如实保存」，另一处的验收表却要求每项都有完成记录 |
| 每条标准能不能判 | 「质量要好」没法判；「不超过 8 行」能判 |
| 计数的口径对不对 | 把「某个程序被调用了几次」当成「返修了几轮」，两者不是一回事 |
| 边界有没有重叠 | 两个并行单元都能改同一个文件 |
| 停止条件全不全 | 有没有上限；卡住了多久算停 |
| 没说清时的默认处理写了没有 | — |

谁来查：拍板人自己过一遍；大的任务可以让评审方的模型先只审规则、不干活，指出矛盾后由拍板人修改。

说实话的部分：纸面上看得出的矛盾，这一步能挡住；真跑才暴露的那种挡不住。所以兜底必须是「从严、记录、继续」，而不是指望规则完美。

## 6. 一个最小单元的规则长什么样（示意）

下面只是示意，不是固定模板。字段可以按任务增减，四条底线不能少。

```markdown
# 单元：给导出功能加上进度提示

## 目标
导出超过 3 秒时，界面显示进度；失败时显示原因。

## 边界
- 能改：src/export/ 下的文件
- 不能碰：其他目录；任何配置文件
- 不做：重试功能、导出格式调整

## 完成标准与验收
| 编号 | 标准 | 怎么判 | 谁判 |
|---|---|---|---|
| S1 | 现有测试全部通过 | 运行测试命令，退出码为 0 | 程序 |
| S2 | 新增进度提示的测试，覆盖「超过 3 秒」和「失败」两种情况 | 读测试代码和运行输出 | 评审方 |
| S3 | 只改了允许改的文件 | 对比改动清单 | 程序 |

## 什么时候停
- S1—S3 全部通过：停，达标。
- 开发和评审最多来回 2 次；单次会话最长 30 分钟。
- 20 分钟没有任何动静：停，推不动。

## 停下交什么
一句话结论；S1—S3 逐条的结论和证据位置；没解决的；规则缺口（没有就写无）。

## 没说清的怎么办
从严处理、记进「规则缺口」、继续做其余的。
```
