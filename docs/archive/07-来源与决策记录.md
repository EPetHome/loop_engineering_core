# 07 来源与决策记录

这套设计不是凭空想的，来自一次实战和随后的复盘。这里记下：实战里发生了什么、暴露了什么问题、每个设计决定出自哪句话。

## 1. 实战：Promax 项目的一次调度循环试行

背景：Promax 项目的一个任务要求「7 个场景带独立检查各跑 1 次，流程全部走通」。2026-09-30 试行了一个调度脚本，让开发方和评审方自动来回。

当时的做法：

```text
A 组：开发方修流程漏洞 ⇄ 评审方审（最多 3 次）
        │ 通过
        ▼
B 组：开发方把 7 个场景整批跑一遍 → 评审方全量复核
        ├─ 通过 → 完成
        ├─ 返修 → 退回 A 组（只许 1 次）
        └─ 停止 → 等用户
```

时间线（本机时间）：

| 时间 | 发生了什么 |
|---|---|
| 09-30 13:11 | 用户启动 |
| 13:11—16:08 | A 组来回 3 次（返修、返修、通过），用满上限 |
| 16:08—16:29 | B 组开发方跑了 20 分钟后自己结束了会话，没交付；调度脚本停止，没有任何通知 |
| 约 23:00 | 用户来问进度，才发现已停了六个半小时 |
| 当晚 | 查清原因并补上等待办法 |
| 23:31 | 用户续跑 |
| 10-01 00:08 | 7 个场景跑完 |
| 01:08 | 开发方交付，自查 5/7 |
| 01:16—01:35 | 评审方全量复核，结论「停止」：按现有标准 5/7，且标准本身有两处自相矛盾，要用户先定口径 |

结果：从 3/7 推进到 5/7，没有达到 7/7。

## 2. 暴露的四个结构性问题

| # | 问题 | 具体表现 |
|---|---|---|
| 1 | 真实反馈来得太晚，规则的缺口两头都漏 | A 组三轮验证的都是离线用例，而用例和评审标准出自同一份规格。规格本身的缺口，开发方和评审方都不会质疑。启动约 12 小时后才暴露 |
| 2 | 出口很难收敛 | 要求 7 个场景在同一批里一次全过，每个只跑 1 次，修一处就全部重跑。两批的失败原因各不相同，像打地鼠 |
| 3 | 停了没人知道，卡住也发现不了 | 16:29 的停止没有任何通知；当晚实测时还有一次成员启动后 11 分钟毫无动静，而调度脚本只有「单次最长 240 分钟」一道保险 |
| 4 | 停止之后没有接着走的路 | 评审方判「停止」后，原命令重跑只会再停一次；「一轮」怎么算也说不清 |

次要问题：试运行用的是玩具场景，没覆盖真实情形；开发方和评审方的取证工作重复；A 组名额刚好在最后一次用完。

## 3. 那一批失败的四个根因

| # | 根因 | 教训 |
|---|---|---|
| R1 | 检查方手写整份结构化草稿，引文里的引号漏了转义，整份就不合法 | 要求成员手写严格语法是不可靠的 |
| R2 | 修稿的成员为了「保险」，把本来正确的原句也改了，原句不再逐字 | 修稿指令只说「只修格式」不够，要写明什么不许动 |
| R3 | 程序把「预检被调用的次数」当成「返修轮数」，最多 2 次 | 用容易量的数代替真正想量的事，会把流程卡死 |
| R4 | 写作成员看得到也跑得了只该调度方用的检查命令 | 每个成员只该看到自己的部分 |

R3 是规格作者（陪用户讨论的模型）写规格时留下的缺口，不是开发方实现错了。这直接引出「谁来查规则」这个问题。

## 4. 从教训到设计

| 教训 | 设计里的对应 |
|---|---|
| 标准只有一句话，自己打架 | 底线 1：完成标准必须能逐条检查；标准只有一个出处 |
| 规格缺口两头都漏 | 启动前查一遍规则；成员可以在结果里记规则缺口 |
| 停了却什么都没交 | 底线 4：任何停止都要交结果；成员交不出时程序代写 |
| 停了没人知道 | 停止即通知；没动静也算停；状态随时可查 |
| 文字规则被忽略，程序门禁管用 | 标准的三种呈现形式，优先程序门禁和逐条填表 |
| 成员用了不该它用的命令 | 每个成员只看到自己的部分 |
| 一处卡住，整批搭进去 | 单元要小；简单和复杂用同一套单元 |
| 整批一次全过难收敛 | 「累计达标加护栏」作为可选做法 |
| 评审方把正式记录写进了项目文档 | 循环的文档只落工作区；基线和正式记录由拍板人写 |
| 第一稿设计写成了流程制度 | 骨架收缩到最小；其余都是可选做法 |

## 5. 决策记录（2026-10-01，按讨论顺序）

| # | 决定 | 用户原话（节选） |
|---|---|---|
| 1 | 循环要做成所有任务通用的，不只服务一个任务 | 「严格来说我讨论的不是本次任务的 loop，而是一个可以复用到所有任务的 loop。」 |
| 2 | 第一稿太死，骨架收缩 | 「是不是写太死了，我的本意是建立一个循环，有开发、有检查，制定标准控制完成标准、验收、什么时候停等情况，循环停止 == 给结果。」 |
| 3 | 四条底线成立 | 「认同。」 |
| 4 | 标准要以能被遵守的形式呈现；人读、程序读各一份 | 「我们制定的标准规定要以什么形式呈现，各个 agent 才会时刻遵守」「认同。」 |
| 5 | 用户和陪他讨论的模型是同一个拍板人角色 | 「我和你 cc 都是拍板人角色，只是我去落下最后的执行指令到控制台。」 |
| 6 | 模型不守运行 | 「是不希望你守着」（因为耗费 token） |
| 7 | 拍板人在循环之外，不承担循环里的责任；结果要随时能拿到；基线由拍板人更新 | 「你把自己想成是我就行了，我和你是位于循环之外……只需要保证我们随时打开一个会话，查看结果就能拿到。我们在分析结果，我们自己去更新基线。」 |
| 8 | 循环的文档只落在循环范围内；基线不属于这个范围 | 「循环相关的一切都只落文档到他们循环这个范围内，基线不属于这个范围。」 |
| 9 | 规则要写全：目标、边界、验收标准、何时停、什么叫完成 | 「这些都得想清楚。全部要落到规范上。」 |
| 10 | 保留工作区；规则不得被成员修改 | 「工作区这个概念也得继续保留着，因为是所有成员交接文档的地方。规则也应该存在，但是不得被其他员工所修改。」 |
| 11 | 防篡改做到三层即可；评审结论只留工作区，正式记录由拍板人写 | 「我同意我同意。」 |
| 12 | 支持并发和串行混合；用户只启动一次，之后一起验收 | 「我们讨论好哪些可以并行，哪些要串行，然后制定好规则……我在这个过程中只要负责启动就行了，剩下的就是我和你一起验收。」 |
| 13 | 去掉「中途拍板」；规则没说清的从严处理、记下来、继续 | 用户问：「为什么需要我们来拍板呢？」 |
| 14 | 同一套机制既能做简单闭环，也能做复杂闭环 | 「对小问题可以做到简单的开发、评审、交付。这么的一个简单闭环，以及具备一些并发串行的复杂闭环。」「你的理解是正确的。」 |
| 15 | 收口，落成文档；整体叫 Loop Engineering | 「整个开发过程是全自动的……我只负责启动与验收，中间的开发、代码自测这些串行运行全部在循环内部。成我们自己的一套定制的 Loop Engineering。」 |
| 16 | 要有一份任何模型都能照着用的使用手册 | 「以后我用到其他的模型，那个模型读完手册应该也能够运行这一套程序。」 |

讨论过但没采纳的：

| 方案 | 为什么没采纳 |
|---|---|
| 五步固定流程加十四栏任务卡 | 写太死；把一个任务的形状当成了通用骨架 |
| 单列「主理人」角色 | 用户纠正：模型和用户是同一个拍板人角色 |
| 模型用后台守望程序盯着循环、被事件唤醒 | 用户不希望模型守着 |
| 「等拍板」作为一种停止，裁决后从停下处接着走 | 违背「只负责启动和验收」；改为缺口留到验收处理 |
| 多个单元由用户逐个手动启动 | 违背「只启动一次」；改为编排程序自动启动 |
| 便宜模型做的观察员（Sidecar） | 发现停止是程序的事；讲成人话可由评审方按格式写。暂不做，见 [08](08-计划与未定事项.md) |

## 6. Promax 那个任务自己的口径（属于该任务，不属于通用循环）

供参考，说明「可选做法」在一个具体任务里是怎么定的：

- 出口：同一份冻结代码下 7 个场景累计都走通即可；没过的最多重跑 1 次；失败记录保留；同一原因出现两次必须回去修；代码一改全部重跑。
- 检查到上限没做完、如实保存：合规，但该场景不算走通。
- 返修按真实发生的次数算，重复调用检查程序和成员自查不占名额。
- 草稿只是格式写错时，单独给 1 次改格式的机会。
