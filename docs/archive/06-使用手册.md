# 06 使用手册

首次接手先读根目录 [AGENTS.md](../../AGENTS.md) 的短流程，再处理本次任务；不需要先通读本手册。这份手册解释具体操作，遇到问题时只查相关小节。背景和历史也只在需要时查。

## 0. 先知道三件事

1. **你和用户是同一个角色：拍板人。** 你们都在循环之外。用户的原话是「你把自己想成是我就行了」。
2. **你不在循环里干活，也不守着循环。** 你的工作在启动之前和停止之后。
3. **引擎已经有了**（当前安装以根 README 为准；本手册最初写在引擎到位之前）。日常准备按下文做；规则、必要检查、启动及验收合并的具体操作见 [10-来龙去脉与接手手册](10-来龙去脉与接手手册.md) 第 5 节，历史试验不是每次启动的前置要求。

## 1. 整件事的样子

```text
你和用户讨论 ──▶ 复用/填写规则 ──▶ 必要检查、唯一启动指令 ──▶ 用户启动一次
                                                              │
                                              （循环自动运行，你们都不在）
                                                              │
你和用户验收 ◀── 读结果 ◀── 循环停止，结果在工作区 ◀──────────┘
      │
      ▼
你们更新项目基线
```

循环里面只有一件事反复发生：开发方做，评审方查，不达标带着修复清单再做，直到达标或到上限。**循环一停，必须有结果。** 详见 [02-循环结构](02-循环结构.md)。

## 2. 你的工作，一步一步

日常顺序：**目标/授权范围/完成标准与预算 → 复用合适的已有规则、模型工具配置和测试入口 → 必要检查 → 唯一启动命令**。以下步骤可合并，不是小任务的固定大清单。

### 第一步：和用户把需求说清

- 用户头脑风暴时，你帮着把话落到「要做成什么」。
- 缺关键事实就问，不要猜。关键业务歧义须在启动前解决；已授权的常规实现选择由执行者决定，不逐项等待确认。
- 先明确目标、授权/禁止范围、可验收的完成标准与预算。需求没说清，规则写得再细也是错的。

### 第二步：拆成单元，定先后

- 使用能独立验收的合理工作单元，不是越小越好。
- 问自己：这两个单元会不会改同一批文件？会，就串行或合并；不会，才能并行；有协作接口时安排集成单元。
- 多单元任务把先后关系简要说明；已授权范围内的常规拆分由执行者决定。
- 小问题就是一个单元，不要硬拆。

### 第三步：写规则

优先复用合适的已有规则与测试入口；新增门禁只补足缺口，必要时确认命令、测试发现范围和失败原因，不要求先实现一份完整成功解。每个单元的内容见 [03-规则怎么写](03-规则怎么写.md) 第 1 节。写的时候守住这几条：

| 要做 | 不要做 |
|---|---|
| 每条完成标准带编号，写明怎么判、谁判 | 写「质量要好」这类没法判的话 |
| 能用程序判的，写成程序检查 | 指望成员自觉遵守一句文字 |
| 标准只写在一个地方 | 在提示词里把标准再抄一遍 |
| 写明上限：最多来回几次、最长多久、多久没动静算卡住 | 不写上限 |
| 写明「没说清的从严处理、记下来、继续」 | 留一个「遇到问题找用户」的口子 |
| 列明能改哪些文件 | 只写「改相关文件」 |

写完后**查一遍**（[03](03-规则怎么写.md) 第 5 节的清单）。你自己写的规则，你自己最容易看不出毛病，所以：

- 把规则给用户过目，用户确认后才算定。
- 大的任务，建议让评审方的模型先只审规则、不干活。

### 第四步：复用配置、做必要检查，准备唯一启动指令

- 复用已确认的模型、工具、权限与预算配置，检查本任务需要的路径和边界。成员提示由引擎依据本次 context 生成，只补任务特有的 notes，不重复手写角色启动协议或抄写标准。
- `validate` 核对规则结构、依赖与已声明的并行边界，不运行门禁或模型；`doctor` 检查 Python/POSIX、源码和成员程序存在性，可选查 CLI 版本。它们不验证凭据、远程模型/额度、业务可行性或所有运行冲突；未验证的如实记录。
- 常规任务不先做临时成功解，不把假成员完整演练、全引擎回归或真实模型试调用列为启动条件。完整引擎回归和适配器演练用于安装、升级、相关接口或安全边界变化后的针对性验证；高风险/可行性验证只查具体疑点，付费调用须另有授权。
- 查看相关数据根目录的全部运行，必要时核对进程、实际引擎路径和本任务涉及的资源；不能只凭 latest 终态判断全部空闲。
- 在对话里给用户唯一启动命令，并记入本任务说明。日常入口为 `cd /Users/Admin/Desktop/loop && /opt/homebrew/bin/python3.12 run_loop.py "tasks/<任务>/task.json" --root /Users/Admin/Desktop/loop/loop-data`。默认只生成 `交付结果.md` 和 `delivery-overview.json`，不调用简报模型、不扫描全部日志判断长度；需要 AI 简报时在同一命令末尾追加 `--brief`，完整终态且未取消时调用一次，短日志也生成，失败保留原结果，返回原引擎退出码。
- 按项目授权在基线留一行指针：哪个循环、工作区在哪、结果看哪个文件。这样下一个会话能找到。

### 第五步：交给用户启动

- 把启动指令和「启动后会发生什么、大概多久、停了你会看到什么」告诉用户。
- 然后你的工作就停了。**不要守着，不要轮询，不要设后台任务把自己唤醒。**

### 第六步：用户回来找你时，读结果

- 先看状态和结果文件，再说话。不要凭记忆说。
- 结果里看四样：停止类型、标准逐条的结论、证据位置、规则缺口栏。
- 汇报时结论先行，分清三种话：
  - **观察**：记录里直接看到的。
  - **判断**：你的推断，要说明是推断。
  - **不知道**：没查到的，直接说不知道。
- 开发方的自评不是结论，评审方的结论才是。评审方的结论你也不用逐条重查，但拿不准时回工作区看原始记录。

### 第七步：和用户一起验收

| 停止类型 | 你和用户做什么 |
|---|---|
| 达标 | 一起看结果，用户认可后，你们更新基线 |
| 未达标，规则没问题 | 分析卡在哪。可选：加次数重启、把单元拆小、换做法 |
| 未达标，规则有缺口 | 看缺口栏；和用户定怎么改；改规则，版本加一；重新启动 |
| 推不动 | 查日志找原因（环境、工具、成员没交付）；修好后重新启动 |

过不过、认不认，由用户说了算。你给建议，不替用户宣布。

### 第八步：更新基线

- 基线只由你和用户更新，循环里的成员不碰。
- 只写验收认可的内容。评审方的结论留在工作区，要不要写成正式记录由你们定。
- 没验证的写「未验证」，不要写成完成。

## 3. 你不能做的事

| 不能 | 为什么 |
|---|---|
| 在循环运行期间介入、守着、轮询 | 用户明确不要，耗费 token；也违背「里外分开」 |
| 在循环运行期间改规则 | 规则只能在停下之后改 |
| 替用户启动 | 启动是用户的动作 |
| 替用户宣布通过 | 验收的最终决定在用户 |
| 让成员改规则，或默许成员自己变通 | 那等于成员改标准 |
| 把「进程正常结束」「开发方说过了」当成达标 | 都只是线索 |
| 为了显示通过而降低标准 | — |
| 缺事实时猜 | 用户的要求：不知道就问，禁止猜 |

## 4. 最容易犯的错（都是实战里真犯过的）

| 错 | 后果 | 怎么避免 |
|---|---|---|
| 完成标准只有一句话 | 跑完才发现标准自己打架 | 逐条编号，每条写明怎么判 |
| 同一条标准在几个地方各写一遍 | 写得不一样，成员无所适从 | 一个出处，别处引用编号 |
| 用一个容易量的数代替真正想量的事 | 例如拿「某程序被调用几次」当「返修几轮」，重复调用就把名额耗光 | 按真实事件计数 |
| 把只给一个角色的命令发给了所有成员 | 别的成员拿来用，把流程卡死 | 每个成员只看自己的部分 |
| 必要的接口/风险试运行只测了玩具场景 | 真跑时才暴露问题 | 针对具体疑点检查等待、超时等真实边界；不是每个日常任务都完整演练 |
| 一个单元塞太多东西 | 一处卡住，整批几个小时搭进去 | 拆小 |
| 停了没人知道 | 空转很久 | 停止必须通知；没动静也算停 |
| 把流程写得太死 | 小任务填表比干活还累 | 骨架只有「开发 → 评审 → 停止交结果」，其余按需 |
| 相信自己写的规则没问题 | 开发方和评审方都照着有缺口的规则做，两头都查不出 | 用户确认；启动前查一遍；允许成员在结果里记规则缺口 |

## 5. 成员等待方式的一个技术坑

如果成员是以「非交互、一次性」的方式启动的（一条命令跑完就退出），那么**成员一旦发出一条不带工具调用的回复，会话就结束了**。它起的后台任务会被一起杀掉。

所以：成员需要等某件事跑完时，不能「结束这一轮、等通知」，必须在前台阻塞等到结束。通用角色提示由引擎依据 context 生成；有任务特有的等待方式时才在 notes 补充，不要求每次重写角色协议。

实战里因为漏了这一条，一个成员跑了 20 分钟就退出了，什么都没交。

## 6. 怎么对用户说话

- 结论放最前面，待用户决定的事放最前面。
- 两个以上对象的对比用表格；流程和结构用文本图。
- 用户同时在跑好几条线，容易丢进度。每次实质回复都让用户一眼知道：现在在哪、这一步在做什么、下一步是什么。
- 用户纠正过的事要记住，不要让他说第二遍。

## 7. 遇到这份手册没写的情况

按这个顺序判断：

1. 这件事在循环之内还是之外？之内的，交给规则和循环；之外的，是你和用户的事。
2. 它会不会让成员改标准，或让你在运行期间介入？会，就不做。
3. 它会不会让「停止却没有结果」成为可能？会，就不做。
4. 还拿不准，问用户。
