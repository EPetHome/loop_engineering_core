# 02 循环结构

三张图：最小闭环（单元）、复合闭环（多个单元）、全景。

## 1. 单元：最小的闭环

一个单元 = 一个任务 = 一个工作区 = 一份规则 = 一个结果。

```text
        规则（成员只读）
        完成标准 ｜ 怎么验收 ｜ 何时停 ｜ 停下交什么
                      │
                      ▼
   开发 ──交付──▶ 评审 ──▶ 达标？ ──是──▶ 停：交结果（达标）
     ▲                       │否
     │                       ▼
     └──── 修复清单 ◀── 还有次数？ ──否──▶ 停：交结果（未达标，卡在哪）

   中途环境坏了、成员没交付、太久没动静 ──▶ 停：程序代写结果（推不动）
   遇到规则没说清的 ──▶ 从严处理、记进结果、继续做其余的
```

每一步的含义：

| 步 | 谁 | 做什么 |
|---|---|---|
| 开发 | 开发方 | 按规则做；做完自测；按标准的编号逐条自评；写交付 |
| 评审 | 评审方 | 从原始证据独立判每一条标准；给出「通过」或「返修」；返修必须带修复清单 |
| 达标？ | 调度程序 | 读评审结论；核对每条标准都有结论 |
| 还有次数？ | 调度程序 | 对照规则里的上限计数 |
| 停 | 调度程序 | 写结果，通知拍板人 |

小问题就用这一个单元：规则只有几行，来回次数定得很少，一次开发、一次评审、交付结果。

## 2. 复合：多个单元按安排排起来

```text
              ┌─▶ 单元 A ─┐
   启动 ──────┤           ├──（都达标）──▶ 单元 C ──▶ 单元 D ──▶ 总结果
              └─▶ 单元 B ─┘

   A、B 并行；C 等 A、B 都达标；D 等 C
   某个单元没达标：依赖它的不启动，不相干的照常跑
```

- 每个方框里面都是第 1 节那张图，一模一样。
- 编排程序只做一件事：看各单元的状态，启动条件满足就启动下一个。
- 「谁和谁并行、谁等谁」这张任务安排，是规则的一部分，由拍板人在启动前定好。
- 用户仍然只启动一次。

## 3. 全景

```text
┌──────────── 循环之外：拍板人 ────────────┐
│ 讨论 → 需求 → 方案 → 规则 + 提示词         │
│                    （用户启动一次）        │
│ 全部停下后：看总结果 → 验收 → 更新基线      │
└────────┬───────────────────▲─────────────┘
         │ 放入规则            │ 只读结果
         ▼                    │
┌──────────── 循环之内 ──────────────────────┐
│ 编排程序：按任务安排启动各单元               │
│ 每个单元：开发 ⇄ 评审，停止即交结果          │
│ 工作区：每个单元一个，文档全落在里面          │
│ 规则：成员只读，每次交接核对指纹              │
└────────────────────────────────────────────┘

基线在循环之外，循环里谁都不碰
```

## 4. 停止只有三种，都是终点

| 停止 | 什么时候 | 结果里写什么 | 拍板人验收时做什么 |
|---|---|---|---|
| 达标 | 评审方逐条都判通过 | 标准逐条的结论和证据位置 | 验收；更新基线 |
| 未达标 | 来回次数或时间到上限；或规则缺口大到不可能达标，提前收工 | 卡在哪几条、试过什么、规则缺口有哪些 | 看原因；改规则后重新启动 |
| 推不动 | 环境坏了、某一方没交付、太久没动静、规则被改 | 停在哪一步、最后的动静、日志在哪 | 修好后重新启动，从断点接着走 |

「推不动」时成员自己交不出结果，由调度程序代写一份最小结果。这样不会出现「停了却什么都没有」。

**没有「等拍板」这种停止。** 早期设计里有过，后来去掉了，理由见下一节。

## 5. 规则没说清的时候

成员遇到规则没覆盖、或规则自相矛盾的情况，只有两条路：自己定，或者停下来问拍板人。

- 自己定：等于成员改了标准，不允许。
- 停下来问：用户就不再是「只负责启动和验收」了，违背愿景。

所以规定第三条路：

```text
成员遇到规则没说清的事
      │
      ▼
按最严的理解处理（拿不准算没过；拿不准就不做）
      │
      ▼
记进结果的「规则缺口」一栏：哪一条、卡在哪、有哪几种理解
      │
      ▼
继续做不受影响的部分
```

只有一种情况会提前收工：缺口大到后面怎么做都不可能达标，再跑只是白耗。这时按「未达标」停止，结果里写明原因。

代价要说清楚：一个五分钟就能裁决的小缺口，可能让一个单元白跑到上限。这是用机器时间换拍板人不被打扰。把单元拆小，可以把这个代价压低。

## 6. 简单闭环和复杂闭环的差别

| | 简单闭环 | 复杂闭环 |
|---|---|---|
| 单元个数 | 1 个 | 多个，有并行有串行 |
| 规则多大 | 几行：做成什么样、怎么算过、最多来回几次 | 一份任务安排，外加每个单元各自的规则 |
| 其余 | 相同 | 相同 |

相同的部分：四条底线、三种停止、工作区、规则只读、停止即交结果。

做的过程中发现的小毛病，本来就在单元里消化：评审指出 → 开发修 → 再评审。只有「规则本身没说清」才留到验收时处理。

## 7. 可选做法（不进骨架，按任务挑）

| 做法 | 什么时候用 |
|---|---|
| 启动前先查一遍规则 | 按用户愿景应该每次都做；它是「中途不拍板」的前提。见 [03](03-规则怎么写.md) 第 5 节 |
| 先小规模试，再全量 | 验收要靠真实运行、且全量很贵的任务 |
| 冻结 | 验收期间某些文件不能变的任务。冻结范围内一改，之前的结果全部作废 |
| 累计达标加护栏 | 验收单元多、每个都有偶发失败的任务。没过的单元可以重跑，但要设重跑上限、保留失败记录、同一原因出现两次必须回去修 |
| 中断产物另存 | 续跑会覆盖旧日志和旧目录的任务。旧的保留、改名标注、不计分 |
