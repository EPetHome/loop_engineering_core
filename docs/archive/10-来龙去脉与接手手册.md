## 0. 先读这一页

**这是什么**：一套让 AI 成员自动「开发 → 评审 → 不达标再来 → 停止交结果」的办法，加一个执行它的程序（引擎）。人只在两头出现：启动之前把要什么写成规则，停止之后验收。

**三条不能破的规矩**

1. 你（陪用户的 AI）和用户是同一个角色，叫**拍板人**，都在循环之外。你不在循环里写代码，也不守着循环运行。
2. 启动、宣布通过、说「合」，都是用户的动作。你准备好一切，把命令交给用户。
3. 循环一停必须有结果。开发方说自己做完了不算数，评审方的结论和程序门禁才算；最后认不认由用户说。

**读的顺序**

| 你要做什么 | 读哪里 |
|---|---|
| 接手当前任务与状态 | 根 README、当前任务的说明/记录；第 8、9 节仅为早期快照 |
| 用这套办法准备一个任务 | 根目录 [AGENTS.md](../../AGENTS.md) 短流程；本文第 5 节仅在需要细节时查 |
| 想知道为什么这样设计 | 本文第 2 节，再看 [01](01-愿景与原则.md)、[07](07-来源与决策记录.md) |
| 查引擎的命令和规则字段 | `engine/docs/03-规则配置参考.md`、`engine/docs/11-CLI命令速查.md` |

## 2. 来龙去脉

```text
09-30  在一个真实项目里试行「调度循环」：一个脚本轮流启动开发模型和复核模型
  │    结果：修的那组来回 3 次通过；跑的那组 7 个场景只过 5 个，复核方叫停
  ▼
10-01  复盘出四类问题（见下表）→ 用户要求：做成所有任务都能用的循环
  ▼
       讨论。第一稿被用户批「写太死」→ 收成一个骨架加四条底线 → 写成设计文档 01—08
  ▼
       用户把设计交给 GPT6 PRO，它交回引擎 0.1.0 → 我们动手复核：部分达标
  ▼
       用户定：不让它补，以它为基础自己迭代；开发交给 pi，走循环本身
  ▼
       写本机接法脚本 → 真实成员最小试跑：第 1 次推不动，补规则后第 2 次达标
  ▼
       迭代 01（循环自己改自己）：46 分钟达标 → 验收 → 用户说「合」→ 合并后再验证达标
  ▼
       用户定：剩下四项一次做完（真实项目小试、累计达标加护栏、评审方可取证、版本号）
  ▼
       准备到一半，用户决定交接 → 写本文
```

**复盘出的四类问题**（这套办法就是为它们设计的）

| 问题 | 这套办法怎么对付 |
|---|---|
| 真实反馈来得太晚，规则有缺口时开发和复核两头都查不出 | 完成标准逐条编号、能用程序判的写成程序；启动前先演练；成员可以把规则缺口记进结果 |
| 「整批全过、每项只跑一次、修一处全重跑」难收敛 | 拆成小单元，每个单元自己达标 |
| 停了没人知道，空转很久 | 停止必发桌面通知；有硬时限 |
| 停止之后没有接着走的路 | 任何停止都交结果；结果里有逐条结论、证据位置、规则缺口 |

**用户说过的、定了调的话**

| 原话 | 意思 |
|---|---|
| 「循环停止 == 给结果」 | 没有结果的停止算故障 |
| 「你把自己想成是我就行了」 | AI 和用户同为拍板人，不要把自己画成循环里的角色 |
| 第一稿「写太死」 | 骨架只有「开发 → 评审 → 停止交结果」，其余按任务选用，不做固定的多步流程和大表 |
| 「我们以这个为基础，自己迭代」 | 引擎就在本文件夹里改，不再找 GPT6 PRO |
| 「用 pi 来修，你不要完成，如果开发工作很大的话」 | 量大的开发交给循环里的成员，陪用户的 AI 只写规则、验收脚本和小胶水 |
| 「全部要落到规范上」 | 目标、边界、验收标准、什么时候停、什么叫完成，都要写成规则 |

每个决定的出处见 [07](07-来源与决策记录.md)。

## 3. 谁做什么

```text
循环之外                              循环之内
┌──────────────────────┐            ┌─────────────────────────────────┐
│ 拍板人 = 用户 + 陪用户的 AI │            │ 开发方（pi：GPT-6.1 Sol，档位 max）  │
│                      │  规则       │        │ 交付                    │
│ 讨论 → 写规则和验收脚本  │ ─────────▶ │        ▼                        │
│ → 演练 → 给启动命令     │            │ 引擎：冻结候选、跑程序门禁          │
│                      │            │        │                        │
│ 用户启动（只这一次）     │            │        ▼                        │
│                      │  结果       │ 评审方（pi：GPT6 Astra，档位 xhigh） │
│ 读结果 → 验收 → 合并    │ ◀───────── │        │ 逐条结论                │
│ → 更新基线            │            │ 达标就停；不达标带修复清单回开发方    │
└──────────────────────┘            └─────────────────────────────────┘
```

| 角色 | 做 | 不做 |
|---|---|---|
| 用户 | 定要什么、确认规则、启动、说过不过、说合不合 | — |
| 陪用户的 AI | 帮着把话落成规则；写验收脚本和小胶水；启动前演练；停下后读结果、验收、合并、更新基线 | 不替用户启动；不守着运行、不轮询；不在循环里写功能代码；不替用户宣布通过 |
| 开发方 | 在项目副本里改代码、自测、逐条自评 | 不改规则和验收脚本；不碰原项目 |
| 评审方 | 读候选和门禁证据，逐条给结论 | 不改代码；和开发方不能是同一个身份 |
| 引擎 | 复制副本、冻结候选、跑门禁、核指纹、计次数和时限、停止时写结果和发通知 | 不写回原项目；不替人做语义判断 |

模型的分配是这位用户的固定约定：开发只用 `openai-codex/gpt-6.1-sol`（上下文 272K，大任务要拆），评审只用 `openai-codex/gpt-6-astra`。用户点名别的型号时按点名的来。

## 5. 完整流程：从头脑风暴到合并

日常准备只有：**目标/授权范围/完成标准与预算 → 复用合适的已有规则、模型工具配置和测试入口 → 必要检查 → 唯一启动命令**。以下步骤是可合并的操作索引，不是小任务的固定清单；已有规则/配置/测试能用就复用。常规启动不要求准备者先实现成功解、假成员完整演练、全引擎回归或真实模型试调用。安装、升级、相关接口或安全边界变化才做相应的完整引擎回归与适配器演练；高风险/可行性验证限定具体疑点。

### 第 1 步：和用户把要什么说清，写出开工卡

- 用户先说想法，你帮着落到「做成什么样」。缺关键事实就问，关键业务歧义在启动前解决，不要猜。
- 复用已有确认，缺少时写出简短开工卡：

| 行 | 写什么 |
|---|---|
| 做完的样子 | 能观察、能验收的完成标准，不是「优化一下」这种话 |
| 授权范围与本阶段不追求 | 能改什么、不能碰什么，防止越做越多 |
| 资源预算 | 轮次、时限、成员启动上限及已确认的模型/工具 |
| 再启动上限 | 这个任务最多启动几次；到了就停下讨论，不自动再来 |

- 用户说了「开始吧」之后，已授权的常规实现选择由执行者决定，不再停下来逐条要确认；做完时说明实际选择。

**产出**：目标、授权、完成标准与预算已明确。

### 第 2 步：拆单元，定先后

- 使用能独立验收的合理工作单元，不是越小越好；小任务允许只有一个。
- 两个单元会改同一批文件，就串行（后一个 `depends_on` 前一个）或合并；不会才能并行。引擎会在启动前拦下已声明范围重叠的并行单元。
- 串行时，后一个单元拿到的是前面达标成果叠加后的代码；有协作接口的任务安排集成单元。

**产出**：单元清单和先后关系，画成一张小图给用户看。

### 第 3 步：把完成标准逐条写出来，分清谁来判

每条标准带编号，归到三类之一：

| 类 | 怎么判 | 例子 |
|---|---|---|
| 程序判 | 写成门禁命令，退出 0 算过 | 受影响的原有测试、必要新增验收检查通过 |
| 评审方判 | 读代码、读证据才能判的 | 文档有没有同步；有没有做目标之外的改动 |
| 只记录 | 这次不当门槛 | 耗时 |

能用程序判的一定写成程序，不要指望成员自觉遵守一句文字。标准只写在规则文件一个地方，别处只引用编号。

**产出**：每个单元一张标准表。

### 第 4 步：复用测试入口，必要时补验收脚本

优先复用原测试作为门禁，只针对缺口补充可重复的断言。新命令、发现范围或依赖有疑点时，检查其能否执行、实际发现了什么，以及失败是既有问题、新行为尚未实现还是环境故障；不要求先做出整份成功解来证明标准。

验收脚本是标准的一部分，由拍板人确定并保护，成员只读。需要新脚本时放在 `source` 内受保护目录，随副本运行；字段、取值、退出码用实际断言检查，不能只读假成员自报 PASS。引擎接口/安全边界变化可复用 `engine/acceptance/_harness2.py` 等现有离线验证入口，不把完整循环演练变成每个业务任务的准备条件。

**产出**：适合本任务的门禁命令；仅在必要时增加受保护验收脚本。

### 第 5 步：写规则文件 `tasks/<编号-名称>/task.json`

优先复用适合本任务的已有规则与已确认模型/工具配置；需要新建时可用 `engine/loop.py init` 生成草稿并填写 TODO。下面只是结构示例，路径、门禁和预算须按本任务替换，不照搬旧引擎迭代的全套门禁：

```json
{
  "schema_version": 1,
  "task_id": "只能用字母数字点横线",
  "title": "人读的名字",
  "source": "../../engine",
  "agents": {
    "dev":    {"kind": "command", "identity": "sol-developer", "output": "stdout", "inherit_env": [],
               "argv": ["{python}", "/Users/Admin/Desktop/loop/adapters/pi_member.py",
                        "--model", "openai-codex/gpt-6.1-sol", "--thinking", "max",
                        "--tools", "read,bash,edit,write,grep,find,ls"]},
    "review": {"kind": "command", "identity": "astra-reviewer", "output": "stdout", "inherit_env": [],
               "argv": ["{python}", "/Users/Admin/Desktop/loop/adapters/pi_member.py",
                        "--model", "openai-codex/gpt-6-astra", "--thinking", "xhigh",
                        "--tools", "read,grep,find,ls"]}
  },
  "limits": {"max_parallel": 1, "max_wall_seconds": 18000, "max_member_invocations": 24},
  "completion": {"mode": "independent"},
  "notes": "给每个成员都会看到的补充说明",
  "units": [{
    "id": "单元编号", "depends_on": [], "goal": "一句话目标",
    "criteria": [{"id": "S1", "text": "标准全文", "gate_ids": ["G1"]},
                 {"id": "S2", "text": "要评审方判的标准", "gate_ids": []}],
    "gates": [{"id": "G1", "argv": ["{python}", "-m", "unittest", "test_feature.py"], "timeout_seconds": 600}],
    "writable_paths": ["能改的目录/", "能改的文件"],
    "protected_paths": ["验收脚本目录/", "原有测试文件"],
    "developer": "dev", "reviewer": "review",
    "max_repairs": 2, "max_infra_retries": 1, "max_protocol_retries": 2,
    "stage_timeout_seconds": 3000, "max_seconds": 9000
  }]
}
```

要点：

| 项 | 怎么填 |
|---|---|
| `source` | 被改项目的目录，相对路径以规则文件所在目录为准。引擎只复制、不写回。里面不能有符号链接；依赖目录（`node_modules`、`.venv`）不会被复制 |
| 成员为什么用 `command` 加接法脚本 | 引擎内置的 pi 接法禁止加载扩展，而这位用户的约定是每次启动 pi 都带权限插件、带 `--offline` 和思考档位。接法脚本把这些固定好了 |
| 两个成员的 `identity` | 必须不同，否则规则检查不过 |
| 每个门禁 | 必须至少被一条标准引用；`argv` 是参数数组，不是 shell 字符串 |
| 门禁在哪跑 | 引擎每次把候选抄一份新副本，在里面跑。只给最小环境，`HOME` 换成临时目录，不带密钥环境变量 |
| `writable_paths` / `protected_paths` | 目录以 `/` 结尾；受保护优先。验收脚本和原有测试一定要保护 |
| `max_repairs` | 首轮之后最多再返修几次。2 表示最多 3 轮 |
| `max_protocol_retries` | 成员把交付的 JSON 写错时的修格式机会，开发方和评审方各算各的 |
| `stage_timeout_seconds` | 单次成员运行的硬时限。迭代 01 里 Sol 每次 10—17 分钟，评审 2 分钟左右 |
| `notes` | 只补本任务特有的业务/等待约束与测试入口。成员提示由引擎依据本次 context 生成，不重复手写角色启动协议，不重抄标准 |

所有字段的含义和默认值：`engine/docs/03-规则配置参考.md`。

写完先做结构检查：

```bash
cd /Users/Admin/Desktop/loop && /opt/homebrew/bin/python3.12 engine/loop.py validate "tasks/<任务>/task.json"
```

**产出**：`task.json`，结构检查通过。

### 第 6 步：写任务说明 `tasks/<编号-名称>/说明.md`

## 6. 被改的项目不能直接在副本里跑时怎么办

引擎让成员在副本里改，门禁也在副本里跑。有四种情况会卡住：

| 障碍 | 表现 |
|---|---|
| 依赖环境不在副本里 | `node_modules`、`.venv` 不会被复制，门禁在副本里起不来 |
| 配置里把路径写死 | 成员在副本里改了什么，真跑时读的仍是原项目 |
| 项目不能整个当 `source` | 里面有符号链接（引擎拒绝），或体积太大（每个成员、每道门禁都要抄一份） |
| 评审要看的证据读不了 | 例如运行记录是压缩文件，而评审方默认不能执行命令 |

解法是**让门禁脚本自己搭一个临时运行环境**，`source` 只取真正要改的那个子目录：

```text
① 把候选抄一份，把写死的路径改成指向这一份
② 搭临时的运行配置：配置文件同样改路径；凭据用符号链接指向原文件，跑完即删，不复制密钥
③ 新建运行目录，用原项目里已装好的程序（按绝对路径调用）真跑
④ 程序判定：跑完了、读的确实是候选、成果和回执对得上
⑤ 把评审方读不了的记录转成可读文本，连同摘要写成证据包
```

写这种门禁脚本要守的几条：

- 产物全部写到门禁自己的工作目录（规则里用 `{workspace}` 传进去），原项目只读不写，候选副本也只读不写。
- 脚本放在 `source` 之外时不受引擎的完整性保护，把它的指纹记进任务说明，验收时核一遍。
- 要证明「读的是候选」：既查原项目的路径在运行记录里出现 0 次，也查候选里改过的行确实出现在运行记录里。
- 真跑会超时：脚本自己给被跑的程序设时限并按不通过退出，规则里门禁的 `timeout_seconds` 要比它大，否则引擎会当成环境故障直接停为推不动。
- 不通过时在标准输出最后打印一行 `LOOP_FAIL_REASON=<原因>`，供限次重跑判断是不是同一个原因。
- 真调模型的检查结果不稳定：同样的输入这次过、下次不过都见过。这类门禁要配限次重跑。

已有一个做好的例子：`tasks/05-真实项目场景小试/scene_gate.py`，针对哪个项目、实测了什么，写在同目录的 `说明.md` 里。
