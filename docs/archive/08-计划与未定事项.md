## 2. 要做的开发工作

| # | 做什么 | 说明 |
|---|---|---|
| 1 | 规则的格式 | 人读一份、程序读一份。程序那份至少要能读出：标准的编号清单、上限、没动静的阈值、可改文件范围 |
| 2 | 结果的格式 | 停止类型、标准逐条的结论与证据位置、没解决的、规则缺口。程序能填的硬数字由程序填 |
| 3 | 单元调度程序 | 读规则；轮流启动开发方和评审方；每次交接核对「每条标准都有结论」和规则指纹；计数；到条件就停；写状态；写结果；成员交不出时代写结果；从断点续跑 |
| 4 | 可观测 | 状态命令（一行一个单元）；停止时桌面通知；没动静按「推不动」处理 |
| 5 | 防篡改 | 启动时把规则副本放进工作区、设只读并加锁、记指纹；每次交接核对；正本留在循环外 |
| 6 | 编排程序 | 读任务安排；启动条件满足就启动单元；某单元没达标时，依赖它的不启动；全部停下后出总结果 |
| 7 | 成员提示词的通用部分 | 工作区怎么用、交付怎么写、「没说清的从严处理并记下来」、非交互模式下怎么等待 |

## 3. 建议的先后

```text
第一步  定规则格式和结果格式（1、2）
          │
          ▼
第二步  做单元调度程序，带可观测和防篡改（3、4、5）
          │        用一个很小的真实任务试跑；试跑要像真的
          ▼
第三步  第一次正式使用：一个单元的任务
          │
          ▼
第四步  做编排程序（6），试一个「两个并行加一个串行」的小例子
          │
          ▼
第五步  复杂任务正式使用
```

理由：先把单元做对。编排只是把单元排起来，单元不稳，排起来只会放大问题。

这些开发工作本身也可以按这套办法来做：每一项是一个单元，有规则、有评审。只是第一、二步时还没有引擎，要用手工方式（拍板人准备、用户逐次启动、读结果）来完成。

## 4. 还没定的事

| # | 事项 | 现状 |
|---|---|---|
| 1 | 这套东西管多大范围 | 文档放在桌面的 Loop 文件夹，不属于任何一个项目。是否所有项目都用、各项目怎么引用它，没有明说 |
| 2 | 观察员（Sidecar）最终要不要 | 讨论中的建议是先不做，用户没有再提，但也没有明确说「不要」 |
| 3 | 规则的程序可读格式用什么 | 没定 |
| 4 | 通知到哪 | 桌面通知可以由程序直接弹；推到手机没有实测过 |
| 5 | 「同一原因出现两次」由谁认定 | 用到「累计达标加护栏」时才需要；建议由评审方认定，没有确认 |
| 6 | 开发方和评审方各用什么模型 | 按项目约定。Promax 现在的约定是开发用一个模型、复核用另一个模型，执行和复核不能是同一方 |
| 7 | 调度程序自己死掉怎么办 | 例如机器休眠或进程被杀。现在的兜底只有状态命令能看出「最近动静是很久以前」。是否加独立的看门程序，没有定 |
| 8 | 引擎的开发由谁做、什么时候做 | 没有定。按用户的习惯，复杂的开发任务交给开发成员做，不由陪用户讨论的模型直接写 |
| 9 | 第一次正式使用用在哪 | 讨论中提到用在 Promax 的下一轮任务上，没有最终确认 |

## 5. 已知的局限

- **规则不可能一次写全。** 启动前查一遍能挡住纸面上的矛盾，挡不住真跑才暴露的缺口。兜底是「从严、记录、继续」。
- **从严处理有代价。** 一个很小的规则缺口可能让一个单元白跑到上限。把单元拆小可以压低代价，不能消除。
- **防篡改不是绝对的。** 成员和拍板人用同一个系统账号，只能做到防手滑、必被发现、可恢复。
- **成员遵守文字规则是概率问题。** 能给出保证的只有程序门禁和独立评审。
- **验收省不掉。** 循环给的是结果，认不认仍然要拍板人花时间看。
