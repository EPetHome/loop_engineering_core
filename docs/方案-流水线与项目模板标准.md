# 方案：项目方法只写一份，批次只填参数，分支改用 worktree

日期：2026-10-25
分支：`feat/pipline-temp-standard`
状态：已拍板（2026-10-25，第 3、9 节）；按第 8 节分三段开发。本文件不授权提交或推送。

## 1. 结论

近期开工准备重，主要不是因为缺一份工具说明，而是两件事：

- loop 的约定让每一批都把项目方法（门禁、棘轮、准备检查、启动脚本）重写一遍；
- 同步和基线这类固定步骤，每次都靠模型手工做。

本方案把这些固定部分收进 loop 和项目级配置，每批只写一份 `批次.json` 加提示词。

```
现在：出loop → 读文档/源码 → 翻旧批次 → 复制改写 gate/棘轮/准备/启动 → rsync 同步 → 外部基线 → 空跑修错 → 写提示词
改后：出loop → 读工具清单 → 写 批次.json + 提示词 → loop 开工（建分支、自测按指纹跳过）→ loop 启动（单段/串行/并行）
```

预计每批准备从 40–60 次工具调用降到 15–20 次。这是按两段样本推算的，实施后要用真实批次对照。

### 2.3 流水线：串行和并行已经是 loop 的能力

`pipeline.ts` 现有的调度：

| 能力 | 现状 |
|---|---|
| 串行 | `steps` 里的各步依次执行，前一步全部 done 才启动下一步 |
| 并行 | 同一步里的多段同时启动，受 `maxParallel` 限制（默认 2） |
| 同一工作区强制串行 | `repoKey` 用 `git rev-parse --show-toplevel` 识别工作区；同一工作区的段自动排开，不同 worktree 可以并行 |
| 资格核对 | 启动下游前核对上游的 `readyEpoch`，上游资格失效就停 |

所以调度不是协调方的能力。协调方实际补写的是每段的外壳（例如 `后端审查修复二三-20261022/段启动.sh`）：

1. 导出 `GIT_DIR` / `GIT_WORK_TREE`。原因是 dev分支 不是 git 仓库，用 worktree 后这一步就不需要了。
2. 串行时，下一段开工前把上一段的成果提交到外部基线，作为本段的开工依据，并拍结构快照。
3. 跑 `自动执行检查.mjs`。
4. 手抄 Pi 启动参数。计划里写 `prompt` 时，程序生成的 `piCommand` 和 `bin/pi-dev` 是两份各自维护的启动逻辑。

## 4. 设计

### 4.1 分支与工作区

```
远端（GitHub / GitLab / …）
  ↑ git push：每次由用户授权，loop 不自动推
运行版 = 仓库主检出，停在发布分支（默认 main，可配置）
  │      只接收合入；合入后就是可用版本
  └─ git worktree ──→ dev分支/      固定路径，日常开发都在这里
                        每批切到新分支：feat/… fix/… refactor/…（从发布分支拉）
     （按需）──────→ dev分支2/     并行时再开一个，用完可以移除
```

worktree 就是同一个仓库的多个工作分区：共享历史，每个目录各检出一个分支。

| 规则 | 内容 |
|---|---|
| 分支名 | `<类型>/<描述>`。类型取 `feat`（功能）、`fix`（缺陷）、`refactor`（结构，行为不变）、`docs`、`test`、`chore`；描述可以用中文 |
| 提交说明 | `<类型>: <描述>`，类型和分支一致；正文写批次名和段名 |
| 开发方不提交 | 段完成（评审、验收、释放都通过）后由程序提交，说明从 `批次.json` 生成。串行的下一段以这个提交为开工依据，不需要再提交外部基线 |
| 合入 | 在运行版里把批次分支合并进发布分支，由用户授权。`loop 合入` 只在本地合并和提交 |
| 同步 | 开工时在 dev分支 里从发布分支拉新分支；运行版有了新合入，就合并发布分支。不再用 rsync |
| 分支专属文件 | `.autoreview.json` 的本机字段、`deploy/acceptance/` 这类验收环境写进 `.git/info/exclude`（只在本机生效，不进远端）。开工工具检查它们确实被排除，不再靠 rsync 排除清单保护 |
| 工作区位置 | `.autoreview.json` 的 `workspaces` 指定名字到路径，例如 `{"dev分支": "../loop-batches/dev分支"}`；没写时默认 `../<仓库目录名>-dev分支`。worktree 放在运行版目录外面，不嵌套 |
| 本机文件 | `.autoreview.json` 的 `localFiles` 列出只在本机存在、不进仓库的文件（例如验收环境的密钥配置）。`loop 开工` 检查它们已被 git 忽略；worktree 里缺少时从运行版复制，已有的不覆盖 |
| 兼容 | 外部基线（`GIT_DIR`）只给不是 git 仓库的项目用，不再是默认 |

### 4.2 项目方法分层：gate.py 拆成三层

把现在一份 `gate.py` 里混在一起的内容拆开：

| 层 | 归谁 | 内容 | 写几次 |
|---|---|---|---|
| loop | 引擎 | 失败分类（退出码 75 归环境、78 归方法、`AUTOREVIEW_FAILURE=`）；越界检查（改动文件对照 `scope`）；本段开工依据；资源身份；权限自动执行检查 | 引擎里一份 |
| 项目 | 项目维护者 | 怎么测：JDK 路径、mvn 和前端检查命令、结构棘轮、准备和验收环境脚本 | 一次。放在项目的 `.autoreview/methods/`（待定 D3），`.autoreview.json` 固定指向这里 |
| 批次 | 协调方 | 本批参数：段、提示词、允许修改的路径、测试选择、棘轮模式（例如「不得增大代码总量」）、启用哪些能力、模型 | 每批一份 `批次.json` |

loop 调用项目方法时多传三个环境变量：

| 变量 | 内容 | 取代 |
|---|---|---|
| `AUTOREVIEW_BASE_REV` | 本段开工依据。会话开始时 loop 已把它记在 `state.baseline`，这里只是传给方法 | 每批的 `开工依据.json` |
| `AUTOREVIEW_BATCH_FILE` | `批次.json` 的绝对路径 | gate.py 里硬编码的批次路径 |
| `AUTOREVIEW_STAGE` | 段名，已有 | — |

越界检查收进 loop：门禁之前，用 `git diff --name-only $BASE_REV` 加未跟踪文件，对照 `批次.json` 的 `scope.allow` / `scope.deny`。越界按产品失败打回，复用现有的门禁返修路径，不新增暂停点。

`自动执行检查.mjs` 收进启动入口（`bin/pi-dev` 和流水线共用），由指纹控制，不再每批复制。

### 4.3 首次自测：用指纹代替 isFirst

```
开工时程序计算：指纹 = loop 版本（git describe --always --dirty）
                   + 项目方法文件的哈希（.autoreview.json 的 methods.paths）
                   + 方法相关配置字段
                   + （可选）methods.probe 的输出，例如 java -version、node -v
   ├─ 与记录一致 → 跳过方法自测
   └─ 不一致或没有记录 → 自测一次 → 通过后写记录；失败就走现有准备流程（有限恢复，受限修复）
记录：~/.pi-autoreview/projects/<项目根哈希>/methods.json（每个项目一份，和来源索引同一个目录）
```

| 项 | 规则 |
|---|---|
| 自测包括 | 项目方法的 `--self-check`、启动入口的权限检查、在开工依据上空跑一次门禁 |
| 为什么不用布尔值 | 布尔值不知道什么时候该变回 false。指纹在 loop 升级、方法改动、配置改动时自动失效 |
| 空跑门禁的缓存 | 结果按提交的树哈希记录。发布分支的树和某次已经通过门禁的候选一致（正常合入就是这样）时不重跑；否则在后台跑，不占模型调用。这个结果只用来识别基线上已有的失败，不算新候选通过 |
| 手动重来 | `loop 开工 --recheck`，用在环境变了但指纹没变的时候，例如 Docker 或数据库升级 |
| 不变的部分 | 每个候选的门禁、评审、验收照常跑；不跨候选复用结论 |

### 4.4 流水线：单段、串行、并行用同一入口

单段就是只有一段的流水线。`批次.json` 同时取代 `启动Loop.sh`、`段启动.sh`、`启动流水线.sh` 和 `流水线.json`：

```json
{
  "name": "后端审查修复二三",
  "branch": "refactor/后端审查修复二三",
  "pi": { "model": "opencode-go/deepseek-v4.1-flash", "thinking": "max",
          "args": ["--autoreview-reviewer-model", "openai-codex/gpt-6-astra", "--autoreview-reviewer-thinking", "xhigh"] },
  "stages": {
    "批2": { "prompt": "../../prompt/提示词-后端审查修复-批2.md", "workspace": "dev分支",
             "scope": { "allow": ["promate-auth/", "promate-skill/"] } },
    "批3": { "prompt": "../../prompt/提示词-后端审查修复-批3.md", "workspace": "dev分支",
             "scope": { "allow": ["promate-auth/"] }, "ratchet": "no-growth" }
  },
  "steps": [["批2"], ["批3"]],
  "maxParallel": 1
}
```

| 改动 | 内容 |
|---|---|
| 启动统一 | 写 `prompt` 时由 `bin/pi-dev` 启动；删掉 `pipeline.ts` 里那份重复的 `piCommand` 拼接 |
| 串行接力 | 同一分支上的串行段：上一段完成时程序提交，下一段以这次提交为开工依据 |
| 并行 | 并行段放在不同的 worktree（`dev分支`、`dev分支2`），各自一个分支。`repoKey` 已经按工作区区分，不用改 |
| 兼容 | 现有的 `start` 写法保留，给特殊场景用 |
| 不变 | e2e 仍然可选，返修归属、`readyEpoch` 核对都不改 |

### 4.5 开工工具与工具清单

新增 `bin/loop` 子命令。每个都支持 `--dry-run` 和 `--json`，输出给模型读的结构化结果：

| 命令 | 做什么 | 取代 |
|---|---|---|
| `loop 开工 <批次.json>` | 检查运行版干净且停在发布分支；在 worktree 里从发布分支拉批次分支；检查分支专属文件已排除；按指纹决定是否自测；空跑门禁（有缓存就跳过）；打印启动命令 | rsync 同步、外部基线、空跑修错 |
| `loop 启动 <批次.json>` | 单段直接开窗口，多段走流水线 | 各种启动脚本 |
| `loop 状态 [<批次.json>]` | 各段阶段、轮次、暂停原因、总结路径 | 协调方定时 sleep 再查 |
| `loop 合入 <批次.json>` | 本地把批次分支合并进发布分支，提交说明按规范，不推送；冲突时停下并报告 | 三方对比、手工搬文件 |

工具清单写在 `工具清单.md`，放在 loop 仓库根目录，给协调方模型读。每个工具写清：

- 名称和用在哪个阶段；
- 输入，包括参数和 `批次.json` / `.autoreview.json` 的字段；
- 输出，也就是 JSON 字段；
- 失败分类；
- 会改哪些文件。

加一条测试核对清单和代码一致：子命令、`批次.json` 字段、`.autoreview.json` 字段都要对得上。

全局 `CLAUDE.md` 的「出 pi 提示词」先读工具清单，README 只在需要细节时再查。

## 10. 验收标准

A1. 操作：在一个 git 项目里写一份单段 `批次.json`，执行 `loop 开工`，再执行 `loop 启动`
    预期：dev分支 worktree 切到 `批次.json` 指定的新分支；不需要 `GIT_DIR`；启动的 Pi 会话加载了权限扩展、autoreview 和 Ponytail
A2. 操作：项目方法和 loop 都没变，第二次执行 `loop 开工`
    预期：输出写明「指纹未变，跳过方法自测」；方法脚本不被重写；没有调用模型
A3. 操作：改动一个项目方法文件（或升级 loop）后执行 `loop 开工`
    预期：输出写明指纹变化的部分；自测执行一次，通过后记录更新
A4. 操作：两段计划 `steps: [["甲"],["乙"]]`，两段在同一个 worktree
    预期：甲完成后程序提交，提交说明符合 `<类型>: <描述>`；乙的开工依据是这次提交；整批完成
A5. 操作：两段计划 `steps: [["甲","乙"]]`，两段分别在 dev分支 和 dev分支2
    预期：两段同时启动，各自在自己的分支上完成
A6. 操作：开发方改了 `scope.allow` 以外的文件
    预期：门禁前就以越界打回原会话，返修消息列出越界文件；计入业务返修，不暂停
A7. 操作：门禁脚本读取 `AUTOREVIEW_BASE_REV` 和 `AUTOREVIEW_BATCH_FILE`
    预期：两个变量分别等于本段开工依据和 `批次.json` 的路径；单段和流水线下都能取到
A8. 操作：执行 `loop 合入`
    预期：批次分支合并进运行版的发布分支，形成规范的提交；没有推送；有冲突时停下并列出冲突文件
A9. 操作：执行工具清单的一致性测试
    预期：清单里的子命令和字段与代码一致；任意一边新增或删除而另一边没同步时，测试失败
A10. [人工] 操作：下一个真实批次用 `批次.json` 和 `loop 开工` 准备
     预期：从「出loop」到启动，协调方的工具调用明显少于近期的 27–59 次
