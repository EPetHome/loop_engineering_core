## 三、已拍板的规则（不要改）

1. **准备阶段的时限提醒**（不阻断）：对有开发方的单元，如果 `max_seconds < (max_repairs + 1) × stage_timeout_seconds`，就提醒。原文："单元 X 的时限 S 秒，按阶段时限 T 秒算最多只够约 K 轮开发，返修上限 M 次可能用不满；建议把单元时限至少调到 (M+1)×T，或者调低阶段时限"，其中 K = floor(S / T)。预览的单元行也要显示 `时限可容纳约 K 轮（按阶段时限）`。
2. **每轮计时**：每轮记录 `history[i]['timing'] = {'developer_seconds', 'gate_seconds', 'review_seconds'}`，墙钟秒数，保留一位小数；包含协议重试和基础设施重试；没有开发的轮（verify，或者 3 号新加的"先评审"轮）`developer_seconds = 0`。
3. **返修前的时间判断**，放在返修上限判断之后、`reserve_operation('repairs')` 之前：
   - `reserve = ceil((gate_seconds + review_seconds) × 1.25)`
   - `available = deadline − now − reserve`
   - `need = 0.5 × developer_seconds`
   - 如果 `available ≤ 0` 或 `available < need`：停止，类型 `NOT_MET`。原因原文："时间不够返修：剩余 A 分钟，扣除门禁和复审预留 R 分钟后，不足上一轮开发用时的一半（N 分钟）；未开始返修，保留当前候选和问题清单"（分钟保留一位小数）。
4. **返修开发的时限**：本轮开发调用的 `timeout = min(stage_timeout_seconds, (deadline − reserve) − now)`。如果是因为这个预留上限而超时，就停止，类型 `NOT_MET`。原因原文："返修开发用完了本轮可用时间（已为门禁和复审预留 R 分钟），没有交付；保留上一候选和问题清单"。普通超时（阶段时限、空闲超时）仍按现在的处理方式。
5. **告诉开发方剩余时间**：
   - 受管开发的 `loop_build`、`loop_submit_check`、`loop_delete`、`loop_copy` 回执加 `seconds_left`（整数，本轮开发截止时间减当前时间，最小为 0）；
   - 返修轮的开发提示词加一句："本轮开发限时约 N 分钟（已扣除门禁和复审预留）；受管工具的回执里有 seconds_left，时间不够时先交付已经完成的修复"。
6. **自测按轮累计分配**：`rounds = max_repairs + 1`；第 r 轮（从 1 开始，超过 rounds 按 rounds 算）的累计上限是 `ceil(cap × r / rounds)`，`cap` 是 `unit_selftest_cap()` 算出的单元总额度。本单元已用次数达到累计上限，就拒绝自测。报错原文："本轮自测额度已用完（本单元已用 U 次，到第 r 轮累计可用 L 次，总额度 C 次），剩余额度留给后续返修；请直接交付，由正式门禁检查"。没用完的额度自然顺延到下一轮。`max_repairs = 0` 时第 1 轮可以用满。
7. 预览单元行显示自测分配，例如 `自测：单元 20 次，按 3 轮累计分配（7 / 14 / 20）`。

## 七、设计约束（陷阱）

1. **测试不能真的等几十分钟**：用 monkeypatch 改 `time.time()`，或者用很小的时限和快速假成员；测试单个停止原因时，把判断函数单独拿出来测。
2. **guardian 的 `deadline_epoch` 仍是 `self.deadline`**：只缩小传给 `run_job` 的 timeout，不要改 guardian 的看门狗逻辑。
3. **`check_time()` 在很多地方被调用**：新的停止判断不能和它的"时限已到"混在一起，原因文字要能区分。
4. **按轮额度和运行级额度两层都要过**：先查本轮累计上限，再查运行级 `reserve_operation('selftests')`。
5. **verify 单元和没有开发方的轮**：`developer_seconds = 0` 时 `need = 0`，只检查 `available > 0`。
6. **协议格式修复轮**（`protocol_repair`）不是新的业务轮：计时算进本轮，不增加 round。
