## 三、已拍板的规则（不要改）

1. 字段和状态名严格按公共规则第三章 3.1，以及 3.2 里的 `review_bar`。
2. **默认过线口径**（单元没写 `review_bar` 时使用），作为常量写进 `adapters.py`，原文如下：
   > 必须修（blocking）：①违反标准原文；②能给出具体输入或场景复现错误结果；③会破坏下游单元、数据或安全。至少满足一条，并写出反例和位置。

## 六、改造规格

### 6.1 协议（`protocol.py`）

- `response_schema()` 的 issue 项加上 `severity`（枚举）、`counterexample`、`locations`、`spec_refs`。在 schema 里都是可选字段，必填与否由 `validate_report()` 按角色判断。
- `validate_report()`：
  - v2 受管评审的每个问题：`severity` 必填；`blocking` 必须有非空的 `counterexample` 和至少 1 条合法的 `locations`（格式、相对路径、在 `code` 里是普通文件、行号合法）；`spec_refs` 是字符串数组。
  - 把现在只在 `frozen` 时生效的"FAIL 必须有依据"推广到 v2 受管评审的**所有轮次**，依据改成：该标准的失败门禁、已知仍 OPEN 的必须修问题（不含遗留和 ADVISORY），或本报告里该标准的 `blocking` 问题。报错原文："标准 X 判 FAIL 但没有必须修的问题：请在 issues 写明 blocking 问题（含反例和位置）；只有建议项时请判 PASS"。
  - 第 2 轮起问题必须写 `files` 的现有要求保持不变。
  - v1 / 非受管：新字段允许出现，并做类型检查，但不要求必填。

### 6.2 台账（`handoff.py`）

- `record_findings()`：新问题记下 `severity`（没写的按 `blocking`）。`advisory` 的状态是 `ADVISORY`，`state_note` 写"建议项，不阻断，交拍板人决定"。已有问题再次出现时不改 severity。另外保存 `counterexample`、`locations`、`spec_refs`，供结果页和开发方使用。
- `freeze_review()`：已知未解决问题的判断排除 ADVISORY；评审本轮的 `advisory` 问题既不算回归，也不进遗留列表。
- `rebind_history()`、`apply_resolutions()`：ADVISORY 项保持 ADVISORY，不被改成 UNKNOWN 或 OPEN；评审对 ADVISORY 项写 `issue_resolutions` 时拒收，报错说明建议项不需要关闭。

### 6.3 引擎（`engine.py`）

- 交给开发方的 `feedback.issues` 只保留 `blocking`（v1 / 非受管里没写 severity 的也算 blocking）。
- 按第三章第 4 条加停滞判停。
- `finish()` 的结果里加上 `advisory_findings`：所有 ADVISORY 项的副本。

### 6.4 提示词（`adapters.py`）

## 七、设计约束（陷阱）

1. **`finding_id` 不含 severity**：同一个问题前后两轮标的级别不同时，仍按 ID 视为同一个问题，以第一次为准（公共规则 3.1）。
2. **`rebind_history()` 每轮都会运行**：确认它不会把 ADVISORY 改成 UNKNOWN，否则建议项会混进待解决列表。
3. **停滞判停不能误伤**：本轮开始时没有 OPEN 必须修问题（例如只有失败门禁触发的返修），就不判停滞。
4. **协议拒收会消耗协议重试次数**：报错信息要一次说清怎么改，避免模型来回试。
5. **`locations` 里的路径**：要过 `relative_path()` 和 `safe_child()`，不能接受绝对路径、`..` 或符号链接逃逸。
6. **v1 兼容**：`engine/tests` 下的 234 条旧测试基本都是 v1，必须全部原样通过。
