# 单一入口：一处读配置，一个命令入口

## 目标

项目只对接一个 Loop 入口；Loop 内部怎么读配置，不能漏到项目里出问题。现在同一个配置项被各处各读：

- `reviewTimeoutMin`：Pi 扩展（`autoreview.ts:320`）只认启动参数，不读 `.autoreview.json`；Claude/Codex Hook（`hosts/review-hook.ts:225`）认环境变量再认文件；只评审（`review-only.ts:71`）认启动参数再认文件；`setup-acceptance.ts:188` 只认文件。
- 真实后果：产品智能体项目写了 `reviewTimeoutMin: 90`，Pi 实际按 60 算；`checkRoundBudget` 只在评审时调用，批次开发完才以「评审失败」暂停。

本段要做到：配置只有一处读取，开工、启动时就把配置错误报出来；用户和项目只用 `bin/loop` 一个命令。

- 完整设计（只读，以本提示词「已拍板」为准）：`/Users/Admin/Desktop/loop/docs/方案-单一入口.md` 第三节 1、4。

## 已拍板

- **唯一读取入口**：`config.ts` 新增 `resolveProjectConfig(root, overrides)`，返回评审参数（`maxRepairs`、`reviewerModel`、`reviewerThinking`、`reviewTimeoutMin`、`reviewerCmd`）、`gate`、`acceptance`、`preparation`、`methods`、`context`，并在里面调用 `checkRoundBudget`。
- **取值顺序**：显式启动参数或环境变量 → `.autoreview.json` → 默认值。Pi 扩展的 `autoreview-*` flag 默认值改为空字符串，才能区分「没写」和「写了默认值」。
- **所有读取点改用它**：Pi 扩展、Claude/Codex Hook（`hosts/review-hook.ts` 的 `loadConfig`）、只评审、`bin/loop` 的开工和启动、`methods.ts`、`preparation.ts`、`project-context.ts`、`setup-acceptance.ts`。这些模块不再自己 `readMarker` 后各自解析字段。
- **提前报错**：`bin/loop 开工`、`bin/loop 启动` 及它们的 `--dry-run` 先调用 `resolveProjectConfig`；出错时非 0 退出、报错原文与现在的 `checkRoundBudget` 文案一致，不建 worktree、不切分支、不开会话。
- **能看到生效值**：`开工`、`启动` 的 `--json` 输出新增 `effectiveConfig`，至少含 `reviewTimeoutMin: { value, source }`，`source` 取 `flag` / `env` / `file` / `default`。
- **命令入口**：新增 `bin/loop 开发 <pi|claude|codex> [原 loop-dev / pi-dev 的参数…]`，内部调用现有 `bin/pi-dev`（pi）或 `bin/loop-dev`（claude、codex），参数原样透传，`--dry-run` 输出与直接调用相同的命令。`bin/pi-dev`、`bin/loop-dev` 保留可直接调用。

## 边界

- **代码主要涉及**：`config.ts`、`autoreview.ts`、`hosts/review-hook.ts`、`review-only.ts`、`loop.ts`、`methods.ts`、`preparation.ts`、`project-context.ts`、`setup-acceptance.ts`、`bin/loop`。
- **不改**：配置字段名和含义、各字段默认值、`checkRoundBudget` 的规则、评审与验收提示词、合入队列和流水线调度行为。
- **文档不在本段改**：README、接入手册、工具清单、项目模板留给下一段统一改；本段只在交付说明里列出需要下一段同步的文档点。
- **测试**：放在 `test/`；评审方、宿主用替身；项目用系统临时目录里的临时仓库。
- 开发方不提交。

## 验收标准

A1. 操作：临时项目 `.autoreview.json` 写 `reviewTimeoutMin: 90`、`gate.timeoutMin: 20`、`acceptance.timeoutMin: 60`，不传任何启动参数，执行 `bin/loop 开工 <批次.json> --dry-run --json`
    预期：成功；`effectiveConfig.reviewTimeoutMin` 为 `{ value: 90, source: "file" }`
A2. 操作：同 A1 的项目，启动替身 Pi 开发会话并触发一轮评审
    预期：不出现「必须小于一轮总预算」报错；本轮评审超时保护按 90 分钟计
A3. 操作：同 A1 的项目，分别经 Pi 扩展、Claude/Codex Hook、只评审三条路径加载配置
    预期：三条路径得到的 `reviewTimeoutMin` 都是 90
A4. 操作：同 A1 的项目，启动参数传 `--autoreview-review-timeout-min 120`
    预期：生效值为 120，`source` 为 `flag`
A5. 操作：临时项目不写 `reviewTimeoutMin`，`gate.timeoutMin: 20`、`acceptance.timeoutMin: 60`，执行 `bin/loop 开工 <批次.json>`（不带 `--dry-run`）
    预期：非 0 退出，报错写明预算不足；没有新建 worktree，没有新建或切换分支
A6. 操作：同 A5 的项目执行 `bin/loop 启动 <批次.json> --dry-run`
    预期：非 0 退出，报同样的错；没有启动任何会话进程
A7. 操作：执行 `bin/loop 开发 pi --cwd <临时项目> --dry-run <提示词>`，再执行 `bin/pi-dev --cwd <临时项目> --dry-run <提示词>`
    预期：两次输出的启动命令相同
A8. 操作：执行 `bin/loop 开发 claude --cwd <临时项目> --dry-run`，再执行 `bin/loop-dev claude --cwd <临时项目> --dry-run`
    预期：两次输出的启动命令相同
A9. 操作：用一个所有字段都写在 `.autoreview.json`、不传启动参数的现有项目配置跑 `npm` 门禁命令（`node --test test/*.test.ts`）
    预期：全部通过
