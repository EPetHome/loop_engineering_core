## 六、改造规格

| # | 修什么 | 怎么修 |
|---|---|---|
| B1 | 中文和特殊字符路径进不了指纹 | 所有取路径列表的 git 命令都加 `-z`，按 NUL 切分，不 trim、不去引号；所有 git 调用加 `-c core.quotePath=false`。`hash-object` 失败就算取证失败（见 B2），不能跳过 |
| B2 | git 失败被当成「没改动」 | 凡是用来准备评审材料或证明「没改动」的 git 调用，都必须检查退出码和 `killed`。只有 `stash create` **成功且输出为空**时，才退回 HEAD 提交。取证失败一律暂停（原因：「无法读取工作区状态：<错误摘要>」），不发出任何肯定性结论。仓库还没有任何提交时（`rev-parse --verify HEAD` 失败），开会话就提示「仓库还没有提交，自动评审已关闭」，然后关闭 |
| B3 | 评审失败还推进基线、丢掉旧必修 | 把「调用记录」和「成功评审检查点」分开：只有解析成功的评审，才更新「上次成功评审的快照」「上次成功评审的指纹」「待复查的必修」。失败的调用只留记录。`/review` 续审时：一次成功评审都没有，就按第 1 轮材料送（带需求原文）；否则送从上次成功快照到现在的 diff，加上上次成功评审的必修和开发方最新回复 |
| B4 | 基线存的是字符串 HEAD；指纹算了却没用 | 快照一律存解析好的 40 位提交 id，不能存 `HEAD` 字样。指纹由三部分组成：HEAD 提交 id、工作区 tree hash、每个未跟踪文件的 hash。暂停与否**直接比较指纹**；变化文件列表只用来解释，列表为空但指纹变了也要暂停（原因写「工作区或提交发生了变化」） |
| B5 | 新会话第一条就 `/review` 送空材料 | 没有基线时，`/review` 以当前 HEAD 提交作为基线，材料包括全部未提交改动和未跟踪文件。没有记录到需求原文时，在输入里写明「本会话没有记录需求原文（手动 /review），请按改动本身和项目文档评审」 |
| B6 | 暂停流程自己再抛错 | 整个后台评审任务的最外层要有 catch。暂停时，写总结、`appendEntry`、`setStatus`、通知这几步各自 try/catch：总结写失败，仍要发通知并说明原因。不允许出现未处理的 rejection |
| B7 | 没有生命周期清理 | 每个评审任务配一个 AbortController，把它的 signal 传给 `pi.exec`。监听 `session_shutdown`：取消正在跑的评审，把状态存成暂停（原因：「评审被中断（会话关闭或重载）」），并设一个已失效标记，旧任务之后不再调用任何 pi 或 ctx 接口。`session_start` 恢复时，如果读到「评审中」，改成上面那种暂停并提示输入 `/review`，不能静默改回空闲 |
| 提醒 | 未交付提醒 | 按第三章第 2 条实现 |
| S1 | R5/R6 断言会假绿 | 断言要查结构化结果（状态里这一轮解析成功、结论是「通过」或「需返修」），不能只查总结里有「结论：」三个字 |
| S6 | README 启动示例 | 给出完整的日常启动命令（见下）。再写三句提醒：没有标记不代表已经评审过，可以用 `/review-status` 查；完成后也可以手动 `/review`；要接着用同一个开发会话，用 `pi --session <开发会话id>` 精确恢复，不要只写 `pi -c` |
