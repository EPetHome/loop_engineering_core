# 流程对齐 4：测试瘦身

## 目标

Loop 现在有 528 个测试（算上子项共 883 项），全部跑完要 10.5 分钟。其中 119 个是按「返修1」「二次返修」「本批」「补充」这类轮次命名的：评审每打回一次，就往上加几个。按功能看，有不少重复、臃肿。`test/hook.test.ts` 一个文件串行就要跑约 7 分钟，是整套测试慢的主因。

用户要求：测试测到核心，不重复、不臃肿。

## 已拍板

- 先出清单，等用户确认后再动手删或合并：
  - 按 Loop 的核心功能分组，每组列出保留、合并、删除哪些测试，以及理由。
  - 每删一个，写明它原来覆盖的行为现在由哪个保留的测试覆盖。
  - 清单发给用户后停下等答复，用户确认后才改。
- 每个核心功能至少保留：主流程一条，关键出错情况各一条。
- 优先合并：同一行为的多个用例并成一个参数化用例，共用临时仓库和进程；把大文件拆开，好让它们并行跑。合并不够时才删。
- 测试按功能命名和组织。改完以后，不再有名字以「返修N」「第N次返修」「二次返修」「三次返修」「本批」开头的测试。功能本身就叫返修的（比如返修上限、返修计数）照常命名。
- 目标：门禁命令 `node --test test/*.test.ts` 在本机 5 分钟内全部跑完，并且全部通过。
- `test/e2e.mjs` 的场景和断言由用户定，不动。

## 边界

- 在第三段完成后的批次分支上继续，前三段新增的测试也一起整理。
- 只改 `test/`。只有在测试需要的辅助接口时才动产品代码，而且不改行为。
- 已有验收标准对应的覆盖不能降低。
- 开发方不提交。

## 验收标准

A1. 操作：在开发空间执行 `node --test test/*.test.ts`
    预期：全部通过，总耗时不超过 5 分钟
A2. 操作：列出所有测试的名字
    预期：没有以「返修N」「第N次返修」「二次返修」「三次返修」「本批」开头的
A3. 操作：对照瘦身前后的 `test/e2e.mjs`
    预期：没有任何变化
A4. [人工] 操作：看开发方给的保留、合并、删除清单
    预期：每个核心功能都还有主流程和关键出错情况的测试；删掉的都是重复的
