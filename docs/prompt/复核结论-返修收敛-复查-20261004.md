## 3. 新发现的问题

### N1 · 阻塞：B2 剩余边界——收集不完整但仍声称 reads_complete=true

**位置：** `E/pi_events.py:124-134`、`:367-368`、`:377-385,408-417`；下游 `E/observability.py:124-136`、`E/engine.py:140-155`。

这不是声称 6 号新引入了整条失败路径，而是原 B2 的“不能证明完整则未知”要求仍未完成。

#### 反例 A：半条工具事件后超时/取消

本复查仅用 `PiEvents(None, ...)` 在内存验证，未创建日志、未启动进程或模型：

```python
p = PiEvents(None, 65536, code_path='/code')
p.feed(b'{"type":"session","cwd":"/code"}\n')
p.feed(b'{"type":"tool_execution_start","toolCallId":"r1",'
       b'"toolName":"read","args":{"path":"a.py"}')  # 未结束、无 LF
p.finish('timeout')
```

观察结果：

```text
reads=0, distinct_files=0, repeat_reads=0, read_paths=[], tools_by_name={}
coverage.reads_complete=True
cost_sessions([该会话, 后续完整会话]).cross_reads = [0, 0]
```

`cancelled` 同样复现。原因：`:380-381` 在检查 `self.buffer` 之前返回；finally 保存投影后清空 89 字节残片，没有留下覆盖不完整标记。不能从“还没解出 start”推断“没有读取”。

这是适配器真实可达入口，不是假造不可调用的状态：`adapters/pi_member.py:88-100,140-159` 在 timeout/cancel/nonzero 或收集异常时调用 `events.finish(reason)`；runner 也有对应收尾入口（`E/runner.py:246-248,282-284`）。

#### 反例 B：真实触发单事件解析上限

内存构造 `PiEvents(None, 128, diagnostic_bytes=64, code_path='/code')`，先 feed session，再 feed 超过 128 字节的工具开始记录。`feed()` **实际抛出** `EventError(reason='event_limit')`；随后按适配器异常处理调用 `finish('event_limit')`。

仍得到 reads=0、read_paths=[]、tools_by_name={}、reads_complete=true、stream_valid=true，`summarize(..., 1).usage.reads=0`。`:368` 抛错前没有置覆盖无效；该情形甚至可以没有残留 buffer，因此仅补 buffer 判空还不够。

**影响：** 失败调用仍进入成本记录；结果表/运行合计会把未知写成零或已观察小计，后续 cross_reads 也不会被污染为 None。有地图的调用还可能被 M2 错报成地图外读取 0。原先已修的 unmatched-end 路径确实返回全 None，不能替代这两条异常路径。

**建议修改：**

1. 在终止收集时，先记录未消费残片/未消费数据及解析器异常的覆盖缺口，再保存 usage；解析上限等抛错位置也应设置持久的不完整标记。
2. 五个读取字段统一 None，小计只留 coverage；让现有 cross_reads/M2 未知传播自然生效。
3. 补“残缺事件+非 ok 收尾”“实际 feed 超限+异常收尾”反例，并断言表格、合计及下一会话 cross_reads。不要粗暴把所有非 ok 调用都清零或把原始日志保留截断当作流损坏；完整实时投影仍应保留准确数字。
