# 验收能跑完、归因清楚、每条写明验了什么

## 目标

自动验收经常跑不完：验收方模型断线后挂住，要等整轮时限用完才被杀掉，所有条目都被判成「无法验证」，整轮暂停，可实际上证据往往已经留齐了。另外，用户看不出验收到底验了什么，总结里只有「通过」和一段摘录。背景见 `docs/方案-开发测试闭环.md` 第 6 节批 2，问题单见 `iusses/验收方模型断线卡住导致整轮无法验收.md`（只读）。

历史数据（`eval/报告/基线-20261027.md`）：98 轮验收共 20.8 小时；无法验证 173 条，其中模型退出、超时或限流 44 条，另有 5 条没写原因。

1. **及早发现挂住**：验收方连续一段时间没有任何新动作（工具调用、会话记录、证据都没有变化），就判定为挂住，结束这次调用，不再等到整轮时限用完。
2. **挂住后按证据补判**：证据目录里已有证据的条目，另开一次调用（用 `strongModel`），只根据已有证据补写报告，不重新实测；证据不全的条目判为「无法验证：验收方模型断线」。补写的报告仍由程序按证据判定，规则不变。
3. **归因写清楚**：总结和暂停原因里，要把「验收方模型断线或挂住」和「被测系统超时或崩溃」分开写；不要混入 pi 的无关告警（例如 `No project session found`）。每条「无法验证」都必须写明具体原因，不能为空，也不能只写「验收方没有报告这一条」。
4. **写明验了什么**：总结里每条验收结果后面，附上实际执行的命令（取自证据文件里的 `$` 行，最多 3 条，太长就截断），以及验收方自己写的脚本路径。
5. **归因回归测试**：从 `~/.pi-autoreview` 的历史门禁日志和验收 `result.json` 里，挑出有代表性的失败输出，脱敏、缩短后做成测试样本，覆盖产品失败、环境问题、方法问题、验收方断线、被测系统被关掉这几类，把失败分类固定下来。

## 已拍板

- 挂住的判定时间默认 5 分钟，可以通过配置调整。补判的耗时计入本轮预算；剩余时间不够补判时，有证据的条目照常按证据判定，其余判为「无法验证」并写明原因。
- 补判不能让没有证据的条目变成「通过」；证据和摘录的核对规则一条都不放宽。
- 被测系统真的超时或崩溃时，处理方式保持不变。
- 不改验收标准的写法，不改【块 1】。

## 验收标准

A1. 操作：用验收方替身模拟"证据全部留齐之后挂住、不再输出"，跑单测。
    预期：在挂住判定时间内结束调用；补判后各条按证据判定；整轮用时明显少于时限。
A2. 操作：用替身模拟"只留下部分证据就挂住"。
    预期：有证据的条目按证据判定，其余判为「无法验证：验收方模型断线」。
A3. 操作：用替身模拟"被测系统真的超时"。
    预期：行为与修改前一致。
A4. 操作：查看上述场景生成的总结。
    预期：每条结果都附有实际执行的命令或脚本路径；每条「无法验证」都有具体原因；暂停原因里不出现 `No project session found`。
A5. 操作：执行 `PATH="/Users/Admin/.hermes/node/bin:$PATH" node --test test/*.test.ts`。
    预期：全部通过，其中包含用历史样本做的归因回归测试。
