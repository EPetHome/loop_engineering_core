# 任务：用 pi 自动评审扩展覆盖旧 Loop（pi-autoreview）

> 执行方：pi（opencode-go/deepseek-v4.1-flash）　·　生成日期：2026-10-04　·　**不提交**
> 工作目录：`/Users/Admin/Desktop/loop`（git 仓库，分支 dev）

## 一、目标

把这个仓库里的旧 Loop 整体换成一个 **pi 扩展**。用户照常启动 pi 开发会话，只多加一个 `-e`。之后：

```
开发方写完，最后一行写【交付完成】
  → 扩展自动调用评审（Astra，每个开发会话固定复用一个评审会话）
  → 评审只分「必修 / 小问题 / 需求疑问」
  → 有必修：作为下一条消息发回【同一个】开发会话，开发方返修 → 再评审
  → 没有必修，或返修满 3 次：停下，弹 macOS 通知，写一页总结
```

用户不再在开发和评审之间来回转话。

## 三、已拍板的规则（不要改）

1. **覆盖旧 Loop**：仓库里只留新扩展，加上 `docs/` 里的历史资料。旧代码直接删除（见第四章清单）。
2. **触发**：开发方最后一条回复的最后一个非空行是 `【交付完成】` 时，自动评审。最后一行是 `【需要你决定】` 时，不评审，只通知用户。这两条约定由扩展在 `before_agent_start` 里追加进开发方的系统提示，用户自己的提示词不需要改。
3. **复用会话，禁止新开**：开发方就是用户启动的那个会话，返修意见用 `sendUserMessage` 发回这个会话。每个开发会话固定一个评审会话（用 `--session-id` 指定同一个 id），第 2 轮起评审会记得上一轮。
4. **评审只分级**：必修、小问题、需求疑问。规则全文见 6.4，原样写进 `review-prompt.md`。
5. **只把必修发回开发方**。小问题和需求疑问只写进总结，交给用户决定。
6. **停止条件只有两个**：没有必修 → 完成；已经返修 3 次后评审仍有必修 → 暂停。**不设任何总时限。**
7. **任何异常都是暂停，不是终止**：不回滚、不删除、不改开发成果。弹通知，写总结。用户输入 `/review` 就能接着来。
8. **评审单次保护**：一次评审最长 60 分钟。超时、退出码非 0、输出为空或解析不出格式，都算这一次失败；在同一个评审会话里重试 1 次，再失败就暂停。
9. **评审能跑命令、不能改文件**：评审前后各取一次工作区指纹，不一致就暂停，并在总结里列出变化的文件。
10. **模型**：评审默认 `openai-codex/gpt-6-astra`，思考档位 `xhigh`；可以用 flag 改，只供测试用。开发方的模型由用户的启动命令决定，扩展不管。
11. **第一版只支持 git 仓库**：不是 git 仓库时，开会话就提示「不是 git 仓库，自动评审已关闭」，然后什么都不做。
12. **总结不写进项目**：写到 `~/.pi-autoreview/<项目目录名>/<开发会话id>.md`。
13. **不引入 npm 依赖**：只用 Node 内置模块和 pi 提供的接口；不建 `package.json`，也没有 `node_modules`。

### 6.4 `review-prompt.md`（原样写入，不要改写）

```markdown
# 评审规则（自动评审）

你是独立评审方。你只读、只分析，不修改任何文件，不改 git 状态。可以运行只读命令（例如运行测试、grep、git diff/log/show）来确认问题；会写文件的命令（格式化、安装依赖、生成代码、git add/checkout/stash 等）不要运行。

## 你拿到的材料
需求原文、本轮改动（diff 和新增文件列表）、开发方的交付说明；第 2 轮起还有上一轮的必修清单和开发方的逐条回应。需要时自己去读文件。

## 分级
**必修**（满足任意一条，并且必须能指出具体位置）：
1. 违反需求原文的明确要求（写出是哪一条）
2. 可复现的错误（给出输入或步骤，以及错误结果）
3. 破坏已有功能、数据或安全
4. 违反开发原则（高内聚、低耦合、单一职责、不重复等），并且已经导致本次需求出错，或者让下一步改动必须同时改多处（写出是哪几处）

**小问题**：其余一切，包括一般性的结构、命名、风格、可读性、更好的写法，以及没有造成上面后果的原则问题。

**需求疑问**：需求没写清、没写到的地方。需求没写的，不能算必修。

## 第 2 轮起
只做两件事：
1. 复查上一轮每条必修：已修 / 未修 / 接受异议（开发方的异议有道理就接受）。未修的继续列为必修。
2. 只在本轮新改动的代码里找新的必修。没改动的代码里新发现的问题，最多列为小问题。

## 输出格式（严格按下面的标题，不要输出别的标题）
## 结论：通过 或 需返修
## 必修
1. 位置：相对路径:行 或 相对路径:起-止
   问题：……
   依据：需求第几条 / 复现方式 / 破坏了什么 / 违反的原则及后果
   建议：……
（没有就写「无」）
## 小问题
- 位置：一句话
（没有就写「无」）
## 需求疑问
- ……
（没有就写「无」）
## 上轮必修复查
- 第 N 条：已修 / 未修 / 接受异议 —— 一句话
（第 1 轮写「无」）

必修按严重程度从高到低排列。有必修时，结论必须是「需返修」；没有必修时，结论必须是「通过」。
```

### 6.7 评审输入文件（每轮写到 `~/.pi-autoreview/<项目目录名>/review-input-<开发会话id>-r<轮次>.md`）

- **第 1 轮**：
  - `## 需求原文`：开发会话里第一次 `before_agent_start` 拿到的 `prompt`（已经展开过 @文件）。这段要用 `appendEntry` 存下来。
  - `## 开发方交付说明`：开发方最后一条助手消息的文本。
  - `## 本轮改动`：从「开发开始时的基线」到现在的 diff，以及新增的未跟踪文件列表。
- **第 2 轮起**：不再附需求原文（评审会话里已经有了）。附开发方的最新回复（里面有逐条回应）、上一轮的必修原文，以及从「上一轮评审时的快照」到现在的 diff 和新增的未跟踪文件。
- diff 超过 200KB 时，只给 `git diff --stat` 和文件列表，并写一句「改动太大，请自己读文件」。

### 6.8 调用评审（`pi.exec`，cwd 设为项目目录）

```

  --session-id <评审会话id>
  --model <评审模型> --thinking <评审档位>
  --no-extensions --no-skills --no-prompt-templates --no-themes
  --tools read,grep,find,ls,bash
```

### 6.9 工作区快照与指纹（只用不改索引的 git 命令）

- 快照 = `git stash create` 的输出；工作区干净时输出为空，就用 `HEAD`。另外记下未跟踪文件列表：`git ls-files --others --exclude-standard`。
- 「从快照到现在的 diff」= `git diff <快照>`，再加上快照之后新出现的未跟踪文件列表。
- 指纹 = 已跟踪部分的 tree hash（快照提交的 `^{tree}`，干净时用 `HEAD^{tree}`），加上每个未跟踪文件的 `git hash-object`。评审前后各取一次，比较是否一致。

### 6.10 状态与持久化

- 状态包括：开关、需求原文、开发开始时的基线、上一轮快照、评审会话 id、每轮记录（时间、耗时、必修、小问题、需求疑问、复查结果）、返修次数、当前状态（空闲 / 评审中 / 完成 / 暂停及原因）。
- 每次变化都用 `pi.appendEntry("autoreview-state", 状态)` 存进会话。`session_start` 时读取最新一条恢复，这样用户用 `pi -c` 重开同一会话，也能接着数轮次、接着用同一个评审会话。

### 6.11 什么情况做什么

| 情况 | 动作 |
|---|---|
| `agent_settled`，最后一行是【交付完成】，当前空闲 | 开始评审（异步进行，见 7.3） |
| `agent_settled`，最后一行是【需要你决定】 | 暂停，通知「开发方需要你决定」 |
| `agent_settled`，没有标记，且上一步扩展刚发过返修消息 | 暂停，通知「开发方停下了，但没写交付标记」 |
| `agent_settled`，没有标记，平时对话 | 什么都不做 |
| 评审中又触发 | 忽略，状态栏仍显示「自动评审中（第 N 轮）」 |
| 评审无必修 | 完成：通知 + 总结 |
| 评审有必修，返修次数小于上限 | 发返修消息：空闲时直接发，忙时用 `deliverAs: "followUp"` |
| 评审有必修，已达上限 | 暂停（达到返修上限）：通知 + 总结，列出未解决的必修 |
| 评审失败两次 | 暂停（评审失败），总结里附错误摘要 |
| 评审前后指纹不一致 | 暂停（评审改动了工作区），列出变化的文件 |

### 6.12 解析评审（`core.ts`）

- 按 `## ` 开头的标题切分。缺 `## 必修` 标题，就算解析失败。
- 必修条数 = `## 必修` 一节里以 `数字.` 开头的行数；这一节只有「无」时为 0。
- 结论和条数矛盾时，以条数为准，并在总结里记一条提示。

## 七、设计约束（陷阱）

1. **`AGENTS.md` 里是旧 Loop 的规则**，对本任务一概不适用。不要因为它说「不要改 engine」就不删。
2. **用 `agent_settled`，不用 `agent_end`**：`agent_end` 之后 pi 还可能重试、压缩、继续执行排队的消息。
3. **不要在 `agent_settled` 的处理函数里 `await` 整个评审**：启动评审后马上返回，评审跑完再回送；同一时间只允许一个评审在跑；评审期间用 `ctx.ui.setStatus` 显示进度。
4. **`sendUserMessage` 在忙的时候不带 `deliverAs` 会抛错**：先看 `ctx.isIdle()`，忙就用 `deliverAs: "followUp"`。
5. **`pi.exec` 是 `shell: false`，stdin 被忽略，没有 env 参数**：提示词一律用 `"@文件"` 传，命令一律写绝对路径；子进程会继承 pi 自己的环境变量（用户启动时已经设好 PATH）。
6. **`git diff` 不包含未跟踪文件**：要另外列出来。不许用 `git add -N` 之类会改索引的命令。`git stash create` 只生成一个对象，不动工作区和 stash 列表，可以用；`git stash`（push）禁止。
7. **RPC 模式不接受 `@文件` 形式的提示**：联调驱动要用 `prompt` 命令发正文。
8. **`-p` 只输出最后一条助手文本**：这段文本就是评审结果；输出为空就算失败。
9. **`review-prompt.md` 的路径**按扩展文件自身所在目录解析（`import.meta.url` 或 `__dirname`，以 jiti 下实际可用的为准），不要依赖 cwd。
10. **`~/.pi-autoreview/<项目>/` 可能不存在**，写之前先 `mkdir -p`。
11. **开发方这一侧不加任何时间限制**；联调驱动可以为每个场景设上限（例如 20 分钟），那只是测试工具，不是产品行为。
12. 只删第四章列出的路径；`docs/` 虽然写满了 Loop 的内容，也保持原样。

## 八、开发习惯

- 按顺序做：先写 `core.ts` 和单测，跑通；再写 `autoreview.ts`，用 `--help` 确认能加载；再写联调；最后删旧代码、重写文档。删旧代码放在后面，前面出问题时还能对照。
- 每改一步就跑一次单测。
- 注释少而准，用中文。不写与本任务无关的文件。
- 测试纪律：任何失败都原样写进简报。删测试、跳过、反复重跑直到变绿，都不算修好。

### 9.4 联调（`test/e2e.mjs`，RPC 驱动）

驱动的做法：

1. 每个场景新建一个玩具仓库：`mktemp -d /private/tmp/autoreview-e2e-XXXX`，`git init`，提交一个带错误的 `calc.py`（`def add(a, b): return a - b`）。
2. 在玩具仓库里启动开发方（模型用便宜的）：
   ```
   pi --offline --mode rpc --model opencode-go/deepseek-v4.1-flash --thinking low
      --no-extensions --no-skills --no-prompt-templates --no-themes --tools read,edit,write,bash
      -e <权限扩展> -e /Users/Admin/Desktop/loop/autoreview.ts <场景 flag>
   ```
   不要加 `--no-session`。
3. 用 `prompt` 命令发：「修复 calc.py 中 add 的错误，新建 test_calc.py 并用 python3 运行通过。」
4. 一直读事件，直到总结文件里的状态变成「完成」或「暂停」（每个场景最多等 20 分钟），然后关闭 pi。

假评审 `test/fake-reviewer.mjs`：用环境变量 `FAKE_MODE` 选择行为，用 `FAKE_STATE_DIR` 记录自己被调用了几次。

| # | 场景 | flag / 环境 | 期望 |
|---|---|---|---|
| R1 | 返修 1 次后通过 | `--autoreview-reviewer-cmd test/fake-reviewer.mjs`，`FAKE_MODE=pass-after-1`（第 1 次有 1 条必修，第 2 次通过） | 状态「完成」，评审 2 次、返修 1 次；开发会话只有一个会话文件，里面恰好有 1 条以「【自动评审 · 第 1 次返修】」开头的用户消息；玩具仓库没有新提交 |
| R2 | 达到上限 | `FAKE_MODE=always-fix`，`--autoreview-max-repairs 1` | 状态「暂停（达到返修上限）」，评审 2 次、返修 1 次；开发成果仍在玩具仓库工作区 |
| R3 | 评审失败 | `FAKE_MODE=fail`（退出码 1） | 假评审恰好被调用 2 次；状态「暂停（评审失败）」；开发成果仍在 |
