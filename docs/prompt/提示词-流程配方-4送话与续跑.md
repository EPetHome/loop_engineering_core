# PA 对接：送话与续跑

## 目标

用户在 PA 的卡片上答复以后，PA 要能把用户的原话一字不改地送回指定批次的指定段，让它接着干，并拿到回执。还有一类暂停是在整批层面发生的，这时流水线进程已经退出，送话找不到对象，需要另外提供「续跑」。

## 已拍板

- **授权：PA 转达的话，按用户本人在会话里说的话处理**，包括答复 [授权]。来源要写进三处：会话状态、总结、交付总表。防线靠 PA 对账，所以每一条被会话读取的转达，都必须发出 `resumed{via:"pa", id}`。如果这个事件没发出去，`errors.log` 里要带上这条转达的编号。
- **`loop 送话 <批次.json> --stage <段> --id <编号> --text-file <文件|-> [--wait 秒] --json`**，流程按方案 §5.2：
  1. 按 `id` 查重。这个编号已经有记录，就返回原来的回执，不重发。
  2. 核对目标会话的身份（pid 加启动时间）。会话已经不在，返回 `failed「会话已关闭」`，不新建会话，也不恢复会话。
  3. 读 `<段>.phase.json`，段正在运行或评审时返回 `rejected「段正在运行」`。这种情况不落盘，也不占用这个 `id`。
  4. 先落盘写 `<段>.words/<id>.json`，里面记原文的 sha256，状态记为 `sending`。
  5. 按宿主投递：pi 走新增的「用户原话」收件位置；Claude 走现有的本地认证 socket；Codex 走 `queue --thread`。
  6. 投递成功记为 `delivered`。调用超时或者结果说不清，记为 `unknown`，不重试。
  7. 会话那一侧核对通过后，把状态改成 `read`。`--wait` 秒内等到了 `read` 就返回 `read`，否则返回 `delivered`。
- **会话那一侧怎么处理**：
  - 送进会话的文本是 `【用户原话 · 经 PA 转达 · <id>】`，换行，然后是原文，一字不改。
  - 宿主收到后核对三件事：有这条记录、哈希一致、状态是 `delivered`。一个编号只能用一次。
  - 核对通过：去掉消息头，把原文当作用户在会话里打的话处理，和现在用户自己输入走同一条路径。暂停会解除，返修计数清零，需求、决定、标准、授权照常更新。
  - 核对不通过：当作机器消息处理，不进入标准和授权的解析，并发一条事件，`reason.text` 写「送话核对失败」。
  - 段已经做完时也可以送话，等于用户说「再改一下」。这同样发 `resumed`。
- **辅助防护**：`loop 送话` 发现调用方带着 `AUTOREVIEW_STAGE` 或 `AUTOREVIEW_PIPELINE_DIR` 环境变量，就直接拒绝。
- **`loop 续跑 <批次.json> --id <编号> [--grant-file <文件|->] --json`**，流程按方案 §5.6：
  1. 按 `id` 查重。
  2. 读 `batch.phase.json` 的 `next`。值是 `manual` 就拒绝，并附上原因。流水线还在运行就拒绝（核对 pid 加启动时间）。
  3. `next` 是 `grant` 时，把原话写进流水线目录的 `grants.pa.jsonl`，记下编号、原文、时间和 `via:"pa"`。流水线读授权时，把这里的内容和标准文件里的授权行合在一起。原话解析不出授权答复就拒绝。不改用户的标准文件。
  4. 在后台重启编排：各段都已完成时，走 `pipeline.ts --from 验收`；否则走 `loop 启动` 的多段路径。
  5. 发 `resumed{stage:null, via:"pa", id}`。
- **授权文件对账**：
  - `loop 查询` 的 `batch.paGrants` 列出 `grants.pa.jsonl` 里的全部编号。
  - 流水线每次读授权时，在 `resumed`、`paused` 或 `done` 事件的 `detail.paGrantsUsed` 里，列出这次实际用到的全部 PA 授权编号。
  - 每段的 `paRelays` 列出最近被读取的转达编号。

## 验收标准

A1. 操作：段处于「需要你决定」，执行 `loop 送话 --id m1`，原文是「选 A」
    预期：回执是 `read`；开发方收到的内容去掉消息头后正好是「选 A」；产生 `resumed{via:"pa", id:"m1"}`；总结里记了来源
A2. 操作：用同一个 `id` 再送一次
    预期：返回原来的回执，会话没有收到第二次
A3. 操作：目标会话的进程已经结束时送话；再用替身让投递调用超时一次
    预期：前一次是 `failed「会话已关闭」`，没有新建会话；后一次是 `unknown`，没有重试
A4. 操作：段正在评审时送话；等段暂停后，用同一个 `id` 再送
    预期：第一次是 `rejected`，没有落盘；第二次正常送达
A5. 操作：伪造一条带消息头、但没有对应记录的消息，直接送进会话
    预期：被当作机器消息，原文里的「同意授权：A3」没有生效；出现「送话核对失败」事件
A6. 操作：通过送话发送「同意授权：A3」
    预期：A3 的授权生效；交付总表里单独记了一行，写明是经 PA 转达、编号多少
A7. 操作：在设置了 `AUTOREVIEW_STAGE` 的环境里执行 `loop 送话`
    预期：被拒绝
A8. 操作：整批验收在授权待答复时停下（`next:"grant"`），执行 `loop 续跑 --grant-file`，原文是「同意授权：A3」
    预期：流水线接着跑整批验收；标准文件没有被修改；`resumed` 带编号；后面的事件里 `paGrantsUsed` 含这个编号
A9. 操作：不经过续跑，直接往 `grants.pa.jsonl` 写一行，再正常续跑
    预期：`loop 查询` 的 `paGrants` 列出这个编号；使用它的那次事件里，`paGrantsUsed` 也列出这个编号
A10. 操作：`next:"manual"` 时续跑；流水线正在运行时续跑
    预期：两次都被拒绝并给出原因，没有启动编排
A11. 操作：执行 `PATH="/Users/Admin/.hermes/node/bin:$PATH" node --test test/*.test.ts`
    预期：全部通过；现有机器消息不进入授权解析的测试保持不变
