# 流程对齐 1：流程顺序、开工强制检查、交付证据

## 目标

用户不相信 Loop 报的「完成」，因为看不到测了什么、验了什么。2026-11-04 核实到的情况：

- Loop 改它自己的代码时，开发空间里没有 `.autoreview.json`。运行版的这个文件被 `.git/info/exclude` 排除，不进 Git，开工时也不复制。于是 Loop 当成「没配门禁」直接跳过。交付记录写「门禁：未配置；验收：未配置」，只要评审通过就报完成。
- 写了验收标准、项目却没配验收时，验收被悄悄跳过。
- 段没有记下门禁结果时，交付记录填「完成资格已确认」（`merge-queue.ts` 写交付记录处），看起来像通过。
- 总结里满是编号和内部用语，用户看不出每条需求到底验了什么。

本段要做到四件事：

1. 开发空间里 Loop 用的配置和运行版一致。
2. 走哪条流程由批次写明，配置对不上就在开工时拒绝。
3. 每轮顺序改为评审 → 测试 → 验收。
4. 完成时给用户一份交付报告，按需求逐条列出证据。

## 已拍板

- 流程只有两条，由驱动任务的协作者在批次里写明，Loop 不猜：
  - 带验收：开发 → 评审 → 测试 → 验收 → 提交
  - 不带验收：开发 → 评审 → 测试 → 提交

  两条都必须跑测试（项目门禁）。字段名和写法由开发方按 `批次.json` 现有习惯定；不写时按「带验收」处理。
- 开工强制检查。以下任一情况，开工都直接拒绝：不派发开发方，不建开发空间，并说明缺什么、怎么补。
  - 项目没有门禁配置。
  - 段走「带验收」，项目却没配验收。
  - 段走「不带验收」，它的提示词里却写了「## 验收标准」。
- 开工输出写明每段走哪条流程（把步骤完整写出来），以及这样选的依据。
- 运行版的 `.autoreview.json` 不在 Git 里（被忽略）时，开工把它带进开发空间。开发空间里已有同名文件时不覆盖，并说明。
- 每轮顺序改为：评审 → 测试 → 验收。
  - 评审有必修：直接打回，这一轮不跑测试和验收。
  - 评审通过、测试失败：带上测试输出打回，不跑验收。
  - 测试超时、命令找不到这类环境问题：仍按现有规则暂停交给用户。
- 交付报告放在段总结开头；单段完成通知和交付记录里给出它的路径。内容如下：
  - 每条验收标准写原文（操作、预期），不能只写编号。每条写清实际执行的命令或脚本、看到的结果、结论。
  - 测试：执行的命令、总数、失败数、耗时、日志路径。
  - 评审：结论、必修条数、返修次数。
  - 哪一项没跑，就写「没跑」和原因。不准写「通过」「完成资格已确认」这类没有依据的字样。
- 交付记录里，段的门禁、评审、验收结论缺失时写「没有记录」，不再填「完成资格已确认」。
- 测试按功能命名和组织；不新增名字里带「返修N」「本批」的测试。

## 边界

- 基于 dev 最新代码开发（已合入「配置核对与卡住通知」）。
- 相关位置以开工时的代码为准：
  - 一轮的顺序：`review.ts` 的 `runOneReviewRound`（门禁 `gateStep`、评审 `callReviewer`、验收 `acceptanceStep`），pi 和 Claude/Codex 共用这一处。
  - 开工：`loop.ts` 的 `cmdOpen`、`copyLocalFiles`。
  - 开工检查：`preflight.ts`。
  - 配置读取：`config.ts`。
  - 段完成结论：`pipeline-core.ts` 的 `completionChecks`。
  - 交付记录：`ledger.ts` 和 `merge-queue.ts` 里写交付记录的地方。
  - 验收总结里的「实际执行」：`acceptance-core.ts`。
- `README.md` 的「门禁」「一轮的顺序」「流水线与批次」「开工」各节，以及 `工具清单.md`，同步改成新行为。
- 改了已有测试的断言时（例如「门禁先于评审」），交付时列出改了哪些、为什么改。
- 不改：评审和验收提示词的判定规则、验收标准的解析规则、`test/e2e.mjs`，以及合入队列的排队和合入行为（这些留给下一段）。
- 测试放在 `test/`。宿主、开发会话、评审方、验收方用替身，项目用系统临时目录里的临时仓库。
- 开发方不提交。

## 验收标准

A1. 操作：临时项目的 `.autoreview.json` 配了门禁，但被忽略、不进 Git；执行 `bin/loop 开工`，然后让开发方交付
    预期：开发空间里有同样的门禁配置；这一轮总结里有门禁的实际执行结果，不是「未配置」
A2. 操作：项目没有配门禁，执行 `bin/loop 开工`
    预期：开工失败，输出写明缺门禁、怎么配；没有建开发空间，也没有派发开发方
A3. 操作：段走「带验收」，项目没配验收，执行 `bin/loop 开工`
    预期：开工失败，输出写明缺验收配置、怎么配；没有派发开发方
A4. 操作：段走「不带验收」，提示词里写了「## 验收标准」，执行 `bin/loop 开工`
    预期：开工失败，输出写明流程和验收标准对不上
A5. 操作：配置齐全的两段批次（一段带验收、一段不带）执行 `bin/loop 开工`
    预期：输出分别写出「开发 → 评审 → 测试 → 验收 → 提交」和「开发 → 评审 → 测试 → 提交」，以及各自的依据
A6. 操作：开发方交付，评审给出必修
    预期：带必修打回；这一轮门禁和验收都没有执行
A7. 操作：开发方交付，评审通过，门禁失败
    预期：带门禁输出打回；这一轮验收没有执行
A8. 操作：评审、门禁、验收都通过后，打开这一段的总结
    预期：开头是交付报告：每条验收标准的原文、实际执行的命令或脚本、看到的结果、结论；测试的命令、总数、失败数、耗时；没跑的项写「没跑」和原因
A9. 操作：段完成记录里没有门禁结论时，查看交付记录里的这一段
    预期：写的是「没有记录」，不出现「完成资格已确认」
