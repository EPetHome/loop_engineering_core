# 流程对齐 3：返修减负

## 目标

现在每一轮返修后，验收都要把全部条目从头重跑一遍（验收不复用旧的通过结论）。一批里只改了一两处，也要把整套验收再跑一遍，返修很重。用户要求返修不能太重。

## 已拍板

- 一段之内：
  - 第 1 轮做完整验收。
  - 之后各轮返修，只验上一轮「不通过」「部分验证」「无法验证」的条目。
  - 这些条目都通过后，完成前再把全部条目完整验一次，全部通过才算完成。
  - 完整验收时，之前通过的条目如果失败，照常打回，打回消息写明「之前通过，这次失败」。
- 多段批次的整批验收同样处理：返修后只重验没过的条目，完成前做一次完整验收。
- 每轮总结写明：本轮验了哪几条（写标准原文），哪几条沿用上一轮的结论。
- 第一段做的交付报告里，每条写明最终结论来自哪一轮的完整验收。
- 用户发来新一版验收标准时，从完整验收重新开始。
- 测试（门禁）每轮仍然全量跑；评审规则不动。

## 边界

- 在第二段完成后的批次分支上继续。
- 相关位置以开工时的代码为准：
  - `review.ts` 的 `acceptanceStep`、`runOneReviewRound`
  - `acceptance.ts` 的 `runAcceptanceStage`
  - `acceptance-core.ts`（条目、结论、总结）
  - 整批验收：`pipeline.ts`
- `README.md` 里「自动验收」相关的描述同步更新，包括把「不复用旧通过结论」改成新规则。
- 改了已有测试的断言时，交付时列出改了哪些、为什么改。
- 不改：验收方提示词的判定规则、验收标准的解析规则、`test/e2e.mjs`。
- 验收方用替身，项目用系统临时目录里的临时仓库。
- 测试按功能命名；不新增名字里带「返修N」「本批」的测试。
- 开发方不提交。

## 验收标准

A1. 操作：首轮验收 5 条里有 2 条不通过；开发方返修后再交付
    预期：第二轮只验那 2 条；总结写明本轮验了哪 2 条，其余 3 条沿用上一轮
A2. 操作：返修后那 2 条都通过
    预期：完成前又完整验了全部 5 条；5 条都通过才标完成
A3. 操作：完成前的完整验收里，之前通过的一条失败了
    预期：打回开发方，消息写明这条之前通过、这次失败
A4. 操作：返修中途，用户发来新一版验收标准
    预期：下一轮按新标准做完整验收
A5. 操作：多段批次整批验收有 1 条不通过，退回对应的段返修后再跑
    预期：整批验收这次只验那 1 条，通过后再完整验一次全部条目
