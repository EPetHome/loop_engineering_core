# 用户追加需求（2026-10-05）：评审不再依赖交付标记

本条是用户在本轮返修中追加的需求，和本轮 5 条必修一起处理。交付时，请在交付说明里写明「已按 docs/prompt/补充需求-不靠标记自动评审.md 改动」，方便评审方对照。

## 为什么改

现在必须由开发方在最后一行写【交付完成】，评审才会自动开始。ds4.1 这类模型从来不写这一行，评审就一直等用户手动输入 `/review`。是否开始评审，应该由程序判断，不能依赖模型自觉。

## 新规则（pi 扩展、Claude Code 插件、Codex 插件三处都要做到）

开发方停下时（pi 是 `agent_settled`，宿主是 `Stop`）：

| 最后一行 | 工作区与「上次成功评审时」的指纹相比（还没评审过就和开发基线比） | 动作 |
|---|---|---|
| 【需要你决定】 | 不看 | 暂停并通知，不评审（与现在相同） |
| 【交付完成】 | 不看 | 评审（与现在相同） |
| 没有标记 | **有变化** | **直接评审**，和写了【交付完成】一样 |
| 没有标记 | 没变化，且刚发过返修消息 | 暂停，原因写「返修后没有任何改动」 |
| 没有标记 | 没变化，且不是刚返修 | 什么都不做（普通对话） |

- 「未交付提醒」这个功能删掉。现在的提醒逻辑（`autoreview.ts` 的提醒分支、`hosts/hook.ts` 的 `remindUndelivered`）改成上表第 3、4 行的行为。
- 指纹沿用 B4 的定义：HEAD 提交、工作区 tree、未跟踪文件的 hash。取证失败就暂停，与现有规则一致。
- 状态是「暂停」时不自动评审（与现在相同），用户用 `/review` 恢复。
- 开发约定 `CONVENTION` 的文字改成：「交付时最后一行写【交付完成】，评审会立即开始；不写的话，程序检测到改动也会自动评审。需要用户决定时，最后一行写【需要你决定】。收到自动评审消息后，逐条写「第 N 条：已修」或「第 N 条：异议：理由」。」
- `/review` 保留，作为手动入口。

## 顺带处理：评审重试和 Stop Hook 时限（用户默认选 A）

宿主 Stop Hook 的上限是 3700 秒。一轮评审的两次尝试（首次加 1 次重试）**共用 60 分钟**：重试只能用剩下的时间，剩余不足 1 分钟就不再重试，直接暂停（原因写「评审超时」）。pi 扩展也按同样规则处理。

## 插件更新

- **不要改 `plugins/autoreview/hooks/hooks.json`**。Hook 命令直接执行仓库里的 `hosts/hook.ts`，改完代码后 Claude Code 和 Codex 都会自动用上新代码；`hooks.json` 不变，Codex 的信任哈希也就不会失效。
- 改完后核对两边确实跑的是新代码：Claude Code 用 `claude -p`、Codex 用 `codex exec`（带 `--dangerously-bypass-hook-trust` 只用于联调），各跑一个「开发方不写标记，但改了文件」的玩具场景。期望：自动评审，零干预。
- pi 扩展：新开的 pi 会话会自动加载新代码。本会话不要 `/reload`。

## 测试

- 删掉「未交付提醒」相关的旧测试，补上新规则的测试：
  - 无标记 + 有改动 → 评审
  - 无标记 + 无改动 → 不评审
  - 返修后无标记且无改动 → 暂停
  - 【需要你决定】→ 暂停
  - 两次尝试共用 60 分钟：首次用掉 59.5 分钟后不再重试
