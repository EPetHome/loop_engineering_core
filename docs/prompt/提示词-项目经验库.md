# 项目经验库：注入开发和评审，起草候选，由用户批准写入

## 目标

pi 每开一个新会话，都不记得这个项目以前犯过的错。Codex 统计了 Promate 的 96 个开发会话：35% 的产品问题是换个会话又犯一次（`/Users/Admin/Desktop/loop/eval/经验/Promate-候选-20261027.md`，只读）。背景见 `/Users/Admin/Desktop/loop/docs/方案-开发测试闭环.md` 第 5.1 节（只读）。

给每个项目一份经验清单 `<项目根>/.autoreview/经验.md`（项目根就是 `.autoreview.json` 所在的目录），并做到以下五件事：

1. **注入开发方**：pi 扩展（`autoreview.ts` 追加系统提示的地方）和 Claude Code / Codex 宿主（`hosts/hook.ts` 注入开发约定的地方）都带上这份清单，要求开发方动手前对照。
2. **注入评审方**：评审输入里加一节「对照清单」，走现有「项目来源与代码定位」的同一路径。这一节里写明：评审发现的问题属于某条经验时，标出它的编号。
3. **返修标注复发**：返修消息里，凡属于某条经验的必修，注明「经验 Pxx，第 N 次出现」。N 在该条已有次数上累加；计数存在本机，不改项目文件。
4. **起草候选**：会话完成时，如果本会话出现过必修，就用评审模型做一次独立的只读调用，逐条判断：命中已有经验、与已有候选同类、还是新问题；新问题按清单格式起草成候选。候选存在本机，不写项目。同一类问题要在 2 个以上不同的开发会话里出现过，才列进总结开头的「需要你做的事」。
5. **用户批准**：`bin/loop` 新增一个子命令，能列出待批候选、批准（写进项目的经验.md）、拒绝（以后同类不再提），还能把一份现成的候选文件导入成待批候选。首批就用 Codex 的草稿导入。

## 已拍板

- 清单里的每一条都只能由用户批准后写入。开发方、评审方和 Loop 程序都不能自己往项目里加。
- 不依赖 Codex 或协调方在场：候选的收集和起草都由 Loop 自己完成。
- 每条的格式：标题一行，下面「现象」「根因」「正确做法」各一行；次数、证据、失效条件写在这三行下面。注入时只带标题和这三行，不带证据，以控制 token。
- 上限 30 条。超过时照常注入，同时在总结的「需要你做的事」里提示合并或退役。
- 没有经验.md 的项目，开发方和评审方拿到的输入与修改前完全一致。
- 起草候选失败时，只在总结里提示，不影响会话的完成状态，也不暂停。
- 首批：用户已批准 `/Users/Admin/Desktop/loop/eval/经验/经验-草稿.md` 的全部 20 条。本任务只做导入和批准能力，并用临时项目验证；真正写进 Promate，由用户在合入后执行命令完成。

## 边界

- 代码主要涉及 `autoreview.ts`、`hosts/hook.ts`、`core.ts`、`review.ts`（评审输入与返修消息）和 `loop.ts`（新子命令）。测试放在 `test/`，项目和数据全部在系统临时目录里造。用法同步到 `README.md` 和 `工具清单.md` 的 `bin/loop` 一节。
- 不改 `review-prompt.md` 的评审规则正文（标编号的要求写在注入的那一节里），不改 `test/e2e.mjs` 的场景和断言，不改 `eval/`、`iusses/`、`temp/`。
- 不写任何真实项目的文件（包括 Promate），也不写真实的 `~/.pi-autoreview`。
- 批准写入时，如果该项目还有进行中的开发会话，就先不写，提示稍后再批。
- 不提交，不推送。

## 验收标准

A1. 操作：造一个临时项目，`.autoreview/经验.md` 里写 3 条经验；启动一次开发会话，跑完一轮评审。
    预期：开发方的系统提示和评审输入里都有这 3 条（标题和三行），都不带证据部分。
A2. 操作：把这个项目的经验.md 删掉，再跑一遍。
    预期：开发方的系统提示和评审输入与修改前一致，没有经验这一节。
A3. 操作：让评审替身判出一条属于经验 P02 的必修。
    预期：返修消息里写着「经验 P02，第 N 次出现」，N 等于这一条原有的次数加 1。
A4. 操作：两个不同的开发会话先后完成，都出现了同一类新问题的必修（起草调用用替身）。
    预期：第一个会话完成后不提示；第二个完成后，总结的「需要你做的事」里列出这条候选；项目文件没有任何变化。
A5. 操作：执行新子命令列出候选，批准一条，拒绝一条。
    预期：批准的那条按格式追加进经验.md；被拒绝的那一类以后再出现，也不再提示。
A6. 操作：在有进行中开发会话的项目上批准一条候选。
    预期：不写入，并提示稍后再批。
A7. 操作：把 `/Users/Admin/Desktop/loop/eval/经验/经验-草稿.md` 导入一个临时项目，然后全部批准。
    预期：临时项目的经验.md 里正好 20 条，每条都符合已拍板的格式；草稿文件本身没有变化。
A8. 操作：执行 `PATH="/Users/Admin/.hermes/node/bin:$PATH" node --test test/*.test.ts`。
    预期：全部通过。
