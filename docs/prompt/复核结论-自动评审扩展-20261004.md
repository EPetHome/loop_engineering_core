## 三、新发现的必修（提交阻塞）

### B1：中文及需转义的未跟踪文件被静默排除，评审改文件也可能“通过”

- **位置**：`autoreview.ts:129-134,166-173`；违反第三章第 9 条及 6.9。
- **反例**：git 默认 `core.quotePath=true`，新增未跟踪 `说明.md` 后，`ls-files --others --exclude-standard` 输出带双引号和八进制转义的路径。代码直接将显示字符串传给 `hash-object`，文件不存在，非零结果又被直接丢弃。评审新增、修改或删除该文件，前后 `untracked` 都没有它，无法触发暂停。含制表符/引号的路径同类，`.trim()` 还会破坏首尾空白路径。
- **本次只读证据**：对仓库中已存在的未跟踪 `docs/prompt/提示词-复核-自动评审扩展.md`，使用 `git -c core.quotepath=true ls-files --others --exclude-standard -- <路径>`，将输出原样传给 `git hash-object`，得到 `fatal: could not open '"docs/prompt/\346…md"' for reading: No such file or directory`。未修改该文件。
- **最小修正方向**：路径列表用 `-z` 按 NUL 分隔，不 trim/不把 git 显示形式当真实路径；hash 失败暂停而非跳过。补中文及特殊字符路径的指纹回归。

### B2：git 取证失败被解释成干净 HEAD 或无改动，保护失效仍可宣布完成

- **位置**：`autoreview.ts:125-134,167-173,292-305`；违反第三章第 7、9 条。
- **反例**：仓库存在未合并索引条目时 `stash create` 失败；前后均回退 HEAD。评审修改已跟踪冲突文件后，两个 tree 仍是 HEAD tree，未跟踪列表不变，扩展不会暂停。另一个反例是保存的 stash 对象已不可读：`git diff <旧快照>` 非零、stdout 为空，代码仍把它渲染为“无受跟踪改动”送审。
- **原因**：没有区分“成功但 stdout 空”和“命令失败/超时”；`diff.code`、`stat.code` 等不参与决策。无初始提交的 git 仓库也走这条静默降级路径。
- **最小修正方向**：所有用于建立材料或证明未改动的 git 调用必须检查退出码/终止状态；只有成功的空 stash 才能回退已解析的 HEAD。无法取证就暂停并保留错误摘要，不能生成肯定性结论。

### B3：失败评审也推进复查基线，/review 继续时会漏掉未审改动和旧必修

- **位置**：`autoreview.ts:292-298,337-359,398-403`，`core.ts:163-168`；违反第三章第 7、8 条和 6.7 的续审语义。
- **反例 A**：首轮有改动 A→B，评审因启动/凭据错误两次失败，根本没获得有效评审会话。代码仍记录失败轮并令 `lastSnapshot=B`。用户修好环境后 `/review`，轮次为 2，输入只有 B→B 的空 diff，不再带需求原文，上一轮必修也为“无”。这不是继续审原来的成果。
- **反例 B**：第一轮有必修 X，第二轮失败；失败记录的 `mustFixRaw=""` 成为最后一轮。第三轮 `/review` 取它作为上一轮必修，X 不再出现在复查清单；暂停总结也不把 X 列入“未解决的必修”。历史各轮仍留有文本，但返修流程已失去有效待办。
- **最小修正方向**：区分调用记录与成功评审检查点。失败不能推进已审范围或清空待复查必修；恢复要重送未成功审过的输入，首轮未成功时仍须带需求。补“失败两次→/review→输入完整性”测试。

### B4：干净快照保存字符串 HEAD 而非对象 id，基线会漂移；指纹不同也可能放行

- **位置**：`autoreview.ts:126-139,154-161,294-295,335-355,519`；违反 6.9 的快照含义及第三章第 9 条。
- **反例 A**：干净仓库开工，baseline 存为字符串 `HEAD`；开发期间发生提交，交付时 `git diff HEAD` 不再比较开发开始时的提交，已提交的本轮改动消失。扩展不自动提交，不代表外部用户或开发方永远不提交。
- **反例 B**：评审前干净，before.ref=`HEAD`、before.tree=A；评审违规修改并提交后再次干净，after.ref=`HEAD`、after.tree=B。tree 不同，但 `git diff --name-only HEAD HEAD` 是空；`changed.length===0`，流程继续。代码虽计算了不同的 fingerprint，却从未用它决定暂停。
- **最小修正方向**：干净快照也固定为当时 commit id；直接比较指纹决定是否暂停，变化列表只用于解释，不能反过来作为唯一保护判据。

### B5：新会话第一条命令直接 /review，已跟踪改动全部漏出评审输入

- **位置**：`autoreview.ts:423-438,517-525,292-305`；违反 6.3“立即评审当前改动”，也与 `README.md:26` 不符。
- **反例**：工作区已有 `calc.py` 的未提交修改，加载扩展后尚未发模型提示，直接输入 `/review`。扩展命令不会经过 `before_agent_start`，因此 baseline 未设置；294–295 行主动构造空 stdout，最终输入显示“无受跟踪改动”。这个手动命令并没有审它承诺的当前改动。
- **最小修正方向**：手动首审明确初始化合适的比较基线（例如固定的 HEAD），不能以缺 baseline 为由静默传空材料；需求不足可明示，不应伪装成无改动。补无需模型的入口测试。

### B6：暂停兜底本身再次抛错，磁盘异常不再是“只暂停”

- **位置**：`autoreview.ts:237-239,274-281,404-413,438,545`；违反第三章第 7 条。
- **反例**：项目内开发成果正常，但 `~/.pi-autoreview/<项目>/` 不可写。写输入/总结抛 EACCES，`startReview` 捕获后调用 `pause`；`pause` 再次写同一路径，先于通知又抛 EACCES。`startReview` 以 `void` 发起，没有 rejection 收口，通知也不执行。状态 appendEntry 或初始 setStatus 失败还可能在 try 之前逃逸。
- **结果**：至少产生未处理拒绝且没有预期降级提示；默认 Node 行为下可能导致进程退出，而不是稳定暂停。文件系统不可写当然无法强行写总结，缺陷在于没有安全降级。
- **最小修正方向**：收口整个异步任务，暂停记录、总结写入、通知分别容错；总结失败仍应尽力提示位置和原因，绝不让错误处理再次变成未处理拒绝。补写盘失败测试。

### B7：后台评审无生命周期清理，/reload 可并发同一评审会话并触发过期 API 异常

- **位置**：`autoreview.ts:193,243-264,391-413,491-504,533-552`（无 `session_shutdown`/取消处理）；违反第七章第 3 条的单评审和第三章第 7 条。
- **反例**：评审在后台运行时用户 `/reload`。旧 `pi.exec` 没有传 signal，也没有 shutdown 清理，评审子进程继续。新扩展恢复 `phase=reviewing` 后直接改 idle、清锁；用户 `/review` 又启动同一个评审 id 的第二个进程。旧任务结束后调用快照/暂停/状态 API，这些 API 已失效，错误处理也再次调用失效 API。
- **独立 API 证据**：`$PI/dist/core/agent-session.js:2603-2607` 在 reload 发 shutdown 后 invalidate；`$PI/dist/core/extensions/loader.js:288-306` 的 appendEntry/exec 检查 active，exec 没有自动生命周期 signal；`$PI/dist/core/extensions/runner.js:441-449,552-571` 使旧 ctx 抛错。
- **最小修正方向**：为后台任务建立可取消生命周期，在 shutdown 时停止/收尾并持久化暂停；新运行实例不得假设旧评审已退出，旧任务不能继续调用失效上下文。补重载期间单评审及安全暂停测试。不是要求支持多开发方并行。

## 四、Q3：pi -c 恢复的静态推演

1. **正常保存、确定重开同一开发会话**：`saveState` 追加完整状态；下一进程的 `session_start` 从最新 custom entry 恢复 requirement、baseline、lastSnapshot、rounds、repairs、reviewerSessionId（`autoreview.ts:198-200,496-502`）。假设原来评审 2 次、返修 1 次，恢复后仍是 2/1，同 id，下一轮编号为 3（403 行）。
2. **计数不是每次启动清零**：只有显式 `/review`，或从 done 开始下一次评审，才重置 repairs（398 行）；这是 6.3 的要求。轮次没有重置。暂停会提示输入 `/review`（510–512 行），不会开一个新开发会话。
3. **中断评审不能宣称可靠续跑**：正在评审的状态只变 idle，不写“上轮中断”暂停、不通知、不确认子进程是否存活（504 行）。已完成调用记录能恢复，不代表进行中的评审、待送返修消息具有事务性恢复。B3/B7 也分别影响失败续审及旧评审仍在运行的情况。
4. **裸 `pi -c` 不保证选中开发会话**：子评审没有独立 `--session-dir`（258–264 行），默认与开发会话同 cwd 分组。pi 按文件 mtime 选最近会话（`$PI/dist/core/session-manager.js:445-457,1354-1361`）。正常评审后开发方会再保存状态，通常重新成为最新；但评审期间父进程意外退出、评审文件更新更晚时，`pi -c` 可以选中评审会话，里面没有开发方的 autoreview-state。建议隔离评审存储目录；当前至少应记录开发 id 并用 `--session <开发id>` 精确恢复。这是条件性风险，不是声称每次 -c 都会选错。
5. **分支不是线性历史**：状态和最后助手文本读取均使用 `getEntries()` 而非当前 `getBranch()`（297、496、537 行）；`/tree` 后恢复可能读到弃用分支。保存还直接传同一个可变 state 对象（198–200 行），而 pi 内存 entry 不深拷贝（`$PI/dist/core/session-manager.js:901-910`），不能把内存历史当不可变快照。当前线性退出重开不受此引用问题影响，分支/导航需后续专测。

**结论：线性、已落盘、明确选中同一个开发会话时，计数和评审 id 的恢复成立；“任意中断后只用 pi -c 就可靠接着跑”不成立。**

## 五、Q4：快照范围与缓存误停

普通已提交 git 仓库、路径可正确处理、git 成功且 HEAD 不漂移时，stash tree + 未跟踪内容 hash 的比较思路成立；未跟踪文件只附路径供评审自行读取，是规格明确允许的，不要求 git diff 包含其正文。

| 项目情形 | 是否容易暂停 | 原因 |
|---|---|---|
| `.gitignore` 正确覆盖未跟踪缓存/输出 | 通常不会 | `ls-files --others --exclude-standard` 排除它们；stash 不纳入这些未跟踪文件。 |
| 有 `.gitignore`，但没覆盖该缓存路径 | 会 | “有文件”不等于“规则匹配”；首次生成或内容变化就进入差异。 |
| 无项目 `.gitignore`，生成 `__pycache__/` | 高风险 | 通常没有内部忽略规则。新建/重建 pyc 会进入指纹；每次删除后重跑会重复触发。 |
| 无项目 `.gitignore`，生成 `.pytest_cache/` | 不应一概说会 | 标准 pytest 通常自己写内部 `.gitignore`（`*`），仍被 `--exclude-standard` 忽略；没有这种内部规则或文件已跟踪时才会进入检测。此处为机制分析，未运行 pytest。 |
| 无匹配规则的 `node_modules/.cache`、dist/build 输出 | 高风险 | Git 不按目录名字自动认作缓存；本地/全局 exclude 或目录内部规则可能改变结果。 |
| 缓存/构建文件已被 git 跟踪 | 会，且根目录忽略规则无效 | 已跟踪文件纳入 tree，`.gitignore` 不能令其自动退出跟踪。 |

这是相对业务意图的“误停”：检测到的写盘确实发生，但不一定是评审改源码。R5 的 pycache 暂停符合当前规格，却仍是需要管理的日常体验风险。应提示用户预先配置忽略规则或使用不落盘的测试选项；不应让扩展自行改项目 `.gitignore`，也不应为少误停而默默关闭保护。

另有 **S3：未跟踪文件后续修改未进入本轮材料**。首轮新建 `new.py` 后，名字记进 `lastUntracked`；下一轮修改同一个未跟踪文件，`newUntrackedFiles` 只做名字差集（`autoreview.ts:166-173,351-352`），git diff 又看不到它。上一轮已有必修的位置可被定向复查，但该文件的新缺陷不易发现。它沿用了派单 6.9 的简化方案，不据此追加一项擅自扩大的硬要求；建议后续保存未跟踪内容 hash，至少列出“本轮改过”的路径。

保护范围还不包含 ignored 文件、一般 `.git/` 元数据和项目外文件；允许 bash 的评审不是沙箱。不能把当前机制宣传成“技术上保证不能写文件”。

### ② nudge 有没有掩盖产品缺陷

**掩盖了零干预触发的验收缺口，没有使后半段接线测试完全失去价值。**

- `test/e2e.mjs:22-23,290-300` 在无标记时最多追加八次模型提示，结果不要求 `nudges===0`。
- 它仍能证明“模型后来写出标记→扩展评审→返修/暂停/总结”的条件链路。
- 它不能证明“开发方首次完成任务→无人干预自动评审”。若去掉测试工具的提醒，这类会话按 `autoreview.ts:537-550` 会静默停住。
- 当前规格本来要求平常无标记不做事，所以这主要是模型遵约依赖和产品验收不足，而不是据此认定触发函数写反了。

### ③ gpt-6.1-sol max 风险多大

**未验证、不能给成功率，也不能因 max 档位就认为已消除风险。** ds4.1 六次漏写是该模型/提示组合的警报，不是 gpt-6.1-sol 的统计样本。模型切换、长上下文、其他项目规则和异常中断仍可能漏写。影响是漏评而非安全地完成，用户又可能已离开屏幕，因此不能忽略。

建议修完阻塞项后，用用户真实启动配置做无 nudge 验收；把“自动触发”和“人工提醒后链路”分成两项结果，至少包含首次交付和返修交付，不把有 nudge 的通过合并为全自动通过。本次不执行这些测试。

### ④ 是否需要产品兜底

**建议加非侵入提示，不建议偷偷自动发新模型消息或绕过标记直接评审。** 开发方 settled、无交付/决定标记、且相对本次开发基线确有改动时，向用户提示一次：“检测到改动，但未收到【交付完成】；如已完成，请输入 /review。”同一批改动去重，避免普通对话反复打扰；已暂停/正在评审不再重复提醒。

这会调整“平常无标记什么都不做”的已拍板规则，应由用户确认并补单测；不是要求今天临时实现。现阶段至少在 README 告知：没有标记不代表已评审，可用 `/review-status` 查询，确认工作完成后 `/review` 手动启动。

## 决策卡
- 结论：🔴 不能提交为日常可直接使用版本；B1–B7 会造成漏评、漏检或不安全异常退出。
- 需要用户定的事：是否将“有改动但无标记时提示 /review”纳入产品规则。
