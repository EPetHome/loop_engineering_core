## 已拍板与实现落点

### 1. 卡与输入

- 保持 `version:1` 和前三步合法卡兼容。开发卡固定顺序为开发评审 → 可选测试 → 可选验收 → 可选提交 → 可选部署。**部署必须位于提交之后；卡没写部署即不部署，即使项目配置 enabled=true。** 卡写部署但配置缺失、未启用或 cmd/check 不合法，在建立资源前明确拒绝。继续复用 `.autoreview.json.deployment` 的 enabled/cmd/check/timeoutMin，不另造脚本 DSL 或第二套部署配置。
- 只评审卡采用 `nature:"评审"`、`flow:["评审"]`，一张卡一个指定的已有提交比较（显式 base/head；字段布局按现有 review-only 能力做最小一致设计，并在帮助和示例里完整写明）。首次启动解析成固定 commit/tree；后续分支移动不能悄悄换评审对象。需求/标准/说明文件仍作只读输入；不要求伪造开发提示词、写范围或 dev 发布目标才能只评审一个已有提交。
- 不允许只评审卡混入开发评审、测试、验收、提交、部署，不通过只评审结果取得开发合入资格。多任务必须验收的底线不豁免，因此本步只评审卡限定单任务并清楚诊断。纯 `[测试]` 仍按原底线拒绝。
- 相关输入分别计算：只改部署配置不重跑之前的评审/测试/验收；部署自身绑定发布提交、部署配置、方法文件及执行目录身份。只评审绑定明确的 base/head、需求/标准、模型和时限。不能改坏前两步真实旧账本的输入指纹兼容，不通过迁移伪造旧结论。
- 运行中修改仍用受控改卡，下一安全边界生效，直接改文件暂停；不得用改卡把只评审变开发、换受评提交或在发布后悄悄追加部署授权。已冻结部署配置变化不能继续旧命令，也不能静默采用新命令。

### 2. 部署节点与发布生命周期

- 新部署执行器只依赖内核和共享执行能力，不引用 `submission-node.ts` / `development-node.ts` 或旧队列状态。从旧实现抽出必要的命令/检查/回退能力，旧路径维持原行为直到第五步；不要复制整套队列或重建通用流程引擎。
- 正常调度在本批提交的本地合入与 origin/dev 推送成功后执行部署。无部署卡保持原流程；推送失败、提交意图未完成、Loop 外合入没有明确发布身份时均不自动部署、不自动重推。部署失败不扣开发/测试/验收返修次数，也不抹掉之前通过和发布事实。
- 现有 `mergeManaged`、`resumeManaged`、各宿主及 CLI 有“有 publication 就返回/释放”的路径；必须逐个核对并统一成“发布 → 本卡安排的部署 → 收尾”，不能只有一个入口能部署，也不能在部署前删掉它需要的空间。重复回调/续跑不得重复部署或重复回退；未知副作用的在途尝试保留现场并提示人工核对，不能自动当作没跑过。
- 候选树通过后压缩提交会改变 commit，部署必须绑定**实际发布提交及其相同的已检查树**。执行 cwd、实际检出版本、发布身份在 cmd/check/回退各边界重新核对，不部署桌面脏内容或较新的其他批次。复用旧部署“与同项目检查互斥”的实际执行边界及进程登记，不用测试/验收全机槽冒充项目部署锁，不长时间占账本短锁。
- cmd 失败、check 失败、超时、取消、资源释放未知分别记录。沿用现有语义：cmd 失败保留日志并停止；cmd 成功而 check 失败，只有能证明目标仍是本批发布且上一版明确、无脏内容/别批活动时，执行安全回退并重新部署上一版。目标已前进、来源不明、停止/取消、消费者未释放则不回退。回退产生的预期版本变化须在事务中登记，不被普通源码变化守卫误判；命令擅自改源码仍作废。
- 不强推，不用 reset/stash 处理用户成果。旧部署回退只处理本机目标/运行版本，没有远端强推回退；本步保留这一边界并明确展示“当前本地/远端/运行版本”和回退状态，不能称远端已回退，也不能再次自动推送消除差异。不要引入未授权的生产远端撤回策略。
- 部署结果/尝试/日志写同一内核账本，带命令、发布 commit/tree、时间、配置版本、失败类别、回退过程和释放证明。支持已实现且安全的“只重跑部署”路径：不重新开发/评审/测试/验收/提交/推送；已成功的同一部署只复用，未确认的在途副作用不能盲重跑。失败回退后旧发布已不在当前目标时先拒绝并说明真实版本，不能自动重发旧版本。

### 3. 只评审节点

- 复用 `static-review.ts` 的真实评审调用、格式解析、有界调用重试和证据；报告保留既有 `review-only.ts` 的 base/head、改动范围、必须修改/建议、耗时、模型和证据。新节点不能调用带准备/验收/队列编排的 `runReviewRound`，也不能调用开发交付自动提交来形成候选。
- 检出指定已有提交到登记的隐藏隔离目录，运行前后守卫该目录/索引和输入；当前用户工作区的暂存、未暂存、未跟踪内容不进入评审、不被修改。只读本地已有对象，不 fetch 或切用户分支。无开发宿主、无返修信封、无产品修复计数、无测试/验收/提交/部署命令。
- 有必须修改就记录“不通过”并只出报告，不退回任何人；建议可延期，不当必须修改。调用失败/超时/格式错误记没验证并保留真实证据。`重跑 --node 评审` 只调用此节点，绑定原候选和已确认输入，不转成开发续跑。
- 检查对象若运行期间被改动，这次结论作废；未知消费者或脏目录不强制删除。正常结束释放登记的临时检出、保留报告/账本和证据，不新建可发布的任务提交。不能因已有 head 本来就在 dev 上就显示“已合入（Loop 外）”。
- 保持五种批次状态约定，不为评审发明合入资格：查询明确显示“只评审已结束”、报告结果及资源状态，不误称进行中/可合入/已合入；可沿用“等你决定”并说明仅供查看报告，无自动返修。只评审 `合入`（含接受未验证）必须拒绝，因为用户安排的是只出报告。
- 现有直接 `bin/loop 评审` 入口保留，不在第四步删除或无意改变其行为；新卡路径纳入统一内核状态/命令，三宿主查同一账本。
