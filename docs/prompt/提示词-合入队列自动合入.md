# 合入队列：满足条件自动合入，合入不再触发评审

## 目标

合入队列在最新发布分支上测过后，只通知「可合入」，等用户执行 `loop 合入`（`merge-queue.ts` 的 `notify`）。实际操作中，用户常在开发会话里让 AI 手动合入：既绕过了队列重测，钩子又多跑一轮无效评审。改为：项目打开开关后，评审、验收、队列重测都满足条件的批次由程序自动合入；合入在会话外进行，不触发评审；冲突由程序分析后退回。

背景、已核对的事实和完整设计见 `/Users/Admin/Desktop/loop/iusses/合入队列测过后仍停等人工导致手动合入重复评审.md`（只读）；上一批合入队列的设计见 `docs/prompt/提示词-合入队列.md`。

## 已拍板

- `.autoreview.json` 新增 `"merge": { "auto": false, "push": false }`，两项都默认关；不配置时行为与现在完全一致。用户给某个项目打开，即长期授权。
- **自动合入条件**，全部满足才合：队列在最新 `release` 上合并后门禁通过；验收没有「不通过」；没有「部分验证」（不分原因）；「人工」条目不挡，合入后在通知和交付总表里逐条列出。不满足时停在「可合入」，通知里写明是哪条没满足。
- **进队资格带上验收结论**：段完成时，pi（`autoreview.ts`）和 Claude Code / Codex（`hosts/hook.ts`）写入的段状态都带上不通过、部分验证、人工条目；多段批次按全部段加整合 e2e 合计。
- **合入方式不变**：沿用现有 `loop 合入` 的核对和 Git 比较交换，把 `release` 原子更新到测过的提交，不重新计算合并；运行版收尾沿用现有逻辑。运行版有与合入内容重叠的未提交改动时不合入，通知用户。
- 只合到 `release` 指定的那一层。
- `merge.push` 打开时，自动合入成功后把 `release` 推送到它的上游远端；失败时保留本地合入、通知原因，不强推、不自动重试。
- **冲突**：
  - 文本冲突：退回消息带上已先合入的批次改了哪些文件及其提交说明；解决后排到队尾，通过后自动合入。
  - 能合上但在最新 `release` 上门禁失败：本批完成资格里门禁已通过，所以标「与已合入批次冲突」，不记为本批自身缺陷。
  - 发布分支过期：沿用现有重测，通过后直接自动合入。
  - 同一批次第 3 次退回：停止自动排队，通知用户。
  - 开工时本批 `scope.allow` 与进行中批次重叠：提示「建议改为串行」，不阻止开工。
- **撤回**：新增 `loop 撤回 <批次.json>`。`release` 仍停在这一批的合入提交时，用比较交换退回合入前的提交；之后已经有别的批次合入时不动 `release`，通知用户。
- **记账**：自动合入后在交付总表这一批下写「已合入 <提交>」，并列出还没验的人工条目。
- **清理**：不自动删开发空间和分支，只把批次标成已合入，由 `loop 清理` 按登记回收。
- **兜底**：开发会话的工作区提交和树，与本批在队列里测过的合并结果完全相同时，不再评审，总结写明原因。放在共用评审入口，pi 与 Claude Code / Codex 都生效。
- 不覆盖：非 git 项目、没通过 `loop 开工` 登记的批次，行为不变。

## 边界

- 代码主要涉及：`merge-queue.ts`；`loop.ts`（撤回、开工时 scope 重叠提示）；`config.ts`（`merge` 字段）；`pipeline-core.ts`（段状态带验收结论）；`autoreview.ts`、`hosts/hook.ts`（完成时带验收结论）；`review.ts`（兜底）；`ledger.ts`（已合入记录）。用法同步到 `README.md`「开工、启动、状态与合入」，以及 `工具清单.md` 的 `bin/loop` 与「.autoreview.json 字段」两节。
- 第 1 段（生产 Loop 指路与校验）已在同一分支提交。指路卡里「合入」那一行可按本段行为调整措辞，第 1 段的其他行为不改。
- 测试放在 `test/`，一律用系统临时目录里的 git 仓库，配替身门禁、替身开发会话；远端用本地 bare 仓库。
- 不改 Loop 自身的 `.autoreview.json`（Loop 不打开自动合入）；不改 `docs/方案-开发测试闭环.md`（历史方案，保留）、`review-prompt.md`、`test/e2e.mjs` 的场景和断言、`eval/`、`iusses/`、`项目文档/`、`项目模板/`、`temp/`。
- 不对真实仓库跑队列，不提交，不推送。

## 验收标准

A1. 操作：临时仓库打开 `merge.auto`；单段批次门禁通过，验收没有不通过和部分验证，有 2 条人工
    预期：自动合入，`release` 指向测过的提交；交付总表这一批下写「已合入 <提交>」并列出 2 条人工；整个过程没有触发评审
A2. 操作：同 A1，但验收有 1 条部分验证；再做一次未配置 `merge` 的情况
    预期：两次都不自动合入，停在「可合入」；前者通知写明是哪条部分验证挡住，后者行为与现在一致
A3. 操作：两个并行批次改同一文件，A 先自动合入
    预期：B 文本冲突退回，消息含 A 改了哪些文件及其提交说明；B 解决后排到队尾，通过后自动合入
A4. 操作：B 能合上，但在最新 `release` 上门禁失败
    预期：退回消息标「与已合入批次冲突」，不记为 B 自身缺陷
A5. 操作：同一批次第 3 次被退回；另开工一个 `scope.allow` 与进行中批次重叠的批次
    预期：前者停止自动排队并通知；后者提示建议串行，照常开工
A6. 操作：运行版有与合入内容重叠的未提交改动时触发自动合入；再做一次不重叠的
    预期：前者不合入并通知；后者合入后未提交改动原样恢复
A7. 操作：对刚自动合入的批次执行 `loop 撤回`；再对其后已有别的批次合入的批次执行一次
    预期：前者 `release` 回到合入前的提交；后者 `release` 不变并通知
A8. 操作：打开 `merge.push`，用本地 bare 仓库作远端自动合入；再让推送失败一次
    预期：成功时远端 `release` 等于合入提交；失败时本地合入保留、通知原因、没有强推
A9. 操作：开发会话工作区的提交和树与队列测过的合并结果相同时触发评审，pi 与 hook 两条路径各一次
    预期：都不再评审，总结写明原因
A10. 操作：执行 `PATH="/Users/Admin/.hermes/node/bin:$PATH" node --test test/*.test.ts`
    预期：全部通过；未配置 `merge` 的既有队列测试断言不变
