## 三、已拍板的规则（不要改）

1. **`code_map`**：开发方报告的可选字段，字符串，去掉首尾空白后非空，≤ 8000 字；评审方写这个字段就拒收。受管开发的提示词要求提供：列出本单元每个新建或修改的文件、各自做什么、对应哪些标准，以及关键的取舍。返修轮在上一份地图的基础上更新，不要从头重写。
2. **地图怎么传**：引擎记下最近一次被接受的开发方 `code_map` 和它所在的轮次，放进下一次开发和评审的上下文：`context['code_map'] = {'round': r, 'text': ...}`，并出现在 `prompt_view()` 里。第 1 轮没有地图时为 `null`。
3. **读取指引**，写进提示词：
   - 返修开发："先读 code_map 和 issue_history 里待解决问题指出的位置（files，有 locations 时按行号），只在需要时再读其他文件；不要通读目录或整份规格"；
   - 第 2 轮起的评审："先看 comparison 的完整差异和 code_map，细读改动的地方和待解决问题所在的位置；没改动的代码只在核对问题时再读"。
4. **每个会话的统计**（在 `pi_events.py` 处理事件流时累计，放进该会话的 `usage`）：
   - `tools_by_name`：各工具调用次数；
   - `reads`：read 调用总数；`distinct_files`：读过的不同文件数；`repeat_reads`：同一会话里再次读同一个文件的次数；
   - `read_paths`：读过的路径列表（去重，按首次出现排序）。本次 `code_path` 下的路径一律转成相对路径，`code_path` 之外的保留绝对路径并标记 `outside: true`。
   - `code_path` 从 `session` 事件的 `cwd` 取；没有就从引擎传进来的上下文取。
5. **跨会话重读**：单元结束时，按调用顺序计算每个会话的 `cross_reads`：本会话读的路径里，同一单元更早的会话也读过的个数。
6. **结果页**：每个单元加「#### 成本」表，一行一个会话：成员 / 轮次 / 耗时 / 模型轮次 / 工具调用 / 读文件 / 不同文件 / 会话内重读 / 跨会话重读 / 输入 / 缓存读 / 输出 token / 是否提供代码地图。缺数据写"未知"。`result.md` 开头加一行运行合计：缓存读取 X token、读文件 Y 次、跨会话重读 Z 次。原有的"成员用量"JSON 保留。
7. 只做统计和展示，不设任何成本上限，不因为成本停止运行。

## 六、改造规格

按第三章逐条实现。补充几点：
- 读取统计只在 `event_mode` 下进行；事件里缺少 `args.path` 的 read 调用只计入 `reads`，不计路径。
- 路径归一化要防止 `..` 绕出：先 `os.path.normpath`，再判断是否在 `code_path` 内。
- `cross_reads` 只在同一单元内比较。比较用的是相对路径；`outside` 路径按绝对路径比较。

## 七、设计约束（陷阱）

1. **不能事后解析截断的文件**：`complete: false` 时，事后统计会少算，所以统计必须在投影器里做。
2. **成员可能是 codex 或命令行适配器**，没有 pi 事件流：这些会话的统计字段全部为 `None`，结果页写"未知"，不能写 0。
3. **`usage.json` 已有的字段和含义不变**，只新增字段；`observability.py` 的汇总和 coverage 逻辑不能被新字段打乱。
4. **协议**：开发方没写 `code_map` 不是错误，不要因此拒收；只校验类型和长度。超长时报错说明上限。
5. **上下文预算**：`code_map` 最多 8000 字，放进提示词时，注意 `max_context_bytes` 的检查仍然生效。
