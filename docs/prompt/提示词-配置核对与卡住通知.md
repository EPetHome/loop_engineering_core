# 配置核对与卡住通知

## 目标

协调方写的批次配置，Loop 现在只检查格式，不检查它和实际情况对不对得上，配置错了要等开发方跑到那一步才暴露；暴露时发出的信息又说不清卡在哪、要做什么，批次就停在那里没人知道。2026-11-03 产品智能体「专家团重构」批1开工 13 小时，真正开发约 3 小时，其中 8 小时 50 分是停着没人知道。完整经过见问题单 `iusses/配置错误运行时才暴露且阻塞无人感知导致批次停摆.md`；段启动命令被终端截断、段没启动、流水线无限等待，见 `iusses/段启动命令经Terminal模拟打字超1024字节被截断导致段没启动且流水线无限等待.md`，一并在本批处理。

本批要做到：配置错误尽量在开工时就发现；开工后、开发方动手前，把后续环节空跑一遍；运行中只要卡住、不再前进，Loop 就把正确、能看懂的信息发出去。

## 已拍板

- 错误可以发生，但要能被发现；不要求一次完美（用户 2026-11-03）。
- 卡住了、不再前进了，就必须让人知道，由 Loop 负责把信息发出去，而且信息要正确（用户 2026-11-03）。
- 三层都做，放在同一批：① 写完配置就核对；② 开工前空跑一遍；③ 卡住必须让人知道。
- 卡住时发出的信息要写明三件事：卡在哪（内部错误附错误原文）；开发方最后一条回复是在提问时，附上原话；要人做什么（按真实原因写，不用写死的猜测）。
- 错误原文单独留存，不被下一轮总结覆盖。

## 边界

- 基于合入「单一入口」两段之后的 dev 开发。
- 问题单里点到的位置（以开工时的代码为准）：暂停信息 `autoreview.ts` 的 `pause` / `pauseForError`；写死的处理提示 `onboarding.ts`；事件分类 `events.ts`；段启动与等待 `pipeline.ts` 的 `launchTerminal`、`waitStage`；开工 `loop.ts` / `bin/loop`；配置读取 `config.ts`；越界检查 `scope.ts`。
- 不改：评审和验收提示词的判定规则、验收标准的解析规则、合入队列、交付总表已有内容。
- 测试放在 `test/`；宿主、开发会话、终端用替身，项目用系统临时目录里的临时仓库。
- 开发方不提交。

## 验收标准

A1. 操作：临时项目声明「改 `a.py` 必须同步改 `copies/*/a.py`」，批次范围只写 `a.py`；执行 `bin/loop 开工 <批次.json>`
    预期：开工失败，输出列出范围里缺少的具体文件，并写明怎么补；不创建开发空间
A2. 操作：批次的两段各配一份不同的验收说明，跑到各段验收
    预期：每段验收方的输入里是本段那份说明，不是项目级那份，也不是另一段的
A3. 操作：开发会话运行中，修改工作区的 `.autoreview.json`（它不在本段范围内），然后让开发方交付
    预期：越界检查不判开发方越界；总结里单独记一行「Loop 配置被修改」及改了哪个字段
A4. 操作：配置正确的批次执行 `bin/loop 开工`
    预期：开工输出逐项列出空跑结果（越界检查、评审能否启动、验收前重置、加载验收说明），每项都有结论
A5. 操作：把验收前重置命令配成必然失败，执行 `bin/loop 开工`
    预期：开工时就报重置失败，附命令输出和怎么改；开发方没有被派发
A6. 操作：用替身让评审抛出内部错误
    预期：暂停信息（开发会话提示、系统通知、事件）里有错误原文；再跑一轮之后，仍能查到这次的错误原文
A7. 操作：开发方最后一条回复是在提问，同时评审抛出内部错误
    预期：暂停信息里同时有错误原因和开发方的问题原文
A8. 操作：让验收方把全部条目判为「无法验证」
    预期：暂停信息里是验收方逐条原因的摘要；不出现写死的「多半是环境问题（数据库、测试账号等）」
A9. 操作：流水线派发一段，但该段的启动命令没有执行（会话始终没有报状态）
    预期：在设定时间内发出「<段名> 没有启动」及处理办法；`bin/loop 状态` 和事件里，这一段不再显示「运行中」
A10. 操作：在终端启动方式下，派发一段启动命令超过 1024 字节的段（例如路径和段名含中文）
    预期：命令完整执行，这一段正常启动并报状态
