# 流程配方：批次完成时压成一个提交，合入只由用户执行

## 目标

现在单段批次完成后，候选只挂在合入队列的私有引用上（`merge-queue.ts` 的 `enqueue` 生成「合入候选快照」），批次分支上只有开工时的「批次文档」提交。多段批次每段一个提交，一直没有合成一个。用户每次都要手动把成果合成一次提交。

改为：批次正常完成时，程序把整批压成**一个提交**放在批次分支上，记下分支和提交号，通知用户可以推送。合入发布分支只在用户执行 `loop 合入` 时发生，去掉自动合入。

完整设计见 `/Users/Admin/Desktop/loop/docs/方案-流程配方.md` 的「二、A. 提交模块」和「三、B. 合入只由用户触发」（只读，以本提示词的「已拍板」为准）。

## 已拍板

- **压成一个提交**：
  - 范围从批次分支与 `release` 的分叉点开始，包括开工时的「批次文档」提交。
  - 提交说明是 `<类型>: <批次名>`，类型取分支前缀。正文列出各段名、门禁/评审/验收结论，以及中间历史的引用。
  - 压缩前，先把当前分支头写到 `refs/loop/batches/<批次ID>/pre-squash/<序号>`，中间历史不能丢。
  - 提交前核对：工作区的树必须等于通过检查的候选树。不一致就不提交，按现有的「候选已变化，需要重新检查」处理，分支不动。
  - 提交后核对：新提交的树必须等于候选树。不一致就把分支恢复到压缩前，暂停，不进队列。
  - 排除 `localFiles` 的做法沿用 `workspace.ts` 的 `commitAll`。
- **什么时候压缩**：
  - 单段：开发会话确认完成（`queueStageEvent` 收到 `done`）以后、进合入队列之前。
  - 多段：中间每段照常提交，下一段要以它为开工依据。全部段完成、整批验收通过以后，再压成一个提交，然后进队列。
  - 多段但没配整批验收：全部段完成后压缩并进队列。这条规则是「验收有标准才跑，没有就跳过」。现在这种情况不进队列，要改。
- **一个批次有多个分支**（段单独写了 `branch`）：按分支各压一次，每个分支一个提交。
- **重复完成**：
  - 还没推送：开发会话之后又改了代码、再次完成时，重新压缩，分支上仍然只有一个本批提交。
  - 已经推送（本地记录了推送的提交号）：不改写已推送的历史，在它后面追加一个提交。
- **不能改坏的**：
  - 压缩不改变树，所以不能让已经取得的完成资格失效，也不能触发新一轮评审。pi（`autoreview.ts`）和 Claude Code / Codex（`hosts/review-hook.ts`）两条路径都要保证。
  - 非 git 项目、没有用 `loop 开工` 登记的批次，行为不变。
- **记录与通知**：
  - 交付总表（`ledger.ts`）本批的段落写上分支、提交号和中间历史的引用。
  - 系统通知写：`已提交 <分支> <短提交号>。要推到远端就执行：bin/loop 推送 <批次.json>`。
- **新命令 `loop 推送 <批次.json>`**：
  - 只推批次分支到 `origin`，首次推送时设置上游。不推 `release`，不强推。
  - 远端有分歧时报错并给出原因。
  - 成功后记下推送的提交号，「重复完成」那条规则靠它判断。
  - 支持 `--dry-run` 和 `--json`，和其他子命令一致。
- **合入队列**：
  - 压缩后，候选就是批次分支的头。
  - 照常自动排队，在最新 `release` 上测过以后停在「可合入」，等用户执行 `loop 合入`。
  - `loop 合入`、`loop 撤回` 的行为不变。
- **去掉自动合入**：
  - 删除 `merge.auto`、`merge.push` 的自动合入和自动推送 `release` 的代码路径。
  - `.autoreview.json` 里还写着这两项时，提示「merge.auto / merge.push 已停用，合入由用户执行 loop 合入」，然后忽略，不报错。
  - 「同一批第 3 次退回就停止自动排队」改成无条件生效。
  - 队列里已经持久化、做到一半的自动合入事务，要能收尾，或者安全地转回「可合入」，不能丢失，也不能卡死。

## 边界

- 代码主要涉及：
  - 新模块：批次提交（文件名按现有习惯定）。
  - `merge-queue.ts`（进队前调用压缩、去掉自动合入、退回上限）。
  - `pipeline.ts`（多段结束时压缩）。
  - `workspace.ts`。
  - `loop.ts`（`推送` 子命令）。
  - `config.ts`（停用提示）。
  - `ledger.ts`。
  - 两个宿主里与完成资格相关的部分。
- 用法同步到 `README.md` 的「开工、启动、状态与合入」，以及 `工具清单.md` 的「bin/loop」「合入队列」「.autoreview.json 字段」各节。删掉 `merge.auto` / `merge.push` 的说明，写明流程终点是「已提交、已记录、问推不推」。
- 测试放在 `test/`。一律用系统临时目录里的 git 仓库，配替身门禁和替身开发会话，远端用本地 bare 仓库。涉及 `merge.auto` 的既有测试按本提示词修改，交付时列出改了哪些断言、为什么改。
- 不改名「e2e」。下一段专门做改名，这一段保持现有字段名和文案。
- 不改：Loop 自身的 `.autoreview.json`、`review-prompt.md`、`test/e2e.mjs` 的场景和断言、`docs/`、`eval/`、`iusses/`、`项目文档/`、`项目模板/`、`temp/`。
- 不对真实仓库跑队列，不推送到真实远端。开发方不提交，提交由程序完成。

## 验收标准

A1. 操作：临时仓库里，一个单段批次正常完成
    预期：批次分支上分叉点之后只有 1 个提交，树等于通过检查的候选树；`refs/loop/batches/<批次ID>/pre-squash/` 下有压缩前的引用；交付总表写着分支和提交号；通知里有 `bin/loop 推送` 的完整命令；没有触发新一轮评审
A2. 操作：一个 3 段串行的批次全部完成，没配整批验收
    预期：运行中每段各有一个提交；结束后分支上只有 1 个本批提交，中间历史在 `pre-squash` 引用里；批次进入合入队列
A3. 操作：A1 完成后又改代码、再次完成；然后执行 `loop 推送`，再改一次、再完成
    预期：推送前分支上仍只有 1 个本批提交；推送后的那次完成追加了 1 个提交，之后再推送不需要强推
A4. 操作：完成后、压缩前，往工作区写入一个文件
    预期：不提交，提示候选已变化，分支保持原样
A5. 操作：用测试替身让压缩后的树和候选树不一致
    预期：分支恢复到 `pre-squash` 引用指向的提交，暂停，不进合入队列
A6. 操作：`.autoreview.json` 写 `"merge": { "auto": true, "push": true }`，批次在队列里测试通过
    预期：停在「可合入」，`release` 不变，远端不变；有「已停用」的提示；执行 `loop 合入` 后正常合入
A7. 操作：`loop 推送`，远端用本地 bare 仓库；再制造一次远端分歧
    预期：第一次只有批次分支出现在远端，`release` 没被推；第二次报错并给出原因，没有强推
A8. 操作：同一批第 3 次被退回，项目没有任何 `merge` 配置
    预期：停止自动排队，并通知用户
A9. 操作：执行 `PATH="/Users/Admin/.hermes/node/bin:$PATH" node --test test/*.test.ts`
    预期：全部通过；和本段无关的既有断言不变
