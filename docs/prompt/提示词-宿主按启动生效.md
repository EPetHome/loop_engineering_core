# 宿主插件按启动方式生效：协调会话不再误报暂停

## 目标

Claude Code / Codex 插件现在按目录生效：只要会话的当前目录或上级目录里有 `.autoreview.json`，就把它当作开发会话处理。结果协调方的普通聊天也会：

- 被注入【自动评审约定】；
- 一以【需要你决定】结尾，就收到「暂停（开发方需要你决定）」的 macOS 通知；
- 写【交付完成】时，去评审用户自己还没提交的改动；
- `cd` 进不是 git 仓库的子目录（例如 Promate 的 `dev分支`）后，因为读不到 git 状态，报「自动评审内部错误」并暂停。

`~/.pi-autoreview` 里的记录（10-08 至 10-25）：Claude/Codex 会话共 24 次暂停，15 次是内部错误，5 次是「需要你决定」，大多来自协调会话；只有 1 次完成。

本批改成**按启动方式生效**：只有经 `bin/loop-dev` 启动的会话才是开发会话，和 Pi 必须加 `-e autoreview.ts` 才生效是同一个思路。项目根固定为启动时的目录，不跟着 `cd` 变。

本检出里已经带入了 10-19 一次 Codex 会话做完但没有提交的工作，作为本批的起点：

- `bin/loop-dev`、`hosts/dev.ts`、`test/host-dev.test.ts`；
- `hosts/hook.ts` 里宿主识别的修正；
- `test/hook.test.ts`、`README.md`「Claude Code / Codex 用法」、`项目文档/运行与维护.md`。

先读这些文件，在它们的基础上做。唯一结果写入 `docs/batches/宿主按启动生效/结果.md`，逐条列出 A1–A9 的实现、证据和未验证的内容。

当前工作目录是本批唯一授权的隔离检出（分支 `fix/host-launch-opt-in`）。开始时先用 read 读 AGENTS.md、`hosts/hook.ts` 和 `hosts/dev.ts`，用 bash 执行 `pwd`，然后自主推进实现和受影响的定向自检，不要每一步都停下等批准。

## 已拍板

- 开发会话的标识：`bin/loop-dev` 启动宿主时设置环境变量 `AUTOREVIEW_DEV_ROOT=<项目根的绝对路径>`，也就是 `--cwd` 往上找到的 `.autoreview.json` 所在目录。Hook 只认这个变量。
- 没有这个变量的会话，Hook 对评审相关的事一律不做：
  - 不注入开发约定；
  - 不记录需求和基线；
  - 不评审，不返修，不暂停，不发通知；
  - 不写状态文件和总结。
- 唯一例外是交付总表的「待回写」提醒。它本来就是给协调方看的，SessionStart 照常注入；判断项目用当前目录，和现在一样。
- 有这个变量的会话：项目根取变量的值，不再用 `event.cwd`。会话中途 `cd` 到别的目录，不改变项目根，也不去找别的 `.autoreview.json`。其他行为和现在一致。
- 变量指向的目录不存在，或者里面没有 `.autoreview.json` 时，按现有的「项目配置不可用」处理，并在提示里写明变量的值。
- 先核实两个宿主执行 Hook 时是否会把启动进程的环境变量传给 Hook。在 `hosts/dev.ts` 里实际启动一次宿主，用一个最小的 Hook 事件检查即可，也可以查官方文档。任何一个宿主不传时，不要自己换方案，写【需要你决定】并说明证据。
- 不修改 `plugins/autoreview/hooks/hooks.json` 和两个 `plugin.json`：改了要重装插件，Codex 还要重新信任 Hook。
- 已有的旧状态文件不清理，也不迁移。
- Pi 路径（`autoreview.ts`、流水线）完全不变。
- 已知的基线失败要在本批修好：`test/host-dev.test.ts` 第 26 行那条测试读的是本机真实安装的插件缓存，要求它指向当前检出。在任何 worktree 里都会报「插件仍指向另一份 Loop」，退出码 2。改成用临时的插件目录（例如测试里设置 `CODEX_HOME` 和 Claude 插件路径指向临时目录），不依赖本机的安装状态；`hosts/dev.ts` 的检查逻辑不能为了让测试通过而放宽。
- 开发 `opencode-go/deepseek-v4.1-flash` / max；独立评审 `openai-codex/gpt-6-astra` / xhigh；不跑 e2e。

## 边界

- 只改本检出的代码、文档和必要的测试。不访问、不修改原工作目录 `/Users/Admin/Desktop/loop`（它是正在运行的引擎，本机插件指向那里）、其他项目、凭据、全局设置和已安装的插件缓存。
- 不自动删除任何项目的 `.autoreview.json`。
- 不新增暂停点或阻断机制。
- 不修改 `test/e2e.mjs` 的场景和断言；认为必须修改时写【需要你决定】并停下。
- 测试里的项目目录和状态目录都建在系统临时目录，用完删除；不碰真实的 `~/.pi-autoreview/`。
- 完整 Node 测试由 Loop 门禁执行，开发中只跑受影响的测试文件。
- README「Claude Code / Codex 用法」和 `项目文档/运行与维护.md` 写明：插件只对 `bin/loop-dev` 启动的会话生效；直接打开的会话不评审，只有待回写提醒。

最后交付时写【交付完成】，由 Loop 门禁和独立评审接着执行。

## 验收标准

A1. 操作：在带 `.autoreview.json` 的 git 项目里，用一个没有 `AUTOREVIEW_DEV_ROOT` 的 Claude Code Hook 会话依次发 SessionStart、UserPromptSubmit，再发一次最后一行是【需要你决定】的 Stop
    预期：没有注入【自动评审约定】；没有发通知；`~/.pi-autoreview/` 下没有生成这个会话的状态文件和总结
A2. 操作：同一个会话发一次最后一行是【交付完成】的 Stop，工作区里有未提交的改动
    预期：不启动评审，不调用评审模型，Hook 输出不阻止宿主停下
A3. 操作：同一个项目在交付总表里有一段待回写，没有变量的会话发 SessionStart
    预期：只注入一句待回写提醒，不带开发约定
A4. 操作：设置了 `AUTOREVIEW_DEV_ROOT` 的会话写【交付完成】，用假评审模拟必修
    预期：和现在一样评审、返修、计数；需要用户决定时照常暂停并通知
A5. 操作：设置了变量的会话，Stop 事件里的 `cwd` 是项目里的子目录；这个子目录不是 git 仓库，而且有自己的 `.autoreview.json`
    预期：仍然按变量指向的项目根评审；没有出现「自动评审内部错误」
A6. 操作：变量指向不存在的目录，或者指向没有 `.autoreview.json` 的目录
    预期：按「项目配置不可用」处理，提示里写出变量的值
A7. 操作：用 Codex 的事件格式（带 `turn_id`）重复 A1 和 A4
    预期：结果和 Claude Code 一致
A8. 操作：`bin/loop-dev claude|codex --dry-run` 打印启动命令；再对比 `plugins/autoreview/` 下的文件
    预期：打印的环境里有 `AUTOREVIEW_DEV_ROOT=<项目根>`；`hooks.json` 和 `plugin.json` 没有改动
A9. 操作：在这个 worktree（不是原目录 `/Users/Admin/Desktop/loop`）里执行全量 `node --test test/*.test.ts`
    预期：全部通过，包括 `test/host-dev.test.ts`；本机已安装的插件缓存没有被读写
