# 流水线与模板标准 · 第 1 段：开工工具、worktree、方法指纹、统一启动

## 目标

现在每开一批，协调方都要手工同步代码、提交外部基线、复制启动脚本，再空跑修错，准备阶段要 27–59 次工具调用。本段把这些固定步骤做成程序：

- 用 git worktree 作为固定的开发空间；
- 新增 `bin/loop` 子命令：开工、启动、状态、合入；
- 方法自测按指纹决定是否执行，只在第一次或有变化时跑；
- 流水线写 `prompt` 的段统一由 `bin/pi-dev` 启动；
- 串行段完成后由程序提交。

设计依据是 `docs/方案-流水线与项目模板标准.md`。先读它的第 2、4.1、4.3、4.4、4.5、9 节；本段只做第 8 节的第 1 批。唯一结果写入 `docs/batches/流水线与模板标准/结果.md` 的「第 1 段」一节，逐条列出 A1–A9 的实现、证据和未验证的内容。

当前工作目录是本批唯一授权的隔离检出（分支 `feat/pipline-temp-standard`）。开始时先用 read 读 AGENTS.md 和方案，用 bash 执行 `pwd`，然后自主推进实现和受影响的定向自检，不要每一步都停下等批准。

## 已拍板

- 分支形态：运行版是仓库主检出，停在发布分支。发布分支由 `.autoreview.json` 的 `release` 指定，默认 `main`。开发空间是 worktree，位置由 `workspaces` 指定，默认 `../<仓库目录名>-dev分支`。每批在开发空间里从发布分支拉 `<类型>/<描述>` 分支。
- 提交：开发方不提交。串行段完成后、启动下一步之前，由流水线在该段的分支上提交，说明写 `<类型>: <描述>`（类型取自分支名前缀），正文写批次名和段名。这次提交不能撤销该段已经取得的完成资格。如果现有资格核对和 HEAD 绑定，要改成按内容核对，并在结果里写明。
- 指纹：由 loop 版本（loop 仓库的 `git describe --always --dirty`）、`.autoreview.json` 的 `methods.paths` 下全部文件的内容哈希、方法相关配置字段、可选的 `methods.probe` 命令输出组成。记录放在 `~/.pi-autoreview/projects/<项目根哈希>/methods.json`，复用 `project-context.ts` 已有的项目根哈希。指纹不变就跳过方法自测，并输出「指纹未变，跳过方法自测」。指纹变了就输出变化的组成部分，执行一次 `methods.selfCheck`（如果配置了）和基线空跑门禁，通过后才更新记录。`--recheck` 强制重新自测。
- 基线空跑门禁按提交的树哈希缓存：loop 在任何候选门禁通过时，记下该候选的树哈希（保留最近 50 个）。开工依据的树和其中某个一致时不重跑。这个结果只用来识别基线上已有的失败，不能当作新候选通过。
- `bin/loop` 子命令沿用方案的名字：`开工`、`启动`、`状态`、`合入`。每个都支持 `--dry-run`（只核对、只打印要做的事，不改任何东西）和 `--json`（输出结构化结果）。
- `loop 开工 <批次.json>`：
  1. 运行版不干净、不在发布分支，或开发空间有未提交改动时，停下并报告，不 stash、不 reset、不丢改动。
  2. 开发空间不存在就 `git worktree add`；存在就从发布分支切出批次分支，分支已存在就直接切过去。
  3. 检查 `localFiles` 已被 git 忽略；开发空间里缺少时从运行版复制，已有的不覆盖。
  4. 按指纹自测。
  5. 打印 `loop 启动` 的完整命令。
- `loop 启动 <批次.json>`：一段时直接用 `bin/pi-dev` 开会话；多段时调用流水线。`批次.json` 是现有流水线计划的超集，旧计划文件照常可用。
- `loop 合入 <批次.json>`：在运行版里把批次分支合并进发布分支，先提交批次分支上还没提交的改动。有冲突就中止合并，恢复到合并前的状态，列出冲突文件。不推送。
- `loop 状态 [<批次.json>]`：列出各段的阶段、轮次、暂停原因和总结路径，数据来自现有的状态文件和总结，不新增状态源。
- 流水线写 `prompt` 的段改由 `bin/pi-dev` 启动，删除 `pipeline.ts` 里重复拼接的 Pi 命令。段级的 `model`、`thinking`、`tools`、`args` 覆盖照常生效。`ponytail: false` 的现有语义要保留，需要的话给 `bin/pi-dev` 加一个关闭 Ponytail 的选项，并让「未加载 Ponytail」的提醒照常出现。
- 开发 `opencode-go/deepseek-v4.1-flash` / max；独立评审 `openai-codex/gpt-6-astra` / xhigh；不跑 e2e。

## 边界

- 只改本检出的代码、文档和必要的测试。不访问、不修改原工作目录 `/Users/Admin/Desktop/loop`、其他项目、凭据和全局设置。原工作目录里有未提交的 `bin/loop-dev`、`hosts/dev.ts`，不在本分支上；本段不依赖它们，也不要在本分支重建它们。
- 不新增暂停点或阻断机制；工具失败只是本条命令退出并报告。
- 不推送，不自动合入；`loop 合入` 只在用户执行时运行。
- 外部基线（`GIT_DIR`）和流水线的 `start` 写法保留兼容。
- 不修改 `test/e2e.mjs` 的场景和断言；认为必须修改时写【需要你决定】并停下。
- 测试里的 git 仓库、worktree 和 `methods.json` 都建在系统临时目录，用完删除；不碰真实的 `~/.pi-autoreview/`。
- 完整 Node 测试由 Loop 门禁执行，开发中只跑受影响的测试文件。
- 第 2 段做越界检查、方法环境变量和权限检查，第 3 段做工具清单和文档。本段不做这些，README 只补 `bin/loop` 的最小用法。

最后交付时写【交付完成】，由 Loop 门禁和独立评审接着执行。

## 验收标准

A1. 操作：在临时 git 仓库里，用一份单段 `批次.json` 执行 `loop 开工`，再执行 `loop 启动 --dry-run`
    预期：开发空间 worktree 建在默认位置，切到 `批次.json` 指定的新分支；启动命令经过 `bin/pi-dev`，加载权限扩展、autoreview 和 Ponytail；不需要 `GIT_DIR`
A2. 操作：项目方法和 loop 版本都没变，第二次执行 `loop 开工`
    预期：输出「指纹未变，跳过方法自测」；`selfCheck` 和空跑门禁都没有执行
A3. 操作：改动 `methods.paths` 下的一个文件后执行 `loop 开工`
    预期：输出写明方法文件发生变化；自测执行一次，通过后 `methods.json` 更新；`--recheck` 在指纹没变时也会执行自测
A4. 操作：运行版有未提交改动，或开发空间有未提交改动时执行 `loop 开工`
    预期：以非 0 退出，报告原因和文件；两边的改动都原样保留
A5. 操作：两段串行计划 `steps: [["甲"],["乙"]]`，两段在同一个 worktree，用假开发方跑完
    预期：甲完成后，乙启动前出现一次提交，说明是 `<类型>: <描述>`；甲的完成资格仍然有效；整批完成
A6. 操作：两段并行计划 `steps: [["甲","乙"]]`，两段分别在两个 worktree，用假开发方跑完
    预期：两段在同一步里启动，各自在自己的分支上完成
A7. 操作：执行 `loop 合入`，分别在没有冲突和有冲突的情况下
    预期：没有冲突时发布分支多一个合并结果，没有推送；有冲突时合并被中止，运行版恢复原状，输出列出冲突文件
A8. 操作：流水线中写 `prompt` 的段，一段带 `ponytail: false`，一段带段级 `model` 覆盖
    预期：两段的启动命令都经过 `bin/pi-dev`；前者不加载 Ponytail，并照常提醒未加载；后者用的是覆盖后的模型
A9. 操作：任意子命令加 `--json`
    预期：标准输出是一个可以解析的 JSON 对象，包含结果和失败原因；加 `--dry-run` 时没有任何文件或分支发生变化
