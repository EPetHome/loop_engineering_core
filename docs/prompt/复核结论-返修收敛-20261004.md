## 3. 发现的问题

### B1 · 阻塞：分级校验没有统一使用“首次有效级别”

**位置：** `E/protocol.py:188-202,210-223`；`E/handoff.py:99-127`；下游 `E/engine.py:748-797`。

**反例一：同一份首审报告里，先建议、后同名必须修。**

条件：v2 受管 reviewer，第 1 轮，issue_history=[]；标准 C 的门禁通过；候选有非空 `value.txt`；预算充足且允许返修。报告 C=FAIL、blocked=false，issues 按以下顺序给出（其他必填字段及绑定均合法）：

```json
[
  {"criterion_id":"C","description":"同一个问题","suggested_fix":"修复建议","severity":"advisory"},
  {"criterion_id":"C","description":"同一个问题","suggested_fix":"修复建议","severity":"blocking",
   "counterexample":"给定输入下得到错误结果","locations":["value.txt:1"]}
]
```

静态结果：

1. 没有 issue 去重/重复拒收；`known_severity` 只读取旧 context，不吸收本报告第一条。
2. `reported` 因第二条而包含 C，FAIL 被接受。
3. 台账按同一 finding_id 去重，第一条固定 advisory，最终只有一个 ADVISORY。
4. 第 1 轮不走 freeze_review，C 仍 FAIL；安排开发返修，但 feedback.issues 已过滤为空，台账也没有必须修项。

**错误：只有有效建议、没有失败门禁，仍触发返修。** 违反首提级别和只有建议不能 FAIL 的核心要求，并直接浪费一次开发调用。现有 `test_advisory_cannot_be_upgraded_to_support_fail`（`test_review_severity040.py:112-115`）只覆盖旧 context 已有建议，不覆盖同报告重复项。

**反例二：历史 blocking 被声明为 advisory，清空必须修元数据。**

context 已有 OPEN/blocking 的同一描述与标准；本轮重报 `severity=advisory,counterexample="",locations=[]`，有合法 files，C=FAIL，门禁通过。协议按本次声明的 advisory 跳过非空反例/位置要求；FAIL 又被历史 OPEN 支撑。台账保留 blocking，却在 `handoff.py:119-122` 把反例和位置覆盖为空。结果是仍阻断的必须修问题丢失了必需元数据。

**建议修法：** 按与 finding_id 一致的身份，先生成包含旧台账及本报告首个出现项的有效分级表；重复项明确拒收或按首项规范化；FAIL 支撑与 blocking 元数据校验都用该有效级别。不要让一次 advisory 重报清空有效 blocking 的必需字段。补两个反例，并核对没有额外 reserve repairs/member 调用。

### B2 · 阻塞：事件流缺失工具开始记录时，读取成本被伪报为零

**位置：** `E/pi_events.py:123-136,246-263`；`E/observability.py:124-143`；`E/storage.py:340-346`。

**反例：** 事件流包含 session，然后收到 `tool_execution_end(toolCallId="r1",toolName="read")`，但对应 start 丢失；之后有正常最终 assistant message、agent_end、agent_settled。

静态结果：

- 原逻辑知道生命周期不完整，设置 `unmatched_tools=True`，`tool_calls=None`。
- 新增 reads/distinct_files/repeat_reads/read_paths 仅检查 event_mode，得到 `0/0/0/[]`；tools_by_name 是 `{}`。
- cost_sessions 把空路径数组视为完整已知集合，首会话 cross_reads=0；结果表显示“工具调用未知、读取 0、重读 0”，后续跨会话计算也会漏掉这个未知前序。

**错误：** 只能知道“没有观察到 start”，不能知道“没有读取”。失败/不完整会话本来就应计入成本，不能用数字零代替未知。这与用户把成本统计定为硬要求直接相关。

**建议修法：** 为新增工具/读取维度维护 coverage；缺 start、缺可识别工具名/ID或坏事件导致无法证明完整时，相关总计设 None，小计另存 observed_total。cost_sessions 不要仅凭 read_paths 是 list 就认定覆盖完整。补 unmatched lifecycle 与后续 cross_reads 的反例。

**不是问题的情况：** 原始 `pi-events.jsonl` 的保留前缀被截断，但实时投影器持续消费完整事件流，此时准确数字应保留，不必一律改成未知。现有 `test_statistics_keep_consuming_after_raw_log_is_truncated` 正是在验证这一点。

## 4. 时间与额度的独立推算

wbhost 给定近似数：首轮开发 3300 秒、门禁 0 秒、评审 630 秒、单元 7200 秒。

| 计算 | 值 |
|---|---:|
| 首轮结束 | 3930 秒 |
| 剩余 | 7200−3930 = 3270 秒 |
| 预留 | ceil(630×1.25) = **788 秒** |
| 返修开发可用 | 3270−788 = **2482 秒**（41 分 22 秒） |
| 至少需要 | 3300×0.5 = 1650 秒 |
| 决策 | 2482≥1650 且大于 0，可开始返修；到单元第 6412 秒触及预留截止 |
