## 一、目标

运行结束时，引擎会调用 `audit()` 做总收尾核对。现在这一步不认识问题台账里的两种状态：`ADVISORY`（建议）和 `DEFERRED`（遗留发现）。只要台账里出现这两种状态，就会出现下面的情况：单元判达标，但整次运行的总收尾核对失败，候选也无法正式导出。

这次要做两件事：

1. 修好 `audit.py`，让它正确核对这两种状态（不是简单放行）；
2. 「返修收敛」带来的每一种新流程，都补一条**跑完整次运行、断言总收尾 PASS** 的测试，把同类问题一次查全。

## 六、改造规格

### 6.1 audit 怎么核对两种新状态

| 状态 | 合法条件（不满足就报完整性错误，错误信息用中文） |
|---|---|
| `ADVISORY` | `kind == 'issue'`；`severity == 'advisory'`；没有有效的 `resolution`（建议项不能被关闭） |
| `DEFERRED` | `kind == 'issue'`；`deferred` 为真；`severity` 不是 advisory |

- 两种状态都照常检查来源绑定、`finding_id` 和原始记录，和 OPEN 走同一套检查。
- `OPEN`、`RESOLVED`、`UNKNOWN` 原有的规则不变。
- 具体字段名以 `handoff.py` 实际写入的为准；和上表有出入时，按代码实际写入的来，并在简报里说明。

### 6.2 端到端总收尾测试（每条都跑完整次离线运行）

每条都要断言三件事：`finalization.status == 'PASS'`、`audit(...)['integrity_ok']` 为真、单元结果符合预期。

| # | 场景 | 单元结果预期 |
|---|---|---|
| E1 | 首审里只有 advisory 问题，判 PASS | PASSED，`advisory_findings` 有 1 条 |
| E2 | 首审里有 blocking 和 advisory，返修后 blocking 关闭，复审 PASS | PASSED，建议仍是 ADVISORY |
| E3 | 冻结复审中，未改动的文件里出现新的 blocking → 记为遗留发现，其余标准 PASS | PASSED，`deferred_findings` 有 1 条 |
| E4 | `first_round=review`，输入已经达标 | PASSED，没有开发调用 |
| E5 | 开发轮失败（`candidate=None` 的那一轮），之后的返修成功 | PASSED |
| E6 | 地图漏写被协议退回（M1），补写后通过 | PASSED |
| E7 | 停滞判停、时间不够返修 | NOT_MET。总收尾仍然是 PASS：总收尾核对的是记录完整，不是业务达标。写测试前先确认现有代码对 NOT_MET 运行的总收尾就是这样定义的；不是的话，按现有定义断言，并在简报里说明 |

- 能复用 `test_review_fix040.py`、`test_repair_merge040.py` 里的离线 fixture 就复用（导入，或者在新文件里另写辅助函数，不要修改原文件）。
- 再加两条 audit 的**负例**：
  - 把 ADVISORY 项篡改成带有效 resolution → audit 报错；
  - DEFERRED 项去掉 `deferred` 标记 → audit 报错。

### 6.3 先红后绿

改 `audit.py` 之前，先跑 E1～E7，把结果留成红灯日志。预期 E1、E2、E3 失败；其他几条如果也失败，说明还有别的兼容缺陷，按第四节的规则一并修，并在简报里写清楚。
