## 三、新字段约定（所有人都按这个写，即使不归你实现）

### 3.1 评审方问题（`issues[]` 的每一项）

| 字段 | 类型 | 规则 |
|---|---|---|
| `severity` | `"blocking"` 或 `"advisory"` | schema v2 受管评审（`managed_tools` 为真、角色是 reviewer）**必填**，所有轮次 |
| `counterexample` | 字符串 | `blocking` 必填且非空：写清在什么输入或场景下，得到什么错误结果 |
| `locations` | 字符串数组，每项 `相对路径:行` 或 `相对路径:起-止` | `blocking` 至少 1 条；路径必须是当前候选里存在的普通文件，行号为正整数且起 ≤ 止 |
| `spec_refs` | 字符串数组 | 可选，规格条款编号 |

- schema v1 或非受管：这些字段可写可不写；没写 `severity` 的按 `blocking` 处理（保持老行为），不强制反例和位置。
- `advisory` 问题在 `issue_history` 里的状态是 `"ADVISORY"`：不交给开发方，不阻断，`continue` 不带走，结果页列在「建议项」。
- 一个问题的 `severity` 以第一次提出时为准，之后重复提出不改变。
- 标准判 FAIL（v2 受管评审，所有轮次）：必须有该标准的失败门禁、仍未解决的已知必须修问题，或本报告里该标准的 `blocking` 问题，否则协议拒收。

### 3.2 其他

| 位置 | 字段 | 规则 | 谁做 |
|---|---|---|---|
| 开发方报告 | `code_map` | 可选字符串，≤ 8000 字 | 4 |
| 单元（v2） | `review_bar` | 可选字符串，去掉首尾空白后非空，≤ 600 字 | 1 |
| 单元（v2） | `first_round` | `"develop"`（默认）或 `"review"`；`verify` 单元不允许写 | 3 |
| 单元历史 `history[i]` | `timing` | `{"developer_seconds", "gate_seconds", "review_seconds"}`，墙钟秒数，没有该阶段写 0 | 2 |

### 3.3 测试里怎么构造评审问题

2、3、4 号在自己的副本里还没有 3.1 的字段（协议会拒收未知字段）。所以：

- 需要触发返修时，**优先用失败门禁触发**，不构造评审 issue；
- 实在需要评审 issue，就按旧格式写（`criterion_id`、`description`、`suggested_fix`、`files`），并在简报里列出是哪些测试，由 5 号合并时补上新字段。

## 五、开发习惯

- Python 用 `/opt/homebrew/bin/python3.12`。
- 照周边代码的风格写：紧凑，报错信息用中文，并且告诉人怎么改；注释少，只写"为什么"。
- 每条新规则至少配一个**反例测试**：改动前它会失败，改动后通过。这是 `engine/AGENTS.md` 的要求：修改内核要用具体故障反例形成闭环。
- 已有测试因为新契约必须修改的，在简报里逐条写清：改了哪个测试、改了什么、为什么。
- 测试命令（必须带短 TMPDIR，否则 macOS 的 AF_UNIX socket 路径会超长）：

```bash
mkdir -p /private/tmp/lw-<主题>
# 快速：只跑 040 套件（约 20 秒）
TMPDIR=/private/tmp/lw-<主题> LOOP_NO_NOTIFY=1 PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=tests040 \
  /opt/homebrew/bin/python3.12 -m unittest discover -s tests040 -p 'test_*040.py'
# 全量：五个套件（约 2 分钟），--out 目录必须不存在
TMPDIR=/private/tmp/lw-<主题> /opt/homebrew/bin/python3.12 tools/verify_release.py --all --out /Users/Admin/loop-wt/<主题>-verify-$(date +%H%M%S)
```

- 开发中跑快速套件；交付前跑一次全量。
