# PA 对接：推事件、只读查询、证据保护、关本机通知

## 目标

personal agent（下称 PA）要知道 Loop 批次卡没卡住、做没做完。现在 PA 只能解析 Markdown 总结来猜，出过把旧暂停重发 44 张卡的事故；Loop 和 PA 还会各弹一次通知。

本段要做到：状态一变，Loop 就往 PA 的事件目录追加一行结构化事件；同时提供一个只读查询。

- 完整设计：`/Users/Admin/Desktop/loop/docs/方案-PA对接.md` 的一、二、三、四、六节（只读）。
- 需求原文：`/Users/Admin/Desktop/loop/docs/需求-PA对接通讯能力-20261102.md`。
- 以本提示词的「已拍板」为准。
- 同一分支上已经提交了「提交与推送」「改名验收」两段，「做完」事件要用到提交模块给出的分支和提交号。

## 已拍板

- **配置**：
  - 放在用户级的 `~/.pi-autoreview/config.json`，字段是 `pa.eventsDir` 和 `pa.localNotify`（默认 `true`）。
  - 环境变量 `LOOP_PA_CONFIG` 可以指向另一份配置，给测试用。
  - 没写 `pa.eventsDir` 就不推事件，行为和现在完全一样。
- **事件格式和触发点**：按方案 §2.1、§2.2 来。
  - 字段：`v`、`seq`、`id`、`at`、`project`、`batch`、`stage`、`status`、`reason{category,text}`、`evidence`、`detail`。
  - 8 种 `status`：`started`、`needs-decision`、`paused`、`repair-limit`、`done`、`failed`、`resumed`、`queue`。
  - 各状态的触发点和 `detail` 内容见方案；暂停事件要带 `detail.next`，取值是 `send`、`resume`、`grant`、`manual` 之一。
- **写入规则**：按方案 §2.3、§2.5 来。
  - 序号：每个批次单独递增，存在磁盘上，重启后接着编，不补发历史事件。
  - 一把全局锁 `~/.pi-autoreview/events/.lock`，锁住序号分配、去重比对和追加写入；判断锁的持有者还在不在，按 pid 加启动时间。
  - 去重：同一段的签名和上次相同就不写。
  - 一个事件就是一次 `O_APPEND` 写入，整行写进去。
  - 写失败不挡批次，原因记进 `~/.pi-autoreview/events/errors.log`；这个序号照样算用掉。
  - 按本地日期写进 `events-YYYY-MM-DD.jsonl`。Loop 对这些文件不改名、不截断、不删除。
- **原因类别**：用方案 §2.4 的固定枚举。
  - 门禁和验收记录自带 `FailureKind` 的，直接用它，不从文字推断。
  - 加一个单元测试：收集代码里所有暂停原因的字符串，每一条都要映射到「其他」以外的类别。
- **「做完」**：
  - 单段：只在提交模块完成后发一次整批的 `done`，带 `branch`、`commit`。
  - 多段：每段完成时发一次 `scope:"段"`，压缩成一个提交后再发一次整批的 `done`。
- **段的当前状态**：
  - 新增 `<段>.phase.json`。两个宿主在开始、评审、暂停、恢复、完成时都要写它。
  - 现有的 `<段>.status.json` 语义不改，流水线接力和合入资格都靠它。
  - 整批暂停时，在流水线目录写 `batch.phase.json`，里面带上 `next`。
- **`loop 查询 [<批次.json> | --all] --json`**：
  - 输出方案 §三 的 v1 结构。
  - 纯读：不调用 `recoverMergeQueue` 和 `kickMergeQueue`，不写任何文件，1 秒级返回。
  - `loop 状态` 保持不变。
  - 预留两个字段：`batch.paGrants`，以及每段的 `paRelays`（最近转达过的编号）。本段先输出空数组，下一段再填。
- **证据**：
  - 事件里只给证据的绝对路径。
  - `loop 清理` 不清理还没到 `done` 或 `failed` 的批次的证据。
- **关本机通知**：
  - 新增 `systemNotify()`，替换 `autoreview.ts`、`hosts/review-hook.ts`、`pipeline.ts`、`merge-queue.ts` 里这 4 处桌面弹窗。
  - `localNotify:false` 时不弹窗，但仍然写 stderr。
  - 这些不受影响：界面里的提示、Claude 的 systemMessage、`.notification.txt`、用 osascript 打开终端窗口。

## 验收标准

A1. 操作：配置好事件目录，开一个单段批次（替身会话）
    预期：事件目录当天的文件里出现 `started`，`seq` 为 1，字段齐全
A2. 操作：替身开发方最后一行写【需要你决定】，并设 `localNotify:false`
    预期：出现 `needs-decision`，`detail.question` 是开发方原文；没有调用系统弹窗；stderr 有这条内容
A3. 操作：制造一次门禁环境失败（`kind=environment`），然后执行 `loop 查询 --json`
    预期：事件是 `paused`，`reason.category` 为「环境」，`evidence` 里有日志路径，`detail.next` 为 `send`；查询返回的原因和事件一致
A4. 操作：返修到上限
    预期：出现 `repair-limit`，`detail.mustFix` 是剩下的必修原文
A5. 操作：单段批次正常完成
    预期：只有一条整批的 `done`，带 `branch`、`commit` 和门禁、评审、验收结论；`commit` 在批次分支上确实存在
A6. 操作：写几条事件后，换一个新进程接着写；再让同一段连续两次报告同样的暂停
    预期：`seq` 接着上次编，没有补发历史；重复的暂停只写了一次
A7. 操作：把事件目录设成只读，再跑完一个批次
    预期：批次照常完成；`errors.log` 里有原因和序号
A8. 操作：批次暂停时执行 `loop 查询 --json`
    预期：合入队列状态文件的内容和修改时间都没变；不会触发恢复或测试
A9. 操作：两个批次的进程同时大量写事件
    预期：当天文件里每一行都是完整的 JSON；每个批次的 `seq` 各自连续
A10. 操作：流水线整批暂停，分别制造「联调准备失败」和「开跑前检查没过」两种
    预期：两次都是 `paused`、`stage:null`；`next` 分别是 `resume` 和 `manual`；`batch.phase.json` 和事件一致
A11. 操作：执行 `PATH="/Users/Admin/.hermes/node/bin:$PATH" node --test test/*.test.ts`
    预期：全部通过，包括检查原因映射覆盖率的那个测试
