## 实施要求

### 1. 先扩展任务身份、账本与开发卡

- 把单任务位置假设改为显式任务身份：逐个核对 `tasks[0]` 和顶层 session/activity/candidate/worktree/repairs 的全部调用者，不只修改 parser。任务级与批次级运行、输入、尝试、计数分开，迟到结果只能记历史。
- 采用一份批次账本及明确任务记录的最小实现；任务记录复用现有字段，适配器传任务 ID。旧单任务账本仍可查、续跑、合入；读取时兼容，查询不得写迁移、派工或恢复资源。不维护两套资格真相。
- 继续 version:1、开发性质、target:dev；支持单任务可选验收、多任务必需验收，固定顺序开发评审 → 可选测试 → 可选验收 → 可选提交。部署、只评审、纯测试卡仍拒绝。
- `acceptance` 为相对卡目录的标准文件路径，包含既有 `## 验收标准` 格式；每个非人工条目标唯一已存在任务 `[任务名]`，跨任务条目也指定责任任务。[授权] 条目仍按原语义要求真实用户决定，不靠文件文字授权。人工条目不强制归属。
- 缺验收、多义/缺失/未知归属、路径非法、空标准、任务重名、逆序、缺测试命令等在建任何分支/目录/模型前拒绝，指出具体条目和改法。禁止模型自行补归属或降低标准。
- `limits.验收` 默认 maxRepairs:3、timeoutMin:20、maxRecoveries:1，与评审和测试独立；验收产品返修按责任任务分别记账，批次轮次仅记录实测，不以环境恢复、改卡、续跑清零。

### 2. 真并行与批次分支

- 每个任务独立隐藏 worktree、任务分支、会话和进程身份；同仓库两个任务必须能同时开发，不能调用旧 `dispatchBatches` 的同仓库串行规则。
- 批次有自己的汇总分支与隐藏工作目录，冻结共同基线；开发评审不占本机测试/验收槽。测试和验收复用 `local-node-queue.ts` 同一跨仓库 FIFO，默认一个槽；排队不算执行、不耗节点时限。
- 任务完成开发评审及卡上测试后，由内核按实际就绪顺序汇入；不等所有任务结束才首次汇入。集成只组合已登记提交，不编辑产品解决冲突、不调用其他节点。
- 汇入记录任务 ID、实际检查候选、基线、输入版本、检查记录、集成前后提交/树和顺序；CAS 保护批次头。同一候选重复回调只汇入一次，旧候选或旧控制代次不能覆盖新成果。
- 冲突只退回本次冲突任务的原开发评审会话，提供冲突及已集成来源；不扣验收次数、不惊动其他任务。冲突处理仍守原 scope 和可证明来源，不能以合并历史夹带越界改动。
- 返修替换旧候选、移出任务时，从冻结基线与保留任务的当前有效贡献重建批次，不能简单 merge 最新分支后留下被撤回代码；保存旧批次 ref 与映射。任务分支若吸收其他任务来源，也要防止移出时把该任务从其他分支重新带回。无法安全证明贡献时暂停具体任务，不猜测删除。

### 3. 验收节点与精确重验

- 复用现有验收模型调用、证据判定、系统启动/清理、授权与人工语义，抽出最小执行接缝。`acceptance.ts/runAcceptanceStage()` 当前会在定向复验后追加完整验收；新卡路径必须去掉这层旧编排，且不能只沿用“所有旧通过项”而漏验返修任务原已通过项。
- 节点只返回统一结果/条目证据，不派返修、不读 ReviewState、不调用测试或提交。内核负责调度和回发。验收在批次 worktree 执行，绑定批次实际树、任务候选映射、标准/授权版本、轮次、范围、输入和释放证明。
- 本轮活跃任务全部就绪、均已汇入才执行一次统一验收。产品失败按条目责任分组，只把各自条目发回对应原会话；未失败任务不改分支、不加评审/测试、不收到返修。
- 固定本轮返修任务集合，等它们全部重新评审/测试并汇入后再验一次；不能甲回来就验，乙回来又验。重验 ID 严格为“不通过项 + 所有返修任务名下条目”。未返修任务的旧通过项保留原实测树、轮次和证据，注明沿用原因，验证任务来源与相关输入未变；不能改写成新树实测。
- 定向重验完成后不追加完整验收。需求已接受跨任务回归漏检风险，不另加隐含全验门槛。非产品失败保留有效结论和原重验集合，有限恢复后只停验收；无证据不能算通过。
- 验收方、恢复/证据收尾共用取得槽后的本轮剩余 deadline，不借换模型、补报告或重启刷新预算。非开发节点写源码、索引/未跟踪内容变化、释放不明时结果无效，保留证据。
- 任一任务达到验收返修上限，通知给出继续修、移出任务、整批放弃的完整命令；程序不得自动代选。继续修通过受控提高该任务有效额度，不清零旧计数；旧决定和其他任务额度不自动扩展。

### 4. 改卡、移出、恢复、状态和提交

- 在既有 CLI 上最小扩展 `--task <任务名>`（任务重跑/续跑/停止）、`重跑 --node 验收`、`改卡 --remove-task <任务名>` 及必要的任务限额覆盖。最终字段/帮助/JSON/测试一致；有同等简洁已有入口则复用并同步方案。
- 移出必须来自真实用户控制决定，不能由返修机器消息、任务文档或模型代签。先冻结意图/保留成果，停止并确认该任务资源，重建剩余任务批次；剩余条目完整重验一次，移出条目记没验证并保留历史，不自动编辑原标准文件。剩两任务以上不得去掉验收；零任务只能明确整批放弃。
- 运行中改卡在边界生效；直接编辑暂停。任务归属、来源、候选/卡版本和 pending 事务变化必须撤销旧派工；改任务测试只失效相关任务测试及依赖批次结论，不连带重评审未变任务。标准/授权变更按真实确认版本处理，旧例外决定失效。
- CLI、Pi、两种 Hook 使用同一内核；每个任务能准确定位原会话和活动，不通过“最近会话”猜测。保持机器信封的正文、来源、任务、尝试和版本核对，区分 sent/read/unknown，拒收不能伪报成功。
- 五种批次状态不变，额外列各任务状态/停点；一个任务失败而另一个在开发时仍显示真实活动，不能全批暂停或显示全批通过。排队、进程身份未知、已合入与资源未释放分列。
- 提交只接受当前批次候选及其任务来源映射上全部必需结论；单任务原流程保持。任务评审绑定各自实测树，批次验收绑定汇总树，不能用“所有树必须字面相同”拒绝合法集成，也不能借映射给未知新代码放行。
- 目标 dev 前进形成不同树仍按前两步保护处理，回到内核给补救，不由提交节点偷偷评审/验收。压缩前保留历史，只推 origin/dev，失败不自动重推；普通与真实用户例外共用候选/目标/资源保护，例外不改写未通过/没验证。
- 合入或整批放弃按登记释放所有任务、批次及调度消费者；未知归属、脏/暂存成果、本机文件变化保留。删除 worktree 后仍按发布时绑定显示各项结论和沿用证据。

## 验收标准

沿用权威需求 A4—A10 原文，编号不重排。以下定义交付行为；本次开发先以隔离程序检查覆盖，未执行的真实业务操作仍写未验证，不因本节而获得真实远端或业务调用授权。

A4. 操作：分别启动两张不合规的两任务卡：一张没有验收节点，另一张的验收标准里有一条没标归属
    预期：两张都被拒绝，分别说明原因（「并行批次必须带验收」/ 指出没标归属的是哪一条）和改法；没有新建分支或目录

A5. 操作：启动一张两个任务的卡，两个任务都带测试
    预期：两个开发会话同时在跑；同一时刻只有一个测试在执行；先完成的任务先合进批次分支

A6. 操作：统一验收时，甲名下一条不通过，乙全部通过
    预期：只有甲收到退回消息，乙的分支没有新提交；甲修好后，重验的只有不通过的条目和甲名下的条目；通过后批次合进 `dev`，并推送到 `origin/dev`

A7. 操作：一份代码已通过评审和测试，提交前代码没变；对照组是提交前代码被改动
    预期：前者提交时不重新评审、不重新测试；后者被拒绝，并说明旧结论已作废

A8. 操作：让一个批次停在测试节点（测试失败后你决定先不修），分别在 pi、对话和终端里查状态，再执行普通合入
    预期：三处显示的状态都是「等你决定」，并写明停在哪个任务、哪个节点、为什么，都不显示「进行中」；合入被拒，逐项列出缺什么，并附可复制的补救命令

A9. 操作：在 A8 的情况下，你在对话里明确说「合入这批」
    预期：助手执行例外合入，代码合进 `dev` 并推送到 `origin/dev`；合入记录写明测试没通过、是你决定合入的、决定时间，不显示为通过

A10. 操作：A1 的批次合入后，查看桌面、仓库同级目录和 `git worktree list`
     预期：没有为本批新建、遗留的目录或 worktree；任务分支和提交仍可在 git 中查到
