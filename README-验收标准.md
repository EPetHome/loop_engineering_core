# 接入 Loop：配置留在项目，规则由 Loop 提供

## 接入项目

在 Loop 仓库执行（其他目录可用 `bin/loop` 的绝对路径）：

```bash
bin/loop 接入 <你的项目目录>
# 非交互确认写入：
bin/loop 接入 <你的项目目录> --yes
# 只探测、预览，绝不写入：
bin/loop 接入 <你的项目目录> --dry-run
```

命令探测项目类型、启动命令、空闲端口、日志和操作说明，先展示计划，确认后只生成或补全 `.autoreview.json` 的 `acceptance`；其他字段保留，已有 `acceptance` 原样保留。推断结果需要按项目实际情况核对；预算或字段不合法时拒绝写入。非交互终端不带 `--yes` 时只展示计划。

接入不创建或修改 AGENTS.md、CLAUDE.md，也不读取、写入或检查项目的 `.autoreview/CONVENTIONS.md`；已有旧文件原样保留，由用户另行决定是否清理。Loop 升级后，下次运行直接使用当前规则，无须同步项目副本。

配置确认后，批次用 `bin/loop 启动 <批次.json>`；临时单会话用 `bin/loop 开发 <pi|claude|codex> --cwd <项目目录> <任务文件.md>`。开发约定在运行时注入；起草需求、验收标准和提示词时，按需指路到本页的写法原文。本页是 Loop 仓库中的唯一写法来源。项目外的对话无法读取本地材料时，由协调者提供本次相关写法。完成后用户直接看 Loop 总结和交付总表，不再抄一份结果到原单。

## 起草需求时写验收标准（自动验收 v7）

用户让你起草需求、任务或提示词时，在末尾加一节「## 验收标准」：

- 每条写「操作」和「预期」：操作是用户从外部做的事（执行命令、打开页面、调用接口）；预期是外部看得到的结果（命令输出、页面内容、接口返回、数据变化、日志）。
- 一条只验一个行为，要有明确终点；不要写「处理所有边界」「完全正确」这类没法逐条核对的话。
- 只覆盖本次需求；代码结构、命名、性能这类不写。
- 不知道具体命令或地址时，操作写到行为层面即可，不要编造命令名。
- 最多 10 条，按重要程度排列。
- 按权限划分，不按难易，只有两种标签：
  - 「[授权]」：要用用户的真实账号、凭证或真实外部平台，或会产生真实后果（真发消息、写正式数据、扣费），又没有测试账号、测试环境可以代替。用户亲手写「同意授权：A3」后，程序照常交给验收方执行；用户写「不授权：A3」就留给用户人工验收；还没答复时，验收前停下来问用户。不要替用户写「同意授权」。
  - 「[人工]」：要用户拍板的主观判断，比如好不好用、文案是否得体、是不是用户想要的，写不出客观的「预期」。程序不交给验收方，完成时列给用户。
- 难做不算：图形界面操作（网页、桌面客户端）、步骤多、耗时长，都照常写成自动验的条目。验收方现在做不到的（比如操作桌面客户端），会报「无法验证」并写明缺什么工具，由 loop 补工具。
- 一条链路里只有一步涉及权限时，只把这一步写成 [授权]，前后能自动验的照常写；能用测试账号或录下来的真实输入（事件、请求样本）代替那一步的，写成自动验的。

格式：

```markdown
## 验收标准
A1. 操作：执行 `todo add 买菜`
    预期：输出「已添加」
A2. 操作：重启服务后执行 `todo list`
    预期：列表里还有「买菜」
A3. [授权] 操作：用正式账号点「同步到飞书」
    预期：正式飞书表里多一行今天的记录
A4. [人工] 操作：看新首页
    预期：布局和文案是你想要的
```

开发时不要补写或修改验收标准；验收标准只认用户发来的消息。

## 起草任务提示词（自动评审 v2）

用户让你起草开发任务的提示词时，优先沿用同一任务文件，通常组织为以下四节：

- 「目标」：要什么结果、为什么，几行就够。
- 「已拍板」：用户定下、不许开发方改的规则、格式、取舍；没有就写「无」。
- 「边界」：允许改哪里、禁止什么、明确不做什么。
- 「验收标准」：按上面的写法。

不要做（这些由开发方或程序负责，写了只是浪费时间和 token）：

- 不重复全仓阅读或手工抄写 HEAD、哈希和测试计数。需要判断目标可行性时，先查来源索引和已有方法，再定向读取相关定义、调用者和测试；候选与内容版本由程序记录。
- 引用已有来源、运行配置和结果入口，避免复制大段规则。目标复杂时补充不能改坏的行为、关键调用入口和验收映射，不硬凑四节或行数。
- 不要写联调或端到端测试的步骤：自动验收和验收命令由程序执行。
- 只有用户明确在意的接口、格式、文案才写进「已拍板」，其余交给开发方按现有代码习惯定。
- 工程事实不足时由 Loop 的准备流程核对已有方法、有限恢复或受限修复；业务取舍和权限缺口才交给用户。不要把无法核实的推断写成已实现。

几段并行或串行开发、最后跑整批验收（流水线）时：每段一份上面这样的提示词；整批验收的标准单独写一份，每条开头标归属，比如「A3. [乙] 操作：打开需求现状页」，没通过时程序按标签退回那一段修；[人工] 条目不用标归属，[授权] 条目照常标（「A3. [乙] [授权] 操作：…」），同意授权写在这份标准文件里。

批次参数写进 `批次.json`，不要在批次目录里写门禁或启动脚本。

## 问题单

问题单方法只在本节维护一份；各项目和项目模板只写指向，不保留规则或模板副本。

| 方面 | 统一写法 |
|---|---|
| 位置和文件名 | 项目根目录下的 `issues/`，一张单一个文件，所有单子放在同一层；文件名就是标题，定下以后不再改 |
| 单头 | 状态、排期、关联单（根因单、上下游）三个固定字段 |
| 状态 | 待修复 → 修复中·<批次名> → 已合入待验·<批次名> → 已解决；已解决时写关闭原因：完成／重复／不做，并写清怎么解决、哪一批、怎么核实的 |
| 正文 | GitHub 模板：问题描述、复现步骤、预期结果、环境与证据（里面写因果链和分层归因，没确认的原因写「待排查」）、本次任务、范围与限制、验收标准、完成后需要提供；不确定的写「待补充」 |
| 建单和开批 | 发现当轮建单；同一根因合为一单；默认先攒着，排批前按同源归并，一批修一个根因；停摆、数据丢失这类不修就没法用的，排期标「立即修」 |
| 只完成一部分 | 用户核实已完成部分后，由协调方关掉原单，剩下的另开新单，两张互相链接 |
| 重复 | 关闭原因写「重复」，并链接到主单；不做的写清「不做」的理由，均由协调方按用户决定关闭 |
| 合入后 | 程序把登记单子的单头改成「已合入待验·<批次名>」，并写明未验证项见本批交付总表或 Loop 总结；回写不是业务验收通过 |
| 关单 | 用户验收通过后，由协调方改成「已解决」并记录关闭原因与核实依据；程序不自动关单 |
| 不做的事 | 不挪文件夹、不改文件名来表示状态 |

开批时，协调方把单头改成「修复中·<批次名>」，在 `批次.json` 的 `issues` 登记本批修哪几张单（字段与路径规则见 [工具清单](工具清单.md#批次json-字段)）。仓库内已跟踪的单子，由程序在开工搬运批次文档时，只在批次分支预写「已合入待验」：随本批提交一起进入目标分支，合入才在目标分支生效，撤回即随提交恢复。不在测过以后改候选树、不在目标分支留下未提交回写，也不追加回写提交。仓库外单子开工不写，合入目标分支成功后直接改文件。

回写只是附带动作：单子不存在、未纳入仓库、不能写入时，只在开工输出、总结和交付总表里提示，不拒绝开工、不退回批次、不阻止合入。用户直接看总结和交付总表中的逐条未验证项，不要求协调方另抄验收结果到原单；最终关单仍由协调方依据用户验收做。

新建单子使用以下模板；不确定的保留「待补充」，不猜事实或原因：

```markdown
# <标题>

状态：待修复
排期：待排期
关联单：无（有根因单、上下游时写链接）

## 问题描述
待补充：问题与影响。

## 复现步骤
待补充：从外部执行的步骤、实际结果。

## 预期结果
待补充：应当看到的结果。

## 环境与证据
待补充：版本、环境、日志或截图路径。
因果链：待排查。
分层归因：待排查。

## 本次任务
待补充。

## 范围与限制
待补充。

## 验收标准
待补充：按本页「起草需求时写验收标准」写操作和预期。

## 完成后需要提供
待补充：改动说明、验证证据及尚未验证项的入口。
```

已解决的单子在状态行写关闭原因（完成／重复／不做），并在「完成后需要提供」补充处理方式、批次和核实依据；部分完成或重复时，在「关联单」互链后续单或主单，文件路径始终不变。

## 可选配置：被测系统怎么启动

`bin/loop 接入` 会探测这些配置。网页、接口这类要先启动服务的项目，核对 `.autoreview.json` 的 `acceptance`（已有的其他字段保留），按你的项目改三处：

- `start`：在项目目录里启动服务的命令。
- `readyUrl`：服务起来以后能打开的地址；程序访问它返回正常就算启动好了，启动前也用它检查端口有没有被别的程序占着。
- `env.PORT`：让服务监听这个端口（服务要认 `PORT` 环境变量；不认的话把端口直接写进 `start`）。

```json
{
  "acceptance": {
    "start": "npm run start",
    "readyUrl": "http://127.0.0.1:38080/",
    "env": { "PORT": "38080" }
  }
}
```

**验收会写数据**（数据库、文件）的项目再加一个 `reset`：程序在首次验收和换强模型重验前执行它；同一次报告更正复用数据与有效证据，把数据恢复到初始状态。它只重置数据，**不要重启或关闭服务**（服务由程序启动和关停，中途被关掉这一轮就作废）。不配的话，从第 2 次验收起数据就不干净，依赖初始状态的标准会验不了，程序会暂停提示你补上。

```json
{
  "acceptance": {
    "reset": "sh deploy/acceptance/reset-data.sh"
  }
}
```

`reset` 在项目目录里用 `sh -c` 执行，拿得到 `env` 里的环境变量和 `AUTOREVIEW_RUN_DIR`，默认 120 秒超时（`resetTimeoutSec` 可改）；输出写进本轮运行目录的 `reset.log`。重置脚本属于验收环境，由项目维护，Loop 准备流程按已授权路径修复方法；不能降低验收标准。

命令行工具这类不用启动服务的项目，只写 `{"acceptance": {}}`（会写数据的同样可以配 `reset`）。其他可选字段（`logs` 收集日志文件、`guide` 操作说明、`timeoutMin` 等）见 [README.md](README.md) 的「自动验收」一节。

## 可选配置：浏览器工具

验收要打开、点击网页时，验收方用无头 Chromium，需要在项目目录安装 Playwright 和 Chromium：

```bash
npm i -D playwright
npx playwright install chromium
```

不想装进项目，也可以全局安装 `playwright`，或者设置环境变量 `AUTOREVIEW_PLAYWRIGHT` 指向 Playwright 所在目录。接入只提示缺少的浏览器工具，不自动安装。

## 程序怎么认「## 验收标准」

- 只认**你发出的消息**里的 `## 验收标准`（单独一行的二级标题），到下一个一级或二级标题为止；模型写在回复里的不算。消息里的 `@需求.md` 会先展开再找。
- 条目可以写 `A1.`、`1.`、`- `，续行缩进；程序统一编号成 A1、A2…
- 定下后冻结。之后你再发一条带 `## 验收标准` 的消息，就替换成新一版；开发方和验收方都改不了。
- 需求里没写时不会卡住：第一次验收前由强模型只看需求原文起草一份，总结里标「自动起草，未经你确认」。
- 开发方觉得某条标准不对，会写「A2：异议：理由」，这时自动验收暂停，由你决定：同意就发新标准，不同意就让它按原标准继续；处理过的异议不会再拦同一段旧回复。
- 开发方认可标准、只质疑验收方法、环境或失败归因时，写「A2：方法存疑：理由」：不暂停，照常验收，理由随该条交给验收方并写进总结；条目按证据照常判定，不会因为这句话就算通过。
- 头脑风暴定稿后，把需求（带 `## 验收标准`）作为开发会话的**第一条消息**发出去，比如 `@需求.md`。如果是在同一个会话里聊到定稿的，就把定稿的需求原文再发一次，程序才能取到标准。
