# Loop 0.4.0：架构与逐环节控制

版本：0.4.0 候选交付。本文描述实际代码，不把 v0.1 设计稿的全部目标当成已经完成。

## 1. 这次到底做了什么

在原 0.3.0 上保留开发、独立评审、候选冻结、问题历史、来源核对和正式导出机制，增加受控准备与统一执行路径。没有增加管理 Agent、网页工作台、后台模型轮询或自动缓存保温。

```text
人工：确认固定执行配置与授权范围
  ↓ register（一次登记，可供多个准备草稿引用）
本地 Codex 专用准备会话
  ├─短 Skill：告诉模型使用哪些工具
  ├─Hook：只放行已声明的准备 MCP 工具
  └─MCP stdio 桥：没有启动、授权、任意命令接口
       ↓ Unix socket
Loop Guard 准备服务（用户单独启动，位于模型可写目录之外）
  begin → patch → check → 必要时 probe → seal
       ↓ 生成预览与唯一 prepared_id
人工终端 launch：确认精确规则与预算
       ↓ SQLite 请求认领与授权账本
create_run → supervise → Controller → UnitEngine
  ├─work/integration：开发 → 门禁 → 独立评审 → 返修
  ├─verify：指定输入 → 门禁 → 按声明执行评审；不调用开发
  └─Pi 开发/返修：loop_build、loop_submit_check
       ↓ 同一 execution.py
隔离构建副本 → 输出边界检查 → 自测/门禁证据分级保存
       ↓
原有最终核对、结果与正式导出
```

Plugin 是安装结构，Hook 是提前拒绝工具调用的入口，MCP 是结构化调用接口；Python 核心负责实际检查、计数、执行和结果。它们不是另一个模型。

## 2. 新增模块与职责

| 模块 | 职责 |
|---|---|
| `loop_guard.py` | 人工登记、CLI 准备、授权启动、本地服务、生成接入配置 |

| `execution.py` | 真实交付检查；探测、自测、门禁共用隔离构建执行器 |

## 3. 编排阶段逐环节怎么控制

### 3.1 固定能力先由用户登记

`register` 读取一份已确认的 schema v2 配置，保存源项目、输出数据根、成员配置、构建配方、源码范围、保护范围、预算上限。普通 MCP 不暴露 register，所以模型不能通过工具自行批准新的 Shell 命令、扩大预算或换安全模式。

这是当前版的明确限制：它不是自动发现一切能力的通用项目扫描器。新工具、新业务测试脚本和新构建副作用需要先在循环外审定，再登记。不能把已有三条 Maven target 路径当成所有 Maven 项目的完整输出清单。

登记时默认把用到的配方在当前源码副本上各跑一次（与正式门禁同一执行器），所有未声明的输出一次列出并拒绝登记，不等到开发跑完一轮才在门禁处发现。如果某个配方在当前源码上没有产生任何输出，会明确标为“未实际验证”，不会当作已验证。规则见 02 手册 §1.2。

### 3.2 专用准备会话，只给少数能力

Hook 的 `PreToolUse` 只允许配置前缀下的九个已知 MCP 工具；任意 Bash、Python、直接补丁、子代理及未知工具默认拒绝。项目阅读也通过受限 `loop_project_*` 工具完成。

这个初版比设计稿中的细粒度编辑策略更保守：准备 MCP **不提供自由文件写入或业务测试作者工具**。已审业务断言在进入准备模式之前形成；本轮只整理 JSON 规则和引用已登记配方。普通 coding 会话不能全局启用此 Hook，否则正常编辑也会被拒绝。

安装后必须验证真实工具命名和 Hook 信任，才能称为宿主接入成功。Hook失效时，schema v2 的正式启动仍需准备与账本；但同权限用户自行运行旧程序、任意 Shell 或别处模型并非本程序能完全禁止。

### 3.3 不反复阅读整套引擎

`begin` 返回当前能力和登记规则；`patch` 只改允许的业务字段及收紧限额；`check` 对全部相关门禁聚合错误。没有默认模型预检、没有自动真实场景试跑。

同 revision 的检查可以缓存，但明确标注覆盖范围。输入、安装和实际配置在 seal/launch 重新核对；缓存不是远程账号、模型质量或未来代码副作用的证明。

准备最多接受40次有副作用的 patch/probe 类动作。无变化 patch不额外执行。`Stop` Hook不要求模型继续，不产生“最后再查一次”的自动续跑。这个动作限制不保证宿主模型的纯思考时间上限，也不是性能收益测量。

### 3.4 必要探测不是完整预开发

只有人工登记了 `probe_allowed`，并通过 `--require-probe` 指明的配方，才能产生可执行探测问题。MCP不接受任意 argv。探测使用真实执行器，时间最多120秒并受配方时限约束。

探测先复制按真实输入规则得到的源码，再进入构建副本。退出非零可能是新功能尚未实现；它与输出越界、命令错误、证据缺失不能混为一谈。当前没有任意测试框架的“发现零测试”自动识别器；需要由已审命令/报告断言覆盖。

### 3.5 封存不是业务通过

seal保存有效规则、输入摘要、安装摘要、准备检查范围与唯一启动请求。原始规范版本仍由用户在最终预览确认；程序不证明自然语言任务正确，不推断用户已经同意模型改写的验收语义。

## 4. 启动与额度

schema v2不能直接 `create_run`，必须带准备记录与授权。根入口、CLI和内部Controller最终共用准入检查。运行中规则、输入和关键安装实现改变会拒绝继续；历史结果本身不会被重写成新格式。

SQLite在事务中认领 `launch_request_id`。同一个prepared_id重复启动返回已有运行，不重新监督、恢复或派工。认领后崩溃但清单未写完，保持待核对，而不是自动再创建一次。

额度分为：成员调用、自测、程序门禁、业务返修，以及用户定义的操作额度。多个运行只有显式引用同一个 authorization_id 时才共享额度；用户新批授权代表新的范围。程序不能从相似任务名称推断它们必须共享授权。

无法确认某次执行是否已经发生的故障不自动退额度。没有实现自动充值、账本自动修复或按真实API请求计费。

旧 schema v1 保留兼容：在已标记受管的数据根中拒绝绕行；未登记的独立旧任务仍可使用旧流程。因此“升级版本”不等于所有旧命令都自动进入受控模式。

## 5. 首次开发和返修都走同一个构建工具

```text
当前 attempt 的编辑树（源码）
       ↓ 真正的 inspect_developer_delivery，不接受额外 excludes
稳定代码快照
       ↓ copy_manifest + 前后指纹核对
本次构建 source/ + home/ + tmp/
       ↓ 固定配方 argv/cwd，单独授权缓存
构建产物与报告
       ↓ 既有源码不得改变；新输出必须已声明
evidence.json + job/receipt.json + 报告摘要
```

`target/` 可以在构建副本里生成；不能进入编辑交付树。产物声明不扩大源码修改权限。开发自测是 `SELF_TEST`，正式门禁是 `GATE`，探测是 `PROBE`；三者共用执行方法，绝不共用通过结论。

成员服务在每次 `_member` 时注册当前 code_path、role、attempt、可选配方和期限。会话复用也不改变当前工具绑定。旧调用令牌不能自动成为新调用权限。

Pi由适配器显式 `-e` 加载随包扩展，不依赖自动发现。扩展移除任意Bash，只保留读查改及Loop工具。注意 Pi 0.87.1 的 `--tools` 白名单同样过滤扩展工具，适配器必须把 `loop_build`、`loop_submit_check` 写进 `--tools`，否则它们不会被注册（已用真实 Pi 核实）。只读评审不获得构建和写入权限。构建中禁止新的编辑请求，并通过前后指纹检查拒绝对象漂移。

严格模式在macOS使用sandbox-exec限制写入，不能写入交付树以外的非授权位置；构建仅允许临时目录和登记缓存写入。当前沙箱不是全面的机密读取隔离，详见安全边界。Linux本次离线测试使用显式audit-only，不把它声称为操作系统隔离。

## 6. 只验证，不反复开发

schema v2增加 `kind: verify`。`input_from` 必须是明确依赖及其候选；无依赖时验证登记输入。不调用developer，不能修改业务代码。`review_mode: gates`只有在用户规则明确选择、每条标准都有程序门禁时才有效；`review_mode: independent`仍执行指定评审。

C06失败后，依赖它的七场阶段不执行，不产生未经授权的回修边。七场可以配置为七个独立门禁并分别保留证据，不能把进程结束冒充七场业务通过。

重新验证已有代码可通过显式选定来源的新verify任务完成。当前没有自动选择“最后的失败目录”、自动抽取半成品或跨DAG无缝恢复的命令。

## 7. 日志与停止原因

原始诊断采用有界前缀保留。超限后仍持续消费完整stdout/stderr并解析协议；每个诊断文件都有retention元数据。只保留前缀不是完整raw日志，不能拿截断片段充当完整审计。

单条事件、最终回复、构建产物、必要报告和运行总目录分别设上限。运行目录配额按周期扫描检查，可能有检测间隔内超量；不是文件系统即时硬配额。

Guardian向适配器提供独立管道和随机nonce；适配器不把该管道传给Pi子进程。外层取消/超时优先保留；当前调用的有效outcome用于补充具体原因。stderr文本不是控制消息。

受管v2只允许程序明确列入的暂态原因重试；普通nonzero_exit、配置错误、输出越界、关键资源限制、缺失回执不自动再次开发。v1保留旧重试政策，不能据此声称未迁移任务也获得完全相同策略。
