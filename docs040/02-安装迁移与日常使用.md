# 安装、迁移与日常使用

## 0. 第一次验收只做离线演示，不替换旧引擎

将ZIP解压到新目录 `Loop-0.4.0`，保留原0.3.0目录、原loop-data与全部失败现场。不在原运行中升级，不把旧数据根直接改为受管根。

本版Python核心仅使用标准库。目标建议Python3.12或更高；本次实测Python3.13.5/Linux。真实成员仍需你本机已安装并确认的Pi、模型和工具链。TypeScript扩展由Pi加载，不要求你在每个业务任务运行tsc。Windows原生/完整Linux严格沙箱未支持。

进入新目录后执行：

```bash
python3 loop_guard.py --version
python3 loop_guard.py doctor
python3 examples040/offline_demo.py --out "$HOME/Loop040-offline-pass"
```

最后一条只使用随包确定性成员和构建fixture，不调用Pi、网络模型、Maven或你的产品。输出目录必须不存在。验收结束不自动删除记录，也不写原项目。

查看 `Loop040-offline-pass/DEMO-RESULT.json`：预期总结果PASSED、最终核对PASS、成员fixture4次、自测2次、门禁10次、返修1次，重复同一启动请求不新增运行。演示包括一次有意评审不通过再修复，然后执行C06与七个程序门禁；七场是协议fixture，不是你的七场业务验收。

另跑失败分支：

```bash
python3 examples040/offline_demo.py --out "$HOME/Loop040-offline-stop" --fail-c06
```

预期C06未达标，后续seven不执行；重复启动不重新派工。以脚本输出expected/actual和实际清单为准。两个demo使用彼此独立状态和授权，不是累计预算共享演示。

安装验收时可执行新增反例套件；不要把它装进日常准备Hook：

```bash
python3 tools/verify_release.py --out "$HOME/Loop040-offline-tests"
# 完整回归（耗时更长）：
python3 tools/verify_release.py --all --out "$HOME/Loop040-all-tests"
```

### 可选：扩展协议模拟与Mac写入策略探针

```bash
python3 tools/verify_pi_extension.py
python3 tools/probe_macos_sandbox.py
```

第一条只使用本机已经安装的Node、TypeScript和Node类型声明，不自动安装依赖；它是最小宿主模拟，不是Pi官方SDK或真实Pi运行验证。缺工具时如实报告缺项。

第二条只在Mac真实sandbox-exec可用时检查允许写入、越界写入和链接逃逸；Linux返回NOT_RUN，不能写成通过。它不调用模型，也不证明Pi认证、Java构建或完整沙箱已经通过。随后仍需本机扩展和工具链的对应验收。

## 1. 将一个实际项目迁入schema v2

### 1.1 从模板填写，不直接运行占位配置

复制 `examples040/project-template.v2.json` 到你指定的任务准备目录。所有TODO都必须替换，程序会拒绝未完成模板。

必须确认：实际源目录、允许修改与保护范围；原来已经选定的开发/评审模型与思考档位；Pi路径；真实构建命令、工作目录、模块/profile、输出与报告文件；阶段预算和总预算。

本版不替你猜“Sol”“Astra”对应的provider/model字串，不自动换便宜模型，也不添加新的付费验证。模型名称照你已确认的配置填写。

对于Maven，`cache_dir`是单独授权的依赖缓存，不要指向整个HOME、源码、引擎、状态目录或运行数据根。模板默认 `mvn -o` 且 `network:false`：要求缓存已经具备依赖。缺依赖时应先按你的授权策略准备缓存，或明确批准受限下载；不能在普通编排里随意安装/联网。

模板中的输出目录、报告文件只是占位。真实命令的模块范围、插件输出、Surefire报告必须由项目事实决定。当前`evidence_paths`是明确文件列表，不接受通配符；自定义插件或动态报告需要准备一个已审的确定性报告汇总命令。

### 1.2 人工登记

以下路径变量由你选择；不要指向0.3.0的活动数据根。

```bash
STATE="$HOME/.local/share/loop-guard-040"
DATA="$HOME/loop-data-040"
python3 loop_guard.py --state "$STATE" register my-project /绝对路径/task.v2.json --root "$DATA"
```

register不是模型启动，不会调用模型。它登记已确认配置与能力，并标记这个数据根为受管根。它不会替你判断所有业务标准正确，也不会验证远程账号额度。项目ID已存在时不覆盖；能力变更请使用新的明确登记版本，例如`my-project-v2`。旧prepared仍保留。

**登记验证（默认开启）**：register会把单元实际用到的每个配方，在当前源码的冻结副本里按正式门禁同一执行器（同一安全模式）各跑一次，再决定是否登记：

| 结果 | 含义 | 处理 |
|---|---|---|
| `VERIFIED` | 退出0，必需报告齐全，声明的输出确实产生且没有越界 | 登记 |
| `VERIFIED_NONZERO` | 非零退出，但报告齐全、输出确实产生（命令真的跑了，可能是功能尚未实现） | 登记，结果附输出尾部；**看一眼尾部，确认是业务断言失败而不是环境问题** |
| 拒绝登记 | 必需报告缺失（`evidence_limit`）；声明了输出却一个都没产生（`no_output`）；输出越界（一次列出所有未声明目录）；改了既有文件；超时；沙箱不可用；配置错误 | 先按 stderr/stdout 排除环境问题，一次改全再登记 |

2026-10-02 验收中出现过这种情况：沙箱拒写导致脚本在写报告前就崩溃，旧判定把它当成"非零退出"放过了，现在一律拒绝。确实因功能未实现、在当前源码上根本跑不起来的配方，必须用 `--skip-verify PROFILE` 显式跳过，预览会写明"未验证"。只被带 `budget_key` 的场景门禁使用的配方不会自动执行（避免消耗真实场景）。`--no-verify` 只用于离线夹具。登记验证的记录会作为该配方的探测结果复用，同一源码不必再 probe。

确有首次执行方式疑点时，可以在配方里明确`probe_allowed:true`，登记时添加`--require-probe PROFILE_ID`。不要为每个普通任务默认加这一项。

### 1.3 先用CLI验证准备链路（不依赖插件）

```bash
python3 loop_guard.py --state "$STATE" begin my-project
# 返回prep_id和revision；用实际值代替下面的PREP_ID/REV。
python3 loop_guard.py --state "$STATE" check PREP_ID --revision REV
python3 loop_guard.py --state "$STATE" seal PREP_ID --revision REV
```

遇到INVALID/NEEDS_CAPABILITY，先处理返回的具体问题；不要提高权限或额外重跑模型。需要探测时，使用check实际返回的question_id：

```bash
python3 loop_guard.py --state "$STATE" probe PREP_ID profile:PROFILE_ID --revision REV
python3 loop_guard.py --state "$STATE" check PREP_ID --revision REV
```

修订本次业务字段：将结构化变化保存成JSON，执行`patch PREP_ID changes.json --revision REV`。顶层字段采用替换语义，不是任意深层JSON Patch；修改units时提供完整新units数组。返回的新revision用于后续check/seal。

### 1.4 人工启动

seal返回精确启动命令。由你在正常终端执行：

```bash
python3 loop_guard.py --state "$STATE" launch PREPARED_ID
```

会显示预览，并要求输入`yes`。非交互人工脚本可显式添加`--approve`；它不是密码或无法伪造的人类证明，必须依赖编排宿主的工具限制，禁止模型调用这个人工入口。

同一个prepared重复执行不创建新运行。确需新一轮，创建新prep、封存，再启动。需要共用同一批剩余额度时，显式添加已有授权：

```bash
python3 loop_guard.py --state "$STATE" launch NEW_PREPARED_ID --authorization AUTHORIZATION_ID
python3 loop_guard.py --state "$STATE" budget AUTHORIZATION_ID
```

不带`--authorization`代表人工批准新授权；程序不会根据相似任务名称自动合并预算。版本/代码安装变化后需要重新准备，不在活动任务中修改发布目录。

## 2. 接入准备插件（Codex 与 Claude Code 共用一个插件）

`plugins/loop-guard/` 是同一个插件，同时带 `.codex-plugin/plugin.json` 和 `.claude-plugin/plugin.json`，共用 Hook 脚本、MCP 桥和技能。包根目录有两份本地市场清单：`.agents/plugins/marketplace.json`（Codex）和 `.claude-plugin/marketplace.json`（Claude Code），市场名都是 `loop-guard-local`。

Hook 只在**准备目录**里拦截：会话工作目录或它的上级目录中有 `.loop-guard-prep.json` 才生效，其他会话一律不受影响。所以即使 Codex 侧插件是全局启用的，也不会影响日常 coding。

### 2.1 先启动准备服务

服务只提供准备能力，不提供启动、充值和任意Shell。使用短的用户私有socket路径，避免Unix socket长度限制：

```bash
mkdir -p "$HOME/.loop040"
chmod 700 "$HOME/.loop040"
python3 loop_guard.py --state "$STATE" serve --socket "$HOME/.loop040/g.sock"
```

这是一个本地程序，不调用模型。保持这个终端运行；业务本身启动后不依赖你打开工作台。按Ctrl+C停止准备服务，不等于停止另一个已经运行的业务任务。

### 2.2 生成准备目录

在另一个终端（输出目录必须不存在）：

```bash
python3 loop_guard.py --state "$STATE" plugin-config \
  --socket "$HOME/.loop040/g.sock" --out "$HOME/.loop040/prep"
```

它生成：准备目录及其中的 `.loop-guard-prep.json` 标记、`AGENTS.md`/`CLAUDE.md`、Claude Code 项目级设置 `.claude/settings.json`，以及 MCP 桥读取的 `~/.loop040/runtime.json`（socket 地址）。它不安装插件、不信任 Hook、不改任何宿主的全局配置；输出里的 `next_steps` 给出两边的安装命令。

### 2.3 装进宿主（一次性）

**Claude Code**（只在准备目录启用，项目级）：

```bash
cd "$HOME/.loop040/prep"
claude plugin marketplace add /绝对路径/Loop-0.4.0 --scope project
claude plugin install loop-guard@loop-guard-local --scope project
claude mcp list        # 应有 plugin:loop-guard:loop_guard ✔ Connected；别的目录看不到
```

**Codex**（插件为全局启用；Hook 只在准备目录生效，其他会话只会多出 9 个准备工具）：

```bash
codex plugin marketplace add /绝对路径/Loop-0.4.0
codex plugin add loop-guard@loop-guard-local
```

然后在准备目录启动 `codex`，进入 `/hooks`，审阅并信任 loop-guard 的 4 个 Hook。Codex 默认跳过未信任的插件 Hook。Codex 安装的是插件的**复制件**：插件文件改动后要 `codex plugin remove` 再 `add`，并重新信任 Hook。

已在隔离配置目录核实（不调用模型）：两边都能安装并识别 MCP 服务；Claude Code 项目级安装只在准备目录可见；`claude plugin validate` 对插件和市场都通过；从 Codex 安装副本用系统 Python 3.9 运行 Hook，Bash 被拒、准备工具放行。

### 2.4 每个宿主一次的哨兵验收

在准备目录启动会话，验证：
- 能调用 `loop_project_info`、`loop_prepare_begin/check/seal`；
- 让它执行 shell 命令（如 `ls`）、改文件、开子代理、调用未知 MCP 工具，全部被拒；
- Stop 不会触发自动续跑；
- 停掉准备服务后，工具返回"准备服务没有运行"，模型不能自称 READY；
- 没有 prepared 记录时，v2 任务不能直接 run/start。

两边工具名不同：Claude Code 是 `mcp__plugin_loop-guard_loop_guard__<工具>`，Codex 是 `mcp__loop_guard__<工具>`（开启 `non_prefixed_mcp_tool_names` 时没有前缀）。Hook 只认这几种写法加九个已知工具名。允许时，对 Claude Code 返回 allow（免确认），对 Codex 不输出任何内容（Codex 0.159.2 可执行文件里有 "unsupported permissionDecision:allow" 报错分支，与文档不一致，所以不输出，走 Codex 自己的审批）；拒绝时两边都用退出码 2 并在 stderr 写原因。

这属于安装或宿主升级验收，不是每个任务再演练一次。Hook 本身不是完整安全边界；读 04 安全文档后再用于实际项目。

## 3. 日常使用应当是什么样

用户与外部模型把任务讨论清楚。模型进入专用准备模式，读取项目能力，begin → patch → check → seal，然后交出唯一命令。没有新能力和具体疑点时，不读整本引擎手册、不写新启动器、不运行引擎全回归。

用户启动。开发和返修都用`loop_build`自测；引擎正式执行门禁与评审。结束后打开本次`result.md`、`report.html`或根包装生成的`交付结果.md`。不以旧latest替代精确run_id。

日常查看和停止沿用：

```bash
python3 engine/loop.py status RUN_ID --root "$DATA"
python3 engine/loop.py stop RUN_ID --root "$DATA"
python3 engine/loop.py audit RUN_ID --root "$DATA"
```

导出命令参数沿用引擎CLI，先用`python3 engine/loop.py export --help`查看；导出仍只创建新目录，不合并原项目。recover只是补停止结果，不是业务续跑。schema v2 的旧CLI retry会要求受管准备，使用新prep/明确授权重启。

## 4. 续轮与续跑

续轮指用已确认的规则开新一轮，续跑指把中途停下的多单元运行接着做完。两者都只起草新计划，不登记、不启动；计划仍按 `register → begin → seal` 准备，启动命令由用户执行。

**续轮（derive）**：从上一轮已登记项目原样复制规则，只改源码。上一轮候选目录只读、不能直接改；要拿候选当新源码，用 `--copy-source` 把源码复制成当前用户可写的副本，并让计划指向副本：

```bash
python3 loop_guard.py --state "$STATE" derive my-project --project-id my-project-next --out "$HOME/my-project-next.json" --copy-source "$HOME/my-project-next-src"
```

只换一个已有源码目录时用 `--source /绝对路径/新源码`，不复制；两个选项同时给出时复制的是 `--source`（否则是上一轮登记的源码）。计划文件和复制目标都必须不存在，命令不覆盖；输出含 `plan` 与带上一轮数据根的 `next_commands`。

**续跑（continue）**：运行已经停止且为 schema v2 受管运行后，用运行编号起草续接计划：

```bash
python3 loop_guard.py --state "$STATE" continue RUN_ID --root "$DATA" --project-id my-project-resume --out "$HOME/my-project-resume.json"
```

它自动去掉已达标单元、从续接单元最新候选接着做，并把未解决问题带进该单元目标；可续接单元不止一个（并行分支）或需要合并上游成果时会明确拒绝，需手工编排。`--fresh-unit` 让续接单元从其冻结输入重做、不用上次候选。续接计划同样要换新项目编号重新登记、准备，再由用户启动。

## 5. 会话复用、简报与旧任务迁移

默认仍是fresh。`developer_session: reuse_repairs`需要真实Mac旧目录拒写验证；不要把Linux离线fixture称为验证过复用。评审与格式修复仍独立。

默认不调用简报模型。明确需要简报时，在启动命令添加`--brief`，同时先配置`LOOP_BRIEF_MODEL`、`LOOP_BRIEF_THINKING`、`LOOP_PERMISSION_EXTENSION`以及可选`LOOP_PI_BIN`。本版删除原作者机器路径与隐式模型选择。缺配置只让简报失败并保留原结果，不重启开发。

直接调用旧schema v1 Pi适配器时也需要显式`--permission-extension`或传入`LOOP_PERMISSION_EXTENSION`（注意agent.inherit_env）；不再静默使用原作者机器里的第三方权限扩展。schema v2已显式加载随包成员扩展，不需要靠第三方扩展实现Loop工具。

旧schema v1没有自动获得v2的授权账本、构建配方或严格重试规则。旧结果可以查看，不能把旧PASS迁移成新的检查。需要选取失败现场代码时，先独立核对、保留原现场，创建明确源码起点和新verify任务；程序不自动认定最新目录就是最佳成果。

## 6. 回滚

停止0.4.0新任务，等待子进程收尾，保留其状态与结果目录。停用专用准备插件/服务，回到原0.3.0目录与原数据根。不要让旧程序写0.4.0数据根，也不要删除正在被引用的授权账本。发布包安装从未覆盖原版本，所以回滚不需要把源码反向补丁回去。
