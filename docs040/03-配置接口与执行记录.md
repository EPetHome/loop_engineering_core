# 0.4.0 配置、工具接口与记录

本文是实现参考，不是要求普通编排模型每轮通读。日常只读Skill与工具返回；真实结构以`rules.py`、`capabilities.py`和`guard_server.py`为准。

## 1. schema v2 与v1

v1继续严格拒绝未知字段，不把新字段悄悄塞入旧格式。v2增加以下顶层字段：

| 字段 | 作用 |
|---|---|
| `execution_profiles` | 已登记的固定执行配方 |
| `security` | `strict`或显式`audit-only`；默认strict |
| `operation_budgets` | 自定义操作额度，例如C06的执行次数 |

v2单元增加 `build_profiles`、`input_from`、`review_mode`，新增`kind: verify`。门禁增加`profile`和可选`budget_key`。

2026-10-03 新增（均为可选）：

| 字段 | 位置 | 作用 |
|---|---|---|
| `review_scope` | 单元，默认 `frozen` | 问题清单冻结：从第 2 轮起，评审 FAIL 只有在以下三种情况才触发返修：失败的门禁、未解决的已知问题、位于本轮改动文件的新问题。其余新发现记为 `DEFERRED`，写进结果页"遗留发现"。连续两轮都只剩"改动处新问题"时提前停止（不收敛）。`open` 恢复旧行为 |
| `max_selftests` | 单元 | 本单元自测上限；不写时把 `limits.max_selftests` 平均分给有构建配方的单元 |
| `files` | 评审 issues 里的每一项 | 问题涉及的项目内相对路径；冻结单元从第 2 轮起必填 |

准备检查的 `warnings` 会列出含"全部 / 所有 / 完整 / 任何"等无边界措辞的验收标准，不阻断；启动预览会列出全部构建和检查命令，以及每个单元的返修上限和评审口径。

已有limits、notes、completion、criteria和修改边界继续有效。v2规范化是幂等的；任务自己手填的门禁argv/output_paths/timeout/max_reruns若与配方不同会被拒绝，而不是静默采用另一值。

## 2. 一份构建配方

下面只是形状示例，实际项目不要不经核对就照抄模块与报告：

```json
{
  "maven-test": {
    "argv": ["mvn", "-B", "-o", "-Dmaven.repo.local={cache}", "test"],
    "cwd": ".",
    "cache_dir": "/人工选择的独立缓存目录",
    "max_cache_bytes": 2147483648,
    "max_cache_files": 200000,
    "output_paths": ["module-a/target/"],
    "evidence_paths": ["module-a/target/surefire-reports/TEST-example.xml"],
    "timeout_seconds": 600,
    "network": false,
    "inherit_env": [],
    "probe_allowed": false,
    "max_reruns": 0,
    "description": "明确本配置的工具和范围"
  }
}
```

`argv`是参数数组，不是Shell文本。支持`{python}`、`{engine}`、`{code}`、`{workspace}`，使用`{cache}`必须显式登记cache_dir。cwd是复制后源码的相对目录。output_paths是副本中新产物范围；evidence_paths是必须存在的明确文件，必须位于声明输出内。路径不使用通配符。

配方源码、调用脚本和插件本身仍可能包含副作用；固定配方并不自动等于安全代码。严格模式加写入沙箱、网络开关、时限和运行后完整性核对；未知行为应报错而不是扩大输出白名单。

缓存独立加锁。等待锁也受阶段期限限制；缓存配额单独检查。缓存可以加速依赖获取，但不会带来PASS复用。当前不自动播种缓存、不删除旧缓存、不承诺不同工具链能安全共享同一个缓存。

## 3. 单元与门禁

开发型单元引用：

```json
{
  "id": "repair",
  "kind": "work",
  "goal": "已审业务目标",
  "developer": "dev",
  "reviewer": "review",
  "review_mode": "independent",
  "writable_paths": ["src/"],
  "protected_paths": ["tests/"],
  "build_profiles": ["maven-test"],
  "criteria": [{"id":"C1","text":"已确认的完成标准","gate_ids":["G1"]}],
  "gates": [{"id":"G1","profile":"maven-test"}]
}
```

程序生成这个门禁的命令、临时输出和相关时限；不要求模型再次手填相同字段。开发自测仅能选择本单元build_profiles中的配方。

验证型单元：

```json
{
  "id": "C06",
  "kind": "verify",
  "goal": "仅验证明确候选，不修改业务代码",
  "depends_on": ["repair"],
  "input_from": "repair",
  "review_mode": "gates",
  "criteria": [{"id":"C06-pass","text":"本场已审程序验收标准","gate_ids":["C06-gate"]}],
  "gates": [{"id":"C06-gate","profile":"c06-scene","budget_key":"C06"}]
}
```

必须同时登记对应配方并设置`operation_budgets: {"C06": 1}`。`budget_key`每次该门禁实际准备执行时消耗，重跑也算。它不自动知道脚本内部偷偷执行了几场或调用了几次模型；真实场景的内部边界仍要在受管执行配方里明确。

gates模式不调用独立模型评审，只能用于用户明确采用纯程序验收的标准；结果`reviewed:false`。需要Astra判断就使用independent并声明reviewer。v2的`reviewer_exec:true`目前明确拒绝：尚未提供受管评审任意执行工具，机械检查应声明为门禁，不能静默删除原有验收要求。

有依赖的verify必须显式input_from；不能根据“最近候选”猜。最终集成verify所选输入的生产链必须覆盖所有代码生产分支，否则拒绝把独立通过拼成整体集成。

## 4. 资源默认值

v2延续v1基础限额，并分离以下维度；这些是工程默认，不是经过真实90分钟业务测试的容量保证。

| 字段 | 默认 |
|---|---:|
| `max_log_bytes` | 每个诊断流保留8 MiB前缀 |
| `max_event_bytes` | 单条事件8 MiB |
| `max_response_bytes` | 最终响应1 MiB |
| `max_evidence_bytes` | 每次证据采集32 MiB |
| `max_build_bytes` | 派生产物1 GiB |
| `max_build_files` | 派生产物100000项 |
| `max_run_bytes` | 受管运行目录组4 GiB |
| `max_run_files` | 受管运行目录组300000项 |
| `max_selftests` | 20次 |
| `max_gate_executions` | 40次 |
| `max_total_repairs` | 10次 |

诊断前缀可能结束在一条JSON中间，retention.json会显示不完整。不要把它重新喂给解析器证明原始事件完整；实际运行状态来自持续消费的完整事件流及封存记录。

总磁盘限制是周期检查，非操作系统磁盘配额；短时间写入可以超过上限后再被停止。目录大小扫描也有开销，大项目需要后续性能验证。源文件限额与构建产物/报告限额不再混为一个参数。

## 5. MCP接口

桥采用本地stdio JSON-RPC，工具调用转到独立准备服务的Unix socket。不提供HTTP监听、不使用OpenAI密钥、不自动启动服务。不完整或超限请求返回错误。

| 工具 | 实际参数 |
|---|---|
| `loop_prepare_begin` | `project_id` |
| `loop_prepare_patch` | `prep_id, revision, changes` |
| `loop_prepare_check` | `prep_id, revision` |
| `loop_prepare_probe` | `prep_id, revision, question_id` |
| `loop_prepare_seal` | `prep_id, revision` |
| `loop_prepare_status` | `prep_id` |
| `loop_project_info` | `project_id` |
| `loop_project_list` | `project_id, path` |
| `loop_project_read` | `project_id, path, start_line, max_lines` |

begin/info可返回完整当前规则；patch/status不反复返回全套规则。seal返回绑定摘要、检查范围、预览路径和启动命令，不包含启动工具。字段名称是revision，不是设计稿里的expected_revision。

project_read限制项目内普通文本、每文件1MiB、每次最多200行和64KiB；拒绝符号链接及常见敏感路径。这不是通用秘密扫描器。列表最多300项，超出会标记截断；当前没有大型仓库全文语义索引。

配置变化patch采用允许顶层字段的替换：title/task_id/notes/units/completion/limits/operation_budgets。source、agents、profiles、security、excludes不能由普通准备更改；允许范围不可扩大，保护路径不可移除，预算只能收紧。业务标准本身仍需人工在启动预览确认，不承诺程序自动理解每句需求。

## 6. 目录与证据

```text
STATE/
  guard.sqlite3                 项目、准备、授权、启动请求、额度预留
  locks/                        进程锁
  prepared/<prepared-id>/       冻结规则与预览
  probes/<prep-id>/...           明确授权的执行条件探测

DATA/
  .loop-managed.json            受管根标记
  runs/<run-id>/
    rules.json / manifest.json  原有权威状态，新增admission关联
    units/<unit>/attempts/...   调用上下文、成员活动、受控自测证据
    units/<unit>/gates/...      正式构建与门禁证据
    result.md / report.html     原有结果
    交付结果.md                  根包装程序摘要，默认不调用AI
  checkouts/...                 当前调用编辑区
  snapshots/...                 冻结输入与候选
```

精确层级以manifest/context给出的路径为准，不自行拼接latest或假定所有build都在同一平铺目录。构建目录里的source/home/tmp为临时数据，关键job回执和evidence进入封存与完整性核对。未提交代码只是保留现场，不能直接正式导出。

适配器专用回执采用`loop-outcome-v1`、随机nonce和有限大小的管道帧。它不是任意stderr里的JSON。管道不传给Pi及其工具子进程。外层已知取消或超时不会被晚到ok覆盖。

## 7. 错误与停止政策

| 类别 | 受管v2行为 |
|---|---|
| 配置错误/不支持能力/非法输出 | 停止，保留现场，不原样重试 |
| 诊断日志保留满 | 记录裁剪，继续解析，不视为业务失败 |
| event/response/evidence/disk硬限制 | 明确阻断，不自动放大 |
| 普通nonzero_exit/回执缺失或不匹配 | 保守阻断，不猜暂态 |
| 已明确暂态且可安全重试 | 仅白名单原因、剩余额度内重试 |
| 业务标准失败 | 开发型单元按授权返修；验证型单元不自动回开发 |
| 交付格式错误 | 原有冻结代码的格式修复路径，不等于重新开发 |

当前并没有针对所有供应商HTTP错误的细致分类器，因此宁可停止，也不声称所有网络失败都能自动恢复。旧v1重试政策仍按兼容路径执行。
