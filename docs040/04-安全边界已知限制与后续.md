# 安全边界、已知限制与后续思路

## 1. 先说明这是什么级别的交付

0.4.0是实现了新路径、带离线反例与完整源码的候选版本，等待用户和Opus复核以及本机验收。不是已经在你的Mac、真实Pi、真实模型和Maven项目中验证过的生产升级。不建议直接覆盖现有稳定目录后重跑那批长任务。

严格区分四个事实：代码存在；离线协议与执行测试通过；本机宿主/操作系统接入通过；真实业务效果通过。它们不会互相替代。

## 2. Hook不能独自提供安全隔离

Hook是早期纠偏。宿主可能存在未覆盖路径、插件未启用、信任未完成或故障后继续调用的情况。只有准备MCP无启动权限、v2准入检查和正确的本机沙箱一起生效，才形成受控链路。

本包不会配置一个拥有完整系统权限的模型，再凭一句提示宣称它被限制。模型可写目录中不能包含Guard账本、发布目录、Hook和人工启动入口。不要在全权限/YOLO会话中将这些约束当成防绕过保证。

人工CLI支持`--approve`供用户脚本使用。它不是人类鉴别器；若模型仍能任意运行该CLI，它也能传这个参数。必须在宿主层限制工具和写入，把人工批准通道放在模型权限之外。本版没有独立系统账户、硬件签名或图形确认代理。

## 3. strict与audit-only

strict要求macOS sandbox-exec。不存在时拒绝，不自动降级；本次Linux测试验证了拒绝分支，但没有验证Mac策略的实际成功路径。

当前Mac策略以“允许读取，限制写入”为主，构建可显式关闭网络。成员调用模型需要网络；其读取范围不是完整的机密隔离。Pi认证、令牌刷新、Java或其他工具启动时需要写哪些缓存/状态，必须在本机明确验证，不能一遇到拒绝就放开整个HOME。默认Pi账户文件保持原本机配置；本版没有新的凭据broker。

2026-10-02 本机核实后，严格模式在原策略之上只增加以下放行（其余写入仍按原策略拒绝）：

| 进程 | 额外放行 | 原因（本机实测） |
|---|---|---|
| Pi 成员 | Pi 代理目录（`PI_CODING_AGENT_DIR` 或 `~/.pi/agent`）下的 `*.lock` 目录与 `auth.json` | 拿不到 settings 锁时，Pi 0.87.1 会忽略整个 settings.json，静默改变模型元数据和思考档位；OAuth 刷新会原地重写 auth.json。settings.json 本身仍不可写 |
| 受管构建 | 系统用户临时目录中的 `.attach_pid<N>`、`.java_pid<N>[.tmp]` 文件及同名本机 socket；另外 `(deny signal)` 后只允许向同一沙箱内的进程发信号 | Mockito inline / Byte Buddy 需要 JVM attach；在 macOS 上 attach 文件不受 TMPDIR 控制 |
| 受管构建 | 不放行文件，改为环境变量 `JAVA_TOOL_OPTIONS=-Djava.io.tmpdir=<本次构建>/tmp` | macOS 上 Java 的默认临时目录也不看 TMPDIR；surefire 派生的测试 JVM 会继承这个变量 |

已知残留风险：如果本机另一个同用户 JVM 的 attach 监听**已经**被启动过（例如之前用 jcmd 或 profiler 连过），构建进程仍可连接它的 socket。因为禁止了信号，构建进程无法唤醒尚未启动监听的 JVM。这与“读取不隔离”同属本策略不防恶意代码的范围。令牌刷新写 auth.json 需要真实模型调用才能验证，本次未验证。

audit-only只用于受信任离线fixture、开发诊断或明确接受风险的测试。它复制构建副本并做前后完整性检查，但**不能阻止恶意脚本向副本外写入或联网**。在此模式跑真实未知代码不能称为已沙箱隔离。

当前session_sandbox仍只负责历史工作区写保护；0.4.0新增执行策略承担受管构建范围。两种保护都需要本机验证，不能把一项通过当成另一项已通过。

## 4. 同一用户权限的边界

SQLite、socket、锁和回执使用私有目录/文件权限，主要防误操作和未授权工具接口调用；同UID管理员能直接篡改文件或替换程序不在此保护范围内。chmod只读也不是对所有同权限进程不可修改的凭证。

安装摘要覆盖包内关键Python、适配器、扩展、插件与根入口。它不覆盖整个OS、所有Node/Java依赖、外部Pi可执行文件、模型供应商或所有第三方扩展内容。工具存在性不等于工具链已经验证。

已登记配置的任务模型仍可能写出逻辑错误或伪造自己正文中的解释；当前候选与正式证据校验、程序门禁和独立评审负责发现可验证问题。系统不声称能识别所有恶意业务代码或所有语义遗漏。

## 5. 输入、构建与报告边界

继承了引擎的默认源码排除规则，例如.git、常见依赖与缓存等；不是“磁盘每个字节都进入候选”。额外exclude只用于对应输入/来源范围，不成为开发交付自由豁免。

产物目录必须具体声明。自定义Maven profile/plugin、动态输出、生成源码、复杂测试报告格式仍需要明确配方。正式生成源码不是临时垃圾；本版没有通用codegen产品化接口，不自动清理不认识的文件。

测试报告存在与命令退出0只是程序证据的一部分。没有通用“零测试发现”或所有测试框架语义解析器；用户的验收应通过既有可信测试/汇总断言规定范围。不要将本包演示中的固定报告文本当成真实业务测试。

构建在快照副本里执行，配方输出范围中既有源码仍不允许被改写。意外输出会停止，不自动扩权。并发候选修改通过工具状态与前后指纹拒绝；外部进程瞬时改动后完全恢复的恶意规避不是全面事务文件系统保证。

## 6. 日志和额度的准确含义

诊断保存使用前缀，不是轮转后保留完整全量。裁剪有元数据；可能没有失败现场最后几条raw事件，但关键结果、活动投影和控制回执独立保存。下一版可在不影响解析状态机的前提下加头尾环形保留。

总目录配额周期扫描，存在检测延迟与大仓库I/O成本；没有文件系统级实时阻断。缓存有单独限额，并非所有授权共享一个全局磁盘总额。相同项目开多个授权时，额度不自动合并。

计量是成员进程、自测、门禁和返修等受管操作，不是内部HTTP请求数、token总价或你订阅账号真实费用。隐藏重试、压缩总结等没有完整测量时保留未知。当前也没有自动退款：中断后无法确认执行是否发生的预留保留待核对。

## 7. 兼容与未实现项

- schema v1仍可在独立未受管根使用。它不会自动拥有v2共享授权、执行配方和错误策略。不能说所有旧入口在任何目录都被全局封死。
- 准备工具不写业务断言文件，不任意执行新脚本。新配方和新断言在循环外审定，不能假装MCP已经支持原设计稿所有编辑能力。
- 未提供通用跨DAG断点续跑、自动提取失败半成品、自动选择最佳候选。可明确登记选定代码为verify输入；来源选择仍由用户和审查者核对。
- 未提供受管评审任意执行工具；v2的reviewer_exec:true明确拒绝。需要的机械证据应由声明的门禁提供，不能无声降低语义评审要求。
- 未提供自动账号登录、缓存播种、网络修复、额度扩容、自动合并或基线更新。
- 没有证明准备一定几分钟结束。工具动作受限不等于控制模型纯思考时间；也没有做与直接Pi的实测性能对照。
- 提供插件包和配置生成器，但没有在你的Codex自动安装/信任插件。宿主版本兼容、工具实际前缀与扩展生命周期需要本机哨兵检查。

## 8. 建议的后续顺序

**先做本机兼容，不先加功能。**验证Python版本、Pi0.87.1或你真实版本、扩展注册、Mac写入拒绝、认证与构建缓存。通过后只用一项低风险真实任务，看是否避免target污染、固定重试和准备过度工作。

**再改善执行能力的覆盖。**依据真实项目补确定性报告格式、自定义构建输出、明确codegen，以及独立评审的受管执行配方。每种能力有一组复用反例，不把它变成每任务新测试工具。

**再做恢复与预算操作体验。**增加精确候选重新验证的向导、同授权剩余额度预览、pending启动认领的只读诊断与人工修复命令。优先防止重复执行，不能一键自动退款重启。

**最后考虑性能。**采集准备、开发、自测、门禁、评审、返修、复制/哈希的实际耗时，再决定增量快照、缓存并发、门禁并行或日志头尾保留。不要先降低模型、跳过评审或复用旧PASS来制造收益。

工作台仍放后面。0.4.0的价值是让正确执行路径明确，常见错误提前暴露，失败不重做；不是界面更复杂。
