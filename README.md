# Loop 自动评审与节点编排（Pi / Claude Code / Codex）

新任务使用 `bin/loop 启动 <开发卡.json>`，无需先开工。六种固定节点为开发评审、评审、测试、验收、提交、部署。卡上没有安排的节点不执行，没验证不是通过。旧 stages/workflow/steps 卡、旧开工、独立 accept-cmd、旧队列发布及 --release 改目标已停用，没有内部兼容开关可重启旧引擎。

正常单会话仍可 `bin/loop 开发 pi|claude|codex`：独立静态评审，必修回原会话；不自动验收、测试或提交用户工作区。配置、字段和资源职责见 [工具清单](工具清单.md)、[运行与维护](项目文档/运行与维护.md)；需求、提示词和问题单的原始写法见 [README-验收标准.md](README-验收标准.md)，其中历史批次执行写法已由本页迁移说明替代，不自动改用户原文。

## 开发卡（第4步）

在有本地 dev 提交的 Git 项目根启动。配置 `.autoreview.json` 及声明的 localFiles 为本机普通未跟踪文件；不会把原目录未提交业务内容搬入任务。卡可以尚未提交，提示词必须是仓库内可读取的文本路径。示例 `docs/batches/小改动/开发卡.json`：

```json
{
  "version": 1,
  "name": "小改动",
  "nature": "开发",
  "target": "dev",
  "flow": ["开发评审", "提交"],
  "tasks": [{ "name": "甲", "prompt": "../../prompt/提示词-小改动.md", "scope": ["src/example.ts"] }]
}
```

```bash
bin/loop 启动 docs/batches/小改动/开发卡.json --dry-run --json
bin/loop 启动 docs/batches/小改动/开发卡.json
bin/loop 查询 docs/batches/小改动/开发卡.json --json
bin/loop 停止 docs/batches/小改动/开发卡.json --json
bin/loop 续跑 docs/batches/小改动/开发卡.json
bin/loop 整合 docs/batches/小改动/开发卡.json --json
bin/loop 合入 docs/batches/小改动/开发卡.json --json
```

- 启动先只读校验，再登记唯一归属，建隐藏 worktree/任务分支，复制本机文件，复用准备/方法和宿主入口。多任务各有目录、分支、会话、进程及计数，并行开发，不使用旧同仓库串行规则。
- 程序只提交允许范围内候选，再静态评审；已有用户暂存拒绝夹带，范围外和本机文件不能提交。同树不造空提交；只压缩提交可复用结论。开发评审默认返修 4 次、每轮 60 分钟，失败调用最多重试一次，机器恢复不清零。
- 结论必须同任务、节点、候选树、输入、用户版本，且证据及消费者释放证明有效。源码、索引、未跟踪、配置、标准、授权、引用文件内容变化不能借旧结果放行。缺少引用确认快照的历史记录保守拒绝；重新引用确认后再交付。
- 原会话接收首行或末行独立【交付完成】。脏文件本身不是交付；正文提及标记、讨论、新要求和用户决定不借旧候选推进。可信原会话返修或当前输入已有交付，可接续干净候选的欠检查。Pi、Claude、Codex 使用同一账本，不双重派发。
- `[开发评审,提交]` 有有效检查后自动排队合入 dev，仅推 origin/dev，不碰 main、不推任务/批次分支、不强推。`[开发评审]` 不暗加提交，结束保留候选，可显式合入。提交节点只发布资格，不再偷偷评审或运行检查。
- dev 前进形成未检查合并树时停止；用统一 `整合 <卡>` 引入可核对的 dev 来源，再回原会话交付新树。保留冻结 scope，不把 dev 新增文件误算任务越界，也不能洗白真实越界。
- 目标有重叠用户改动就拒绝；无交集的暂存、未暂存和未跟踪内容原样保留，不 stash/reset。推送失败保留本地合入及 Git 原因，不自动重推。发布自身合法更新 guide 等登记输入时仅归一化与发布树完全一致的变化。

### 原生 Pi 窗口

Pi 单/多任务默认各自打开独立、可输入的 macOS Terminal 窗口；默认不加 print。`--json` 只改输出，不选后台；明确后台用 `--launcher background`。支持显式 terminal。其他平台默认可见能力不足会报错，不静默转后台。参数通过 argv，不粘贴长命令。

续跑保留原目录、会话、次数及已选前后台模式；停止只撤销一次性窗口请求，不清模式。检查 worker 的后台运输不代表后台开发授权。活动/待认领/未知身份不重复派工；部分启动失败逐任务报原因及命令。窗口持续读取同一账本，显示任务与整批、真实节点活动、排队、返修、停点及释放未知；空闲窗口不算检查运行中，关闭/重载释放轮询。

### 测试、重跑、改卡与放弃

flow 开发评审之后加入测试，任务填写 `test` 原命令，例如 `node --test test/example.test.ts`。没有测试写 `无：原因`，结果没验证，不算通过。默认测试返修 3 次、时限 20 分钟、有限恢复 1 次，与评审/验收完全独立。

- 测试/验收共用一个本机 FIFO 槽，排队不计时、不显示执行中。各次原命令、有限恢复和同命令重试只用本节点剩余 deadline。产品失败回责任任务原会话，修复后先重评审；环境/方法/未知失败不扣产品返修次数；补装和准备复查均通过后，测试重跑仍失败（非超时/中断）按产品失败回原会话，消耗测试返修次数。
- 测试在本次候选的隔离 Git 检出执行，不改原命令。装配 Git 候选、本机文件和既有 ignored 输入/依赖；失败时可按项目已配 recover 有限补装，在独立恢复副本复查后重新装配测试检出，不回写原候选。成功补装的依赖按任务留存有归属和指纹的快照；登记输入、方法、依赖声明及安装输入证明仍匹配时，产品返修后可复用依赖，但仍重新复查和测试，不重置补装次数、不复用旧候选或 dist。scope 内源码也可成为本地依赖的安装输入：完整 Node 观测绑定实际读取及候选符号链接结构，不能只绑定 realpath 后的目标；链接解析链无法证明、路径不规范、未绑定产品输入的元数据/缺失读取、不透明或未知方法保守绑定整个候选及原测试输入，不能凭 node_modules 目录名跨候选复用。只有无候选读取的字面量写入或有效安装观测才可复用独立依赖；未加引号的 shell 展开（包括字符组通配）不能作为字面量证明。缓存复查普通失败仍按剩余额度恢复、复查和测试；中断、超时、保护违规及释放未知不绕过，后续恢复继承未重建依赖的原安装输入。默认保护输入；仅完整观测的 Node 调用树实际完整替换且未消费旧内容时，可将 ignored 普通文件记为本次重建产物。源码、登记输入、依赖永不提升；复杂 shell、未知消费者和伪证明不放行。
- 原开发目录完整守卫，不靠 `.gitignore` 豁免源码、索引或瞬时写回。重命名/别名读取、链接越界、读取后回写及未观测输出不放行。产物路径/哈希/I/O 事件留证，不回写候选。CPython 缓存使用本尝试登记资源下的 PYTHONPYCACHEPREFIX；旧/失效缓存不回写。
- testWorkspaces、attempt.json、test.json、check-workspace.json、interruption.json 保留原取消原因与保护结论。只有消费者真实释放后才删隔离检出/缓存；缺回执、损坏登记或 releaseUnproven 保留现场，所有者死亡/空登记不能洗白。停止可凭后来取得的真实证明结清具体未结项，不凭旧枚举永久自锁。

```bash
bin/loop 重跑 docs/batches/小改动/开发卡.json --node 测试 --json
bin/loop 改卡 docs/batches/小改动/开发卡.json --from /替换卡.json --json
bin/loop 改卡 docs/batches/小改动/开发卡.json --remove-node 测试 --json
bin/loop 放弃 docs/batches/小改动/开发卡.json --json
```

改卡在安全边界应用，保存新旧原文、来源和时间。展示名、test、limits、合法 flow、标准改版和移出任务按既有约束处理；不能替换性质、身份、提示词、受评对象、分支或宿主。移除必需测试/验收、标准改版、提高责任任务验收额度或移出任务，须真实终端或原会话明确用户决定，机器不能代选。用户撤权/新要求不能被机器信封吞掉。

放弃是终态，不是停止或回滚：先保留 ref/候选/证据，再按登记释放；未知消费者、未提交/暂存成果、未知 ignored 文件及本机文件变化保留。已发布事实不因停止/放弃抹掉，不自动回滚。状态把业务结果与资源分别报告。

### 补充遗漏的任务文件范围

沿 `改卡 <卡> --from <替换卡.json>`，只允许给一个任务追加一个已有跟踪的普通文件。保留原 allow 顺序与全部 deny，不能追加目录、链接、未跟踪文件、替换范围或夹带其他改卡。真实用户可在原会话输入 `补充任务「甲」范围：相对文件路径`，绑定任务/精确文件/卡版本，一次性使用；不修改权限配置。

只等责任任务安全边界，无关任务继续；保留成果、会话、候选、次数和历史。显式 `续跑 <卡> --task 甲 --json` 可投递到仍活着的原 Pi 私有收件箱，须匹配 session、PID 启动时间和 launch ID，且无在途检查/票据。不停止或新建宿主；未知/过期信封拒绝并留证，投递、已读不等于检查通过。

### 并行与统一验收

多任务必须在 flow 安排验收，并填写卡的 `acceptance` 标准文件路径。非人工项按 `A1. [甲] 操作：… / 预期：…` 唯一标责任任务，跨任务项也指定一个责任人；缺失/多义/未知归属、非法路径和空标准在资源前拒绝。项目显式配置 acceptance（命令行项目可 `{}`）。[授权] 仍须真实用户答复，标准文件里的授权文字不算授权。

谁先完成任务检查谁先贡献汇入，全部活跃任务贡献到齐后，在批次空间统一验收。失败只回责任任务；同轮返修全部汇入后，仅验“不通过项 + 返修任务名下全部项”，定向成功后不追加 full。未返修任务的通过项保留原实测树/轮次/证据和沿用原因。首次仍按既定完整范围执行；移出任务重建贡献后，剩余项完整重验一次，不编辑原标准。

真实补充要求保留本轮责任集合及范围，不能掩盖共享方法、标准、授权或沿用证据变化。无法证明未变就暂停，不暗中全验。验收默认责任任务各返修 3 次、每次 20 分钟、恢复 1 次，与评审/测试独立。到上限只通知，由真实用户提高该任务额度、移出或整批放弃；次数不清零。同文件混合来源或集成冲突不能猜删，保留其他任务检查，不扣验收次数。

```bash
bin/loop 停止 docs/batches/小改动/开发卡.json --task 甲 --json
bin/loop 续跑 docs/batches/小改动/开发卡.json --task 甲
bin/loop 重跑 docs/batches/小改动/开发卡.json --node 验收 --json
bin/loop 改卡 docs/batches/小改动/开发卡.json --remove-task 甲 --json
```

### 统一合入与仅本地模式

普通合入逐项列出真实欠项和补救命令。例外仍走 `bin/loop 合入 <卡> --接受未验证`：终端须交互确认当前候选与欠项，原会话亲手输入“合入本批”或 Pi `/loop-merge --接受未验证` 使用同一入口；卡/文件/机器消息不是决定。决定绑定完整候选、输入、用户版本与贡献映射，撤权或变标准后重新确认。

多任务例外必须包含全部当前登记候选，含失败任务的当前代码，不能只发已通过任务却称整批合入。例外只豁免检查欠项，不豁免未知来源、未提交成果或释放不明；失败/没验证历史不改成通过。取消确认不发布、不生成通过资格，之后仍可正常返修或受控移出。

本人只授权本地合入时使用：

```bash
bin/loop 合入 docs/batches/小改动/开发卡.json --仅本地 --dry-run --json
bin/loop 合入 docs/batches/小改动/开发卡.json --仅本地 --json
```

保留候选、检查、贡献、目标与资源保护；不请求或执行 git push，查询写“推送：未请求”，不是成功或失败。重复调用不补推；未加参数沿既有 origin/dev 规则。合入后仅释放本批可证明归属且候选干净的 worktree，git 忽略的依赖/产物视为可重建并随目录释放，保留分支、历史、证据；未忽略的未跟踪文件及本机文件变化仍保留，未合入放弃任务的 ignored 保护不变；批次只按实际发布映射授予任务清理资格，已移出任务不继承批次已合入状态。补装缓存按登记随任务终态释放，缓存变化或归属不明则保留。未知释放逐项保留。Loop 外合入只读识别，不补造检查或推送事实。

### 按卡部署（提交之后）

flow 的提交之后加部署，并配置已有项目方法：

```json
{
  "deployment": {
    "enabled": true,
    "cmd": "sh .autoreview/methods/deploy.sh",
    "check": "sh .autoreview/methods/deploy-check.sh",
    "timeoutMin": 10
  }
}
```

卡没安排即使 enabled=true 也不执行。只有本地发布及 origin/dev 推送成功才接续 cmd → check；仅本地或拒推不部署。运行在启动时冻结的 dev worktree，方法/配置缺失在资源前拒绝。部署和同 Git 共用目录实际检查/发布互斥，不占测试/验收本机槽，每条命令独立时限及进程/资源登记。

cmd 失败只停部署；check 失败仅在目标仍为本批、上一版明确、源码/索引干净、无用户挡路文件且消费者释放已确认时反向 CAS 回退本地 dev，并用同一方法部署上一版。不强推远端、不自动再次推送。停止、超时、目标前进、输入变化或未知副作用不自动回退。查询分列本地版本、最近远端推送确认、部署命令及回退事实，不假称实际运行已验。

重复回调/普通续跑只读终态，不重做失败动作。核对现场后可 `bin/loop 重跑 <卡> --node 部署 --json`，绑定原尝试，只跑部署，不重新开发/检查/提交/推送。发布后不能改卡追加部署授权；冻结配置变动时先恢复，未知副作用无忽略开关。

### 只评审卡（已有提交，只出报告）

示例 `docs/batches/只评审/开发卡.json`：

```json
{
  "version": 1,
  "name": "只评审",
  "nature": "评审",
  "flow": ["评审"],
  "tasks": [{ "name": "报告" }],
  "review": {
    "base": "dev~1",
    "head": "dev",
    "requirement": "../../prompt/需求-示例.md",
    "criteria": "标准.md",
    "note": "说明.md"
  },
  "limits": { "评审": { "timeoutMin": 60 } }
}
```

只评审固定本地已有 base/head 的 commit/tree，不 fetch、不开发、不自动返修或发布，不需要 dev/prompt/scope/host。单任务分离检出，原用户暂存/未暂存/未跟踪不参与。报告保留必修、建议、模型、耗时、范围、证据及释放情况；缺回执/脏或未知目录不强删。检查中候选/标准/输入变化使结果作废。查询明确只评审已结束及报告，不显示可合入；包括接受未验证在内一律不能合入。重跑仅评审，可复用同输入有效报告。

直接只评审入口也保留：`bin/loop 评审 --base <已有提交> --head <已有提交> --json`，可加 --requirement/--criteria/--note。退出 0 代表静态无必修，1 有必修，2 调用失败；不代表业务验收通过。缺失/否定释放回执、损坏登记、检出目录/HEAD 变化或未保存（含 ignored）输出均保留现场，报告给出 retainedWorktree；不会凭空登记或 finally 强删抹去未知。

## Claude Code / Codex 用法

```bash
bin/loop 开发 claude --cwd /你的项目 --init /任务文件.md
bin/loop 开发 codex --cwd /你的项目 --init /任务文件.md
bin/loop 开发 pi --cwd /你的项目 /任务文件.md
```

Claude/Codex 需已安装、启用并信任本机插件。Claude 沿 auto，Codex 沿自动审批，不改全局 deny/沙箱；具体已安装程序/Hook 版本由入口核对，不自动安装升级。

本机已有接入无需重复安装。首次接入或迁机时，只有明确授权后才执行以下安装步骤（本批未执行）；先把 Loop 路径核对为实际稳定安装位置：

```bash
LOOP_ROOT='/Users/Admin/Desktop/loop'
claude plugin marketplace add "$LOOP_ROOT"
claude plugin install autoreview@autoreview-local
# 本机桌面版 Codex 的可运行入口；其他机器换成已核对的 CODEX_BIN。
CODEX_BIN='/Applications/ChatGPT.app/Contents/Resources/codex-cli/bin/codex'
"$CODEX_BIN" plugin marketplace add "$LOOP_ROOT"
"$CODEX_BIN" plugin add autoreview@autoreview-local
```

移库/换机器须先核对插件 hooks/hooks.json 的 Node 与引擎路径，再更新插件并新开宿主；不要覆盖其他在用工作区。Codex 输入 `/hooks` 核对并信任 SessionStart/UserPromptSubmit/PostToolUse/Stop。安装不等于 Hook 已获信任或自动审批/业务已验证，入口不会代为信任。CLAUDE_BIN/CODEX_BIN 可指定已安装程序；LOOP_NODE 可指定支持直接运行 TypeScript 的 Node（最低 22.18）。

--init 仅创建缺失的 `{}`，已有配置不覆盖，dry-run 不创建配置。--session 精确续接原会话，不选择最近会话。普通直接打开的 Claude/Codex 会话不自动评审、注入或记状态。

用户 @文件最多展开 3 个、各 200KB，真实输入先记标准/授权，配置错误也不能吞撤权。宿主原生 block/原会话返修保留次数和原文；停止与中断保留证据。Pi 非 Git/无提交目录保持可用，只关闭自动评审并说明原因；历史外部 Git 基线环境不自动迁移。

## 项目配置与准备

配置优先级：显式评审 flag → 支持的环境变量 → `.autoreview.json` → 默认。单会话 maxRepairs/reviewTimeoutMin 管自身静态评审；新卡各节点用 limits。acceptance.timeoutMin 是独立执行器时限，不与评审比较。gate、workflow、steps、workspaces 及 merge.auto/push 不决定流程、预算或发布权限，解析静默，不删改项目配置；新卡实际启动对 gate 最多提醒一次。

新卡开发前的准备只确认核心能跑，不跑全量基线、不以环境问题挡开发。配了 `preparation.recover` 且尚有次数时，check 失败先补装再复查；只有项目明确输出 `AUTOREVIEW_FAILURE=method` 或退出码 78 时不补装，输出文字推断的 method/unknown 仍先补装，已登记卡续跑同样生效。准备或方法自检最终失败时如实记录“环境未就绪”，状态/总结及开工、续跑信封带原因、原始错误和下一步命令，仍启动开发，不冒充检查通过；卡/配置校验及候选、输入、稳定规则被改动的安全保护不放松。

准备 check/recover 及受限 repair.paths、方法 paths/selfCheck/probe、context.sources 内容版本/依赖、权限指纹与 scope 均保留。恢复预算独立，不通过用户接管路径清零机器次数。来源缺失/配置取消阻塞；单会话已登记来源内容变化按既有约定更新并留证，新卡引用快照仍按冻结输入保护。不自动把当前磁盘内容追认为用户新标准。

`bin/loop 接入 <项目目录>` 只处理配置，不读写稳定规则或旧规则副本，不授权业务动作。准备方法非空占位符失败如实记录，模板不是已验运行成品。

## PA、历史与维护

- `bin/loop 查询 [<卡> | --all] --json` 读取新账本及旧 JSON/事件。查询不恢复旧队列、不发布、不迁移历史资格。
- `bin/loop 送话 <卡> --stage <任务名> --id <编号> --text-file <文件|-> --json` 保留已有用户原话协议、哈希、原会话/进程身份和请求去重。重复编号不重新读输入或重发，unknown 不自动重试；运行/未知身份拒绝，开发环境（含新卡身份）不能伪装 PA 用户送话，已读不代表检查通过。新卡原生宿主仍走原通道，不操作终端草稿。
- `bin/loop 续跑 <新卡> --id <编号> --json` 只复用内核整批续跑，不和 --task/--launcher 混用；单任务用普通统一续跑入口，不附带 --id。旧卡明确拒绝，连拒绝收据目录也不创建，不再重开旧编排；旧成功收据不重新授予启动资格。新卡授权原话用送话投到正确任务，不用旧整批 grant-file 执行路径。直接写入的历史 PA 授权仍只读对账，不触发流程或冒充新标准授权。
- 历史 `停止` 仅按登记文件、Git 归属、原 PID/启动时间/owner 核对，取消后续动作；在途副作用/未知消费者不假称释放，不重启旧发布事务。旧目录、分支与历史证据不自动删除。
- `bin/loop 清理 [--apply] --json` 只按登记处理运行材料，保留证据和历史；默认只预览。交付总表追加不覆盖，写入失败提示，不伪造资格。
- 问题单写法只有 [README-验收标准.md「问题单」](README-验收标准.md#问题单) 一份。编辑已明确解决/重复/不做的单子可调用同一安全归档器；`bin/loop 归档问题单 <项目目录> --dry-run --json` 预览，不自动替用户关单。旧开工预写和旧队列自动状态冲突处理已移除。
- `bin/loop 经验 列出|导入|批准|拒绝 <项目目录> …` 保留用户批准门槛、活动会话保护、去重和原始证据；候选草稿不自动进经验库。`漏网 <项目> <会话ID> <描述> <发现方式>` 追加案例/证据导航，不改原结论。

维护示例（替换项目、会话、候选路径，先预览；本批未对用户项目执行）：

```bash
bin/loop 经验 列出 /你的项目 --json
bin/loop 经验 导入 /你的项目 /候选.json --dry-run --json
bin/loop 经验 批准 /你的项目 候选ID --dry-run --json
bin/loop 经验 拒绝 /你的项目 候选ID --dry-run --json
bin/loop 漏网 /你的项目 会话ID '问题描述' '发现方式' --dry-run --json
bin/loop 归档问题单 /你的项目 --dry-run --json
```

## 内部实现（兼容说明）

单会话经 bin/pi-dev、bin/loop-dev 与 autoreview.ts/hosts/review-hook.ts，静态执行器为 static-review.ts。新卡使用 kernel-session、node-ledger 与固定节点。pipeline.ts 只留短迁移诊断，merge-queue.ts 只读旧队列及安全停止，commit-batch.ts 只保留历史结构。pipeline-core.ts 的原子 JSON/状态工具由资源、资料、方法、来源、PA 与宿主观测使用；workspace.ts 的 Git/归属由内核及部署使用。setup-acceptance.ts 负责接入，不包含旧编排。
