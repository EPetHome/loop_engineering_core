## 日常准备与启动

**目标/授权范围/完成标准与预算 → 复用合适的已有规则、模型工具配置和测试入口 → 必要检查 → 给用户唯一启动命令。**

- 关键业务歧义仍须在启动前解决；已授权的常规实现选择由执行者决定，不逐项等待确认。
- 拆成能独立验收的合理工作单元，小任务可只有一个单元；协作任务安排集成。成员提示由引擎依据本次 context 生成，不重复手写同一套角色启动协议。
- 新门禁优先复用原测试；存在疑点时核对命令、测试发现范围与失败原因，不要求准备者先实现整份成功解。
- 常规任务不以临时成功解、假成员完整演练、全引擎回归或真实模型试调用作为启动条件。完整引擎回归和适配器演练用于安装、升级、相关接口或安全边界变化后的针对性验证；高风险/可行性检查限定具体疑点。
- `validate` 只证明规则结构、依赖和已声明边界；`doctor` 只检查本机环境、源码/程序存在性及可选版本。二者不证明凭据、远程模型、业务可行性或所有运行冲突已验证。当前详细步骤见 [06](06-使用手册.md) 与 [10 第 5 节](10-来龙去脉与接手手册.md#5-完整流程从头脑风暴到合并)。

## 一句话

我们在循环之外想清楚要什么，写成规则；启动一次；循环在里面自动完成开发、自测、评审；**循环停止就交结果**；我们验收。

## 术语

| 词 | 意思 |
|---|---|
| 拍板人 | 用户，以及陪用户讨论的那个模型。两者是同一个角色，都在循环之外 |
| 循环 | 「开发 → 评审 → 不达标再来 → 停止交结果」这个自动运转的过程 |
| 单元 | 能独立验收的合理工作单元：一个任务、一个工作区、一份规则、一个结果；小任务可只有一个 |
| 编排 | 多个单元之间谁和谁并行、谁等谁的安排，以及按安排启动单元的程序 |
| 规则 | 拍板人在启动前写好、循环里的成员只能读不能改的全部约束 |
| 标准 | 规则里回答「什么叫完成、怎么验收」的那部分，逐条带编号 |
| 工作区 | 一个单元里所有成员交接文档的地方；循环产生的文档只落在这里 |
| 结果 | 循环停止时交出来的东西；任何停止都必须有 |
| 基线 | 项目自己的长期状态文档。在循环之外，只由拍板人更新 |
| 成员 | 循环里的执行者：开发方、评审方 |
