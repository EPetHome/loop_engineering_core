# pi 自动评审扩展（autoreview）

> ⚠️ **用自动验收的项目，先看接入手册 [README-验收标准.md](README-验收标准.md)**：里面是要复制进你项目的三块（验收标准和任务提示词的写法、启动配置、浏览器工具）。【块 1】已升到 v3（要你权限的条目标 `[授权]`，你同意后程序执行；要你拍板的标 `[人工]`；v2 起准备提示词的模型只写目标、已拍板、边界、验收标准四节，不读代码、不核实现状），已接入的项目重跑一次接入命令就会更新。一条命令接入：`node /Users/Admin/Desktop/loop/setup-acceptance.ts <你的项目目录>`（先给你看要改什么，确认了才写，可以重复跑）。

给 pi 开发会话加一个 `-e`：开发方写完（写不写【交付完成】都行），扩展自动让独立评审检查改动；有必修就发回**同一个**开发会话返修，最多 4 次；没有必修或到达上限就停下，弹 macOS 通知并写总结。

项目的 `.autoreview.json` 里配了 `gate` 时，每轮先跑**门禁**：程序在项目目录执行一条确定性的检查命令（单测、类型检查、e2e 脚本），退出码非 0 就带着输出打回同一个会话，这一轮不验收、不评审。见下面「门禁」一节。

项目的 `.autoreview.json` 里配了 `acceptance` 时，评审之前还会先做一次**自动验收**：程序把系统真的跑起来，由验收方（默认 ds4.1-flash）按验收标准黑盒实操、留证据，程序逐条判定；不通过就带着复现步骤和系统日志打回同一个会话。见下面「自动验收」一节。

另外可以配**验收命令**（`--autoreview-accept-cmd`，和自动验收是两回事）：每次评审完成后执行一条命令（例如本仓库的 E2E），结果写进总结并通知你，不打回开发方。见下面「验收命令」一节。

几段 pi 会话要**并行或串行开发、最后跑整合 e2e** 时，用**流水线**：`node /Users/Admin/Desktop/loop/pipeline.ts <计划.json>` 一条命令开窗口、等各段完成、跑 e2e，没通过的条目按 `[段名]` 退回那一段修，修完自动重跑。见下面「流水线」一节。

同一套评审规则也做成了 Claude Code / Codex 插件（`plugins/autoreview/`，本地市场 `autoreview-local`）：宿主里由 Stop Hook 调评审，有必修时用 `{"decision":"block","reason":…}` 在原会话返修。安装后只有带 `.autoreview.json` 的项目才生效。

## Claude Code / Codex 用法

- 在项目根目录（或某个上级目录）放 `.autoreview.json`，可以是 `{}`；可选 `maxRepairs`（默认 4）、`reviewerModel`、`reviewerThinking`、`reviewTimeoutMin`、`gate`（门禁）、`acceptance`（自动验收），见下文。
- 开发方最后一行写【交付完成】触发评审；有必修时 Hook 把返修消息发回同一会话，最多 `maxRepairs` 次（门禁、验收打回和评审打回共用）。
- 暂停（包括评审被宿主超时或中断）后，在原会话再发一条消息让开发方继续，自动评审就恢复，返修计数重新算。
- 消息里的 `@文件` 由 Hook 展开（最多 3 个，每个 200KB 以内），需求原文和验收标准都按展开后的内容算，和 pi 一致。
- 状态与总结写到 `~/.pi-autoreview/<项目目录名>/<宿主>-<会话id>.state.json` 和 `.md`，不写进项目。
- Codex 首次安装后需要在 Codex 里用 `/hooks` 确认信任；未经信任时 Hook 不执行。
- 联调可用假评审：`AUTOREVIEW_REVIEWER_CMD=/Users/Admin/Desktop/loop/test/fake-reviewer.mjs`、`FAKE_MODE=pass|pass-after-1|always-fix|fail|modify`；假验收方 / 假起草方：`AUTOREVIEW_ACCEPTANCE_CMD=…/test/fake-tester.mjs`、`AUTOREVIEW_CRITERIA_CMD=…/test/fake-drafter.mjs`。

## 门禁（可选，建议配）

门禁是每轮**最先**执行的确定性检查：程序判定，不经过模型。项目里有能一条命令跑完的检查（单测、类型检查、lint、e2e 脚本），就把它配成门禁：

```json
{
  "gate": { "cmd": "npm test", "timeoutMin": 10 }
}
```

| 字段 | 默认 | 作用 |
|---|---|---|
| `cmd` | 必填 | 门禁命令，在开发目录用 `/bin/sh -c` 执行，退出码 0 为通过；stderr 并进 stdout，顺序和终端里看到的一样 |
| `timeoutMin` | `10` | 门禁最多用多少分钟，从一轮总预算 `reviewTimeoutMin` 里扣；门禁加验收（`acceptance.timeoutMin`）必须小于它 |

**一轮的顺序**：门禁 →（配了 `acceptance` 时）自动验收 → 评审。

| 门禁结果 | 程序怎么做 |
|---|---|
| 通过（退出码 0） | 接着验收或评审；评审输入里写明门禁已通过，评审不用再跑 |
| 不通过（跑完了，退出码非 0） | 带命令、退出码、输出最后 40 行和完整日志路径打回原开发会话（「【门禁 · 第 N 次返修】」），这一轮不验收、不评审；计入返修次数（和验收、评审打回共用 `maxRepairs`） |
| 超时、命令找不到（退出码 126/127）、起不来 | 暂停交给你：多半是环境或配置问题，不算开发方的错 |
| 门禁改了项目里的文件 | 暂停（「门禁期间工作区变了」）：把构建产物、缓存、报告加进 `.gitignore`，或让命令写到项目外面 |

- 配了门禁时，开发方的约定里会写明门禁命令，让它交付前先自己跑通；失败和它的改动无关、它也修不了时（原来就失败的测试、环境问题），它会写【需要你决定】暂停。
- 返修后开发方没改代码、也没写【交付完成】就暂停（「返修后没有任何改动」）；写了【交付完成】就再跑一次门禁（它可能改的是环境，比如装了依赖），仍受返修次数限制。
- 完整输出在 `~/.pi-autoreview/<项目目录名>/gate-<会话>-r<轮次>.log`，总结每轮记一行「门禁：…」，没通过时附输出尾部。
- 和「验收命令」（`--autoreview-accept-cmd`）不是一回事：门禁在循环里、每轮最先跑、失败打回开发方；验收命令在评审完成后跑一次、只报告给你。

## 自动验收（可选）

在 `.autoreview.json` 里加 `acceptance` 一节才开启（pi 扩展也读同一个文件）。最省事的是跑接入命令 `node /Users/Admin/Desktop/loop/setup-acceptance.ts <项目目录>`：它会看项目文件推断类型、启动命令和端口，连同【块 1】写法段一起列给你确认。所有字段都可选，`"acceptance": {}` 就是「命令行项目、默认设置」：

```json
{
  "acceptance": {
    "start": "npm run start",
    "readyUrl": "http://localhost:3000/health",
    "logs": ["logs/app.log"],
    "guide": "docs/how-to-use.md",
    "timeoutMin": 20
  }
}
```

| 字段 | 默认 | 作用 |
|---|---|---|
| `start` | 无 | 被测系统启动命令（`sh -c`，在开发目录执行）。不写表示没有常驻服务，验收方直接调用命令 |
| `readyUrl` | 无 | 就绪检查：GET 返回状态码小于 500 就算就绪；启动前也用它查端口是否被占 |
| `readyLog` | 无 | 就绪检查：系统输出里出现这句就算就绪（和 `readyUrl` 二选一；都不写就等 2 秒看进程还在） |
| `readyTimeoutSec` | `60` | 等就绪的上限 |
| `reset` | 无 | 重置数据的命令（`sh -c`，在开发目录执行，环境同被测系统）：程序在每次调验收方前执行，只重置数据、不重启服务；输出写本轮的 `reset.log`。验收会写数据的项目要配，否则从第 2 次验收起数据不干净 |
| `resetTimeoutSec` | `120` | 重置命令的时限 |
| `logs` | `[]` | 还要收集的日志文件（相对 `.autoreview.json` 所在目录），只截取本轮新增的部分 |
| `errorPatterns` | `ERROR` `FATAL` `Traceback` `Unhandled` `panic:` | 系统日志里出现这些就判 G2 不通过；写 `[]` 关掉 |
| `ignorePatterns` | `[]` | 含这些文字的日志行不算错误（过滤已知噪音） |
| `guide` | 无 | 项目操作说明文件（访问地址、测试账号等），原文交给验收方 |
| `model` | `opencode-go/deepseek-v4.1-flash` | 验收方模型 |
| `thinking` | 不传 | 验收方思考档位 |
| `strongModel` | 评审模型 | 强模型：需求里没写标准时起草标准；验收方没做好时换它重验 |
| `timeoutMin` | `20` | 一轮里验收最多用多少分钟，从 `reviewTimeoutMin`（一轮总预算，默认 60）里扣，必须小于它 |
| `env` | `{}` | 给被测系统的额外环境变量；系统还会拿到 `AUTOREVIEW_RUN_DIR`（本轮运行目录） |

**一轮怎么跑**（配了门禁时先跑门禁；再验收、再评审，共用一轮 60 分钟）：

1. 开发方对标准提了异议（「A2：异议：…」）→ 暂停，等你决定。
2. 取验收标准：你发的消息里有 `## 验收标准` 就用它；没有就由强模型只看需求原文起草一份。定下后整个会话冻结，只有你再发一条带 `## 验收标准` 的消息才替换。
   开头标了 `[人工]`（或 `【人工】`，可以写在 `[段名]` 或「操作：」后面）的条目不交给验收方，判为「需人工」，完成时列给你人工验收。
   标了 `[授权]` 的条目要你答复：你在给开发方的消息里亲手写「同意授权：A3」（或「同意授权：全部」），程序就照常交给验收方，并在它的输入里写明这几条可以用真实账号、真实环境；写「不授权：A3」就和 `[人工]` 一样留给你；还没答复时，验收开始前暂停问你。授权跟着标准版本走，你发了新标准要重新答复；只认你打的字，@文件 里的内容、程序发的返修消息里写的都不算。
   记下后马上告诉你「已记录你的授权（A3 你已同意）」（pi 界面、Claude Code 会话里、Codex 走系统通知）；总结的「## 验收标准」下面一直写着「授权：A3 你已同意 / 不授权 / 等你答复」，pi 的 `/review-status` 也有这一行；验收方那一轮的输入（`input.md`）里有「## 用户授权」一节。
   标准全部交给你（`[人工]` 或不授权）时不启动系统、不调验收方。两种标签怎么用见下面「[授权] 和 [人工]」。
3. 程序查端口 → 启动被测系统 → 等就绪；系统输出逐行加时间戳写进 `system.log`。
4. 配了 `reset` 时，程序先重置数据（之后每次重做、换强模型重验之前也都重置一次）。
5. 验收方按标准黑盒实操，必须用运行目录里的工具留证据：`./ev A1 -- <命令>`（跑命令）、`./browser A1 步骤.json`（无头浏览器操作网页，需要 Playwright）。验收方不许启动、停止、重启被测系统，也不许自己清数据。
6. 程序关停系统、清掉端口上验收期间起的残留进程、截取日志、扫错误，再逐条判定（见下表）。证据对不上时，在同一个验收会话里让它重做一次；还是验收方的问题，就换强模型另开会话从头重验一次。
   验收途中被测系统退出时立刻停掉验收方、不再重验，按退出方式归责：被信号关掉（或正常退出、日志没错误）算「被关掉」，这一轮作废、暂停交给你，不打回开发方，关掉之后留的证据也不算数；非 0 退出或日志有错误算「崩溃」，G1 不通过、打回开发方。
7. 不通过 → 带复现步骤、预期、实际、相关日志和证据路径打回开发方，这一轮不评审；通过或部分验证 → 评审，评审输入里附验收结果。

| 层 | 结果 | 条件 |
|---|---|---|
| 单条 | 通过 | 按「操作」做了、结果符合「预期」，证据文件存在且「证据摘录」确实在里面 |
| | 不通过 | 结果和预期不符，同样要有证据 |
| | 无法验证 | 做不了，或者报了通过/不通过但证据对不上；没配启动时「连不上」也算这个，不算开发方的错 |
| | 需人工 | 标了 `[人工]`，或 `[授权]` 条目你不授权：程序不交给验收方，不打回、不暂停，完成时列给你 |
| 程序自带 | G1 | 系统能启动、就绪，并在验收过程中一直运行（中途被关掉记为无法验证，崩溃才算不通过） |
| | G2 | 验收期间系统日志里没有错误 |
| 验收 | 不通过 | 有任何一条不通过（含 G1、G2）→ 打回 |
| | 无法验收 | 无法验证的原因是系统被关掉、数据不是初始状态、没配启动、缺工具、验收方没做好（已换强模型仍不行），或者全部条目都没验证 → 暂停 |
| | 部分验证 | 其余都通过，只有个别条目（标准含糊等）没法自动验证，或有交给你的条目 → 照常评审，结束时列给你人工验收 |
| | 通过 | 全部通过 → 进入评审 |
| 整轮 | 完成 | 同一份工作区快照上验收通过（或部分验证）、评审没有必修 |

**[授权] 和 [人工]**：按权限划分，不按难易。

| 标签 | 什么时候用 | 程序怎么做 | 例子 |
|---|---|---|---|
| `[授权]` | 要用你的真实账号、凭证或真实外部平台，或会产生真实后果，又没有测试账号、测试环境可以代替 | 你写「同意授权：A3」后照常交给验收方执行；「不授权：A3」留给你；没答复就在验收前停下来问你 | 你本机真实的 WorkBuddy（真实账号和 Key）、正式飞书写入、扣费、正式数据 |
| `[人工]` | 要你拍板的主观判断，写不出客观的「预期」 | 不交给验收方，完成时列给你 | 好不好用、文案是否得体、是不是你想要的 |

难做不算：图形界面操作（网页、桌面客户端）、步骤多、耗时长，都照常写成自动验的条目。验收方现在做不到的（比如操作桌面客户端），会报「无法验证」并写明缺什么工具：那是 loop 要补的能力，不是你的活。验收方的规则写明了只用给它的权限：不打开桌面应用、不登录真实账号、不碰正式数据，只有你授权的那几条例外。

授权的条目由验收方执行，默认是 `acceptance.model`（ds4.1-flash）。要让强模型来做这些碰真实环境的条目，把 `acceptance.model` 改成强模型。

一条链路里只有一步涉及权限时，只把这一步写成 `[授权]`，前后能自动验的照常写；能用测试账号或录下来的真实输入（事件、请求样本）代替那一步的，写成自动验的。这些规则也写进了接入手册【块 1】，准备提示词的模型照着写，但不会替你写「同意授权」。

**暂停或要你动手时，提示会写明下一步**，格式是「把接入手册的【块 N】复制到 <你项目里的完整路径>，然后……」：

| 情况 | 提示你做什么 |
|---|---|
| 项目开了验收，但 AGENTS.md / CLAUDE.md 里没有（或是旧版）写法段 | 复制【块 1】到那个文件末尾（每个会话提醒一次） |
| 无法验收：没配启动 | 复制【块 2】到 `.autoreview.json`，改好启动命令和端口，再发消息继续 |
| 无法验收：缺 Playwright | 在项目目录执行【块 3】，再发消息继续 |
| 无法验收：被测系统被关掉 | 不是开发方的问题，这一轮作废；需要干净数据就按【块 2】配 `reset`，再发消息继续 |
| 无法验收：数据不是初始状态 | 按【块 2】配 `reset`（配了就检查重置命令），再发消息继续 |
| 重置数据失败 | 检查 `acceptance.reset`（输出见 `reset.log`），再发消息继续 |
| 无法验收：验收方没做好、全部没验证 | 原因见总结；修好环境或发新标准，再发消息继续 |
| 端口被占用（写明哪个进程占着）、开发方对标准有异议、没有标准 | 各自写明怎么处理 |
| 部分验证后完成 | 哪几条需要你人工验收 |
| 验收标准里有 `[授权]` 条目还没答复 | 回复「同意授权：A3」或「不授权：A3」，回复后自动继续 |

提示出现在：pi 界面；Claude Code 会话里（Hook 的 `systemMessage`）；系统通知（Codex 只有这个，`systemMessage` 是否支持还没实测）；总结开头的「需要你做的事」，没处理完就一直留着。

验收还会暂停的情况：验收期间项目里的文件变了（把运行产物加进 `.gitignore`，或让系统写到 `$AUTOREVIEW_RUN_DIR`）、起草失败。暂停后你发消息让开发方继续就恢复。

运行材料（`system.log`、`logs/`、`evidence/`、验收方输入、`result.json`）在 `~/.pi-autoreview/<项目目录名>/acceptance/<会话>/r<轮次>/`，不写进项目。

## 流水线（几段并行 / 串行 + e2e 收尾）

一条命令跑完：各段开发（每段照常 开发 → 评审 → 返修）→ 全部完成后程序跑整合 e2e → 没通过的条目退回负责的那一段修 → 修完自动重跑 e2e，直到通过。只有需要你决定时才停下通知你。

```bash
PATH="/Users/Admin/.hermes/node/bin:$PATH" node /Users/Admin/Desktop/loop/pipeline.ts 计划.json
```

计划文件（相对路径按计划文件所在目录解析）：

```json
{
  "name": "V2首批",
  "stages": {
    "甲": { "prompt": "提示词/方案二.md", "cwd": "worktree" },
    "乙": { "prompt": "提示词/方案三.md", "cwd": "worktree/promate-frontend" }
  },
  "steps": [["甲", "乙"]],
  "prepare": "bash 联调准备.sh",
  "e2e": {
    "workDir": "worktree",
    "criteria": "e2e验收标准.md",
    "acceptance": { "start": "bash start.sh", "readyUrl": "http://127.0.0.1:38081/", "reset": "sh reset-data.sh" },
    "maxRounds": 3
  }
}
```

| 字段 | 作用 |
|---|---|
| `stages` | 每段的提示词文件 `prompt` 和启动目录 `cwd`。程序按你日常的配置生成 pi 启动命令（`--offline`、gpt-6.1-sol、max、`read,edit,write,bash`、权限扩展、`autoreview.ts`，`--name 计划名·段名` 方便认窗口），不用再写启动脚本。特殊情况可以改写 `start`（自己的启动命令，里面的 pi 必须加载 `autoreview.ts`），两个只能写一个 |
| `pi` | 可选：改默认配置，字段 `model`、`thinking`、`tools`、`args`（追加的参数，比如 `["--autoreview-max-repairs", "2"]`）；每段也可以写同名字段单独覆盖 |
| `steps` | 先后顺序：每一步里的段并行，步与步之间串行。`[["甲","乙"]]` 并行；`["甲","乙"]` 或 `[["甲"],["乙"]]` 串行；`[["甲","乙"],["丁"]]` 混合。不写就是全部并行 |
| `prepare` | 可选：各段都完成后、跑 e2e 前执行的联调准备（在 `e2e.workDir` 里 `sh -c`） |
| `e2e.criteria` | 整合 e2e 的验收标准文件，每条开头标归属：`A3. [乙] 操作：…`。没标的条目没通过时停下找你 |
| `e2e.acceptance` | 和 `.autoreview.json` 的 `acceptance` 同样的字段（启动、就绪、`reset`、日志、模型等） |
| `e2e.maxRounds` | e2e 最多跑几轮（默认 3） |
| `dir` | 可选：流水线目录，默认 `~/.pi-autoreview/pipelines/<name>/`，状态、收件箱、e2e 材料、报告都在这里 |

怎么跑：

- **开跑前检查**：开任何窗口之前，程序先查一遍（不调用模型，几秒钟）：每段的目录在不在、是不是有提交的 git 仓库、提示词文件在不在；pi、权限扩展、`autoreview.ts` 找不找得到；同一步里并行的段是不是在同一个目录；e2e 的地址现在是不是空着；标准里要操作网页时 Playwright 装没装。结果列在终端和报告里，有一项 🔴 就停下（退出码 2），一个窗口都不开。
- **开窗口**：macOS 上每段开一个终端窗口跑它的启动命令（带上 `AUTOREVIEW_PIPELINE_DIR`、`AUTOREVIEW_STAGE` 两个环境变量），你可以看、可以插话；`--launcher background` 改成后台跑，输出写 `<流水线目录>/<段>.log`。
- **接力**：扩展把每段的完成、暂停写进 `<段>.status.json`；一步里的段都完成才启动下一步。某段暂停时通知你，你在它的窗口里处理好，流水线接着等。启动 3 分钟还没收到某段的状态，会提醒你检查它是否加载了 `autoreview.ts`。
- **e2e**：程序自己跑（复用自动验收：启动整合后的系统、重置数据、验收方实测、程序判定），不需要单独的开发会话。
- **回流**：没通过的条目按 `[段名]` 写进那一段的收件箱，那一段的扩展在开发方空闲时把「【流水线 e2e 返修 · 第 N 轮】」发给它。发之前把那一段的评审起点重定到此刻，下一轮评审只看这次的返修改动；e2e 条目当作「上一轮必修」交给评审复查。同一个 git 仓库里的段一次只派一个，不同仓库的同时派。
- **停下找你**（退出码 2）：收到返修的一段没改代码（多半回了「A3：不归我：理由」）、有没标归属或 G1/G2 系统级的条目没通过、e2e 无法验收或环境出问题、联调准备失败。处理好后用 `--from e2e` 从 e2e 接着跑（各段窗口别关）。超过 `maxRounds` 仍没通过退出码 1，全部通过退出码 0。报告在 `<流水线目录>/report.md`。
- 只支持 pi 会话：Claude Code / Codex 的会话空闲时没法从外面唤醒。

## 启动

保留日常启动配置，加载权限扩展与自动评审扩展（替换下面的占位符）：

```bash
cd <你的项目>
PATH="/Users/Admin/.hermes/node/bin:$PATH" /Users/Admin/.local/bin/pi \
  --offline \
  --model openai-codex/gpt-6.1-sol \
  --thinking max \
  --no-extensions --no-skills --no-prompt-templates --no-themes \
  --tools <按任务选> \
  -e /Users/Admin/.pi/agent/npm/node_modules/@gotgenes/pi-permission-system/src/index.ts \
  -e /Users/Admin/Desktop/loop/autoreview.ts \
  "@<提示词绝对路径>"
```

`--tools` 例如 `read,edit,write,bash`，按任务选择。

在本仓库开发时再加 `--autoreview-accept-cmd "node test/e2e.mjs"`，评审完成后自动跑 E2E 实操验收（见下面「验收命令」）。

没有标记不代表已经评审过，可以用 `/review-status` 查。
完成后也可以手动 `/review`。
要接着用同一个开发会话，在上述配置中加 `--session <开发会话id>` 精确恢复，不要只用 `pi -c`（可能选到评审会话）。

## 交付标记

| 标记 | 含义 | 扩展动作 |
|---|---|---|
| 【交付完成】 | 开发方完成本轮全部工作（含自测） | 自动开始评审 |
| 【需要你决定】 | 开发方卡住，需要你拍板 | 不评审，暂停并通知你 |

收到返修消息后，开发方要逐条回应：修好的写「第 N 条：已修」，不同意的写「第 N 条：异议：理由」，全部处理完再以【交付完成】结尾。这两个约定由扩展自动追加进开发方的系统提示，你不需要改自己的提示词。

无标记时由程序判断：工作区与上次成功评审（没评审过就是开发基线）的指纹相比有变化就直接评审，和写了【交付完成】一样；没有变化且刚发过返修消息时暂停（原因「返修后没有任何改动」）；其他情况什么都不做。暂停后你再给开发方发消息让它继续干活，自动评审就恢复（返修计数重新算）；也可以输入 `/review` 立即评审。

## 命令

| 命令 | 作用 |
|---|---|
| `/review` | 不管有没有标记，立即评审当前改动；返修计数从这一次重新算 |
| `/review-off` | 关闭自动评审 |
| `/review-on` | 打开自动评审 |
| `/review-status` | 显示状态、轮次、返修次数、验收命令结果、门禁命令、评审会话 id、总结文件路径 |
| `/accept` | 立即执行验收命令（需要配置 `--autoreview-accept-cmd`） |

## flag

| flag | 默认 | 用途 |
|---|---|---|
| `--autoreview-max-repairs` | `4` | 返修上限（门禁、验收打回和评审打回共用） |
| `--autoreview-reviewer-model` | `openai-codex/gpt-6-astra` | 评审模型 |
| `--autoreview-reviewer-thinking` | `xhigh` | 评审思考档位 |
| `--autoreview-review-timeout-min` | `60` | 一轮总时限（分钟）：门禁、验收（如果有）、评审首次和 1 次重试共用 |
| `--autoreview-reviewer-cmd` | 空 | 仅测试：外部评审命令 |
| `--autoreview-accept-cmd` | 空 | 评审完成后执行的验收命令；空表示不验收 |
| `--autoreview-accept-timeout-min` | `120` | 验收命令时限（分钟） |

## 规则边界

- 评审只读、只跑只读命令；评审前后比对工作区指纹，不一致就暂停。
- 只把「必修」、门禁不通过和验收不通过发回开发方；小问题和需求疑问只写进总结，交你决定。
- 只支持已有提交的 git 仓库；不是 git 仓库或尚无提交时，开会话提示并关闭。
- git 取证失败会暂停，不把错误当作「没有改动」。
- 一次评审失败（超时、非 0 退出、输出为空、解析不出格式）会在同一个评审会话里重试 1 次；两次尝试共用 `reviewTimeoutMin`（默认 60 分钟）的预算，重试只能用剩余时间，剩余不足 1 分钟就不再重试并暂停（原因「评审超时」）。
- 任何异常都是暂停，不是终止：不回滚、不删成果。再给开发方发消息继续干活就恢复自动评审，或输入 `/review` 立即接着评审；失败不会推进成功评审检查点。
- 关闭或重载会取消正在跑的评审；恢复中断会话时不会自己重启评审，你发消息让开发方继续后恢复自动评审，或输入 `/review` 立即评审。
- Claude Code / Codex 里评审期间 Hook 被中断或杀掉，评审子进程不会留在后台：收到中断信号时当场清理；被强杀时，下一次开会话或你发消息时先清理再恢复。
- 自动验收只验标准里写了的内容；「完成」不等于就是你想要的，业务验收仍由你做。标了 `[人工]` 的条目程序不验，完成时列给你；`[授权]` 条目只在你同意后才交给验收方。
- 验收方是弱模型：通过与否由程序按证据判，不信它的自报结论；没有证据、摘录对不上都不算通过。
- 黑盒是软约束：验收方拿不到 diff、工作目录在项目外，但它有 bash，技术上仍能读到源码。
- 验收方的操作是真实执行的：被测系统只能指向测试环境（测试库、测试账号、沙箱支付），否则真发邮件、真扣款的后果会真的发生。
- 被测系统、验收方、评审都登记了进程组，验收结束或被中断都会关停，不会占着端口。

## 验收命令

和「自动验收」「门禁」都不是一回事：门禁和自动验收在每轮评审**之前**执行，不通过就打回开发方；验收命令在评审**完成之后**执行你给的一条命令，只报告结果，你看完再决定。想让命令的结果推动开发方返修，就把它配成门禁。

- 触发：只要配置了 `--autoreview-accept-cmd`，每次评审结论为完成（状态「完成」）都会立即执行，不靠开发方自觉；返修轮和任何暂停都不执行。
- 执行：在项目目录用 `/bin/sh -c` 运行，退出码 0 为「通过」，非 0 为「不通过（退出码 N）」，超过时限为「超时」，起不来为「无法执行」。执行期间状态栏显示「验收命令执行中」，不自动评审，`/review` 会提示等待。
- 结果：总结状态行下多一行「- 验收命令：…」，「## 验收命令」一节写命令、触发方式、耗时、输出最后 20 行；完整输出在 `~/.pi-autoreview/<项目目录名>/accept-<开发会话id>-r<轮次>.log`。结束时弹通知。
- 中断：执行中关闭或重载会话，记为「中断」；恢复会话时提示，输入 `/accept` 重跑，不会自动重跑。
- 开始新一轮评审时清掉上一次验收命令的结果（代码可能已经变了）。
- Claude Code / Codex 插件暂不支持验收命令（Stop Hook 有时限）。

## E2E 实操验收（本仓库）

`node test/e2e.mjs [A1 …]`：依托 pi 真实跑一遍开发与评审（A8、A9 还带自动验收），开发方和真实评审都用 `opencode-go/deepseek-v4.1-flash`，驱动只发一条需求，全程不提醒。

| 场景 | 开发方 / 评审 | 预期 |
|---|---|---|
| A1 真实开发 + 真实评审 | ds4.1 / ds4.1 | 完成；评审能解析；`test_calc.py` 能跑、`add` 正确；评审会话复用 |
| A2 返修一次后通过 | ds4.1 / 假评审 | 完成，评审 2 返修 1；返修消息和第 2 轮输入正确 |
| A3 达到返修上限 | ds4.1 / 假评审 | 暂停（达到返修上限），成果还在 |
| A4 评审失败 | ds4.1 / 假评审 | 暂停（评审失败），重试 1 次 |
| A5 评审改了文件 | ds4.1 / 假评审 | 暂停（评审改动了工作区） |
| A6 不写标记也会评审 | ds4.1 / 假评审 | 完成（开发方写了标记则无法判定） |
| A7 评审完成后自动执行验收命令 | ds4.1 / 假评审 | 完成，验收命令执行 1 次，结果进总结 |
| A8 自动验收：验收方关掉被测系统 | ds4.1 / 假评审 + 假验收方 | 暂停（无法验收：被测系统被关掉），不打回开发方、不评审，端口已释放 |
| A9 自动验收：重做前程序重置数据 | ds4.1 / 假评审 + 假验收方 | 完成，第 1 次验收和重做前各重置一次 |

每个场景还要满足：零人工干预、只有一个开发会话、没有新提交、总结计数与会话状态一致。结果三种：🟢 通过、🔴 不通过（产品问题）、⚪ 无法判定（模型行为或环境问题，重跑即可）。报告在系统临时目录 `autoreview-e2e-*/report.md`，通过的场景清理现场，其余保留现场，看完手动删。退出码：0 全部通过，1 有不通过，2 验收未完成。

## 总结

写到 `~/.pi-autoreview/<项目目录名>/<开发会话id>.md`，每轮评审后覆盖写一次，包括各轮必修/小问题/需求疑问、未解决必修、改动文件和开发方在基线之后新增的提交数（只记录）；配了自动验收时还有：开头的「需要你做的事」、验收标准（来源和版本）、每轮的逐条验收结果、未通过的验收标准、验收额外发现；配了验收命令时还有最近一次验收命令的结果。
